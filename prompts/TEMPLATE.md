## For each changed/new ticket
Read the FULL thread before deciding anything. Decision table:
- `triageVerdict = needs_clarification` AND `waitingOn = <client-side>` → NOT actionable (client hasn't answered). Skip.
- `blocked: true` → NOT actionable: a dependency in `dependsOn` is not done. Never nudge it, never treat it as stale, never count it as owed. It releases itself when the board flips `blocked` to false.
- New untriaged ticket → trigger the app's own triage: `POST .../tickets/{id}/triage`. Do NOT write your own triage comment.
- Client answered (their comment is latest, turn flipped to team) and the mechanism is confirmed by the thread → BUILDABLE.
- `review` ticket where the client commented last → REWORK FEEDBACK: run a fix through the pipeline (same ticket, follow-up branch), reply with what changed + direct links.

## Build flow (results sweep first, then launches)
- **Results sweep FIRST, every run:** list `/root/harness/builds/<project>-*/` dirs with a `RESULT` file but no `COMMENTED` marker. Close each out: `PR_MERGED`/`PR_CREATED` → post the what-shipped board comment (direct prod links incl. a real sample record URL for dynamic routes, De-AI voice, near-zero em dashes; PR_CREATED notes it awaits the operator's merge), move status per convention; `PLAN_BLOCKED` → post the plan's open questions, flip turn to client; `REVIEW_BLOCKED`/`EXECUTE_EMPTY` → one ALERTS.log line, no board comment; `BUILD_DEFERRED` → nothing; `BUILD_DEAD <detail>` → the build died repeatedly and auto-resume gave up: post an honest board comment (the build failed repeatedly and a human will pick it up — no fake progress claims), plus one ALERTS.log line. `ABANDONED_TIMEOUT <why>` → the lane ran long past its deadline (or its checkout vanished) and `bin/lane-reaper.sh` killed it. Act only when `<dir>/REAPED` exists: the reaper writes the verdict BEFORE it signals, so a dir with the verdict and no `REAPED` is a kill that has not landed yet, and the next reaper tick finishes it. With `REAPED`: post an honest board comment (we stopped the run after it went long past its deadline, no progress claim, no date), and NO second ALERTS.log line, because the reaper already wrote one. The relaunch is not yours: do NOT relaunch or re-queue it, because `bin/blocked-resolver.sh` owns it, on its capped rebuild ladder, and when that ladder is spent it pages ABANDONED and leaves the run for a human. Then `touch <dir>/COMMENTED`.
- **`PLAN_MALFORMED` — a plan whose tasks name no check (SDLC item 5):** the plan gate scored every task block for its own `VALIDATE:` command and its own `SATISFIES:` criterion, the repair pass ran once, and tasks were still untraced. Nothing was built and nothing reached a reviewer. Read the RESULT line and do what it says: `requeued once` means YOU relaunch it, because nothing else will — a refused plan changes nothing on the board, so no scoped tick will name this ticket again until the daily sweep. No board comment and no ALERTS line: re-verify the thread and relaunch the build in THIS tick with the ordinary detached launch command if a slot is free — slots are the first word of `/root/harness/bin/free-slots.sh <project>`, and `unlimited` there means this project is Fly-routed so the local slot gate does not apply to it; if no slot is free, write the ticket's queue line with `/root/harness/bin/queue-line-put.sh <project> <KEY> <ticket-id> <size> <kind> <reason>` (key first, never a hand `echo >>`) so the queue tick launches it. Relaunch ONCE — the second `PLAN_MALFORMED` on a ticket comes back as `held for a human`; `held for a human` means this ticket has now produced two untraced plans, so write ONE ALERTS.log line naming the ticket and `<dir>/plan-gate.txt` (which lists the offending task blocks) and leave the ticket for a person. Either way `touch <dir>/COMMENTED`.
- **Every other stop has an owner too (SDLC item 6):** these end a build with no PR and no requeue, so nothing downstream closes them unless you do. `SECURITY_BLOCKED` / `REFUTE_BLOCKED` → the security lens or the refutation lens refused a diff the general review had already approved; the code sits on its branch, unmerged, and no human has read the objection. Write ONE ALERTS.log line naming the ticket and `<dir>/security-review.md` (or `<dir>/refute-review.md`), and post a short comment on the ticket saying the change is held for a human read before it goes further — no fix claim, no date, and do NOT relaunch the build. `BUILD_REFUSED` → the context gate found rules/checkout drift it could not heal, or this box has no checkout of the repo: nothing was planned, a re-run repeats it, so ONE ALERTS.log line naming the ticket and the reason from the RESULT line, no comment. `PLAN_STALE` → the thread moved while the plan was being written (or since the snapshot a resumed plan was written against); the next tick re-plans it against the newer thread, so no ALERTS line and no comment. `QUEUED_FLY` → not a stop at all: the build was handed to the Fly builder pool and is still running there, writing its own RESULT in its own dir — nothing to post. `PR_CREATE_FAILED: <gh error>` → the build was approved and its branch was pushed, but no PR opened (the RESULT ratchet refused a url-less create claim). A reaped `RESULT_MALFORMED PR_CREATED …` line is the same case. Post NO board comment, no PR link and no what-shipped comment, write no second ALERTS.log line (`bin/run-build.sh` wrote one when the create failed) and do NOT relaunch the build: `bin/pr-url-reconcile.sh` re-links the record if the PR did open, and `bin/blocked-resolver.sh` rebuilds it fresh otherwise. In every one of these cases `touch <dir>/COMMENTED` so the sweep stops re-reading it.
- **`DECOMPOSED` / `DECOMPOSE_FAILED` — an XL plan, split or not (SDLC item 6):** `DECOMPOSED <children>` → the decomposer already posted the split and filed the child tickets; nothing to add on the parent, and the children are ordinary new tickets from here. `DECOMPOSE_FAILED` → the split was attempted and no children were filed, so the work is stuck where nobody can see it: ONE ALERTS.log line naming the ticket and `<dir>/decompose-run.txt`, no comment. Either way `touch <dir>/COMMENTED`.
- **`ROLLOUT_FILED` / `ROLLOUT_FAILED` — a rollout master, waves filed or not:** `ROLLOUT_FILED <n>` → the rollout lane already posted the wave list on the master and filed one child per wave; the children are ordinary new tickets from here (each carries `Part of #<parent>`, `Order: <n> of <total>` and, where it follows an earlier wave, its dependency on that wave, so each one builds when the one before it has merged). **The master stays `in_progress` on purpose:** it is the master of a rollout, not a ticket somebody forgot to move. Do not move it, do not close it by hand, and add nothing on it; it closes when its waves have shipped. `ROLLOUT_FAILED <reason>` → the body carried a rollout section but no wave was filed, so the work is stuck where nobody can see it: ONE ALERTS.log line naming the ticket and `<dir>/rollout-run.txt`, no comment. Either way `touch <dir>/COMMENTED`.
- **Name the rung in the close-out comment, and rest it on the evidence (SDLC item 2):** say in plain words which terminal you are closing — `PR_MERGED` = merged, with the deploy still pending unless you probed it; `PR_CREATED` = built and waiting on merge. Never "shipped", "live" or "done" off a `PR_CREATED`. What that sentence rests on is `<dir>/evidence.md`, the build's deterministic evidence block (repo-suite exit code, each mechanical gate's verdict, QA screens claimed vs screenshots on disk, fix rounds, planned-vs-changed files, the settled tier and why) — the same block that rides in the PR body. When the thread asks what was actually checked, quote its `Digest:` line instead of describing it from memory.
- **Launch detached, up to one build per FREE slot** (slots = `cat /root/harness/flags/build-slots` minus running builds): re-verify the thread, then `setsid /root/harness/bin/run-build.sh <project> <ticket-id> <KEY> > /root/harness/logs/<project>.<key>-build.out 2>&1 &` — do NOT wait; a later run's sweep closes it out.
- **Duplicate-work check before ANY launch:** `gh pr list --state all --search "<KEY>"` + `git ls-remote --heads origin "*<key>*"`. If a PR already covers the scope, don't build. Then `/root/harness/bin/free-slots.sh <project> <ticket-id> <KEY>`: a first token `0` with `identity:` in the parenthetical means this ticket id already has a build under another key — launch nothing, and never launch a decomposed child under its `<PARENT>.<n>` title label, because the board's own key is the only launch key.
- **Stale-turn recovery:** if `waitingOn` is the client side BUT the newest comment is from a non-team human, flip the turn to team (`POST .../turn`) and evaluate normally.
