# Build discipline — mined from 56 BLOCKed builds + 40 near-miss reviews (2026-08-13)

Every rule below exists because real builds shipped the mistake and a review
round had to catch it. The counts are how many builds burned on it. Builders:
self-check your diff against this list before committing. Reviewers: cite rule
numbers (D1, D14…) in findings so recurrence stays measurable.

## A. Tests that PROVE (the #1 block cause: 33 of 56 blocked builds)
- **D1 Mutation-check before you claim a test.** Deliberately break each core ticket behavior (return null, swap the formula, hardcode a branch) and confirm a test goes red. A suite that stays green under mutation is not done.
- **D2 At least one test through the production entry point** — the real route/orchestrator/CLI/component wiring, not only injected pure seams. Deleting the production call site must fail a test.
- **D3 Assert outputs, not source text.** Values, amounts, order, rendered copy. A regex over source code is documentation, not proof; if you must pin source, guard the absent-symbol case so `indexOf === -1` fails instead of passing.
- **D4 Feed pure functions only inputs the production pipeline actually generates** — a test fixture the composer can never produce proves nothing (fixture luck).

## B. Honest claims & verification (16 builds)
- **D5 No forward-written claims.** Never write a comment, docstring, PR line, or doc describing behavior you have not confirmed the code has. Cut a planned behavior → update every claim about it in the same commit.
- **D6 Record true exit codes.** Never pipe a verification command through `tail`/`head`/`grep` and then claim it passed — the unpiped exit code is the claim. Fabricated or synthesized red.txt output is a firing offense for a build.
- **D7 Execute it once as shipped, before the PR:** every documented script command verbatim from its own header; every new/changed page rendered including the zero-row/empty state; `npx tsc --noEmit` green; multi-row path of any batch SQL exercised; new screens reachable by clicking from the nav (nav entry ships in the same PR).
- **D8 Human steps ride in the PR body.** Any manual step (migration apply, env var, prompt push, republish) and any verification you could NOT run (no DATABASE_URL, suite unrunnable) appears verbatim in the PR body AND board comment as a named condition — a step mentioned only in the plan/log is dropped. A verification you could not run is a `[NOTE] not verified here` line, not a condition the review waits on (BH-7123).

## C. Failure, absence, completeness (23 builds)
- **D9 Never map failure to success.** Check `res.ok` and the specific result fields before acting; CLIs/verifiers aggregate failures and exit nonzero; a caught error surfaces in status — never a recorded SUCCESS, never a success counter bumped on an error path.
- **D10 Classify errors narrowly.** A blanket catch must not report a specific expected state ("migration required", "scanned PDF"); match exact codes/fields, log the rest with their real classification (err.name/status), rethrow or surface.
- **D11 Absent ≠ zero ≠ approved ≠ unchanged.** No `?? 0` on missing money/state, no `Number("")`, no truthy-only guards on authz; empty/unparseable input aborts before any destructive write; reject out-of-range explicit user input — never clamp or silently fall back.
- **D12 Completeness is earned.** Any cap, `take`, cursor, failed sub-read, or skipped record propagates an explicit incomplete/deferred flag into the result and the UI copy; capped work is persisted and drained later (defer, never drop), drain math from raw pre-filter counts; never claim an exact count you didn't measure.
- **D13 Status copy must be true in every state that renders it** — "nothing to write", "pending", counts: if a failure path or sibling code path can render the string while it's false, the string is a bug.

## D. Authorization & data paths (9 builds)
- **D14 Authorization = role AND resolved identity AND row.** Null/blank caller id fails closed even for privileged roles; hiding a row in a list is not authorization — every mutation re-validates the target row; resolved scope reaches every query that renders data.
- **D15 Gate every path to the same datum.** Sibling verbs (PATCH and POST), generic routes (/api/settings), second lanes, exports, and adjacent persistence (agent output logs, brain extraction) — enumerate and cover them all before claiming enforcement.

## E. Writes & data safety (12 builds)
- **D16 Idempotency keys bind to payload; terminal ops are retryable.** Replayed key + different payload = 409; a retried finalize returns the same sealed result; multi-write sequences are transactional — no partial-failure half-states.
- **D17 Identity keys normalize once, identically, everywhere** (trim/lowercase at write, lookup, and match); add an inverse-case test per identity lookup; duplicate normalized keys refuse, never pick one.
- **D18 Every create path gets its delete/re-run story:** new child tables join existing delete transactions; re-runs clean stale artifacts from prior wider runs; vendor-mirror rows tombstone (keep raw snapshot), never hard-delete owned mirror data.
- **D19 Verifiers against shared DBs are surgical:** per-run unique fixture prefixes, delete only exact ids you created, teardown failure fails the verifier.
- **D20 Migrations must pass the repo's auto-apply classifier** — no DROP or destructive statement even as a "defensive no-op"; one refused statement blocks the file and ships code without its column.
- **D21 Bound recurring work:** explicit concurrency, total deadline, and row caps on every cron/sweep phase; no per-run unbounded row growth.

## F. UI & client code (10 builds)
- **D22 The touched-file iron laws are findings at the level the REVIEW LEVELS rule gives them (BH-7123): a BLOCK on a core flow a user cannot finish, a [NOTE] everywhere else:** sortable headers sorting the displayed value, no dead identity rows, no native dialogs, 375px no-body-scroll — on every file you touch, verified, not assumed.
- **D23 Client async discipline:** `useTransition` for navigation pending states (no hand-rolled booleans), AbortController or request-versioning on racy fetches, pending reset in `finally`, load failure rendered distinctly from "no data".
- **D24 Server code never calls an export of a `"use client"` module** — client exports render as components or pass as props; shared helpers live in a shared non-client module.

## G. Scope & hygiene (8 builds)
- **D25 Surgical diffs:** no regenerated artifacts, no out-of-scope edits, no cherry-picked sibling-ticket commits; dead-code pass on your own diff (unused imports, re-declared importable constants, duplicate validators) before commit.
- **D26 Never fabricate values.** URLs, ids, tokens, sample records come verbatim from the ticket thread or this session's tool output; otherwise ship null + an honest "not configured" — never a plausible placeholder.
- **D27 Wire to the real consumer:** before changing behavior behind a helper/route, list its actual production callers and verify reachability from each — a correct pure layer behind a zero-consumer route is a dead feature.

## H. Added 2026-08-13 evening (project-3 TK-70 / TK-64+TK-67 incidents)
- **D28 A migration that exists only as a runnable script is a hope, not a migration.** Every schema change ships in the form the project's APPLY MECHANISM executes (scripts/migrations/*.sql where the internal endpoint exists) in the same PR as the code that reads the new tables — and the ticket is not done until the apply is VERIFIED against prod (the feature renders / SELECT succeeds). TK-64 shipped finance tables only as a run-me-manually .ts; prod never got them and the finance tab threw for days (TK-67).
- **D29 Platform-binary packages never load eagerly in a route.** A top-level import of a native/optional-platform dep (@ffprobe-installer, sharp-like binaries) makes the WHOLE route 500 when the binary isn't traced into the serverless bundle. Dynamic-import inside the exact branch that needs it, add the binary to outputFileTracingIncludes, and exercise the route once as-shipped (D7) on a payload that skips the heavy path. TK-70: every attachment save failed, including screenshots that never touch video analysis.

## I. Added 2026-08-24 (stack-evals replay pilots 1321/1313 + builder-swap)
- **D30 A builder's green claim is not evidence — only the harness's own run is.** The pipeline executes the repo's suite itself (`$BUILD/harness-suite.txt`); a claimed-green contradicted by HARNESS_EXIT is an instant BLOCK and a verification-integrity finding. (A builder shipped "done" with 13/16 of its own tests failing — the tests had never been executed; dangling references proved it.)
- **D31 At SIZE M+ the plan carries a System Invariants section, decided by the planner, never left to a builder:** cross-run state store + durability defense, failure-vs-success semantics per side effect (write-vs-send ordering explicit), adversarial negatives for any classifier gating irreversible actions, and neighbor interactions (caps, cron lanes, locks, schedulers). Every blocked replay-pilot challenger traced to one of these being undesigned, not to builder skill.
- **D32 Requirements coverage is bidirectional.** SATISFIES lines prove tasks trace to requirements; the plan's Requirements Coverage matrix proves every ticket requirement — including negative/policy ones ("stop posting X", "no more Y") — traces to a task and a test that pins the behavior (or its absence). A requirement with no row is a plan defect the reviewer checks against the TICKET, not against the plan's own list.

## J. Added 2026-08-26 (intent discipline)
- **D34 Declare your intent before the first behavior-changing edit.** One line in the execute output: `INTENT: <where the intended behavior is defined — file:line, docstring, spec, or the ticket line> :: agree` when every source you checked says the same thing, or `INTENT: <source> :: CONFLICT: <which sides disagree, which one you are trusting, why>` when they do not. A build with no behavior change (docs-only, config-only) writes `INTENT: none (no behavior change)`. The expensive builds are not the ones that implement the wrong thing loudly — they are the ones where a docstring contradicted the ticket, or a plan contradicted the schema, and the builder picked a side silently, leaving the reviewer to discover the choice by reading the diff against the wrong source. A declared CONFLICT is not a failure; it is the reviewer's to rule on, and it costs one line to hand them. `bin/intent-gate.sh` reads this mechanically and feeds it into the GENERAL review lens' prompt, alongside the tamper and reproduction gates (the security-only and refuter lenses do not receive GATES_NOTE — same as those two gates). **Enforcement is warn-first:** `INTENT_GATE_ENFORCE=0` (the default) never blocks a build — it collects GATES_NOTE data for a week from 2026-08-26. After that week, if absence is rare, the flag flips to 1 in **`env/global.env`** (the env file `run-build.sh` sources `set -a` — never `fleet.conf`, which is a positional project registry whose first column is read as a project name) and a diff-producing build with NO intent line becomes a `REVIEW_BLOCKED`. Malformed lines and declared CONFLICTs never block at any setting.
  - **The flip decision, made from data:** every build logs its outcome to `pipeline.log` as `GATES tamper=N repro=N intent=N scope=N`. On the hub (remote builds land in `builds/` too, via `fly-results-ingest.sh`):
    ```
    grep -ho 'intent=[0-9]*' /root/harness/builds/*/pipeline.log | sort | uniq -c | sort -rn
    ```
    `0`=declared `1`=**MISSING** `2`=malformed `3`=could-not-run `4`=conflict `5`=none. Flip only if `intent=1` is a small share and `intent=2` smaller. The `scope=` field is `bin/scope-gate.sh`'s own rc, on the same warn-first switch (`SCOPE_GATE_ENFORCE=0`): `0`=every changed file was planned `1`=**unplanned files in the PROTECTED set** (workflows, manifests, `prisma/`, env files, an unplanned migration — the only rc that demotes when armed) `2`=unplanned but nothing protected `3`=could-not-run (no plan file list, no diff, unresolvable base — never read as in-scope). Arm it on the same evidence: `grep -ho 'scope=[0-9]*' /root/harness/builds/*/pipeline.log | sort | uniq -c | sort -rn`, and flip only if `scope=1` is rare enough that a demotion is a real surprise rather than the planner's file list being short. Nothing aggregates this automatically yet — the manual grep is the honest v1, and a builder that cannot reliably write the line is a prompt bug, not a build to block.

## Mined 2026-08-26 (rule-miner)
- **D33 Serialize on shared resources, not just shared data.** Two tasks that share no files or payloads can still share a repo checkout, a deploy slot, a database, an API rate limit, or a machine — that shared resource is a dependency edge. Before launching work in parallel, name the resources the branches touch in common and guard each one; a data-flow reading of independence is not enough. TK-66 and TK-67 were enqueued to the build pool while the project-3 box was already building both — different tickets, different files, no lock, duplicate work. **What "serialize" may mean (the operator, 2026-09-13 — "we never lock and serialize"): a DEDUPE check (`flock -n`, skip if held, one owner per key), a SHORT critical section around the mutation itself (a few seconds, released before the real work), or an explicit CAP that refuses and re-offers. Never a blocking wait for another task's lifetime — that is a queue, and a queue is how a wave of tickets turns into an afternoon.**

## Mined 2026-09-14 (rule-miner)
- **D35 Match the error the production client actually returns, not the engine behind it.** A degrade / missing-table / timeout branch must match the status and message the wire returns in prod, and the test fixture must pin that production code — not the database engine's native code the client never surfaces. A PostgREST app that classifies a missing table as `42P01` / `relation does not exist` never takes that branch (PostgREST answers `PGRST205` / schema cache), so the suite stays green on a fixture the wire never produces. TK-561's `isMissingDatabaseTable` logged a failed snapshot read instead of returning `[]` on an unapplied table, and the "loud skip" hint it exported for the next wave would never fire; the same repo already had the right matcher in `campaign-register-scan.ts` and `source-copy-load.ts`.
- **D36 A raw vendor snapshot is the payload minus the PII you already encrypt.** Writing the untouched vendor row next to `emailEnc` / `phoneEnc` makes the encryption decorative: export drops the ciphertext columns then ships `rawJson`, and every "stored encrypted" consent string is false. Strip those fields in the same write (`email`, `phoneNumbers`, names, nested `lead.email`); the HighLevel lane already does this. TK-269 stored email, phone, and name in `AttributionRecord.rawJson` while `/privacy` and `/disclosure` said they were stored encrypted.

## Mined 2026-09-18 (BH-476)
- **D37 Document it in a dated note, never by appending to a contract doc.** What changed goes in ONE new file, `docs/notes/<YYYY-MM-DD>-<KEY>-<slug>.md` (what changed, why, which rule/state/command it touches, plus a `Doc: <NAME>[, <NAME>]` line naming the docs it belongs to), and it is never edited after merge — a correction is a later note. The contract docs keep only what is TRUE now; `docs/notes/INDEX.md` is a git-ignored render of `bin/render-doc-index.sh` (BH-8254): your PR never commits it, and CI runs `bin/render-doc-index.sh --check` to validate your note. The numbers that bought this rule: `docs/MERGE-CONDUCTOR.md` was in 18 of the 100 PRs merged 2026-09-13..15, `docs/BUILD-CONCURRENCY.md` 14, `docs/RUN-BUILD-GRAPH.md`, `docs/OPERATOR-SETUP.md` and `docs/EVENTS.md` 9 each, and on 2026-09-16 nine of seventeen cromford builds answered `BUILD_DEFERRED file overlap` on exactly those five files. `guardrails/doc-monolith-edit` checks a diff that edits one of them outside its `<!-- changes:begin -->`/`<!-- changes:end -->` region unless the PR title starts with `docs:`, and fails it once the guardrail is armed in `.github/workflows/harness-ci.yml` (a separate adoption PR, not yet opened); until then a reviewer cites this rule.

## Added 2026-09-22 (BH-1524)
- **D38 Gate on the repo's test selection, not a list you picked.** When the repo ships a selector (cromford: `bin/test-impact-gate.sh`), run it before your final commit: `bin/test-impact-gate.sh --base origin/main --table <file>`. It ranks what your diff can reach by why each suite was picked (self > reads > always > named > source > closure). It runs that ranked list up to its cap and its time budget (settings rows `lane.fly-pool[.<project>].test_impact_gate_cap` / `…_budget_s`; defaults 80 suites and 450 s), and names everything past either bound as left to CI. It does NOT run every suite your diff can reach. Read the left-to-CI list: if a suite that pins the file you changed is on it, run that suite too before your final commit. Paste the generated table into the PR body as your gate table. Don't retype it. Four lead PRs on 2026-09-22 (#1478, #1481, #1496 and the gh-rest-lib ceiling raise) each paid an extra review round for a pinned suite the selector had picked and the builder's hand-written gate list had not. CI ran it and it went red one round late.

## Mined 2026-09-21 (rule-miner)
- **D39 A typed-confirm destructive gate must keep focus on the confirming input through the enabling keystroke and through a parent re-render.** A focus effect keyed on callback identity (a parent passing a fresh `onClose`/`onCancel` on every render) re-runs when the typed word enables the confirm control, and it can move focus onto the now-live button so Space/Enter fires the delete. Stabilize cancel with refs (empty hook deps); do not key a focus effect on callback identity. Pin it: type the word, rerender with a new `onClose={() => {}}`, assert `activeElement` is still the input and a following Space does not `fetch`. TK-1563's Delete-everything dialog (project-5 #1655): after the word "delete" was typed, a parent re-render stole focus onto the enabled button and a space bar sent `DELETE /api/account`.
- **D40 In a `"use client"` module, `NEXT_PUBLIC_*` values are literal `process.env.NAME` member reads.** Next inlines only that form into the client bundle; `process.env[name]`, `process.env[CONST]`, or a helper that indexes by a runtime string is `undefined` in the browser and the fallback host/key/url is what ships. Object keys may be computed (`{ [CONST]: process.env.NEXT_PUBLIC_FOO }`); the VALUE must still be the literal member. Pin it twice: a static guard that asserts the literal names and bans the computed read (D3's absent-symbol case), plus one rendered-output assertion that the real value (not the fallback) reaches the DOM. TK-1563's Profile card (project-5 #1655) used a non-literal `NEXT_PUBLIC_*` access, so the portal link fell back to the wrong host in the browser.

## Added 2026-09-25 (BH-2414)
- **D41 Name every new source file by rooted path on a non-comment line in a `tests/*.sh` suite.** cromford CI runs `bin/test-impact.sh orphans --check`, and it fails a PR that adds a script or source file no shell suite names. A node test that imports the file by a relative path does not count, and neither does the file's own directory. This applies to console-ui too: a new `console-ui/src/lib/x.js` or `console-ui/src/screens/X.js` needs a `tests/*.sh` suite that names `"$DIR/console-ui/src/lib/x.js"` on a line that is not a comment. The check skips any line whose first non-blank character is `#`, so a path named only in a comment is still an orphan (a trailing comment after real code still counts). Follow `tests/cost-breaker-console.bh-2331-test.sh`: it names both new sources by path, drives the pure half with `node`, and runs the node suite when the dependencies are installed. The pre-PR gate runs the same check and hands an ORPHAN line back to the fix turn. On 2026-09-25 three pool PRs (#2382, #2388, #2402) opened red on it, and each one cost a full CI run, a lead review round and a lead fix agent.

## Mined 2026-09-28 (rule-miner)
- **D42 Never delete a test file or a test case without a `TEST-CHANGE:` block saying why.** `bin/test-tamper-scan.sh` diffs `BASE...HEAD` (from the merge-base, so a stale base is not the excuse). It counts every deleted test file and every removed case opener, and any nonzero count with no `TEST-CHANGE:` line in `plan.md` or a commit message in range exits 1, so the build is `REVIEW_BLOCKED` before a reviewer reads a line of it. Nothing in the builder prompts tells you that line exists, so write it yourself. Before you commit, run `git diff --name-only --diff-filter=D origin/main...HEAD` and check the removed `it(`/`test(` openers. For each deletion, either restore the test or add a `TEST-CHANGE:` block to the commit message that names each deleted file or case and why it is safe to lose it: the code it pinned is gone, or a named replacement now pins the same behavior. A retitled or split case is not a deletion (the scan pairs those). A test that went red on your change is not a reason to delete it; it is D1 doing its job. The same week, five builds burned a review round on exactly this, with `JUSTIFICATION: NONE`: pool-cromford-BH-2637-202609270321 (deleted_files=2), BH-2649-202609270521 (5), BH-2651-202609270401 (10), BH-2652-202609270140 (10), and pool-project-4-TK-2037-202609230439 (deleted_cases=1).
- **D43 Never give a `bin/lib` file a `/root/harness` default.** A sourced lib resolves its root as `${HARNESS:-${H:-}}` and nothing else. When that comes back empty, it refuses cleanly: the function returns non-zero, which its callers already read as "unreadable" or "cannot fetch", and it never builds a path from an empty root. The literal default belongs to the entry point in `bin/`, which is outside the scan. `tests/lib-root-literal-ratchet.bh-2613-test.sh` counts every `${NAME:-/root/harness…}` default and every `NAME=/root/harness…` statement in `bin/lib/**/*.sh`. In delta mode, on every PR and every merge-queue batch, it goes red when your diff raises any lib's count or adds a lib that has one. It runs in the batch, so a local pass that skipped it still dequeues the whole batch. Before you commit, run `RATCHET_BASE=origin/main bash tests/lib-root-literal-ratchet.bh-2613-test.sh`. See `docs/notes/2026-09-26-BH-2613-lib-root-resolution.md`. On 2026-09-28 four pool PRs added exactly this and each failed a merge batch: #3342 `bin/lib/prebuild-repro/thread.sh`, #3368 `bin/lib/split-watchdog-act.sh`, #3385, and one in batch #3390. Each cost a dequeue, a lead fix agent and another CI run.

## Added 2026-09-29 (BH-3451)
- **D44 Ask the hub for a probe instead of a human, when the probe exists.** Some checks need credentials only the hub holds, like the GitHub App. If the check you need is one of `app-status-write <owner/repo> <40-hex sha>`, `app-permissions <app-slug>`, `app-installation-repos` or `d1-count <table> <all|last-24h>`, don't write that it needs a human. Write `HUB_PROBE: <name> <args>` on its own line, at column 0 and outside any code block. A builder puts it in the final output. A reviewer puts it in `review.md` above the TIER/VERDICT lines. The harness files it when the build ends, and the hub lane runs it and posts the result on the issue. A check that is not on that list gets `NEEDS_HUMAN: <the step>` instead. Anything else on a `HUB_PROBE:` line is dropped.

## Added 2026-10-06 (BH-4869)

## Added 2026-10-07 (BH-5289)
- **D47 A fixture secret carries a visible marker inside the value**, a word like `fixture` or `example`, so the leak guard and a reader both know it is not real. Never a realistic key with nothing in it that says fake.
- **D48 No `$RANDOM` in a test; the determinism lint is red on it.** Use a fixed value or the test's name. And don't name a test variable `D`, `DIR` or `ROOT` and pass it to `find`: the test-impact scanner reads that as a whole-tree scan, and the suite runs on every diff.
- **D49 Never commit a timing row.** `catalog/ci-suite-durations.tsv` is git-ignored since BH-5518: CI composes it from its own runs (docs/ci-durations.md). Never list it in a PR and never `git add -f` it. A new suite with no row weighs the median until CI measures it, and a missing row no longer turns a batch red.
- **D50 Report a harmless metric, don't gate on it.** Time, size and line count are reported; money and safety caps stay hard gates. Also keep paths out of `eval` and `declare -a X="(…)"`: the trace gate cannot see inside either.

The reasons and knobs for D47-D50 are in docs/OPERATING.md.

## Added 2026-10-08 (BH-5269): conflict discipline (#5269)
Parallel builds collide on a few shared files. The CONFLICT HOTSPOTS section of the project primer lists this project's measured hotspots. docs/OPERATING.md#conflicts has the reasons.
- **D51 Add a new file; do not append to a shared list.** A new entry, case, note or test goes in its own file, keyed by the ticket.
- **D52 Register through the directory or fragment pattern when one exists** (a `*.d/` directory, `entries/`, a generator that joins fragments). Never hand-edit the generated output.
- **D53 No per-ticket changelog comments in file headers.** What changed goes in the dated note (D37) and the commit message.
- **D54 A test installs a lane's libs with `scratch_install_closure` (D46).** Never a hand-written lib list.
- **D55 Do not add logic to a hotspot file when a module for that concern exists.** Put it in the module, or in a new module that the hotspot calls in one line. The plan lists every hotspot file it names under `## Shared files`, one line each, with a reason (plan-contract §11). The plan gate flags a hotspot that is named and not listed.

## Added 2026-10-09 (BH-5792): assert the fields you own
- **D56 Assert the fields the feature owns, not the whole payload.** Compare `.ready`, `body.accounts`, the rows you wrote. Never `jq -S .` of the whole document, `assert.deepEqual(body, {…})` or `eq … '{"a":…,"b":…,"c":…}'`. A whole-output pin breaks the day another ticket adds an unrelated key: #4126's utilization-tickets T1, T5 and T6 went red when BH-4010 added `pauses` and `prs`, and each break cost a fix round and a new review. A whole-output pin is allowed only in a contract test: a file named `*.contract.test.*`, or one with a `# contract-test` (or `// contract-test`) header line. `bin/test-payload-pin-lint.sh --base origin/main .` warns on it; run it before you commit. docs/TESTING.md has the reasons.

## Added 2026-10-09 (BH-5797): test discipline (41 BLOCKs)
From the 300-PR review-block analysis (295 BLOCK findings over 186 PRs, #4168 to #5787). The pre-PR gate runs scratch-closure, the determinism lint, the orphan ratchet and the fast-lints data checks before the push. A finding still red after the fix turn is a fix, not a PR.
- **D58 Install a lane's libs with `scratch_install_closure`, never by hand (20 BLOCKs).** `scratch_install_closure <script> "$T"` copies the script and every lib it sources. A hand `cp` of a bin/lib file, or a loop over a lib list, is red in the scratch-closure lint and blocks the build (D46). Seen in #5709, #4895, #4749, #4747.
- **D59 Never silence a guard to get green (5 BLOCKs).** Do not add an allow-list or baseline line or a lint-silencing marker (scratch-closure, gh-guard, determinism) to make a check pass. Fix the code the check names. If a marker is truly right, put its reason on the same line (`# determinism: ok — <reason>`): `bin/marker-reason-lint.sh` fails the build on a bare marker, and the lead review gets every added marker in its request notes to judge. A public-leak allow-list is different: a `KNOWN_FAKE_*` or `KNOWN_PUBLIC_*` entry in bin/share, a gitleaks marker or ignore line, or a line in a leak or identifier allow-list labels the PR `needs-human`, and no lead review is asked until a person clears it. Seen in #5645, #4867, #4811, #4803.
- **D60 A test reads nothing that moves (5 BLOCKs).** No wall clock, no `$RANDOM`, no `GH_TOKEN` or other env from the box, no box-local file under /root or $HOME, and no moving `origin/main`: pin the clock (a `*_NOW` seam), fix the values, build fixtures in the scratch dir, and fetch or pass the base the test needs.
- **D61 Register every new file or suite (4 BLOCKs).** A new source file is named by a suite (D41). A new shim gets its suite. A new lane, knob or list entry goes where its registry reads it (the `*.d/` fragment, the catalog row). Do not commit a timing row (D49). Seen in #4685, #4618, #4606.
- **D62 Every new branch gets a test, and no test gets weaker (4 BLOCKs).** Each new `if`, `case` arm or exit path has a case that drives it. Never loosen an assertion, a count or an expected string to get green; a changed expectation is a `TEST-CHANGE:` block with the reason (D42). Seen in #5302, #4977, #4761.
- **D63 Prove each new test can fail, on fixtures in the format the real code writes (3 BLOCKs).** Run it red first, or break the code it pins (mutation) and watch it go red (D1). Build fixtures with the real writer, or copy a real sample, never a shape the production code never emits (D4). Seen in #5086, #4977, #4942.

## Added 2026-10-10 (BH-5789): fixture hygiene
- **D64 Fixtures look fake on purpose.** An IP in a test is RFC 5737 (`192.0.2.x`, `198.51.100.x`, `203.0.113.x`), never a tailnet `100.64/10` or an RFC1918 address. A fake token or secret has the word `fixture` in its value (`tok-fixture-1`). No real hostname, tailnet name or client name. `bin/fixture-hygiene.sh` (rules pack) is red on a new test line that breaks this, and the verify step runs gitleaks with `GITLEAKS_REQUIRED=1`.
The reasons and knobs for D64 are in docs/notes/2026-10-10-BH-5789-fixture-hygiene.md.

## Added 2026-10-13 (BH-6392): test ownership
- **D65 A test belongs to its ticket (D51, enforced).** Put a new case in `tests/<topic>.<this-key>-test.sh`. Edit a test of another ticket only to change a premise this PR changes. Name it in the plan under `## Tests that must change`, and write `TEST-CHANGE: <path> — <the premise>` in a commit message; the PR body copies it. `bin/pr-self-check.sh` rule `test-ownership` refuses an edit to `tests/*.<other-key>-test.sh` with no such line. 49 of 297 conflict pairs in the 2026-10-06..13 study were test files edited by two PRs.

## Added 2026-10-13 (BH-6394): stacked commits
- **D66 A PR carries only its own ticket's commits (enforced).** When the plan says to stack, open the PR with the parent branch as base. Never rebase a parent's commits onto main. If the parent merges first, merge main and let the parent's commits drop out. `bin/pr-self-check.sh` rule `foreign-commits` refuses a first-parent commit whose subject leads with another ticket's key, unless the base is that ticket's branch or the conductor holds the PR as STACKED_WAIT. In 7 days, 24 of 458 ticket PRs carried another ticket's commits, and #6355 broke batch #6368.

## Added 2026-10-18 (lesson-propose: closes-overclaim)
- **D67 Use Refs, not Closes, when any ticket item, acceptance test or owed step is not in this PR.** Write `Closes #N` in the PR body only when this PR delivers every scope item and every acceptance item of ticket N. GitHub closes the ticket on merge whatever the plan says. A SLICE line in plan.md does not stop that close. If one item is deferred, skipped, owed as a hub or human step, or left as a SKIP test, write `Refs #N`. Then add one body line for each missing item. The line names the item and gives its owner: a follow-up issue number you filed, or the parent issue that stays open. Do the same when the PR title or Why section says the build is whole. Before you open the PR, compare the body keyword with the plan's deferred items and with the Evidence table. If any claim is NOT RUN or INCONCLUSIVE for an acceptance item, the keyword is `Refs`. If you adopt an open PR whose body says `Closes` and the scope is partial, edit the body to `Refs`.

## Added 2026-10-22 (BH-7945): limits are knobs
- **D69 Every new limit is a knob.** Every new limit, rate, threshold, price, timeout, cap or `max_tokens` is a knob: a seed row in the project's settings or config table, plus a code fallback with a comment that names the row. Create the row in the same PR. A literal with no row or knob read is `[BLOCK hardcoded-knob]` in review. In one project, interview answers were cut at 1024 output tokens with no prod row, and four other calls had no DB key at all.
