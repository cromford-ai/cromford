## Iron guardrails (this machine)

1. **You (a Claude session) never run `gh pr merge`, never push to main, never deploy.** Merging happens ONLY through the gated tier-1 step inside `run-build.sh` (mechanical gate + the reviewer's `TIER: 1` line both required; the review model is a DB route, not a fixed model), the merge conductor and merge queue (which land every reviewed tier on the same double gate plus its iron-law scan), or a command the operator sends from the console. The tier is a recorded risk class, not a merge gate (the operator, 2026-10-05), except in a project an operator opts in with `tier_gate_mode.<project>=human` (BH-4579, `bin/lib/tier-gate.sh`). Either way the approval is bound to the sha that was reviewed: a PR whose head moved after the review is never merged — unless the rebased head's patch-id (`--verbatim`, whitespace included) is identical to the approved one, or `bin/lib/patch-same.sh` proves the head only took clean main merges (BH-2310), in which case the approval is rebound to the new sha without a new review (the operator, 2026-09-14) — and otherwise it is re-reviewed against the new head, and if that still blocks, `bin/blocked-resolver.sh` runs an agent fix round or rebuilds the ticket fresh (the operator, 2026-09-13: nothing in this harness waits on a human review; a ladder that runs out records an ABANDONED outcome, it does not ask for one). One exception, still with no human in the loop (the operator, 2026-09-24): when a PR runs out of CI repair rounds (`BR_CI_REPAIR_ROUNDS`), it is PARKED, not abandoned. The PR stays open until the re-plan's PR supersedes it (then it is closed unmerged), with a warn digest note (not a page), and the harness automatically enqueues a narrower re-plan of the ticket with the parked PR's repair history attached. That happens at most `BR_CI_REPLAN_MAX` times per ticket (default 1). The next CI exhaustion after that is ABANDONED, as above, and `BR_CI_REPLAN_MAX=0` restores immediate ABANDONED. Output of a build wave is a PR + a board comment.
2. **Never touch production databases with writes** except the board itself (comments, status) through the app's own API. No `prisma db push`, no migrations applied to prod from this box.
3. **No secrets in commits, comments, or logs.** Env lives in `/etc/harness/env/` (chmod 600; `bin/lib/env-path.sh` resolves it, `/root/harness/env` is a compat symlink for one release) only.
4. **When in doubt, comment on the ticket and stop.** A wrong question costs nothing; a wrong build costs a revert.
