BUILD DEDUPE: locks are for DEDUPE, never for taking turns (the operator, 2026-09-13 — nothing waits in line behind another build). Before launching a build for a ticket, check that /root/harness/locks/build-key-<project>-<KEY>.lock is not already held — `flock -n 9 9>/root/harness/locks/build-key-<project>-<KEY>.lock && echo free` — and SKIP that ticket this tick if it is held (that KEY is already building; log it as 'skip :: already building [evidence: lock /root/harness/locks/build-key-<project>-<KEY>.lock]'). Launch every other buildable ticket immediately: never wait for another build to finish, never serialize a wave, and never hold a lock across a build. run-build.sh enforces the same dedupe itself and answers BUILD_DEFERRED if it loses the race, which is a re-offer next tick, not an error. Triage-only actions (reading, commenting, status) need no lock at all.
DECISION LOG: end your final message with one line per ticket you acted on OR deliberately skipped this tick, format exactly 'DECISION: <ticket-key> :: <action> :: <one-line reason>' (actions: launch|queue|comment|status|skip|defer|close|escalate). ONE line per ticket, so when a tick does several things to the SAME ticket, log the single most consequential one by this precedence, highest first: launch > queue > escalate > comment > status > defer > close > skip. Read it as "what most changed this ticket's world": starting the build outranks the status move that records it; handing a blocked ticket to a human outranks the comment that carries the handoff; and telling the client the work shipped outranks the status move or the close that tidies up after it — the comment is the part the client experiences, so a merged build that was commented and then closed is 'comment', never 'close'. 'close' is the right verb only when closing IS the whole decision and nothing was said to the client (a duplicate, a withdrawn request, a ticket the client already resolved). These lines are harvested into a routing log — keep reasons specific ('client answered fee question, mechanism confirmed', not 'processed'). If you touched no tickets, emit no DECISION lines.
DIRECTION: a comment from a project principal on a ticket, or on its PR, is DIRECTION for the next agent round. It is not a person taking the fix. A person has taken the fix ONLY when a comment line opens with 'Taken by: <person>' or '[human-fix]'. Never infer "in progress", "someone is on it" or "a fix round is running" from free text: a narrowing comment, a review note or an instruction from the operator means the next round should follow it, not that the round is already happening.
EVIDENCE: every skip or defer whose reason claims a fix, round, build or rebuild is in progress must end with exactly one evidence tag: '[evidence: lock <path under /root/harness/locks/>]' (a lock that is held right now), '[evidence: pid <n>]' (a running process), '[evidence: job <id>]' (a job row) or '[evidence: hold:human-fix]' (the ticket carries a Taken by: or [human-fix] line). If you cannot name one, do not skip on that ground. The harness audits every untagged claim, does not honour it, and hands the ticket to bin/blocked-resolver.sh.
QUEUE LINE TAGS: never write /root/harness/logs/READY-QUEUE.log by hand (no echo, no >>, no editor). Write or rewrite a ticket's line only with `/root/harness/bin/queue-line-put.sh <project> <KEY> <ticket-id> <S|M|L|XL> <kind> <reason>`; it writes exactly '<KEY> <ticket-id> size=<S|M|L|XL> kind=<bug|feature|copy|migration|infra> :: <reason> project=<p>', one line per key, under the queue's lock. The line starts with the ticket key, never a timestamp: a line that does not start with the key is logged as a writer bug. size is your honest estimate of the build's effort from the thread; kind is exactly one of those five words (docs and wording changes are copy). An overlap-guard DEFER keeps the ticket's line; to record the defer reason, call the same script again (it replaces that key's line). Consume a line with /root/harness/bin/queue-line-drop.sh <KEY>. The pre-plan lane reads the size= and kind= tags without a model: a size=S or kind=copy ticket is not pre-planned, because its build plans it in minutes (bin/lib/preplan-lib.sh:preplan_small_reason). Size honestly; a wrong S only costs the pre-plan's head start, never the plan.
PLAN_BLOCKED RESULTS: A PLAN_BLOCKED build marked COMMENTED is not a settled ticket: when a REOFFER line names it, or its thread moved after the RESULT, re-read it and relaunch if its blocker is gone.
