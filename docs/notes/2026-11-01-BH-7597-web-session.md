# Saved browser sessions of the web-task lane (BH-7597, slice C0)

Doc: DB-COORDINATION-SPEC

## What changed

A web-task run that signed in once must not need 2FA on every run. This slice
adds the store half: a run-bound, encrypted save and load of the Playwright
`storageState`, with an age limit and a size cap. It is the rebuild of
PR #8037, which was closed unmerged on 2026-10-23 because its size cap was a
literal with no settings row. Two changes from #8037 (the operator's comment
6522650131): the size cap is a settings row, and `wsess_forget` checks that
the path is in `$TMPDIR` before it removes anything.

This slice does not add the hook in the sign-in step. The sign-in step
`bin/lib/web-signin-step.mjs` has no production caller on main yet (#8250).
The hook is slice C1. Until C1, nothing in production calls these routes or
the client.

- The session is `web_vault` field `session_state` of `(project, site)`
  (BH-7595's table). No new table. The upsert on `uq_web_vault_entry` keeps
  one session per `(project, site)`, so a new save replaces the old one.
- `POST /api/web-session/save {project, site, run_id, machine, value}` and
  `POST /api/web-session/load {project, site, run_id, machine}` in
  `worker/jobs/src/routes/web-session.js`. Both need the header
  `x-web-vault-run-token` and pass the same checks as
  `POST /api/web-vault/read`: a claimed `web-task` run of that project, held
  by that machine, the token of that claim, a live lease, the site on
  `lane.web-task.<project>.allowed_domains`. The field is never taken from
  the body, so a run cannot write any other vault field.
- The value is a string with no NUL and at least 1 byte. A bad shape is 400
  and writes nothing.
- Size cap: settings row `lane.web-task.session_max_bytes` (default 262144,
  1024..1048576; a missing, non-integer or out-of-range value uses 262144,
  a value with spaces is trimmed). The save checks it AFTER the run checks,
  so an unverified caller gets its own 403 refusal. Over the cap is
  `400 value must be 1..<cap> bytes`, with no audit row and no write. The
  code value `SESSION_MAX_BYTES_DEFAULT` is only the fallback of the row.
- Client HTTP timeouts: lib knobs in `catalog/lanes.d/_lib.web-session.json`,
  rows `lib.web-session.web_session_timeout_s` (curl `-m`, fallback 15) and
  `lib.web-session.web_session_connect_timeout_s` (curl `--connect-timeout`,
  fallback 5), applied with `lib_env_apply web-session` when the caller loaded
  `bin/lib/lane-gate.sh`.
- Every refusal, `expired`, `no_entry` and key error writes one
  `web_vault_audit` row (`set` for a save, `read` for a load; actor is the
  machine, `run_id` is set). An ok save writes the row and its audit row in
  one batch. An ok load writes its audit row and `last_used_at` in one batch
  before the value leaves.
- Age limit: settings row `lane.web-task.session_max_days` (default 14,
  1..365; a missing or bad value uses 14). A session whose `updated_at` is at
  or before `now - session_max_days` is refused `404 expired`. The row is not
  deleted: the next save replaces it, and `bin/web-vault.sh stale` still
  reports it after `web_vault.retain_days`.
- `POST /api/web-vault/read` refuses field `session_state` with
  `403 use_session_load` and one audit row, so the load with its age check is
  the one path to a session. The refusal comes after the run checks: a caller
  with a bad token gets `bad_token`.
- Both rows come from `worker/jobs/schema.d/202611111811-bh-7597-web-session.sql`.
- Client `bin/lib/web-session.sh`:
  - `wsess_save <project> <site> <file>`: rc 0 prints
    `web-session: saved <project> <site>` only on a 200 with `stored:true`;
    rc 1 refused or unreachable (a worker size refusal prints
    `web-session: 400 value must be 1..<cap> bytes`); rc 2 bad arguments, a
    missing, empty or too large file, or no run environment (no request is
    sent). The client cap is the same row, read with `setting_get` when the
    caller loaded `bin/jobs-client.sh` (as `bin/web-task.sh` does). No
    `setting_get`, an outage, no row or a bad value uses 262144. The worker
    is the authority; the client check only saves a request.
  - `wsess_load <project> <site>`: rc 0 prints the path of a mode-600
    `storage-state.json` in a new mode-700 `web-session.XXXXXX` dir under
    `$TMPDIR`; rc 3 `web-session: none (no_entry|expired)` means sign in
    again; rc 1 another refusal, unreachable, or a 200 with no value; rc 2 no
    run environment. On rc 1 and rc 3 no file is left.
  - `wsess_forget <path>`: removes the file and its dir only when the file
    is `storage-state.json`, not a symlink, in a dir `web-session.XXXXXX`
    whose physical path (`pwd -P`) is directly in the physical
    `${TMPDIR:-/tmp}`. A symlinked dir, a `..` that leaves `$TMPDIR`, a dir
    one level too deep, or a `$TMPDIR` changed since the load is rc 2, and
    nothing is removed.
  - The bearer and the run token go to curl in a config on a file descriptor
    (`wv_curl_cfg run`), never on argv. The value goes from the answer file
    to the session file through `jq`, never into a shell variable, stdout or
    stderr.

## What C1 owes

- Fill `bin/lib/web-task/session.sh` (`wt_session_load`, `wt_session_save`)
  with `wsess_load` / `wsess_save`.
- Call the save after a successful sign-in, and the load at the start of a
  run; when the site still shows a sign-in page, sign in and save again.
- Keep the session file out of the lane snapshot and every artifact, and
  call `wsess_forget` when the browser has read it.
- The acceptance suite `tests/web-task-session.bh-7597-test.sh` (run 1 signs
  in and saves, run 2 skips sign-in, an expired session makes run 3 sign in)
  and the real 2FA proof.
- An expired session is refused and not deleted (a #8037 review note). A
  later ticket can delete it.
