# A rule-based risk tier signs off low-risk PR heads (BH-5022)

Doc: MERGE-CONDUCTOR

## What changed

- `bin/lib/risk-tier.sh` (new) classifies ONE PR head `low|medium|high` from
  its compare answer, with no model call. High means a high glob, a sensitive
  glob or a lead-protected glob is touched, the diff has 300 or more files, or
  it is over the size limits. Wave 1 keeps low small (the operator, 10-07 04:23Z). Low means
  EVERY path is under `docs/`, `console-ui/src/screens/` or
  `console-ui/src/ui/`, or is a NEW test file outside `tests/lib/` (an added
  `tests/<name>-test.sh`, `tests/mc/<name>-test.sh` or
  `console-ui/tests/<name>.test.js`), and the diff is under 300 changed lines.
  Edits to existing tests always get a lead review: any change to an existing
  test file is not low, even a purely additive one, because an inserted
  `exit 0` is additive. So is a deleted or renamed test. Anything under
  `tests/lib/`, and any shared test helper or fixture, is never low, new or
  not. `prompts/` is not low either: prompt-eval CI only replays the triage
  prompts, so `build-discipline.md`, `remediator.md`, `plan-contract.md` and
  `product-stages/` would go unreviewed. No `bin/` file is ever low, and
  neither is anything under `worker/`, `catalog/`, `cron/`, `checks/`,
  `guardrails/`, `.github/`, `fly/` or `config/`, or a schema file. That set
  is constants in the lib (`RT_LOW_CEILING`, `RT_LOW_NEW_TESTS`,
  `RT_LOW_LINES_MAX`): a settings row can narrow it but never widen it.
  Everything else is medium, which is today's full lead review. A read that
  fails is never low.
- `bin/lead-review-enqueue.sh` classifies each builder-approved head with no
  standing verdict when `risk_tier.mode` is `shadow` or `enforce`, except on a
  lead-authored PR (`to_is_lead` on the PR author, the `lead_pr_authors` row
  the merge fence reads; an unreadable row or author counts as lead). The fence
  never clears a lead PR on a risk-tier row, so those get a lead review as
  before. A head that cannot be classified is cached as `unclassified`, so its
  compare is not read again every tick:
  - low + enforce posts `bin/lead-verdict.sh post … MERGE --source risk-tier
    --note "low risk: <reasons>"` and requests no lead review. When the
    sign-off is withheld (a protected path, or an authority that is not the
    lane's or cannot be read) `lead-verdict.sh` exits 5 and writes NO row, so
    nothing stands on the head and the lead review is requested with
    `priority: 1`. A `withheld` line in `risk.tsv` records it, so later ticks
    re-confirm that request and do not post the sign-off again;
  - high requests the lead review with `priority: 1`. A re-confirm with
    `priority: 1` raises an existing request row to priority 1 (it is never
    lowered, and no second request is made);
  - shadow logs one `WOULD sign off` line and requests as before.
- The jobs worker accepts `source=risk-tier` on `POST /api/verdicts`. It needs
  the lead token, it may only say MERGE, and the row STANDS like a lead row,
  so every merge lane that reads `vd_standing` sees it.
- The worker adds the `risk_tiers` table and `GET`/`POST /api/risk-tiers`.
  `lead_review_requests.priority` is BH-5151's (1..1000, higher first, applied
  by `bin/lead-review.sh` after hotfix order); a high head uses priority 1.
- A head's tier is cached in `state/lead-review-enqueue/risk.tsv` for 7 days,
  keyed on a checksum of the rules rows as loaded. Changing any rules row
  reclassifies every cached head on the next tick.
- `bin/lead-review.sh` supersedes a request whose head already has a standing
  risk-tier MERGE, before any model call, but only a request the enqueue filed
  (`requested_by` `lead-review-enqueue:*`). One a person filed (REQUEST LEAD
  REVIEW, `bin/lead-verdict.sh request`) is reviewed.
- `to_lane_lead_fence` clears a lead-authored PR only on a `lead` or `human`
  row, never on `risk-tier`.
- Mission Control: `/merge-queue` has a RISK TIERS section with a `?tier=`
  filter, and the PR screen shows the live head's tier.

## Knobs

All of these are settings rows. The worker signs them (`risk_tier.` is a
protected prefix). Signing records who wrote a row; it does not gate the
write. That is why the low ceiling is a constant in the lib and not a row.

- `risk_tier.mode.<owner>.<name>`, else `risk_tier.mode`. Values are
  `off|shadow|enforce`; with no row it is off. Wave 1 honours these rows for
  `example-org/cromford` only (`RT_MODE_REPOS`, a constant). Any other repo
  stays off whatever its rows say, until a later wave adds a gate for it.
  `risk_tier.mode.example-org.cromford = enforce` is seeded by
  `worker/jobs/schema.sql`.
- `risk_tier.high_globs`, `risk_tier.sensitive_globs`, `risk_tier.low_globs`.
  Each is a space-separated glob list. `risk_tier.low_globs` only narrows the
  wave-1 low set above.
- `risk_tier.high_lines` (600), `risk_tier.high_files` (25),
  `risk_tier.low_lines` (300, and a row above 300 still reads 300).

## Why

BH-5022 is wave 1 of #4973. Every builder-approved head waited on a lead model
review, even a docs-only diff. Now a low-risk head is signed off by rules, and
the lead review goes to medium and high heads, high first.
