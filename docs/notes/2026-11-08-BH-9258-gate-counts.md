## Fix 4: the daily count

The pre-PR selection gate writes `gate.txt` on the pool machine. The hub reap
copies it to `builds/pool-<P>-<key>-<stamp>/gate.txt` (`bin/fly-pool.sh`,
`POOL_RECORD_FILES`). Before this change no code counted these files. The
27-of-38 unattributed rate of #9061 took a hand grep.

### The count rule (`bin/lib/sg-day-counts.sh`, `sg_day_counts`)

- A file counts for the UTC day D when its mtime t is `D 00:00:00Z <= t < D+1 00:00:00Z`.
  The mtime is the hub copy time (the reap), not the gate start time.
- Only `<builds>/pool-<P>-*/gate.txt` counts. A local build `<P>-*` and a deeper
  `gate.txt` do not.
- A dir maps to the LONGEST pool project P for which the dir name starts with
  `pool-P-`. So `pool-project-6-os-…` never counts for `project-6`.
- The class of one file, from its `rc:` and `unattributed:` lines:

| gate.txt | class |
|---|---|
| `rc: 0` | `rc0` |
| `rc: 1`, no `unattributed:` line, or `unattributed: -` | `rc1_attributed` (GATE_RED) |
| `rc: 1`, `unattributed: <suite list>` (BH-9061) | `rc1_unattributed` |
| `rc: could-not-run…` | `could_not_run` |
| `rc: off`, `rc: no-selection`, `rc: 10`, no `rc:` line | `gates` only |

Every file counts in `gates`. A project with no file gets zeros. A missing or
unreadable builds dir gives `{}`, and each row then carries `gates_today: null`.

### Where the count goes

1. `bin/pool-tick-summary.sh` (hub, every 2 min) adds `gates_today` to each
   pool project's row. The run log line adds `gates=<sum> unattributed=<sum>`
   (`-` when there is no count).
2. `POST /api/pool/tick-summary` validates it: day `YYYY-MM-DD` plus the five
   counts as whole numbers. Absent or null is stored as null. Any other shape
   rejects that row only. It rides in `summary_json`: no schema change.
3. `GET /api/pool/status` returns it. Two PRIMARY KEY reads, unchanged.
4. The project page `/p/<project>` shows the SELECTION GATES TODAY section
   under the main-red banner (`console-ui/src/screens/GateCountsPanel.js`). It
   makes one GET of its own, in parallel with the page's other reads. A project
   with no pool row shows no section.
5. The MCP `pool_status` tool passes `gates_today` through, so Archie reads
   the same count.

## Fix 3: host notes for the context-kill family

Each suite ran up to 10 times on main b3a3541c under 2 x nproc busy loops
(8 CPUs), on 2026-11-08:

| suite | loaded runs | result | row |
|---|---|---|---|
| `tests/context-kill-lanes.bh-2538-test.sh` | 1 | run 1 failed: 7 `FAIL: E:` lines, `111 pass, 7 fail` | `^FAIL: E: `, host-timing |
| `tests/context-kill.bh-653-test.sh` | 10 | 0 failures | none |

The ticket hint `0 call\(s\)` matches no line a context-kill suite prints, so
the ERE comes from the captured lines. The fixture is
`tests/fixtures/selection-gate-host-notes.bh-9258/context-kill-lanes-2538.run.txt`
(cost row cut after 3 fields, box name `fixture-box`, model `fixture-model`).
`tests/selection-gate-host-notes.bh-9258-test.sh` proves the ERE against it.

`host_note` in `bin/selection-gate.sh` compares the suite's own fail count
with the FAIL lines in the window. It read only `<m> failed`. The context-kill
suites print `<n> pass, <m> fail`, so a red cut off above the window was not
seen for them (the BH-9047 bh-2309 row too). The match now reads `<m> fail`
as well. A mismatch only keeps the suite red.
