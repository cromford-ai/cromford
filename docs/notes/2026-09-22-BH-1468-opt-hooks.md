# BH-1468: `bin/blocked-resolver.sh` grows an optional-module seam, and four counters on the tick line

Doc: MERGE-CONDUCTOR

**What was missing.** Two siblings are queued behind one thing that does not
exist. #1470 wants to carry an unchanged verdict onto a moved head and rebase a
derived-only conflict; #1471 wants to adjudicate one iron-law ruling for a whole
family of PRs that share a cause. Neither is a change to the resolver's ladder —
both are a rung that runs INSTEAD of a rung, and there was nowhere in
`bin/blocked-resolver.sh` to put one. Each sibling would otherwise have cut its
own hole in the same four places, and the two holes would not have agreed about
what rc 0 costs.

**What changed.**

1. **An optional loader**, immediately after the required `bin/lib/br/` loop.
   It sources `bin/lib/br/opt/mechanical.sh` and `bin/lib/br/opt/family.sh` when
   they exist, and it is the OPPOSITE of the required loop in every failure:
   absent is silent, a file that fails `bash -n` is one log line, a source that
   returns non-zero is one log line, and none of the three touches
   `logs/ALERTS.log` or fails the tick. The required loop pages and exits 1
   because a half-synced CLASSIFIER would drain parks wrongly; a missing
   optional module simply does nothing, and paging a hub every ten minutes for a
   file nobody has written yet is how an alert log stops being read.

2. **Four `command -v`-guarded hook sites.** `br_opt_carry_rung` then
   `br_opt_conflict_rung` in `br_one`, after the already-merged guard and before
   the ladder resolves a rung; `br_opt_family_pre` at the top of
   `br_adjudicate`; `br_opt_family_record` at the END of the `ACCEPT` and
   `REJECT` arms. `bin/lib/br/opt/README.md` is the normative contract — argv,
   call site, what rc 0 means and what rc 0 COSTS — so the two builders read the
   same table next to the files they are writing.

   Two placements are decisions, not accidents. `br_opt_family_pre` runs BEFORE
   the lane's observe check, because #1471's observe behaviour is to log
   `WOULD carry family` and write no marker — it can only do that if it is
   asked, and an observe mode that hides every carry is a worse predictor of a
   real tick than none. `br_opt_family_record` runs at the END of each verdict
   arm rather than before the `case`, because the per-PR
   `iron-law-accepted-<head>` marker is written by the ACCEPT arm and #1471 keys
   its family row on a marker that already exists; putting the call before the
   case would have handed it a marker-less state. A run with no verdict reaches
   neither arm, which is the "a dead session stores nothing" rule for free.

3. **`br_count <token>` and four fields on the tick line** —
   `carried= mechanical= families= llm_rungs=`, between `retired=` and
   `projects=`. The ticket asked for `BR_N_CARRIED + 1` at the site that did the
   work; that cannot work, because every row is dispatched inside a subshell
   (the per-key `flock`) and the assignment dies with it. So the counter is a
   token appended to a per-tick scratch file, `TICK_COUNTS`, made and removed
   exactly the way `TICK_DONE` and `TICK_REBUILDS` already are. This slice
   writes only `llm`, at the three sites that reach a model call (the fix
   round's `execute`, the adjudication's `review`, `mc_rereview`), and it is
   written for REACHING the call: an adjudication that came back empty was
   billed exactly like one that ruled. The other three tokens are the modules'
   to write, which is why `br_count` is part of the published contract.

4. **Two knobs**, declared in `catalog/lanes.d/blocked-resolver.json` and
   described in `env-templates/lanes/340-blocked-resolver-tick-budget.env.example`:
   `BR_OPT_OFF` (comma list, no spaces, of modules not to source — one kill
   switch for every optional rung, never a flag per behaviour) and
   `BR_FAMILY_TTL_SECS` (0 = a ruling never expires). The second is read in the
   LANE even though its only consumer is a module that does not exist yet: the
   lanes registry refuses a knob whose lane script never names it, and the
   console has to be able to explain the setting before the module lands.

**What did NOT change.** After this merges the lane does exactly what it does
today: no module exists on any box, every hook is `command -v` guarded, and
`carried`, `mechanical` and `families` read 0 on every tick line. `candidates=`,
`retired=` and `rebuilds=` keep the meanings #1480 gave them and are not
redefined.

**What this slice deliberately does not build.** The issue body asked for six
sections and four modules — `retire`, `cost`, `mechanical`, `family` — plus
`br_opt_prepass`, `br_opt_cost_sort` and `br_opt_rebuild_ok`. PR #1480 landed
the retire pre-pass, the cost-ordered rungs and the per-tick rebuild cap inline
on main first, so those three hooks now have no consumer and a `retire.sh`
dropped in later would run beside the pre-pass main already has. the operator's
2026-09-22T20:15Z comment narrowed this ticket to what the two live siblings
import; the hooks and knobs above are that list and nothing else. Adding a name
to `BR_OPT_MODULES` later is a one-word edit.

**Open item carried over.** The `TODO (#1477)` comment in `br_one` — a
cap-refused park does not age `oldest_untouched` — is left in place. It waited
on `br_opt_rebuild_ok`, which this slice does not build.

**A note for the sibling reviewers.** CI's `bash -n` loop in
`.github/workflows/harness-ci.yml` does not glob `bin/lib/br/**`, so the modules
#1470 and #1471 ship get a parse check only from the loader at runtime and from
their own suites. Not changed here (workflow files are the scope gate's
protected set, and the retry comment did not ask for it).

**Tests.** `tests/blocked-resolver-opt-hooks.bh-1468-test.sh` — 74 assertions
driving the real lane against a scratch `$HARNESS` with a canary module at each
hook. `docs/verification-map/resolver-opt-hooks.md` is how an operator verifies
the seam on a box.
