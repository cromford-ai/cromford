# bin/alert-line.sh: one alert line, noted at emit time (BH-2314 part 1, BH-2362)

Doc: ALERTS-STATE-MACHINE

## What changed

- **New `bin/alert-line.sh [--severity s] [--id k] [--project p] <text>`.**
  The line is `<stamp> <text>`, where the stamp is `ALERT_LINE_STAMP` or
  `date -u '+%F %TZ'`. There's no prefix, and embedded newlines become spaces.
  In this order:
  1. `BEAT_STRICT=1 beat.sh {kind:"alert",akey,project,line}` (under
     `timeout 30`). The akey and project are minted exactly the way the
     poll-commands re-beat mints them. `--severity` and `--id` become the
     payload's `severity` and `alertid`, and are sent only when given.
  2. Only when that returned 0, it touches
     `state/alert-line-sent/<sha1 of the stamped line>`.
  3. It appends the line to `logs/ALERTS.log` on every path, last.
  It exits 0 always. A missing beat.sh, jq or python still appends. Markers
  older than `alert_cfg ALERT_LINE_MARKER_TTL_S` (default 86400) are deleted on
  each call.
- **`# >>> alerts re-beat` in `bin/poll-commands.sh`** deletes and skips a line
  whose marker exists. An unmarked line takes today's path unchanged, so one
  emission is one `/api/alerts/note`, not two.
- **Ratchet `tests/alert-writers-ratchet.bh-2314-test.sh`.** It counts raw
  ALERTS.log writes per file under `bin/`. A raw write is a `>>` or `tee -a`
  outside quotes whose target ends in `ALERTS.log`, or is a `$VAR` the same
  file points at ALERTS.log. The counts live in
  `tests/alert-writers-ratchet-baseline/<path under bin/>.txt`, one file per
  writer (136 files, 403 sites at 337373a). A file over its count, or with raw
  writes and no count, is red. A baseline whose file dropped to 0 prints a
  NOTE. A file whose header block carries `# alert-writer: by-design — <why>`
  is skipped. Eight files carry it: alert-line.sh, poll-commands.sh,
  lane-alert.sh, beat.sh, lib/alert-state.sh, lib/jobs/req.sh, jobs-client.sh
  and alert-triage.sh.

## Why

A bare `echo >> ALERTS.log` reached the table only through the re-beat, a
minute later. A line written just before a box died was lost, and so was every
line on a box whose poll-commands cron was broken. This slice converts no call
site. The later waves move writers onto the helper, and each deletes or
lowers its own baseline file, so waves in flight never touch the same path.

## Semantics worth knowing

- A marker means beat.sh returned 0 under BEAT_STRICT. That's a 2xx, or the
  state machine handled the line locally (log-only, suppress, info, a batched
  warn), which is the same outcome the re-beat would have had. No marker means
  the re-beat carries the line as it always did. The worst case is today's
  behaviour: one extra note.
- The same stamped text emitted twice in one second hashes to one marker, so
  the second copy is re-beaten. That's one extra note, counted by the state
  machine as a repeat of the same row.
