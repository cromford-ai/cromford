# Roadmap ideas: capture, manage and import (BH-7243.1, BH-7264)

Doc: CONSOLE, worker/jobs/README.md

Slice 2 of 5 of #7243. It fills the seams that BH-7243.0 (#7263) left: the
roadmap index, the idea list and the idea page in Mission Control, the move,
edit, detail and summary routes on the jobs worker, and a one-shot import of
an existing roadmap HTML file. No schema change: every table and index comes
from `worker/jobs/schema.d/202610182038-bh-7243-roadmap-ideas.sql`.

## Screens

| Path | Shows | Request |
|---|---|---|
| `/roadmap` | one row per project: IDEAS, NEXT, DISCARDED, TOTAL. The project cell opens its list. | `GET /api/coord/roadmap/summary` |
| `/roadmap/<project>` (`?view=list`, `?lane=`) | the ADD IDEA form, lane chips, the ideas table (newest change first) with MOVE TO NEXT / BACK TO IDEAS / DISCARD / RESTORE | `GET /api/coord/roadmap/ideas?project=&lane=` |
| `/roadmap/<project>/idea/<id>` | the fields, the EDIT form, the newest 50 events | `GET /api/coord/roadmap/ideas/<id>?project=` |

Each screen makes one request, and the worker answers it with one D1 batch of
2 statements. A Skeleton shows until it answers. There is no poll; each write
reloads the read. No link leads to `/roadmap` yet: the IDEAS tab is lit there,
and `/ideas` is not changed by this slice.

The ADD IDEA form makes one `idem_key` when it opens and a new one only after
an add lands. A second submit while the first is in flight does nothing, and a
retried request is a replay on the worker. Every move goes through the in-app
confirm dialog; the console never calls a native dialog.

## Routes (worker/jobs/src/routes/roadmap-ideas.js)

- `POST /api/roadmap/ideas/move {id, project, to_lane, expected_version, reason?, actor}`
- `POST /api/roadmap/ideas/edit {id, project, title?, note?, link?, source?, expected_version, actor}`
- `GET /api/roadmap/ideas/<id>?project=` → `{idea, events, as_of}` (newest 50 events)
- `GET /api/roadmap/summary` → `{projects:[{project, counts, total}], as_of}`

The coord proxy admits the two writes through
`console-ui/functions/_lib/coord-writes.d/7243-roadmap-ideas-manage.js` and
stamps the actor. GETs pass as they are.

### The CAS rule

A move or an edit is one batch of 3 statements, each bound to `id` AND
`project`: the event insert, the update, and a read of the row. The event
and the update carry the same condition (`version = expected_version`, and
for a move `lane <> to_lane`), and the event runs first so it reads the old
values. Both apply or neither does.

| Case | Answer |
|---|---|
| the update wrote the row | 200 `{idea}` |
| no row with this id in this project | 404 (another project's id lands here; nothing is shown) |
| a move to the lane the idea holds, at the current version | 200 `{idea, unchanged:true}`, no event, no version bump |
| any other miss (stale or ahead version) | 409 `{error:"stale version", idea}` with the stored row |

A move to `discarded` stamps `discarded_at`; a move out of it clears it. The
retention rule `roadmap_ideas.discarded` reads that column, so a restored idea
leaves the retention window. An edit writes `detail = {"before":{...}}` with
the old values of the changed fields. `idem_key` is not editable.
`expected_version` may be a string of digits, because a proxy can forward one.

## Import (worker/jobs/src/routes/roadmap-import.js, bin/roadmap-import.sh)

`bin/roadmap-import.sh --project <p> --file <roadmap.html> [--dry-run]` is an
operator tool, not a lane. It parses the HTML with Python's stdlib
`html.parser` and sends the rows to `POST /api/roadmap/import` in calls of at
most 500 rows.

| `<h2 id>` section | Goes to |
|---|---|
| `later` | `roadmap_ideas`, lane `ideas` |
| `next`, `now`, `shipped` | `roadmap_ideas`, lane `next` (Now and Shipped are computed by BH-7243.2 from links, never stored) |
| `decisions` | `roadmap_decisions`, kind `log`, status `decided` |
| `open` | `roadmap_decisions`, kind `open`, status `open` |
| anything else (`tldr`, `risks`, `sources`, a new one) | skipped and named in the output |

- Every imported idea has `source='import'` and `source_ref` = its GitHub
  issue or PR URL, or `sha256:` of `section + "\n" + title` when it has none.
  The unique index `(project, source_ref)` makes a second run insert 0 rows.
- A row with a `https://github.com/<o>/<r>/issues|pull/<n>` link also gets a
  `roadmap_links` row. A `shipped` row's link is `closed_completed`; every
  other link starts with `issue_state` NULL until the BH-7243.2 sync reads it.
  The import never writes `closed_other`.
- A decision's id is `imp-` + the first 32 hex of sha256 of
  `project + "\n" + kind + "\n" + ref`, so a re-run is a no-op.
- Each idea the call created gets one `imported` event.

How to run it:

1. Run `bin/roadmap-import.sh --project <p> --file <roadmap.html> --dry-run`. It prints the counts per section and writes nothing.
2. If the counts are right, run the same command without `--dry-run`. It needs `JOBS_URL` and `HARNESS_SECRET` (from `env/global.env`).
3. Read the `inserted ... skipped ...` line. A second run prints `inserted ideas=0 links=0 decisions=0`.

`ROADMAP_IMPORT_ACTOR` sets `created_by` on imported rows (default
`operator:<unix user>`).
