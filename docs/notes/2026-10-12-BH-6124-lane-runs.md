# Lane runs on Fly: the queue contract (BH-6124, BH-6047 part 1 of 5)

Doc: PROJECT-LANES

## What changed

`pl_dispatch` (bin/lib/project-lanes.sh) now asks where a lane runs before it
starts anything. The answer comes from settings rows, read by
`bin/lib/lane-placement.sh`:

- `lane_placement.<lane>`: the exact lane name. `fly` or `hub`.
- `lane_placement.default`: used when the lane has no row. Seeded `hub`.
- `lane_placement.<lane>.hub_only`: free text. When it is set, the lane stays
  on the hub even if it is placed `fly`, and the text is the reason.

The value is trimmed and lowercased. Only `fly` is fly. Any other value, no
row, a settings outage, no jobs client, or a lane name that is not a legal
settings key is hub. Hub is the behaviour before this change, so nothing moves
in prod until an operator sets a row.

For a lane placed `fly`, each eligible project (after `pl_name_ok` and
`lane_project_held`) is POSTed to `/api/lane-runs` as one row, and no local
process starts. The command is stored relative to the harness root
(`bin/<script>`), so a machine re-roots it under its own root. A command
outside `$H/bin/` stays on the hub, and the reason says `cmd not under bin/`.

- 201: counted as `fly`.
- 409 `already_live`: counted as `live`. The partial unique index
  `lane_runs_live` on (lane, project) for `queued`/`claimed` rows is the
  fleet-wide dedupe.
- Anything else: the project starts on the hub as before, and the dispatch
  writes ONE alert through `bin/alert-line.sh --id lane-placement:<lane>`.

The summary line keeps its old text byte for byte and appends
`; placed: <n> fly, <m> hub (<reason>)`, then `, <k> already live` and
`, <f> enqueue failed -> hub` when those are non-zero. `<m>` is the count of
hub processes started.

`bin/lane-run-worker.sh [--once] [--machine ID]` is the machine loop. It
claims one row (one UPDATE ... RETURNING statement: the oldest `queued` row,
or a `claimed` row whose `lease_until` is past), runs
`bin/project-lane-run.sh <lane> <project> 0 $H/<args[0]> <args[1..]>` under
`setsid -w` with `LANE_RUN_ID` set, and reports the real exit status and the
last `PROF ` line. A row is `done` only through the report route, which needs
the claimer's machine id and an integer rc 0..255. A missing rc is a 400.
`--once` drains until a claim is empty, then exits 0.

## Routes (worker/jobs/src/routes/lane-runs.js)

- `POST /api/lane-runs {lane, project, args, box?}`: 201 `{id}` or 409
  `{error:"already_live", id}`. `args[0]` must match `^bin/[A-Za-z0-9._/-]+$`
  with no `..` segment; at most 64 args, 4096 bytes each, 16384 bytes as JSON.
- `POST /api/lane-runs/claim {machine, lanes?}`: 200
  `{id, lane, project, args, attempts, lease_until}` or 204. It awaits
  `sweepDead(env, now)` from the lease seam first. The lease is the row
  `lane_run.lease_s` (30..3600, fallback 120).
- `POST /api/lane-runs/<id>/report {machine, rc, prof?}`: 200; a same-rc
  replay from the claimer is 200 `{replay:true}`; otherwise 409 with
  `reason` `not_claimer`, `rc_mismatch` or `not_claimed`; 404 for no row.
  `prof` is cut to 512 UTF-8 bytes on a character boundary.
- `GET /api/lane-runs/stats?lane=`: per lane, counts by status,
  `oldest_queued_wait_s` (null when nothing is queued) and `live_claimers`.

## Limits of this part

- No attempt cap: an expired lease is re-claimed with `attempts+1` forever
  until part 2's `sweepDead` marks rows `died`. Nothing runs on Fly yet, so no
  row can loop in prod.
- No machine runs `bin/lane-run-worker.sh` yet: no cron line, no Fly app. Part
  3 starts it.
- A row the machine cannot run (bad argv, failed `lri_fetch`) is logged and
  not reported, so its lease expires and it is re-claimed. BH-6128 changed
  this for `lri_fetch`: a failed fetch is now reported rc 66 (see
  `2026-10-12-BH-6128-blocked-resolver-offhub.md`).
- `setting_get` answers "no row" for an empty value, so an empty
  `lane_placement.<lane>` falls to `lane_placement.default`.
