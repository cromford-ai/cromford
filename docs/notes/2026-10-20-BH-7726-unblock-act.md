# The unblock lane's one writer, its refusals and its tripwires (BH-7726, UNB-4)

Doc: MERGE-CONDUCTOR, OPERATOR-SETUP

## What changed

1. `bin/lib/unblock/act.sh` adds `ub_act <decision-record-json>`. It is the
   only code in the unblock lane that writes to GitHub, to a verdict row, to
   the merge queue, to a settings row, to a box or to the critical DM. It
   returns one outcome (`would`, `done`, `failed`, `refused`) and a detail.
   It does not write the ledger row. The tick that claimed the decision
   (#7722) records the outcome.
2. `bin/lib/unblock/tripwire.sh` adds `ub_tripwire_scan <counts-json>`. Four
   tripwires (class burst, one subject on 3+ heads, judge calls, card
   re-declares) each send one warn alert with a stable id. A tripwire never
   stops an action.
3. Nothing calls either function in production yet. The tick, the lane
   registry row and the knob registration are #7722. The rules that make
   decision records are #7723-#7725.

The input contract, the gates and their order are in the header of
`bin/lib/unblock/act.sh`. The suite is `tests/unblock-act.bh-7726-test.sh`.

## The gates, in order

1. A never-auto class (`spend`, `production`, `live-probe`, `client-board`,
   `merge`, `deploy`, `governance`) or a never-auto action (`merge`,
   `force_push`, `deploy`, `pause_project`) is refused. One warn alert, id
   `unblock-never-<key12>`.
2. An unknown action name is refused.
3. The row `unblock.project.<p>.mode`. Absent, `off` or any other word:
   refused `no-opt-in`. `shadow`, or `act` with `UNBLOCK_ACT` not 1: `would`,
   with one `WOULD_<ACTION>` line in `logs/unblock.log` and no write.
4. `post_block` and `queue_approve` are refused while `bin/lead-verdict.sh`
   does not list `agent` in its `--source` set. Every verdict row uses
   `--source agent --reviewer tackler:<key12>` (the operator, comment 6294290340,
   item 1).
5. A PR action re-reads the PR head (moved: refused, no write) and searches
   the comments and reviews for `<!-- tackler:<decision_key> -->` (found:
   `done marker-found`, no write). The search reads up to 5 pages of 100. A
   longer list is `failed marker-search-truncated`, never "not found".

Hard limits at the writer: one box restart per box per hour (a stamp in
`state/unblock/restart-<box>.at`, written before the restart), and one tackler
change per knob key per 24 h (read from the settings row's `actor` and
`updated_at`).

The knob allowlist is the row `unblock.knob_allowlist`. When the row is
absent, the code list is the operator's list from comment 6294290340, item 3:
`lane.fly-pool-tick.pool_tick_max_parallel`, `hub_load.shed`,
`lane.fly-pool.*.pool_record_read`, `lane_placement.*`,
`conductor_remote_spawn.*`. A `*` matches one segment with no dot. A key under
`unblock.*` or `lane.unblock.*` is refused whatever the row says, so the lane
cannot flip itself. Every knob record must carry `min` and `max`, and the new
value must be a number inside them.

## Flip preconditions

All of these must be true before anyone sets the flip rows:

1. #7722 (the tick, the ledger, the lane row) is merged and deployed.
2. #7723, #7724 and #7725 (the rules and the card) are merged.
3. The worker slice that accepts verdict source `agent` (the operator, comment
   6294290340, item 1) is merged, and `bin/lead-verdict.sh` lists `agent` in
   its `--source` set. Until then act.sh refuses every verdict-writing action.
4. A shadow run on cromford shows 0 mismatches against the 2026-10-19/20
   corpus. The full replay through the collectors and the rules is owed by
   #7723-#7725. This PR replays the corpus at the act layer only.

## Flip

the operator, or a Mac session that the operator asks, sets the two rows:

```bash
bin/jobs-client.sh setting-set unblock.project.cromford.mode act "BH-7726 flip"
bin/jobs-client.sh setting-set lane.unblock.unblock_act 1 "BH-7726 flip"
```

That is `unblock.project.cromford.mode=act` and `lane.unblock.unblock_act=1`.
The flip is not part of this ticket.

## Rollback

To stop every act-mode write, roll back one of the two rows:
`unblock.project.cromford.mode=shadow` or `lane.unblock.unblock_act=0`.
The next call of `ub_act` answers `would`.

To roll back one effect that already happened:

| Effect | How to roll back |
|---|---|
| BLOCK verdict row (`post_block`) | Post a newer verdict row on the same head (`bin/lead-verdict.sh post ... MERGE --source human`). |
| BLOCK comment and REQUEST_CHANGES review | Dismiss the review. The comment stays as the record. |
| Dequeue label (`post_block`) | Requeue the PR. |
| Requeue (`requeue`) | Dequeue the PR. |
| Queue under standing approval (`queue_approve`) | Dequeue the PR, then post a BLOCK verdict row if it must not land. |
| Dismissed review (`dismiss_review`) | Post a new review. A dismissal cannot be undone. |
| Fix round (`fix_round`) | Cancel the fix-round job. |
| Lead re-request (`lead_rerequest`) | None needed. The request finishes on its own. |
| Knob change (`setting_set`) | Set the key back to the old value. The settings row's note says `roll back by setting <old>`. |
| Box restart (`box_restart`) | None. The critical alert line is the record. |
| Card (`send_card`) | None. The critical DM is the record. |
