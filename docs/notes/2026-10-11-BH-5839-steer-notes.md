# Step in: notes reach the running build, the ticket and the hold (BH-5839)

Doc: EVENTS, DB-COORDINATION-SPEC

## What changed

The "Step in" box on the ticket page (`/t/<KEY>`) now sends notes. A note has
one of three modes:

| Mode | Where it goes | Who acts |
|---|---|---|
| `now` (Tell the agent now) | the prompt of the next stage the running build starts | `bin/agent-call.sh`, `# >>> steer take` block |
| `ticket` (Add to the ticket) | one issue comment, posted as the App | the hub, `bin/lib/steer-deliver.sh` |
| `hold` (Hold, then tell it) | the `hold` label plus the note; the running build stops after its current step | the hub (`thc_run hold`) and the build (`CC()` defers) |

- Store: one `steer_notes` row per note in the jobs worker
  (`worker/jobs/schema.d/0020-bh-5839-steer-notes.sql`, self-creates through
  `CREATED_TABLES`). Routes: `POST /api/steer`, `GET /api/steer`,
  `POST /api/steer/take`, `POST /api/steer/settle`, `GET /api/steer/outbox`,
  `POST /api/steer/<id>/claim`, `POST /api/steer/<id>/delivered`
  (`worker/jobs/src/routes/steer.js`).
- Status: `pending` → `taken` → `read` for a `now` note; `pending` →
  `delivering` → `delivered` (or `failed`) for a `ticket` or `hold` note.
- A browser writes only `POST steer`, through one coord proxy WRITES row.
  `steer/take`, `steer/settle`, `steer/<id>/claim`, `steer/<id>/delivered`
  and a GET of `steer/outbox` (`BOX_ONLY_GETS`) are 405 from a browser.
- Every send and every read is a `stage_events` row on the job, stage `steer`
  (`SENT`, `READ`, `HOLD`).

## Rules

- The worker refuses a `now` note unless the job is a running build of the
  same ticket (400 with no job, 404 for an unknown job, 409 otherwise).
- Only a `CC()` call is a step boundary. `CC()` sets `AGENT_CALL_STEER=1`, and
  `bin/agent-call.sh` takes nothing without it. A direct caller inside a build
  (`bin/replan-check.sh`, `bin/lib/prebuild-repro/drive.sh`,
  `bin/run-decompose.sh`) does not stop on rc 74, so it must not take a hold
  or a note.
- `take` checks the hold FIRST. The first hold note sent to the job is taken
  once (`build_read_at IS NULL`), and then no `now` note is taken: the stage
  refuses, so those notes stay `pending`. The echo shows "not read: the build
  ended before its next step" for them. A hold note sent to one job does not
  stop another job of the same ticket; the hold label stops the re-offer.
- Without a hold, `take` claims each pending `now` note once as `taken`
  (`UPDATE … RETURNING`). It is not `read` yet. The call's EXIT trap runs
  `steer_settle` with the call's rc: rc 0 makes the notes `read` (with a
  `READ` event, `build_read_at` = the take time). Any other rc (a gate below
  the take refused, or the runner failed) gives them back as `pending`, and the
  next step boundary takes them. When a job phase is open, its EXIT trap
  replaces the take's and runs the settle too. A settle the worker does not
  answer leaves the notes `taken`; the next take takes them again after
  `steer.take_lease_s`.
- A hold refuses the stage with rc 74 and the first line
  `AGENT_CALL_REFUSED steer-hold <id> <text>`. Nothing is called or billed.
  `CC()` writes `$BUILD/BUDGET_DEFER`, answers
  `BUILD_DEFERRED steer-hold <id> <text>` and exits 3. The parallel review
  lenses and every later `CC()` refuse on the same marker. The review log line
  says "a lens deferred on a budget cap or a hold" and quotes the marker.
- The build side fails open. With no `JOB_ID`, no lib or no worker answer, the
  prompt does not change, the note stays pending, and `logs/steer.log` gets one
  line. The take and the settle use `JOBS_RETRIES=0`: one try each, at most
  `JOBS_TIMEOUT` (8 s) per call, so a hung worker costs each `CC()` call up to
  16 s before the stage runs on.
- The parallel review lenses share one `JOB_ID`. Each take is atomic, so a
  `now` note lands in exactly one lens's prompt.
- The hub posts only on an App token minted for that repo (`ghs_*` from
  `gh_auth_for`). No App token is a not-ok report. A PAT comment would read as
  a person's comment to `hold_classify`.
- A hold whose comment was not posted (no App token, or the POST failed) is a
  not-ok report. The label alone does not show the note to anyone.
- Only the box that holds the hub lease delivers. The
  `# >>> steer outbox (BH-5839)` block in `bin/poll-commands.sh` runs only when
  `bin/hub-lease.sh check` is rc 0. The cron line stays `@ungated`.
- One comment per note. The hub claims each note before it posts
  (`POST /api/steer/<id>/claim`, `pending` → `delivering`). Of two boxes on
  one outbox page, only one gets 200. Each comment ends with the marker
  `<!-- steer-note:<id> -->`. Before a post, the hub reads the issue's
  comments. If the marker (or, for a hold, `thc_run`'s "Held from Mission
  Control by <actor>: <note>.") is there, it posts nothing and reports ok. If
  the comments cannot be read, it posts nothing and reports not ok. A claim
  whose report was lost returns to the outbox after `steer.deliver_lease_s`.

## Settings

| Key | Default | Range | Meaning |
|---|---|---|---|
| `steer.attempts_max` | 3 | 1..10 | failed hub deliveries before a note is `failed` |
| `steer.outbox_limit` | 10 | 1..100 | notes the hub delivers per tick |
| `steer.take_lease_s` | 7200 | 60..86400 | seconds before a taken, unsettled `now` note is taken again |
| `steer.deliver_lease_s` | 300 | 60..3600 | seconds before a claimed, unreported note returns to the outbox |

The fragment seeds all four rows with `INSERT OR IGNORE`. A row that is absent or
out of range uses the code fallback. Text caps stay in code: 4000 characters a
note, and 500 for a hold note, because it is the hold reason
(`bin/lib/ticket-hold-cmd.sh` keeps `.[0:500]`).
