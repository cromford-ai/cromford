# The conductor carries a lead MERGE across a clean main merge (BH-6291)

Doc: MERGE-CONDUCTOR

## Why

A lead MERGE stood on head A. A clean `git merge main` moved the head to B.
The conductor reads lead approvals through `mc_lead_ready`
(`bin/lib/mc-lead-ready.sh`). On B, `vd_standing` found nothing, so
`mc_lead_ready` returned 1. The row went to HEAD_MOVED and the conductor bought
a head-bound re-review. A BLOCK from that review parked the PR as
`head-not-reapproved`.

The lead-review enqueue lane (gate 50, `bin/lib/lead-gates.d/50-replay-delta.sh`)
already replays a lead word onto a merge-only head. It runs every 5 minutes.
The conductor reached B first.

## What changed

- New lib `bin/lib/lead-carry.sh`, function `lead_carry <key> <owner/repo>
  <num> <head>`. It takes the newest lead MERGE, MERGE-WITH-NOTES or BLOCK row
  on another head G whose note is not a `lead-replay:` (gate 50's source rule).
  It carries G's word onto `<head>` only when all of these are true:
  1. G's word is not a BLOCK.
  2. `patch_same` (`bin/lib/patch-same.sh`) answers `main-merge` (no new
     non-merge commit since G, and every merge tree equals `git merge-tree` of
     its parents) or `patch-id` (a byte-exact rebase, `--verbatim`).
  3. `la_decide <slug> <num> <head> conductor` is rc 0.
  4. The box has a readable lead token file.
- The carry writes one row through `bin/lead-verdict.sh post <slug> <num>
  <head> <word> --source lead`. That script also publishes the `lead-verdict`
  status. The note is `lead-replay:<G12> how:<how> ref:#<G row id>
  by:merge-conductor`. Gate 50, `lw_replay` and `bin/lead-review-enqueue.sh`
  match the `lead-replay:` token, so no writer posts a second row.
- `mc_lead_ready` calls `lead_carry` once when `vd_standing` answers rc 1
  (nothing stands). If the carry posts a row, it reads `vd_standing` again and
  the later gates run as before. An unreadable `vd_standing` (rc 2) is still
  rc 1.
- The carry runs only when `ACTIONS=1`. A dry-run tick reads and writes nothing.

## Outcomes and state

Each decision is one conductor log line:

```
<key> LEAD_CARRY <carried|refused|held> from=<G12> to=<H12> word=<W> ref=#<id> how=<how|-> patch_old=<id12|-> patch_new=<id12|-> reason=<text>
```

- `carried`: the post returned 0, 4 or 5. The reason names the rc.
- `refused`: the source is a BLOCK, the patch changed, `la_decide` is rc 1,
  the box has no lead token, or the post failed. On a box with no lead token,
  gate 50 stays the writer.
- `held`: the history is unreadable or truncated, there is no fleet.conf root,
  there is no clone, the fetch failed, or `la_decide` is rc 2. The next tick
  asks again. The line is said once a head (attempts line
  `leadcarry-held <key> <head>`).

`carried` and `refused` write the attempts line `leadcarry <key> <head>`. A
head with that line is never asked again.

## Knob

`MC_LEAD_CARRY` on the `merge-conductor` lane, default 1. 0 turns the carry off:
the head waits for gate 50 or a new review, as before.

## Decisions

- No new verdict source. The carry writes `source=lead` with the gate 50 note
  format. A `carry` source would change the worker's source lists and every
  `vd_standing` reader.
- A merge whose tree differs from `git merge-tree`'s clean result is never
  carried, also when the extra edit is in a file the PR does not change. That
  edit becomes part of the new head's diff, and nobody reviewed it.
- Gate 50 still replays a BLOCK onto a builder-rebound head (BH-3930). The
  conductor carry never posts a BLOCK.
- The builder rebind in `bin/lib/mc/settle.sh` is not changed. It is a
  lead-protected path and already logs `REBOUND`.
- `bin/lib/lead-carry.sh` writes lead rows, so it belongs in
  `catalog/lead-protected-paths.tsv`. This PR does not edit that file (it is
  itself protected). An operator must add it.
