# Rule adopt: the hub lane that lands lint-backed rules PRs (BH-3715, BH-3692.2)

Doc: TRUST-PROGRAM

## What changed

A new hub lane, `bin/rule-adopt.sh tick`, runs every 15 minutes from
`cron/lanes/461-rule-adopt.cron` behind `bin/hub-lease.sh check`. It lands the
rule miner's lint-backed rules PR through the normal lead lane. It makes no
model call, uses no SSH, and never merges or pushes. The only way it puts
anything in the queue is `mc_enqueue`, and only on a lead MERGE bound to the
live head.

It only looks at open, non-draft PRs on the `cromford` repo (the slug on
its `fleet.conf` row) whose head matches the contract's `RE_LINT_HEAD_RE`
(`rules/mined-<YYYYMMDD>-lint`). The judgement PR `rules/mined-<YYYYMMDD>`
never matches, so this lane never reviews or queues it.

For each of those PRs:

1. **Head.** `pulls/<n>` gives the live head sha and `mergeable_state`.
2. **Guard.** `compare/main...<head>` must show every non-merge commit
   authored by `harness@box`. Every file must be
   `prompts/build-discipline.md` (modified) or a new
   `prompts/rule-evidence/D<n>.json`, and there must be at least one evidence
   file. Each evidence file, read at the head, must be `lint-backed`, name a
   check, and carry its own D-number. Anything else gets one warn,
   `rule-adopt-foreign-<n>-<sha12>`. A truncated compare, or an evidence read
   that fails, counts as unreadable and gets no warn.
3. **Verdict.** `vd_standing` on the head:
   - MERGE or MERGE-WITH-NOTES goes to enqueue.
   - BLOCK gets one warn, `rule-adopt-block-<n>-<sha12>`.
   - Nothing standing goes to request.
   - rc 2 counts as unreadable.
4. **Request.** `bin/lead-verdict.sh request … --notes "rule-miner lint-backed
   rules; …"`. rc 0, or an `HTTP 409`, counts as requested. Any other failure
   gets one warn, `rule-adopt-req-<n>-<sha12>`, naming
   `bin/harness-ctl.sh review <slug> <n> <head>`.
5. **Enqueue.** A `dirty` PR gets one warn, `rule-adopt-dirty-<n>-<sha12>`.
   The lane never rebases. Otherwise it calls `mc_enqueue`:
   - rc 0 writes the marker and then sends the warn `rule-adopt-queued-<n>`
     ("… queued to merge", never "adopted").
   - rc 2 (merged outright) writes only the marker.
   - rc 1 or 3 gets the warn `rule-adopt-enqueue-<n>-<sha12>`, with no marker,
     and the next tick retries.

Then comes the merged sweep. It reads the last 50 closed PRs. Every `-lint` PR
that GitHub says merged in the last 7 days gets one warn, `rule-adopted-<n>`.
The warn names each rule, its check and its incident ids, read from the
evidence at `ref=main`.

## State, knob, switch

- **Markers** in `state/rule-adopt/` are dedupe only, pruned at 14 days:
  - `enqueued-<n>-<sha12>`
  - `requested-<n>-<sha12>`
  - `noted-<n>`, written only after `lane-alert.sh` returned 0
  - `alerted-<id>`
- **Knob** `RULE_ADOPT_MAX_REQUESTS_PER_TICK` (required, default 3, 1-20).
  It caps new lead review requests per tick. A re-confirm of a head already
  requested does not count. The rest are deferred to the next tick.
- **Kill switch:** `flags/lane-off-rule-adopt`.
- **Log:** `logs/rule-adopt.log`, one line per tick:
  `tick prs=.. lint=.. queued=.. requested=.. deferred=.. blocked=.. foreign=.. dirty=.. unreadable=.. noted=..`.

## Known limit

If Mergify dequeues a PR on the same head after `mc_enqueue` returned 0, this
lane does not ask again, because the `enqueued-` marker is keyed on the head.
A new push (a new head) or a pruned marker re-arms it.

## Touches

`bin/rule-adopt.sh`, `cron/lanes/461-rule-adopt.cron` and
`catalog/lanes.d/rule-adopt.json` are new, pinned by
`tests/rule-adopt.bh-3715-test.sh`. `merge-conductor.sh`, `bin/lib/mc/*`, the
lead prompts and `.mergify.yml` are unchanged.
