# Ported-flag routes answer a D1 overload with a 503 (BH-6805)

Doc: OPERATING

## The gap

`withD1Retry` (BH-6690) retries a "D1 DB is overloaded" rejection 3 times, with
exponential backoff and jitter (base 50 ms, max 1000 ms). After the third
attempt it rethrows the same error, with `d1Attempts` set. The ported-flag
routes did not catch it. The throw reached `withSentry` as an HTTP 500. Sentry
issue CROMFORD-HARNESS-Z counted 64 such events in 24 h, stack
`readPortedFlag -> withD1Retry`.

## What changed

- `d1OverloadGuarded(table, fn, label)` in `worker/jobs/src/lib/http.js` runs
  `fn`. On an error where `isD1Overloaded(e)` is true, it writes one
  `console.warn` line (`d1-overload: <table> <label> answered 503 after <n>
  attempt(s)`) and answers 503 `{error: "<table> unavailable", detail,
  retryable: true, d1_attempts}`. The body matches the BH-6807 verdict 503. It rethrows every other error as the same object, so Sentry
  still reports a real bug.
- `worker/jobs/src/routes/flags.js` uses it on the 3 ported-name paths:
  `GET /api/flags/<name>`, `PUT /api/flags` and `DELETE /api/flags`. The legacy
  (non-ported) paths and the `GET /api/flags` list do not change.
- The read-back after a committed ported write is the exception. `writePorted`
  runs the upsert batch, then reads the row back. If that read-back still
  overloads after the retries, the write has landed. The route answers 200
  `{flag: null, written: true}`, not the 503, and writes one warn line
  (`d1-overload: harness_flags read-back <name> after a committed write, ...`).
  `bin/lib/jobs/req.sh` re-sends any method once on a 503 "overloaded". A
  re-sent PUT would write a second `config_changes` audit row, or answer a false
  409 "flag moved". The body has no "overloaded" and no `retryable`. On the box,
  `_flag_written` (bin/lib/jobs/flags.sh) reads `written:true` as a landed
  write. `flag_set`, `flag_clear` and `_flag_import_one` cache the state with no
  row, return 0 and send no second request.
  `tests/flags-written.bh-6805-test.sh` pins this. A non-overload error on the read-back still throws to Sentry.

## Why a 503, not the code default

`readPortedFlag`'s only default is `null`, "no row". GET maps that to 404, and
`flag_fetch` (`bin/lib/jobs/flags.sh`) caches a 404 as "off". A `paused-*` row
that is on would read as off during an overload. A 503 whose body holds
"overloaded" is the answer `bin/lib/jobs/req.sh` retries once. After that,
`flag_fetch` answers from its last-good cache.
