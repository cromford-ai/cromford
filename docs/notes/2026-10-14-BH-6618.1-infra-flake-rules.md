# CI test value report: the infra and flake rules (BH-6637, BH-6618.1)

Doc: CI-RUNNERS, FLAKY-TESTS

## What changed

Three rule files of the registry `bin/lib/ci-test-value/rules.d/` now decide
rows. Before this change every row of `occurrences.tsv` was
`unknown U1.undecided`. Now a row can be `infra` or `flake`. Rows that no rule
decides stay `unknown U1.undecided`. The rule files 30, 40 and 60 are still
placeholders (BH-6618.2).

## The rules

The first rule that decides a row wins. The order is the file order.

`10-infra.sh` (`ctv_rule_infra`), first match wins in this order:

- `I1.cancelled`: the job conclusion is `cancelled` or `timed_out`, and the
  unit is a `job:<name>` row. The driver writes a `job:` row only when the log
  names no unit with rc > 0.
- `I2.step`: the first failed step name (`CTV_STEP`) matches a row of
  `catalog/ci-test-value/infra-steps.tsv` (bash `=~`, POSIX ERE, `LC_ALL=C`).
- `I3.pattern`: the unit's excerpt file matches a row of
  `catalog/ci-test-value/infra-patterns.tsv` (`LC_ALL=C grep -E`).

`20-flake.sh` (`ctv_rule_flake`):

- `F1.same-head-green`: the same workflow went green on the same head sha.
  a) `GET repos/<R>/actions/runs?head_sha=<sha>` has a run with the row's
  `workflow_id`, the same `head_sha` (checked again, the API filter is not
  trusted), status `completed`, conclusion `success`, and another run id or a
  later attempt of this run. b) The row's job name has conclusion `success` on
  another attempt of this run. Step b reads at most 5 attempts, up to the
  latest completed attempt. A `cancelled`, `skipped` or `neutral` run is not
  green.

`50-main-flake.sh` (`ctv_rule_main_flake`):

- `F2.main-unrelated-green`: a push run on `main` failed a `tests/*.sh` suite.
  The rule finds the next green push run of the same workflow on `main`: the
  smallest run id above the row's, created on the row's day or the next day,
  at another sha. The compare from the red sha to the green sha must be
  `ahead`, `behind_by` 0, fewer than 300 files and at most 250 commits. The
  suite must not be a changed path. `bin/test-impact.sh select --changed
  <paths> --map-only` must not print the suite. The rule decides nothing in
  these cases:
  - the compare is unread, 404 or `diverged`;
  - the suite is not in the impact map (a vitest file, a `job:` row, a renamed
    suite);
  - the select fails;
  - the select's `impact:` reason line says `full:`, so CI would run the whole
    corpus for that diff (for example `full: unknown reach`).

## The two catalogs

Both files are `<POSIX ERE>\t<why>`, one row per line. The why column is the
rule's why in `occurrences.tsv`. A blank line and a line that starts with `#`
are skipped. A row with an empty ERE or an empty why is skipped. A row whose
ERE does not compile never matches. The other rows still apply.

To add a row:

1. Add one line `<ERE>\t<why>` to the catalog. Use a real tab.
2. Match text that the tool or the runner prints. Do not match a word that a
   test assertion can print. `rate limit` alone also matches
   `FAIL: expected rate limit message`; use `API rate limit exceeded`.
3. Run `HARNESS_TEST_SANDBOX=1 bash tests/ci-test-value-infra-flake.bh-6618-test.sh`.
   Its CAT checks refuse a row that is not two fields or has a bad ERE. They
   also refuse an `infra-steps.tsv` row that matches a test step: `run the
   traced corpus`, `trace shard`, `worker-jobs unit tests`, `console-ui unit
   tests`, `fan-in`.

The `::error title=CI infra` row matches the text that `bin/ci-retry.sh` and
`bin/ci-apt-update.sh` print. This build did not check that a downloaded job
log keeps that text. GitHub can show a workflow command as `##[error]`.

## The rule read ledger

`ctv_classify_row` runs each rule in `$( )`. A GitHub read in a rule therefore
does not reach the driver's `CTV_GH_READS`, and `--max-reads` would not see it.
The rules read through `_ctv_rr_get` (in `20-flake.sh`):

- The per-run scratch dir is `<out>/.rules-scratch/<runid>/`. The runid is the
  driver's pid and its start time. The first rule read of a run removes the
  dirs of earlier runs.
- Each network read adds one line (the API path) to `<runid>/reads`. Before a
  read, `_ctv_rr_get` adds that line count to `CTV_GH_READS`, so
  `ctv_gh_get`'s `--max-reads` check counts the rule reads too.
- `<runid>/memo/` keeps each answer for the rest of the run. A head list is
  read once per head, and a green list once per workflow and day. An absent
  (44) or unread (75) answer is kept as a `.rc` memo and never goes to
  `cache/`.
- `coverage.gh_reads` is still the driver's own count. It does not include
  the rule reads. The number of rule reads is the line count of
  `<out>/.rules-scratch/*/reads`.

Only answers that cannot change go to `<out>/cache/`: the job list of an
attempt (the driver's key `run/<id>-a<n>-jobs.json`) and a compare of two
fixed shas (`f2/compare-<a>-<b>.json`).

## The F2 impact map

F2 builds the impact map with `bin/test-impact.sh map` (about 21 s) at most
once per report run, and only when a push/main row reaches the reach step.
The map is `<out>/cache/impact-map-f2.tsv`. `<out>/cache/impact-map-f2.stamp`
holds the runid that built it. A different runid rebuilds it. A failed build
is kept as a memo, so later rows of the same run do not retry it.
`CTV_F2_IMPACT_MAP=<file>` replaces the map only when
`HARNESS_TEST_SANDBOX=1`.

## Tests

`tests/ci-test-value-infra-flake.bh-6618-test.sh` has positive and negative
rows for each rule. It checks the ledger and the per-run memo, builds the real
map once, and runs the CLI end to end over
`tests/fixtures/bh-6618/infra-flake/`. In
`tests/ci-test-value.bh-6618-test.sh`, the checks that count the driver's
GitHub reads now subtract the rule reads.
