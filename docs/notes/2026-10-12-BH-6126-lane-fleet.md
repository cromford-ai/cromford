# Lane-run Fly fleet: the autoscaler (BH-6126, BH-6047 part 3 of 5)

Doc: PROJECT-LANES

## What changed

A new hub lane, `lane-fleet`, scales the Fly app `lane-run`. Its machines run
`bin/lane-run-worker.sh` (BH-6124) and claim the `lane_runs` rows that lanes
placed `fly` enqueue. The build pool app is not touched.

`bin/lane-fleet.sh tick` runs every minute on the hub, behind
`hub-lease.sh check` and its own `flock -n locks/lane-fleet.lock`. One tick:

1. Reads `GET /api/lane-runs/stats`, `flyctl machine list -a lane-run --json`
   and `GET /api/lane-fleet/machines`. A failed read stops the tick before any
   start or stop and writes one ALERTS line per read kind per UTC day.
2. Records a Fly `started` machine with no row (`starting` when Fly changed it
   less than `lane_fleet.start_grace_s` ago, else `started`). Marks a
   `started` row `stopped` (or `destroyed`) when Fly lists its machine stopped
   or not at all, at Fly's `updated_at`, so its last cost rows end there.
   Handles each failed start (see below).
3. Decides with `lf_decide` and `lf_pick_stop`. At most one start or one stop.
4. Starts by reusing a Fly `stopped` machine (`machine start`), else
   `machine run` with the size rows. The new id is recorded `starting` before
   the tick exits, so the next tick counts it as in flight.
5. Posts cost rows for every started machine through the current minute.

## The rule

| condition | action |
|---|---|
| a start is in flight | no start |
| a failed start this tick, or `last_failed_at` younger than `lane_fleet.failed_start_backoff_s` | no start |
| `lane_fleet.max_machines` > 0 and live + in flight >= it | no start |
| live < `lane_fleet.warm_floor` | start |
| oldest queued wait > `lane_fleet.scale_up_wait_s` (equal is not over) | start |
| no start due, no queued run at all, live > floor | stop the most idle machine whose `idle_s` > `lane_fleet.idle_stop_s` and that is not busy and not in flight |

A start is in flight while its row is `starting`, it has made no claim since
its row's `started_at` and it is younger than `lane_fleet.start_grace_s`. A
claim from an earlier life of a reused machine does not count. Fly machines in
`created` or `starting` also count. `max_machines=0` means no ceiling.

A stop needs an empty queue. With a queued run under the threshold, an idle
machine can claim it between the read and `machine stop`, and the stop kills
the run.

A failed start is a `starting` row that is past `start_grace_s`, or whose
machine Fly lists `stopped` or `destroyed` (it exited at boot, for example on
a missing Fly secret). The tick writes one ALERTS line per UTC day, runs
`machine stop` when Fly still runs the machine, marks the row stopped with
`failed:true` (which sets `failed_at`) and posts its last cost rows. Then it
starts no machine for `lane_fleet.failed_start_backoff_s`, the warm floor
included. So a machine that never claims costs at most one start per backoff,
not one per minute, and never grows the fleet.

`lane_fleet.image` must name a tag or digest of `registry.fly.io/lane-run`.
Fly gives every machine in the app the lane-run secrets, the GitHub App key
among them, so any other value uses the code default.

## The record

Table `lane_machines` (schema.d/0022), keyed on the Fly machine id. Routes in
`worker/jobs/src/routes/lane-fleet.js`:

- `GET /api/lane-fleet/machines`: the `starting`/`started` rows with
  `in_flight`, `busy` and `idle_s`, and `last_failed_at`. The first claim by
  a machine since its row's `started_at` moves its row from `starting` to
  `started`.
- `POST /api/lane-fleet/machines`: upsert one row (201 insert, 200 update).
  A `stopped`/`destroyed` row takes an optional `stopped_at` (cut to now) and
  `failed:true` (sets `failed_at`).
- `POST /api/lane-fleet/cost {machine_id, through, usd_per_s, ...}`: one
  `cost_rows` row per whole minute after `costed_until` (or after the start's
  own minute, when that is later) up to `through`. Box `lane-run-<mid>`,
  row_hash `lane-fleet:<mid>:<minute start>`, stage `infra`, runner `fly`,
  `lane_id` = the lane the machine held in that minute, else `lane-fleet`.
  A replay writes nothing. At most 120 rows per call, with `incomplete=true`
  when more minutes remain. `usd_per_s` must be a number >= 0 or null; null
  writes a NULL cost and an `UNPRICED:fly-size-unknown:<mid>` note. A minute
  is billed whole, so a start or stop costs at most one minute too much.

## Settings rows (code default in brackets)

`lane_fleet.warm_floor` (1), `lane_fleet.scale_up_wait_s` (60),
`lane_fleet.idle_stop_s` (600), `lane_fleet.max_machines` (0 = no ceiling),
`lane_fleet.vm_size` (shared-cpu-2x), `lane_fleet.vm_memory_mb` (2048),
`lane_fleet.start_grace_s` (180), `lane_fleet.failed_start_backoff_s` (900),
`lane_fleet.image` (registry.fly.io/lane-run:latest; only a tag or digest of
`registry.fly.io/lane-run` is used).

## Operator steps before the lane does anything

The tick writes one ALERTS line a day (`fly-list read failed`) until the app
exists. From the repo root:

1. `flyctl apps create lane-run`
2. `flyctl secrets set HARNESS_SECRET=... JOBS_URL=... GH_APP_ID=... GH_APP_PRIVATE_KEY=... GH_APP_INSTALLATION_<OWNER>=... -a lane-run --stage`
3. `flyctl deploy . -c fly/lane-run.toml --build-only --push --image-label latest`

While every lane is placed `hub` (the default), the queue is empty and only the
warm floor acts: one `shared-cpu-2x` machine stays started.
