# BH-5781: D1 overload relief

Doc: DB-COORDINATION-SPEC, VERIFICATION-MAP

The hub's `logs/jobs-client.log` showed about 230 `D1_ERROR: D1 DB is
overloaded` answers an hour on 2026-10-09. Every one fell at minute
:00/:15/:30/:45. The top routes were single-key settings reads
(`closeout_aged_table`, `archie.*`, `build_queue_rows_only`, `routing_rows`) and
the settings list.

What changed:

- `_jobs_req` sends a request again once on a 503 whose payload says
  `overloaded`. Knobs: `JOBS_OVERLOAD_RETRIES` (1), `JOBS_OVERLOAD_SLEEP` (2),
  `JOBS_OVERLOAD_JITTER_S` (2). A failure after the retry logs
  `after overload retry`. `_jobs_req_file` is unchanged.
- `setting_get` answers from a fresh `state/settings-cache.json` with no
  request (`JOBS_SETTINGS_CACHE_S`, default 60; 0 = off). Signed keys bypass it.
  `setting_set` marks the file stale after a 2xx.
- The worker reads the settings table once per isolate per TTL
  (`settings_cache_ttl_s` row, else `SETTINGS_CACHE_TTL_S` = 30 in
  `wrangler.jsonc`). Another isolate can serve an old row for at most the TTL
  after a write.
- `lane_gate_or_exit` sleeps a stable per-box offset (0..120 s, row
  `lane_start_spread_s`, env `LANE_START_SPREAD_S`) at a quarter-hour minute
  before its first D1 read. `tests/lib/scratch.sh` exports
  `LANE_START_SPREAD_S=0` so no suite waits for it.

### (c) Static D1 cost per call, top 5 routes

Source: the handlers in `worker/jobs/src/routes/` at this PR's base. Counts are D1 statements per call, before this PR.

| Route | D1 statements per call |
|---|---|
| GET /api/settings/<key> (closeout_aged_table, archie, build_queue_rows_only) | 1 for a normal key. A `lead_*` or `risk_tier.*` key also reads `setting_sigs` (+1). |
| GET /api/settings | 1, plus 1 `setting_sigs` read per `lead_*` / `risk_tier.*` row |
| GET /api/model-routes/<role> | 4 without a project (ladder, scope version, own rows, provenance rows); up to 6 with a project (project ladder and project scope version added). +1 table check on a cold isolate. |
| GET /api/archie/actions | 1 (`?day=` rows); 2 with `count_by` + `summary=1` |

After this PR, with the cache on, a repeated settings GET inside the TTL costs 0 statements in the worker, and a box answers repeated `setting_get` calls from its local cache with 0 requests.

### (d) Onset at 2026-10-08 07:00Z

I compared `cron/` and `catalog/lanes.d/` on main at 2026-10-08 05:00Z (2b659e4e2) and 08:00Z (6894b6b55). The only schedule change is BH-5317 (#5335, merged 06:05Z): lead-review, lead-review-enqueue and lead-review-land moved from `*/5` to `*/15`. That change lowers the number of runs. BH-5317 also made a finished review ring lead-land and added an owed-rerun chain (`LEAD_REVIEW_RERUN_MAX`, default 3), which can add runs off the schedule. Those runs do not land on quarter-hour minutes, so they do not explain the bursts. Finding: the cause of the 2026-10-08 07:00Z step was not found from the repo. The hub deploy time and the D1 row count growth are not visible from a build box.
