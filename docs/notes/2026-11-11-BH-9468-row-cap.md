# Resolver caps the read phase of one row (BR_ROW_MAX_SECS), and the loop goes on (BH-9468, #9369 fix 4)

Doc: MERGE-CONDUCTOR

## Problem

On 2026-11-09 one row of `bin/blocked-resolver.sh` held a tick for 504 s of reads. The tick wall bound (`BR_TICK_MAX_SECS`) is asked only between rows, so every row behind that row waited.

A plain time limit on a row was not safe. A fix round holds a row for up to 90 minutes, so a 120 s kill cuts paid rounds. A detached row makes rungs concurrent, and the driver keeps rungs serial (`br_cron_unlock` releases the lane-wide scan lock).

## What changed

`bin/blocked-resolver.d/bh-9468-row-cap.sh` caps a row only until the row COMMITS. It never detaches a row.

1. The row subshell stays in the foreground. No second row starts while one runs.
2. A watchdog (a background job of the lane) sleeps `BR_ROW_MAX_SECS`. Then it stops the row only if the row has not committed: TERM to the row and its descendants (children first), then KILL after `BR_ROW_KILL_GRACE_SECS`.
3. A row commits at the first call of a rung entry point or a state writer: `br_cron_unlock`, `br_record`, `br_json_edit`, `br_save`, `br_event`, `br_set_outcome`, `br_tkey_put`, `mc_row_put` and the rest of the list in `_brrc_wrap`. Each of these is wrapped at run time. The wrapper writes the commit marker under the same flock the watchdog decides under. So a row never writes after the watchdog decided to stop it, and the watchdog never stops a row that has started to write.
4. A stopped row is carried. The log says `row cap: <p>/<rkey> carried — no rung reached in BR_ROW_MAX_SECS=<n>s (rc 143); offered again next tick`. The row takes no rung (rc 3), `br_note_untouched` sees it, and the loop goes on to the next row in the same tick.
5. No starvation. A row carried `BR_ROW_CARRY_MAX` times runs uncapped the next time (`row cap: <p>/<rkey> runs uncapped this tick`). The count is in `state/blocked-resolver/.row-carry[-<project>].tsv` (`<p>\t<rkey>\t<count>`). The file is rewritten each tick and holds only rows still on the candidate list. A row that runs to an end drops out.
6. Not armed: `BR_ROW_MAX_SECS=0`, a one-PR run (`BR_ONLY_PR`) and a hopped rung (`BR_FIX_HERE=1`).

The driver gets four guarded call sites in the rung loop: `brrc_row_begin`, `brrc_row_pid`, `brrc_row_end` and `brrc_tick_end`.

## What the cap does not cover

A rung that is slow after its commit is not stopped. It stays bounded by `BR_TICK_MAX_SECS` between rows, as before.

## Knobs

All three are `catalog/lanes.d/blocked-resolver.knobs.d/` rows:

| Knob | Default | 0 means |
|---|---|---|
| `BR_ROW_MAX_SECS` | 120 | off |
| `BR_ROW_CARRY_MAX` | 1 | never exempt |
| `BR_ROW_KILL_GRACE_SECS` | 10 | (min 1) |
