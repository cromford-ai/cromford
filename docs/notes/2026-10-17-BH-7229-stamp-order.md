# BH-7229: the stale-stamp rule judges dependency, not stamp age

## What changed

- `rp_schema_fragment_name` (`bin/lib/rules-pack-checks.sh`) no longer fails a
  new stamp fragment only because its stamp is older than the base's newest.
  It fails a new stamp fragment when the fragment uses a table or view that a
  fragment of the same worker sorting AFTER it creates. That is the real order
  bug: the composed `schema.sql` would run the use before the CREATE.
- A use is the name after FROM, JOIN, ON, INTO, UPDATE, TABLE, REFERENCES or
  EXISTS, case-insensitive, with `--` comments and quote marks removed. A name
  the fragment creates itself is not a use. The later fragments are the judged
  tree's plus the base's, so a PR branch behind main is still judged against
  main's newer fragments.
- Two finding lines:
  - `... uses table <t>, which <L> at the base creates and which sorts after
    this fragment; take a stamp later than <stamp> (bin/prepush-gate.sh --restamp)`.
    `bin/prepush-gate.sh` prints the `git mv` lines for it, `--restamp` fixes
    it, and the lead review (`sr_stamp_order_line`) reads it as a NOTE because
    the merge conductor restamps before it queues the PR (BH-6842).
  - `... uses table <t>, which <L> in this diff creates and which sorts after
    this fragment; give <L> an earlier stamp than this fragment`. A rename
    cannot fix it, so it stays a BLOCK.
- The CI step `fast always-lints (BH-3860)` prints each line of the rules
  pack's `findings.txt` (max 20) as `::error title=rules-pack::<line>`, so the
  check summary shows the finding and not only "exit code 1".

## Why

Each schema PR that merged made every other open schema PR red. On 2026-10-16/17
#6861, #7155 and #7034 were restamped by hand 3 times each. No SQL order was
wrong in any of them.

## What did not change

The merge conductor's pre-queue restamp (`bin/lib/mc-prequeue.d/restamp.sh`,
`MC_SCHEMA_RESTAMP`, default 1) and the builder's `--restamp` (BH-7187) still
rename a stale fragment. The lead carry (`restamp_same`) still carries the
verdict across that commit.

## Post-deploy check

The ticket wants zero hand restamps in 24 h. Count restamp commits that are
not the harness's own `restamp schema fragments (no SQL change)` commit:

```bash
git log origin/main --since='24 hours ago' --format='%H %s' --no-merges \
  | grep -iE 'restamp' | grep -vF 'restamp schema fragments (no SQL change)' | wc -l
```

Run it for the 24 h before the deploy and the 24 h after it. Main's history
holds the PR branches' commits through the merge commits.
