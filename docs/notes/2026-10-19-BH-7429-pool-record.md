# The pool machine pushes its build record (BH-7429, BH-6896 S2)

Doc: DB-COORDINATION-SPEC, FLY-POOL

## What changed

Before this change, the hub reap in `bin/fly-pool.sh` read each finished pool
machine over `ssh console`: one RESULT read, the newest-dir listing, 27
build-dir files, the failovers.log tail and the full RESULT. Each file was
one Fly call. A machine that had already autostopped answered none of them.

Now the machine posts its build record to the jobs worker, and the reap
reads it there first.

- `fly/builder-runner.sh` `pool_record_write` runs from `run_job`, right
  after the pool-result row (BH-2643). It posts ONE record:
  - the full RESULT;
  - every `POOL_RECORD_FILES` file in the build dir (the RESULT's
    `BUILD_DIR:` line, else the newest dir);
  - the last 65536 bytes of failovers.log.
- `POST /api/pool/records` (`worker/jobs/src/routes/pool-records.js`)
  stores the record in ONE D1 batch: one `pool_record_files` row per file.
- The reap calls `pool_record_get` (`bin/lib/pool-record.sh`) before any
  ssh. If the answer is this machine's record from this run, the reap writes
  `builds/pool-<p>-<KEY>-<ts>/` from it and makes no ssh call for that
  machine. Then it stamps the record (`POST /api/pool/records/reaped`).
- A machine with no usable record takes the ssh path as before. The ssh loop
  now reads its file list from `POOL_RECORD_FILES`, so both sides use the
  same 27 names.

## The contract

- A record is the rows that share (project, ticket_key, machine, build_dir).
  The worker stamps `posted_at` and `reaped_at` with its own clock.
- POST validation: project, key and machine must match `laneName`. The
  build_dir and the file names must start with a letter or digit and hold
  no `/`. A RESULT with a body is required. The limit is 40 files, and a
  body may have at most 1,900,000 base64 chars.
- If a field fails validation, the answer is 400 and nothing is written.
- Every statement in the batch is guarded by "no row of this record is
  reaped". So a re-post before the reap REPLACES the record, and a file the
  new post leaves out is removed. A re-post after the reap is 409
  `already_reaped` and nothing changes.
- The machine skips a file over `POOL_RECORD_FILE_MAX_BYTES` (1,400,000; D1
  caps a row at 2 MB) and posts `{name, skipped:true, bytes}` instead. It
  leaves out an absent or empty file, the same as the ssh pull did
  (`[ -s ]`). A machine with no build dir posts `build_dir: "none"`, with
  RESULT and the failovers tail only.
- The reader uses a record only if ALL of these are true:
  - the knob is 1 and the key is not `RB-*`;
  - `record.machine` is the reaped machine;
  - the record was posted at or after `spawned_at` less
    `POOL_RESULT_ROW_SKEW_S` (60 s; the worker filters on `since`);
  - the record is not reaped yet (the worker filters on `reaped_at IS NULL`).
    The skew window alone does not separate two jobs of one key on a reused
    machine: the handoff sets the new `spawned_at` less than 60 s after the
    previous job posted its record;
  - RESULT line 1 passes `bin/result-prefix-ok.sh`.
  The reader writes only RESULT, failovers.log and the `POOL_RECORD_FILES`
  names. It drops any other name.
- A skipped file is fetched over ssh if the machine is `started`. If the
  machine is stopped, the file stays absent and the `say` line names it:
  `record for <KEY> taken from the jobs API (<n> files, <m> skipped; not on the hub: <names>)`.
  The counts are of the files in the hub build dir.
- Misses:
  - rc 2 (none, another machine's, an earlier run, a noise RESULT): the ssh
    path. When that machine then has a result, the reap writes one line,
    `no build record for <KEY> from <MID> — its files are pulled over ssh`.
    A machine that is still building writes no line, so a busy pool does
    not write one line per tick per machine.
  - rc 1 (worker unreachable, an answer that does not parse or decode): one
    `build record for <KEY> unreadable` line, then the ssh path.
  - Neither one changes the death, deferral or spawn-cap counts.
- A failed stamp is one line. The unread retention rule deletes those rows.

## Rollout

The lane knob is `POOL_RECORD_READ`
(`catalog/lanes.d/fly-pool.knobs.d/POOL_RECORD_READ.json`): int 0..1,
default 0. The schema fragment seeds `lane.fly-pool.project-6-os.pool_record_read = 1`,
so project-6-os goes first. Every other project stays on the ssh path until
an operator sets its row.

The machine reads the same rows itself: the project row, else the lane-wide
row, else 0. A drift between the two reads is safe:

- hub on and machine off: the ssh path;
- hub off and machine on: the unread retention rule deletes the rows.

## Retention

The table is `pool_record_files`
(`worker/jobs/schema.d/202610200226-bh-7429-pool-record.sql`). The fragment
header names the index for each query. Two rules run in the hourly
d1-retention lane:

- `pool_record_files.reaped` deletes a row 1 day after the reap read it
  (`retention.pool_record_files.reaped_days`);
- `pool_record_files.unread` deletes a row nobody read 3 days after it was
  posted (`retention.pool_record_files.unread_days`).

`retention.dry_run` applies. The rows are a transport copy (the hub build dir
is the record), with no money and no history, so they are deleted, not
archived.

## Metric, before and after (scratch copy)

Command: `HARNESS_TEST_SANDBOX=1 BH7429_MEASURE=1 bash tests/fly-pool-reap-record.bh-7429-test.sh`.
It runs 5 two-machine ticks of the real `bin/fly-pool.sh` per path, and
reports medians. A Fly call per machine is every Fly call except the tick's
agent start and listing, divided by 2. The destroy is included.

| path | Fly calls per machine | tick CPU s per machine | margin over an empty tick |
|---|---|---|---|
| ssh (knob 0) | 32.0 | 1.434 | 1.055 |
| record (knob 1) | 1.0 | 0.946 | 0.567 |

The empty tick was 0.758 CPU s. The record arm alone (`pool_record_get` +
`pool_record_install`, 10 runs) was 0.077 CPU s per machine. Three earlier runs
of the same command on this box gave a record margin of 0.61 to 0.72 s, and
one earlier arm run gave 0.079 s.

The Fly-call target (at most 2 per machine) is met. The whole-reap CPU target
(at most 0.15 CPU s per machine) is NOT met on this copy. The arm this change
replaced now costs 0.077 s. The rest of the 0.567 s is reap work that both
paths share and this change does not touch: the cost row, the relay attempt,
the close-out. On this copy the fly stub is a bash script, not flyctl, so the
ssh numbers are a low bound for production.

## Not changed

These parts are unchanged: the pool-result row (BH-2643), the `fly_result`
artifact (BH-2625), the rebase reap, the relay, `next_job_or_destroy` and
`spawn_one`. A record miss falls through to the BH-2643 row path.
