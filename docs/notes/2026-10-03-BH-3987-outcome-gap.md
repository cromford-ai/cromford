# The outcome gap in the daily digest (BH-4017, BH-3987.3)

Doc: ALERTS-STATE-MACHINE

## What changed

The daily digest has an `Outcome gap` block right after `Spend`. It names, per
project, the tickets we paid to build and never merged. Three pieces:

- `GET /api/metrics/outcome-gap` on the jobs worker
  (`worker/jobs/src/routes/outcome-gap.js`, the params, SQL and fold in
  `worker/jobs/src/lib/outcome-gap.js`). Bearer auth like every
  `/api/metrics/*`, read-only, and any bad param is a 400, never clamped.
- `bin/daily-digest.sh` reads it after the main digest validates and merges the
  answer into `state/daily-digest/<D>.json` as `.outcome_gap`.
- `bin/lib/daily-digest-render.sh` prints the block only when `.outcome_gap` is
  there.

Driven by `worker/jobs/test/outcome-gap.bh-3987.test.js` (the route over the
real `schema.sql`) and `tests/daily-digest-outcome-gap.bh-3987-test.sh` (the
shipped lane and the real renderer).

## The gap definition

A (project, ticket) is in the gap when all three hold, as of `to` (the end of
the digest day, `day + 1` at 00:00Z):

- its priced `cost_rows` in the build stages with `ts` in
  `[to - lookback, to)` sum to more than `min_usd`. Unpriced rows
  (`cost_usd IS NULL`) are not summed, so a ticket with only unpriced calls is
  never listed as $0. The answer's top-level `unpriced_calls` counts every
  unpriced build-stage call in the window, and each listed ticket carries its
  own;
- its first priced build-stage row is older than `to - days` (a full grace
  window to merge);
- no merged harness PR as of `to`: no `ledgers kind='merge' status='merged'`
  row created before `to` whose key is a `job_artifacts artifact_kind='pr_url'`
  of a `jobs` row with the same project and `ticket_id`. That is the join
  `readThroughput` uses in `worker/jobs/src/lib/daily-digest/core-sections.js`.
  A `closed` merge row is not merged. Rows with a NULL project or ticket are
  left out.

The four inputs are lane knobs in `catalog/lanes.d/daily-digest.json`, set as
hub settings rows: `DAILY_DIGEST_GAP_MIN_USD` (5), `DAILY_DIGEST_GAP_DAYS` (7),
`DAILY_DIGEST_GAP_LOOKBACK_DAYS` (30, must be greater than days) and
`DAILY_DIGEST_GAP_STAGES` (`plan,preplan,preplan-files,execute,review,fix`).
Out of range is one warn line in `logs/daily-digest.notes.log` and the
default. The route hard-codes only validation ranges and its 5000-group read
cap; past the cap the answer says `truncated:true` and the digest prints
`(cut at the source)`.

## What usually lies

- **A PR hand-merged in the GitHub UI.** Merge-sweep and the conductor never
  saw it, so there is no `ledgers merge` row and the ticket shows as a gap
  though the work landed. `bin/pr-attribution.sh` (BH-3987's attribution
  slice) settles which ticket a merged PR belongs to.
- **Cost rows whose ticket has no `jobs` row.** The merge join goes through
  `jobs`, so spend booked under a ticket key no job ever carried can never
  link to a merge and always shows as a gap. The same goes for a project
  whose `cost_rows.ticket` and `jobs.ticket_id` hold the key in different
  forms.

## Failure and absence

- The route answers 404 when the worker has not been deployed with it yet. The
  lane then leaves `.outcome_gap` out and writes one line in
  `logs/daily-digest.notes.log`; the digest is otherwise unchanged.
- Any other failure (a 5xx, a transport error, a body that is not the answer)
  is `{ok:false, error:"read failed (http=<status|none>)"}` and prints
  `Outcome gap: n/a (read failed: ...)`. The digest still sends, and there is
  no ALERTS line.
- A gap with tickets in it makes an otherwise quiet day not empty: the summary
  line says `empty=0` and the state json `.empty` is `false`.
