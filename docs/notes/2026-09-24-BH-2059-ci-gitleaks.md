# CI runs the share mirror's gitleaks gate instead of skipping it

Doc: CI-RUNNERS

## What changed

- **The shard job installs gitleaks 8.30.1** (`install gitleaks (pinned,
  checksum-verified)` in `.github/workflows/harness-ci.yml`, before the corpus
  step). It is guarded by `bin/ci-tool-present.sh gitleaks 8.30.1`, so an image
  that already has it downloads nothing. The download is checked with
  `sha256sum -c` against a pinned sha256 literal before it is unpacked, and the
  step ends with the same `ci-tool-present.sh` call unguarded, so a runner that
  still lacks 8.30.1 is red there.
- **The corpus step exports `GITLEAKS_REQUIRED=1`**, beside the other
  `_REQUIRED` switches.
- **`tests/share-publish-clean.bh-795-test.sh` fails fast** when
  `GITLEAKS_REQUIRED` is set and gitleaks is not on PATH (`FAIL: gitleaks-gate:
  GITLEAKS_REQUIRED is set …`, exit 1, before any sanitize work). Without the
  switch a laptop still gets the `SKIP gitleaks-gate` line.
- **The gitleaks tarball checksum is in `KNOWN_PUBLIC_CHECKSUMS`**, in both
  `bin/share/mapping.py` and the mirror's shipped guard
  (`bin/share/overlay/tests/no-client-identifiers-test.sh`). Leakcheck's
  `64-hex token` rule reads a sha256 as a secret. Without these entries the
  workflow's own pin would have refused the next publish.
- `tests/share-gitleaks-required.bh-2059-test.sh` pins all of it.

## Why

No CI step installed gitleaks, so share-publish-clean's gitleaks arm skipped on
every PR. A credential-shaped literal that leakcheck lets through but gitleaks
flags (#2032's fixture tokens, as `generic-api-key`) passed CI green and would
only have failed at the next publish. The share mirror had already frozen that
way on 09-13, 09-15 and 09-24.

## Rules this touches

- The gitleaks version in `harness-ci.yml` (`V=` and both `ci-tool-present.sh
  gitleaks <V>` calls) must equal `publish-share.yml`'s `V=`. Different releases
  ship different rule sets and flag different fixtures. Bumping one without the
  other is red in `tests/share-gitleaks-required.bh-2059-test.sh`.
- A version bump also moves the sha256: re-hash the release asset, check it
  against that release's `checksums.txt`, and update the literal in the workflow
  and both `KNOWN_PUBLIC_CHECKSUMS` lists together.
- Not changed: the pool's pre-PR gate (`bin/test-impact-gate.sh`) does not set
  `GITLEAKS_REQUIRED`, so it still skips that arm when its image has no gitleaks.
  `publish-share.yml` still installs without a checksum check.
