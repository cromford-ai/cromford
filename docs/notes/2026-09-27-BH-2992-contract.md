# config_changes: three new kinds and delete rows (BH-2994, BH-2992.0)

Doc: DB-COORDINATION-SPEC

## What changed

`worker/jobs/src/lib/config-changes.js`, the builder for the `config_changes`
audit INSERT, gained two things. The siblings of #2992 import both.

- **Three new `CONFIG_KINDS`:** `COST_CAP` (`'cost_cap'`), `TELEGRAM_TOPIC`
  (`'telegram_topic'`) and `REGISTRY_SEED` (`'registry_seed'`). The object is
  still frozen, the old four are unchanged, and `kind` still only comes from
  code, never from a request.
- **Delete rows:** `configChangeStmts(env, kind, name, was, after = null, ...)`
  treats a null or undefined `after` as a delete. It returns one INSERT with
  `before_json` holding the picked `was` fields and `after_json` holding the
  JSON text `'null'`. `after_json` is `NOT NULL` in `schema.sql` and in the
  worker's own create in `core.js`, so the delete marker is the text `null`,
  not SQL NULL. `JSON.parse` on it returns `null`.
- If `was` and `after` are both absent it returns `[]` (nothing existed and
  nothing was written). The unchanged-write check (`[]` when every audited
  field is equal under `String()`) now only runs when both are present.

## What did not change

- No schema change.
- No route change. The four callers (`routes/contracts.js`,
  `routes/retry-policies.js`, `routes/rules.js` PUT, `routes/review-gate.js`)
  always pass a non-null `after`, so they write the same rows as before. No
  caller reaches the delete branch yet. The #2992 siblings are its consumers.

## Tests

- `worker/jobs/test/config-changes-lib.bh-2992.test.js` (new) covers the kinds,
  the delete (null and undefined `after`), both-absent, create, unchanged and
  changed cases, plus a delete row written through the real `config_changes`
  table (`ensureTable` and node:sqlite).
- `worker/jobs/test/config-changes.bh-2513.test.js` K1 and
  `tests/controls-contract.bh-2513-test.sh` "K all" pinned the kind set as
  exactly four kinds. They now pin the seven.
