# Builds, fix rounds and the lead review run CI's lint job locally (BH-6897)

Doc: CI-RUNNERS, OPERATING

## What happened

On 2026-10-15, four of about 15 approved PRs went red on a CI lint step after approval. The steps were
the state-paths guard (#6858), fixture-hygiene (#6862), race-sigpipe-echo (#6867), and a shellcheck or
render check. The build ran the rules pack and a few fast lints. It did not run the steps of CI's lint
job. A blocked-resolver fix round ran npm typecheck, unit and the scratch-closure lint only.

## What changed

- `bin/ci-local.sh` runs the steps of the jobs "Syntax + shellcheck + config integrity" and "Test
  determinism lint", then `bin/rules-pack.sh`. `bin/ci-local-plan.py` reads the step list from
  `.github/workflows/harness-ci.yml`. A step added to the job runs with no edit to either file.
- A step that runs `bin/rules-pack.sh` itself and ends PASS or RED makes ci-local's own pack run SKIP,
  so the pack does not run twice. When that step ends PREEXISTING, NOTE or COULD-NOT-RUN, the pack runs.
- Each step runs as a `pull_request` run against `--base`, on a fresh detached worktree of the
  committed HEAD, as CI's checkout is. Uncommitted edits and git-ignored renders in the tree do not
  change a step's answer. Each step gets the env CI gives it. The caller's `HARNESS` and `GH_TOKEN` do not
  reach a step: `${{ github.token }}` is empty unless `CI_LOCAL_GH_TOKEN` is set, because the steps are
  the PR's own code. A step that is red is run again on a worktree of the merge-base.
  Green there: RED. Red there too: PREEXISTING, which does not count. The base run cannot start or
  times out: COULD-NOT-RUN, which never blocks. A step that changes a tracked file is RED.
- The build's pre-PR gate (`bin/lib/prepr-gate.sh`) runs it on the first pass and on the late pass.
  Each red step is an in-diff `CI-LOCAL <job> / <step>: ...` finding. It shares the one fix turn.
  Still red after the turn: `rules_pack_block` ends the build `REVIEW_BLOCKED rules-pack`, exit 6,
  and no PR opens. `prepr.txt` records `cilocal=<state>`. `pipeline.log` gets one
  `PREPR <label>ci-local=<state> red=<n>` line.
- `bin/blocked-resolver.sh` fix rounds run the worktree's own `bin/ci-local.sh` before the push, with
  the rules pack. `CI_LOCAL_EXIT: 1` in `fix-verify.txt` means the round is not pushed. The next
  round's brief carries the findings.
- `bin/lead-review.sh` runs the box's copy on the reviewed head, unless CI's lint job is green on that
  sha. Red is a BLOCK with no agent call (reviewer model `ci-local`). The report header has a
  `- ci-local: <state>` line, and the prompt has a `## CI local` section.

## The steps it does not run

`catalog/ci-local-skip.d/bh-6897.tsv`, one row each, with the reason:

- `CI_RUNNER names a known fleet`: it checks a repo variable, not code.
- `merge-from-main push — what can reuse the last green`: it reads the GitHub event and the previous
  run.
- `triage-gate decides RUN/SKIP shapes correctly` and `merge-sweep refuses without record evidence`:
  they write fixed `/tmp` paths, so two runs on one box would collide.
- `fast always-lints (BH-3860)`: it runs the rules pack and then the fast always-suites. ci-local runs
  the pack itself, with no `--skip determinism`. The builder gate (`bin/test-impact-gate.sh`) runs the
  always-suites. A box has no CI durations (the `gh` read answers 401 and `JOBS_URL` is not set), so
  the durations step falls back to the stale seed. Then every always-suite added after the seed is
  unmeasured and joins the fast set. On a pool builder on 2026-10-15 this one step ran 551 s, and the
  whole run passed the 900 s budget. A blocked-resolver fix round does not run the always-suites.

`uses:` steps (checkout, the ShellCheck cache) never run. A step whose `if:` is false for a
`pull_request` is skipped.

## Knobs

`catalog/lanes.d/_lib.ci-local.json`, read through `lane_knob ci-local <ENV>` (libs scope):

- `CI_LOCAL_GATE` (default 1). 0 turns off all three callers. Each records `off`.
- `CI_LOCAL_BUDGET_S` (default 900, 60..3600). Seconds for one whole run. A step past it is
  COULD-NOT-RUN.

## Run it by hand

```bash
bin/ci-local.sh --tree . --base origin/main          # rc 0 clean, 1 red, 2 could not run
bin/ci-local.sh --list                                # which steps run and which skip
bin/ci-local.sh --step 'tests/ sourcing lint' --skip-rules-pack
```

## Limits

- The ShellCheck step needs the pinned binary on PATH or a network to fetch it. Without either, it is
  rc 2 on the head and on the base. A step with rc 2 or more on both sides is COULD-NOT-RUN, not
  PREEXISTING, so the run is `could-not-run` and never `clean`.
- `GUARDRAIL_JUSTIFICATION` comes from `$CI_LOCAL_PR_BODY` only. No caller sets it yet.
- The rules pack re-runs a red `tree` component on the fork. When the fork itself is red on that
  component, the new lines read as pre-existing too.
