BH-10236: a todo ticket whose own PR merged leaves todo; a ticket's PR is found by its key

Doc: MERGED-ADVANCE

Refs #10236 (the ticket row "ticket todo whose key has a merged PR"). The PR rows are in PR #10263 and the ready-ticket row is in PR #10268.

## The stall

project-3, 2026-11-26: TK-837, TK-834 and TK-852 showed `todo` while their work had been on main since 2026-11-24 (#1411, #1414, #1371). The fleet then has no true list of what is left, and a ready `todo` ticket whose work is merged can be built a second time.

Two causes in `bin/merged-ticket-advance.sh`:

1. It read only `in_progress` and `review` tickets.
2. For a ticket with no build dir on the box, it found the PR only in the ticket thread. The lane line of that day: `no-local-build=13 no-pr-in-thread=8`. No fleet box built those 3 PRs, and no thread named them.

Each of those PR titles starts with its ticket key: `TK-837: member Settings ...`.

## What changed

1. `bin/lib/merged-advance-key-pr.sh` (pure): `mka_key_prs` and `mka_key_pick`.
   - A merged PR whose title starts with `<KEY>`, then `:` or ` (`, is a PR of that ticket.
   - A title that says slice or part (`(slice A)`, `slice 2 of 3`, `part 2`) is one slice. It never stands for the whole ticket.
   - The key is matched whole (TK-83 is not TK-837) and without case.
   - The key PR of a ticket is its newest merged PR that is not a slice.
2. `bin/merged-ticket-advance.sh` reads the repo's closed PR list one time a run: `MERGED_ADVANCE_KEY_PR_PAGES` (3) pages of 100, newest update first.
3. A `todo` ticket with a key PR is a candidate and takes the peer path with that PR. The merge fact, the deploy fact, the client-spoke hold, the slice-plan hold, the markers and the retries are the peer path's own.
   - Client-filed: comment, move to `review`, the turn to the client.
   - System-filed: comment, move to `done`.
   - A staging project whose production does not serve the merge: the staging comment ("on staging ... not live on production yet") and a move to `in_progress`. No turn. The app's own audit moves the ticket at the release, as it does for each `in_progress` ticket.
   - A PR address in a `todo` ticket's thread is not used. It can be a reference ("blocked by ...").
4. A `todo` ticket with no key PR is not a candidate. It costs no request and no count against `MERGED_ADVANCE_MAX`.
5. An `in_progress` or `review` ticket with no PR address in its thread takes its key PR.
6. One lane line for each todo ticket that is advanced: `MERGED_ADVANCE_TODO <KEY> was todo; its PR #<n> is merged`.

## Limits

- A PR whose title starts with the key and does not say slice or part, but does only a part of the ticket, moves the ticket. A person who moves it back wins: the lane holds it as `moved-back` and does not move it again.
- A PR that is not in the newest 300 closed PRs has no row. Its ticket is handled as before.
- A PR whose title does not start with the key (for example `Page registry: ...`) is not found.
- The ticket text asks for `review` on staging. This change moves a staging todo ticket to `in_progress`, because the release model of BH-9876 leaves the move to `review` to the app's audit at the release.

## Knobs

- `MERGED_ADVANCE_KEY_PR` (1, 0 = off: no list read, the lane as before).
- `MERGED_ADVANCE_KEY_PR_PAGES` (3).

## How to see it on a live box

`grep MERGED_ADVANCE_TODO logs/<project>.log`, and `bin/merged-ticket-advance.sh <project> --dry-run` prints each comment and move it would post.
