# A red production deploy emails the project owner (BH-8894, slice C0)

Doc: OPERATOR-SETUP

## Why

#8781 item 2 asks that the first deploy failure after a merge reach a person
in-app AND by email to the project owner, and that a repeat failure within
24 h does not alert again. BH-8781 C0 shipped the page (console plus
Telegram through `page_critical`). The fleet had no mail client, so no email
went out.

## What changed

- New seam `bin/lib/vendor/resend.sh`: `resend_send <key_var_name> <from> <to>
  <subject> <text>` POSTs one plain-text email to `https://api.resend.com/emails`.
  The key is passed by variable name. curl reads the url, the headers and the
  body from stdin (`-K -`), so the key is in no argv and no log. In fake mode
  (`HARNESS_VENDOR_FAKE=1`) it answers `tests/fixtures/vendor-fake/resend.json`
  and makes no call.
- New helper `bin/lib/owner-mail.sh`: `owner_mail <ttl> <key> <project>
  <subject> <text>` always returns 0 and prints one word: `bad-args`,
  `not-configured`, `suppressed`, `sent` or `failed`.
  - It stamps `state/owner-mail.json["<key>"] = {at, status:"sending", to}`
    under a flock BEFORE it sends. A crash loses a repeat, never sends twice.
  - `sent` only when Resend answers a non-empty string `.id`. Anything else is
    `failed`: the row records `why` (the key cut), and one warn
    `bin/alert-line.sh` line with id `owner-mail-<key>` names it.
  - A row stamped less than `<ttl>` seconds ago (any status) is `suppressed`.
- `bin/vercel-deploy-snapshot.sh`: on the transition to red, AFTER the
  `page_critical` call, the lane calls `owner_mail "$PROD_RED_REPAGE_S"
  "prodred:<p>"` in a subshell per project. The subshell first runs
  `lib_env_apply owner-mail <p>`, so one project's row never reaches the next.
  The lane writes `<stamp> owner-mail <p> <status>` to
  `logs/vercel-snapshot.log` before the summary line. The summary line is
  unchanged and stays last.

## Knobs

| settings row | env | default | meaning |
|---|---|---|---|
| `lib.owner-mail[.<project>].owner_mail_from` | `OWNER_MAIL_FROM` | "" | sender; empty = no email |
| `lib.owner-mail[.<project>].owner_mail_to` | `OWNER_MAIL_TO` | "" | owner; empty = `HARNESS_GIT_EMAIL` |
| `lib.owner-mail.owner_mail_err_chars` | `OWNER_MAIL_ERR_CHARS` | 200 | length of the recorded `why` |
| `lib.owner-mail.owner_mail_lock_wait_s` | `OWNER_MAIL_LOCK_WAIT_S` | 10 | flock wait on the state file |
| `lib.vendor-resend.resend_api_timeout_s` | `RESEND_API_TIMEOUT_S` | 20 | curl `--max-time` (1..120) |
| `lane.vercel-deploy-snapshot.prod_red_repage_s` | `PROD_RED_REPAGE_S` | 86400 | the email TTL (same as the page) |

`RESEND_API_KEY` is a secret. It is read from the env, else from the last
assignment in the hub's `global.env`. It is never a settings row.

## Operator steps (the email is off until these are done)

1. Verify a sender domain in the Resend account.
2. Put `RESEND_API_KEY=<key>` in the hub's `global.env`.
3. Set the settings row `lib.owner-mail.owner_mail_from` to an address on the
   verified domain.
4. Optional: set `lib.owner-mail.<project>.owner_mail_to` for a project whose
   owner is not `HARNESS_GIT_EMAIL`.
5. Optional: add the GitHub secret `RESEND_API_KEY` and one
   `RESEND_API_KEY: ${{ secrets.RESEND_API_KEY }}` env line in
   `.github/workflows/vendor-contract.yml`. Until then the contract suite
   `tests/contract/resend.bh-8894.contract-test.sh` prints
   `SKIP vendor: RESEND_API_KEY is not set`.

`grep '\[owner-mail\]' /root/harness/logs/ALERTS.log`.
