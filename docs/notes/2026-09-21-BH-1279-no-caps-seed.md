# BH-1279: the schema seed no longer resurrects deleted repo/box caps, and a refused spawn no longer counts against the per-key spawn cap

**What happened, twice.** On 2026-09-14 the operator ordered the fleet uncapped ("all
projects unlimited parallel — build, conductor, review, merge — no caps") and
PR #343 DELETED the `concurrency_rules` rows `repo/*/build`, `repo/project-5/build`
and `box/*/build` from the live jobs D1. Only `ticket/*/*` = 1 (the TK-66/67
double-build guard) was meant to remain; `bin/concurrency-plan.sh` read
`unlimited` for all 9 projects.

BH-1000 (2026-09-20) started re-applying `worker/jobs/schema.sql` on every
deploy, statement by statement, before `wrangler deploy`. That file still
carried:

```sql
INSERT OR IGNORE INTO concurrency_rules (...) VALUES
  ('ticket','*','*',1, ...),
  ('repo',  '*','build',1, ...),
  ('box',   '*','build',1, ...);
```

`INSERT OR IGNORE` is exactly the right verb for protecting a RAISED row — a
re-applied schema must never reset a cap an operator hand-edited — and exactly
the wrong one for a DELETED row: it cannot see the difference between "this
row never existed" and "this row existed and was removed on purpose", so a
redeploy silently re-created both rows every time.

- **2026-09-20**, the first deploy after BH-1000 landed, restored
  `repo/*/build = 1` and `box/*/build = 1`. `docs/BUILD-CONCURRENCY.md`'s "Why
  it needed a document" section had predicted this exact shape from the other
  direction (a raised row surviving a re-apply); this is the mirror failure,
  a deleted row NOT surviving one.
- **2026-09-21 ~20:40Z**, the merge train for PR #1282 (BH-1104, touching
  `worker/jobs`) redeployed the jobs worker and the schema re-apply re-seeded
  both rows again. From 20:40Z to ~22:00Z every pool-routed project (the
  `repo/*/build` rule binds fleet-wide on the pool route —
  `docs/BUILD-CONCURRENCY.md` "Routing decides which caps apply at all") built
  ONE ticket at a time. project-5 sat at queue depth 5 with one executing
  build all afternoon while 13 `ai-build` tickets waited, and nobody was
  told — the ceiling was rediscovered by reading `fleet_status.rules`.

**The fix.** `worker/jobs/schema.sql`'s seed no longer carries a `repo` or
`box` row at all — only `ticket/*/*` = 1. "No row = unlimited" (the
`checkRules` fail-open default, `worker/jobs/src/lib/core.js`) is already
exactly what the 9/14 order asked for, so the correct seed for that state is
no seed: a cap is set the same way it is raised or lowered,
`bin/jobs-client.sh rule-set`, never this file. A re-applied schema can now
never resurrect a row an operator deleted, because it never writes one in the
first place. Pinned by
`worker/jobs/test/concurrency-rules-seed.bh-1279.test.js`.

**Second bug, same ticket: a refused spawn was counting against
`POOL_SPAWN_CAP_PER_KEY`.** `spawn_one` records every entry against the
per-key spawn cap unconditionally, regardless of outcome (BH-1075's own
rule — a cap that only counted the attempts that worked could not bound a
loop of attempts that did not). That rule is right for a build that actually
ran and wrong for a claim the DB REFUSED before `run-build.sh` did anything
else: `job_open`'s rc=9 path (`bin/lib/jobs/jobs.sh`) writes
`RESULT "BUILD_DEFERRED REFUSED <scope> :: <reason>"` for a phase-6
concurrency rule, a pause flag, or a stale retry — none of which ever started
work. With the fleet-wide `repo/*/build` rule back (the first bug, above)
every claim on the pool route was refused, so every spawn still counted, and
17 keys hit `POOL_SPAWN_CAP_PER_KEY` and were parked with `.defer-to-human`
twice on 2026-09-21 alone: one fleet-wide rule refusing every claim converted
into per-key human paging within two ticks.

**The fix.** `pool_spawn_cap_record` now returns the exact epoch line it
appended to a key's `.spawns` log, and that value rides onto the machine json
as `spawn_cap_ts` — from `spawn_one` itself, and from the machine-reuse
handoff in `next_job_or_destroy`, which records against the cap on the same
rule (BH-1075 review round 2) and needed the same fix. The REAP loop reads
`spawn_cap_ts` back off the machine json, and when the reaped RESULT matches
`BUILD_DEFERRED REFUSED *` (and only that shape — a busy slot, this key
already building, a file overlap, or a push rejected downstream all mean the
machine genuinely ran, so those still count), a new
`pool_spawn_cap_unrecord <key> <ts>` removes exactly that one timestamp — the
last matching line, in case two spawns land in the same second — from the
`.spawns` log. Every other deferral-handling behaviour (the deferral counter,
the requeue, the ALERTS line, the DEFER_MAX park) is unchanged. Pinned by
`tests/fly-pool-refused-not-counted.bh-1279-test.sh`.

**Ops applied on the hub 2026-09-21 ~22:00Z, to be REMOVED once this ships:**

- `rule-unset repo "*" build` and `rule-unset box "*" build` (applied a
  second time; the first was on 2026-09-20).
- `pool_spawn_cap_per_key` raised to 12 (was 6, was 2) as a blunt mitigation
  so refusal storms would stop parking keys before this fix landed.
- **A hub crontab line tagged `# no-caps-selfheal`**, running every 10
  minutes: if `bin/jobs-client.sh rules` shows a `repo|box * build` row,
  unset both and append a `[no-caps-selfheal]` line to `logs/ALERTS.log`.
  This was a stopgap enforcing the 9/14 NO-CAPS order mechanically while the
  seed still resurrected rows. **Remove the `# no-caps-selfheal` crontab
  line on the hub once this change is deployed** — the seed can no longer
  produce the row it was watching for, so the line has nothing left to catch
  and is a false safety net past this point. `pool_spawn_cap_per_key` can be
  lowered back toward its documented default (2) once the fix has run for a
  few days without a parking incident — the fix removes the CAUSE of the
  refusal storms, so the raised cap is no longer load-bearing, but changing
  it is a separate, non-urgent operator decision.

**What it touches:** `worker/jobs/schema.sql` (seed), `bin/fly-pool.sh`
(`pool_spawn_cap_record` now prints its timestamp, new
`pool_spawn_cap_unrecord`, `spawn_one` and the reuse handoff carry
`spawn_cap_ts` onto the machine json, the REAP loop reads it back and
un-records on a `BUILD_DEFERRED REFUSED *` result). Tests:
`worker/jobs/test/concurrency-rules-seed.bh-1279.test.js`,
`tests/fly-pool-refused-not-counted.bh-1279-test.sh`.

**Follow-up named in the ticket, not done here:** `bin/concurrency-plan.sh` /
`fleet-status-push.sh` should alert when a pool project's effective ceiling
DROPS between two snapshots with no `rule-set` command in the ledger — a cap
appearing from nowhere is a config change nobody made, and that alert would
have caught both 2026-09-20 and 2026-09-21 the moment they happened instead
of by a human reading `fleet_status.rules`.

Doc: BUILD-CONCURRENCY

**Bounding after this change (review note).** A refusal storm is no longer bounded by the per-key spawn cap plus a human page; it is bounded by `DEFER_MAX` (6): the row is parked `failed` for the blocked-resolver after six refused boots. That is what the ticket asked for. Do not lower `pool_spawn_cap_per_key` back to 2 expecting it to bound refusals again — it only counts spawns that ran.
