# Talk to a staff agent (BH-6823, slice 2/4 of Staff in Mission Control)

Doc: DB-COORDINATION-SPEC, CONSOLE

## What changed

Each staff agent has one chat thread. You write a note in the console. The
agent reads it on its next `bin/staff.sh tick` and writes a reply to the same
thread. The reply names the tick that wrote it.

- Agent page: `/staff/<agent>` shows a CHAT section under the facts (the
  #6822 seam `console-ui/src/screens/staff/agent-chat.js`).
- `/chat`: one `STAFF <NAME>` tab per staff agent from the roster. The tab
  shows the same pane and a link to `/staff/<agent>`. Archie has no thread
  and no tab: Archie is not a `staff_agents` row and is never ticked.

## Why a new table and not `steer_notes`

The ticket said "reuse the steer-note table/route". `steer_notes` has CHECKs
on `mode` and `status` that do not allow a `held` state, and a D1 CHECK cannot
change without a DROP and rebuild. Schema changes are additive only. Mode
`ticket` also puts a note in the steer outbox, and the hub posts it to GitHub.
So the notes go in a new table, `staff_chat`
(`worker/jobs/schema.d/202610162003-bh-6823-staff-chat.sql`). The route shape
(send, take, settle, the `UPDATE ... RETURNING` claim, the lease, settings rows
with code fallbacks) and `STEER_TEXT_MAX` (4000) come from the steer route.

## States

An operator note has one of these states. A reply is a `role='agent'` row with
state `sent` and `reply_to` set to the note id (one reply per note: unique
index).

| state | meaning |
|---|---|
| pending | sent, not read yet |
| held | sent while the agent was stopped; read on the first tick after resume |
| taken | a tick claimed it (`tick_key` set); lease `staff.chat.take_lease_s` |
| read | the tick wrote a reply |
| unanswered | the model call worked but gave no reply for this note (terminal) |
| failed | taken `staff.chat.attempts_max` times with no answer (terminal, no more calls) |

"Stopped" at send time is an active `pause_flags` row named `staff-kill-all`,
`staff-kill-<agent>`, `staff-off-all` or `staff-off-<agent>`, or
`staff_agents.status <> 'active'`. The GET also answers a live `stopped` and
`stopped_by`, so a note sent before a kill shows "agent stopped" too.

## Routes (`worker/jobs/src/routes/staff-chat.js`)

- `POST /api/staff/chat` `{agent, text, actor}` → 201 `{message, stopped, stopped_by}`.
  The browser reaches it through the coord proxy, which stamps `actor`.
- `GET /api/staff/chat?agent=&before=&limit=` → `{agent, messages, next, stopped, stopped_by, as_of}`,
  newest first. `limit` 1..100 (default 50). A bad `limit` or `before` is 400.
  Each row has `tick_id` from `staff_ticks` when that tick row exists.
- `POST /api/staff/chat/take` `{agent, tick_key, limit}` (box only).
- `POST /api/staff/chat/settle` `{agent, tick_key, replies, unanswered, release}` (box only).
  Only notes `taken` by the same `tick_key` move.

`archie` and an unknown agent are 404.

## The tick

`bin/staff.sh tick <agent>`, in order:

1. Kill and off flags (a stopped agent takes nothing), then the soul check.
2. Take up to `STAFF_CHAT_MAX_NOTES` notes (knob, default 5, 1..20). A failed
   take is one log line; the findings tick goes on.
3. Collect and claim items as before. No collector with notes = empty items.
4. The prompt gets `## Messages` and `## Last ticks` before `## Items`. The
   notes ride in the same one `staff-tick` model call as the findings. A tick
   with no notes and no items still makes 0 calls.
5. On rc 0: each note with a reply is settled `read` (em and en dashes are
   folded to ", " first); each note with no reply is `unanswered`.
6. The EXIT trap releases notes that were taken and not settled, then posts
   the tick row (`chat_release; tick_record`). If the release cannot post, the
   take lease returns the notes.

The summary line in `logs/staff.log` ends with `notes=<n> replied=<n>`.
`replied` is the count the worker accepted, not the count the model wrote.

## Settings rows

- `staff.chat.attempts_max` 2
- `staff.chat.take_lease_s` 1200 (above the 600 s tick timeout)
- `retention.staff_chat.days` 365: rule `staff_chat.age` in the BH-6750
  retention job. It deletes only `read`, `unanswered` and `failed` notes and
  their replies. `pending`, `held` and `taken` notes are never deleted.
  `retention.dry_run` applies.
