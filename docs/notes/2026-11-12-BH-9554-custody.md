# BH-9554: ticket custody table and its one write path (slice C0)

Doc: CUSTODY, STATE-STORES, ARCHITECTURE

## What changed

- New jobs D1 tables `ticket_custody` (one row per `(project, ticket)`: state,
  owner lane, lease, next action, deadline, `due_at`, attempt, ladder rung,
  evidence, PR, `rev`, `settled_at`) and `custody_actions` (append-only: actor,
  action, why, result). Schema fragment `202611121607-bh-9554-custody.sql`,
  with one index per query.
- Settings rows: `custody.lease_s` (1800), `custody.lease_max_s` (86400),
  `custody.deadline.<state>_min` for the 8 open states, `custody.deadline_max_min`
  (43200), `custody.due.limit` (200), `retention.ticket_custody.settled_days`
  (7), `retention.custody_actions.days` (90).
- Routes `POST /api/custody/{claim,renew,release,next,settle,act}` and
  `GET /api/custody/{due,row,gaps}` (`worker/jobs/src/routes/custody.js`).
  Each write is one read, then one batch under a `rev` compare-and-set.
- Shell library `bin/lib/jobs/custody.sh` and the jobs client verb
  `custody <sub>`. rc 1 means the DB did not take the write. It writes one
  alert `custody-unreachable-<project>` and has no file fallback.
- Retention rules `ticket_custody.settled` (delete settled rows) and
  `custody_actions.age` (archive, then delete).

## What did not change

No lane calls the library yet (C2). No custodian lane exists yet (C1). The
owner checks still read artifacts (C3). The legacy file markers stay.
