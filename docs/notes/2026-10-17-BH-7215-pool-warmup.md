# Pool machines no longer exit before the hub pushes their job (BH-7215)

Doc: FLY-POOL

## Why

A new pool machine waited a fixed 600 s for `job.json` (`fly/builder-runner.sh`), then
exited 0 and autostopped. `spawn_one` in `bin/fly-pool.sh` ran `fly machine run` first and
did its slow setup after it. On project-6-os, machine `806d29f69d1038` (TK-840) started at
01:04:48Z. The hub's first push failed at 01:16:46Z. The machine exited at 01:16:49Z with
exit code 0. project-6-os had 37 push failures from 2026-10-16 (#7174).

## What changed

1. **The wait is a knob.** `fly/builder-runner.sh` reads `WARMUP_WAIT_S` (default 1800 s; an
   empty, non-digit or 0 value gives 1800). `spawn_one` passes `-e WARMUP_WAIT_S=<n>` on
   `fly machine run`. `<n>` comes from the fly-pool knob `WARMUP_WAIT_S`: settings row
   `lane.fly-pool.<project>.warmup_wait_s`, then `lane.fly-pool.warmup_wait_s`.
2. **Setup before launch.** These steps now run BEFORE `fly machine run`: `spec_repos_load`,
   the `pool gh credential swap` block (App token, read-only token), the account lease, the
   OpenRouter check, the label overlay copy and the harness tarball build. After the launch
   only the machine-bound steps run: the row stamp, the lease rebind, `sleep 20`, the tarball
   copy and the pushes. The pushes keep their order. The `gh-token-read` push moved out of
   the swap block to the start of the push phase.
3. **The lease moves to the machine id.** The lease is taken under a pre-launch id
   `pre-<key>-<epoch>-<pid>`. `pool_account_rebind` (`bin/lib/pool-account.sh`) moves the
   lease file and the shared row to the machine id after the launch. It claims the new id
   with cap 0, then releases the old id. If the claim fails, the old row stays and frees at
   its TTL. Every reap path still releases by machine id. A harness-sync failure now
   releases the lease too.
4. **No credential, no machine.** The no-credential exits of the swap block now run before
   the launch. They buy no machine and log `no machine spawned, job stays queued`.
5. **Measure and alert.** Every spawn that reaches the env push logs
   `<mid>: launch→first push <S>s (warmup wait <W>s)` and `<key>: setup before launch took <n>s`.
   When `S` is over `POOL_WARMUP_ALERT_PCT` (default 80, 0 = off) percent of `W`, one ALERTS
   line per project per UTC day (`flags/alerted-pool-warmup-<p>-<YYYYmmdd>`, swept after 2 days).

The swap and lease log lines now name the ticket key, not the machine id, because no
machine exists yet when they are written.

## Tests

`tests/fly-pool-warmup.bh-7215-test.sh` drives `bin/fly-pool.sh` with a fly stub on a virtual
clock. A 700 s setup against a machine that stops 600 s after start failed the push on the
old order and lands on the new one.

## Owed after merge

Not verified here (needs the hub log). On the hub, `grep 'launch→first push' logs/fly-pool.log`
must show project-6-os spawns well under the wait. There must be no `env/job push FAILED`
across the fleet in the 24 hours after the merge.

An old image whose tarball runner does not arrive in 120 s still uses the image's own
runner with 600 s. The next image bake carries the new runner.
