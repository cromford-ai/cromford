# Prod-behind-main page: one id per project, a reminder, a resolve (BH-8255)

Doc: ALERTS-STATE-MACHINE

## What changed

A new hook of the served-sha watch, `bin/lib/served-sha-watch.d/30-prodbehind.sh`
(`ssw_hook_prodbehind`). It pages ONE critical alert `prodbehind:<project>`
when Vercel production has served an older sha than main HEAD for
`SERVED_SHA_PRODBEHIND_MIN` minutes (default 45) AND the newest production
deployment of the project is `ERROR`. The page goes through
`bin/lane-alert.sh --critical`, with `ALERT_REMINDER_S` set to
`SERVED_SHA_PRODBEHIND_REPEAT_H` hours (default 4) for that one id. The next
`in-sync` verdict resolves it.

- The clock is `.prodbehind.since` in `state/served-sha-watch/<project>.json`.
  It is kept across head changes. The lane already deletes the file on
  `in-sync`, so nothing is stored per sha and nothing grows.
- Knobs: `catalog/lanes.d/served-sha-watch.knobs.d/SERVED_SHA_PRODBEHIND_MIN.json`
  and `SERVED_SHA_PRODBEHIND_REPEAT_H.json`.
- Cost: one extra Vercel GET per behind project per tick past the threshold,
  and one GitHub compare per paging tick.
- Map: `docs/verification-map/served-sha-prodbehind.md`.

## Why

project-3 production served an old build for 27 h. Main moved three times and
each production deployment failed. `10-alert.sh` pages one id per head sha
(`served-behind:<p>:<head12>`) and `deploy-verify` pages one id per sha
(`deployfail:<p>:<sha>`). Each page stood alone, none said how long prod had
been behind, and none escalated.

## "Queue merges never run deploy-verify": confirm or refute

Answered from the code on main 1ed7c322.

- PARTLY REFUTED. A merge that the merge conductor lands from a queue requests a
  deploy check. `mc_settle_merged` (`bin/lib/mc/settle.sh`) spawns the
  deploy-verify lane (`mc_dv_spawn`) or calls `bin/deploy-request.sh`.
- CONFIRMED for every other merger. A PR that Mergify or a person merges with no
  conductor record reaches `bin/deploy-request.sh` only through
  `bin/reconcile-prs.sh`. That path runs only for a harness build row, and only
  on the box whose `env/<project>.env` has `DEPLOY_HOOK_URL`. A hotfix PR such as
  project-3 #576 gets no deploy check.
- `bin/deploy-verify.sh` beats `deployfail:<project>:<sha>` with no severity.
  That is why the page stayed `[UNTRIAGED 45m]`.
- `bin/deploy-request.sh` sends a project with `VERSION_URL` to the deploy
  train, not to deploy-verify.
- The served-sha watch reads main HEAD, so it covers every merger. The new hook
  rides that lane, so it covers queue merges, Mergify merges and hand merges.
  `deploy-verify` and the conductor are not changed.
