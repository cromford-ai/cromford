BH-10236: a READY ticket on an in-app board is launched on the same triage pass, with no model call

Doc: TRIAGE-STATE

Refs #10236 (the ticket row "todo + ready + lock free + no build + no open PR"). The PR rows are in PR #10263. The stale board state row is not in this change.

## The stall

project-3, 2026-11-26, 10:00 to 14:45 UTC: about 25 tickets were `todo` + `triageVerdict=ready` + `waitingOn=team`, with free locks and no build, while the pool ran 1 build.

The triage log of that day shows the cause:

- `triage-state enforce: 163 open, 97 to the model ...`. A ready ticket whose inputs moved is in the model set.
- Each one waits for a model shard that answers `DECISION: <key> :: launch`. A shard takes 20 to 60 seconds, and the tick holds the run lock for up to 32 minutes (`previous run still active ... age=1911s`).
- 8 shards in a row ended `rc=1` on the codex runner between 11:28Z and 11:51Z. Each failed shard is a ready ticket that got no launch.
- The starvation rescue (BH-9113) launches such a ticket with no model call, but only after 3 passes and 2 hours.

## What changed

`tsv_ready_pass` in `bin/lib/triage-starve.sh`. `ts_tick` (`bin/lib/triage-state.sh`) calls it after `tsv_pass`, in enforce mode only.

1. The owed set: each key of the pass's model set whose board snapshot entry is not busy, has `triageVerdict` ready and `waitingOn` team.
2. The launch: `_tsv_inapp_try`, the guarded attempt of the starvation rescue. Its guards: the `.enqueued` marker, the build-key lock, a build dir, a queue row, an open PR, `triage-gate.sh --buildable-strict` (dependencies and holds), the overlap guard. Then `bin/run-build.sh`. Pool capacity stays with `run-build.sh`.
3. One launch per (ticket, input hash): the marker holds the hash.
4. The cap: `TRIAGE_READY_NOW_MAX` (3) launches per pass. A key past the cap is appended to `state/triage-state/<p>/deferred.keys`. `bin/triage-gate.sh` step 1d then answers `RUN ts-deferred`, so the next tick runs and the key does not wait for the 45-minute or 240-minute re-read.
5. A launched key joins the tick's skip set. No model shard is bought for it.
6. One lane line per pass with something owed: `READY-NOW owed <n>, launched <m>: <labels>; waited: <label>=<reason> ...`.

## Limits

- In-app boards only. A GitHub board keeps `bin/launch-fastpath.sh` and rule U13-STARVE.
- Enforce mode only (`lib.triage-state.triage_state_mode`).
- The pass runs when a tick runs. A tick that the gate skips before `ts_tick` launches nothing. The capped keys of item 4 are the one case this change carries to the next tick.
- The order is the decisions order of the pass. "User-facing flows first" (the ticket text) is not built: no field of the snapshot says which ticket is user-facing.
- A ticket that names a dependency only in its thread text, and not in the board's dependency field, is launched. The model shard read that text. `--buildable-strict` does not.

## Knobs

- `TRIAGE_READY_NOW` (1, 0 = off): settings row `lib.triage-starve[.<project>].triage_ready_now`.
- `TRIAGE_READY_NOW_MAX` (3): settings row `lib.triage-starve[.<project>].triage_ready_now_max`.
- `TRIAGE_STARVE_INAPP_LAUNCH=0` also stops it.

## How to see it on a live box

`grep READY-NOW logs/<project>.log`
