# Lead review precision: a daily score of lead MERGEs that went wrong (BH-3548, BH-3479.4)

Doc: MERGE-CONDUCTOR

`bin/lead-review-precision.sh` is a new hub lane (`cron/lanes/714-lead-review-precision.cron`, daily 05:40Z, behind `hub-lease.sh check`). It makes no model call and no SSH.

## What it scores

For each repo in `LEAD_REVIEW_AUTO_REPOS` (the BH-3479.0 contract knob on the `lead-review-land` lane, see `2026-09-29-BH-3479-contract.md`), it lists every PR merged in the last `LEAD_REVIEW_PRECISION_WINDOW_DAYS` days (GitHub `pulls?state=closed&sort=updated`, paged). For each one it reads `/api/verdicts?repo=&pr=&head=` on the MERGED head and takes the newest `source=lead` row on that head whose note carries a `lead-review:` token. A PR with no such row is not counted and not listed. A lead verdict on an older head doesn't count either.

Only `MERGE` and `MERGE-WITH-NOTES` are scored. A lead `BLOCK` that merged anyway is listed with its verdict and left out of `lead_merge`.

A scored PR is **bad** when either holds:

- **reverted**: a commit on main since the window start whose message starts `Revert "` names `#N` followed by a non-digit or the end of the text, so `#12` never matches `#123`. A revert of a re-land still counts the original. A revert whose message names no `#N` (a plain `git revert <sha>`) is not attributed. That's a known gap.
- **batch_failed**: a check run on the head whose name starts `Queue:` concluded `failure` or `cancelled`, read with `filter=all`, so a failed run that a later re-embark superseded still counts.

A PR that is both counts once. `precision = (lead_merge - bad) / lead_merge`, rounded to 3 decimals, and `null` when `lead_merge` is 0.

GitHub spend is bounded: main's commits are read only when a repo has at least one lead MERGE, and check runs only for lead-MERGE PRs. Every read sets `GH_REST_OPTIONAL=1`, so the quota reserve can refuse it.

## Unreadable is never clean

- A failed or unparseable verdict read: the PR counts `unreadable`, is listed with `verdict:"unreadable"`, and is left out of `lead_merge`.
- A failed check-runs read: the PR counts `unreadable`, listed with its lead verdict and `reverted:null, batch_failed:null`.
- A failed commits read: every lead-MERGE PR in that repo counts `unreadable`, and `error` says `commits unreadable (HTTP …)`.
- A failed PR-list page: the repo gets `error:"pulls unreadable (HTTP …)"`, zero counts and `precision:null`. A partial list is never scored.
- Hitting `LEAD_REVIEW_PRECISION_MAX_PAGES` on either list while still inside the window sets `truncated:true`.

## The file

`state/lead-review-precision/<YYYY-MM-DD>.json`, written through a temp file and a rename, sorted keys, no wall-clock field. A same-day rerun over the same answers writes the same bytes.

```
{day, window_days, repos:[{repo, window_days, error, lead_merge, reverted, batch_failed,
  unreadable, precision, truncated, prs:[{pr, verdict, head, reverted, batch_failed}]}]}
```

The ticket describes one object per repo and one file per UTC day. The per-repo objects are wrapped in `repos[]` so several repos still make one file. One summary line per run goes to `logs/lead-review-precision.log`.

## Warn

A repo with `lead_merge >= LEAD_REVIEW_PRECISION_MIN_N` and `precision < LEAD_REVIEW_PRECISION_WARN` fires one `bin/lane-alert.sh --severity warn --id lead-precision-<day>` line naming every such repo and the day file. `state/lead-review-precision/warned-<day>` is written only after lane-alert succeeds, so a rerun that day doesn't repeat it and a failed alert is retried next run.

## Knobs (catalog/lanes.d/lead-review-precision.json)

| env | type | default | meaning |
|---|---|---|---|
| `LEAD_REVIEW_PRECISION_WINDOW_DAYS` | int | 30 | merged-PR lookback |
| `LEAD_REVIEW_PRECISION_WARN` | float | 0.9 | a fraction in [0,1], not a percent |
| `LEAD_REVIEW_PRECISION_MIN_N` | int | 5 | fewest scored lead MERGEs before a warn |
| `LEAD_REVIEW_PRECISION_MAX_PAGES` | int | 30 | 100-row pages per list per run |

The ticket names the first two. `MIN_N` and `MAX_PAGES` are added so the "n ≥ 5" threshold and the page cap are settings rows, not literals; their defaults are the ticket's numbers. A bad value logs one line and falls back to the default.

## ASSUMPTIONS A6: the `Queue:` check-run name

Checked 2026-09-29 against the heads of the 36 most recently merged cromford PRs (`gh api repos/example-org/cromford/commits/<sha>/check-runs?filter=all`). None carries a check run whose name starts `Queue:`. The only merge-queue run is `Mergify Merge Queue` (36 `neutral`, 19 `success`), for example on #3605 (`45094397f9ea`) and #3526 (`756f459ae4df`). None of those 36 heads was dequeued, so this didn't read a failed batch either.

So as shipped, `batch_failed` matches the ticket's `Queue:` prefix and **will read 0 on cromford today**. The matcher was not widened to `Mergify Merge Queue`, because a failed run of that check on a head that later merged needs its own check (is it a batch failure after the MERGE, or a pre-queue condition miss?). Reverts are still scored. Widening it is a follow-up decision.
