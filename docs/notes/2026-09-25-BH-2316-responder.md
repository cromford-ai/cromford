# The responder's 12h cooldown survives a dead hub (BH-2346, BH-2316.3)

Doc: DB-COORDINATION-SPEC

`bin/watchdog-responder.sh` kept its per-key cooldown only in `state/responder/handled.json`. A rebuilt hub started with an empty file and bought the same responder sessions again. It now also uses the `brake:responder-handled` rows from `bin/lib/brake-ledger.sh` (BH-2343).

- **Gate.** The ledger path is on only when `brake_db_on` answers, which means `flags/alerts-db` exists and the jobs client loads. With no flag the pass sends no ledger request and runs the same as before.
- **Read.** After the stale-owed snapshot and the daily-cap stop, the pass calls `brake_read responder-handled 43200` and merges the rows into a temp copy of `handled.json` (`state/responder/handled.merged.*`), keeping the higher epoch for each key. Both cooldown checks read that copy: the persisted stale-owed keys and the wedged queue jobs. The copy is deleted after the wedged-queue loop and is never written back.
- **Write.** After the local stamp, every key the pass stamped (the offered persisted keys and the wedge keys, `<project>:<key>` as-is) gets `brake_mark responder-handled <P:K> $NOW`. The file is written first and the row second.
- **Fail open.** If the read fails (worker down, non-JSON 200) the pass logs `responder: brake ledger read failed (rc=N) — local handled.json only this pass` and uses the local file only, just like the flag-off pass. A read that hits the 5-page cap logs one line and uses the rows it got. If any mark fails the pass logs one line, `responder: brake ledger mark failed for N of M key(s) — local handled.json stamp stands`.
- **Nothing marked when nothing ran.** The daily-cap stop exits before the read. The rc 74-79 "no call" exit comes before the stamp. Neither pass writes to the file or the ledger.

Pinned by `tests/responder-handled-db.bh-2346-test.sh`, which runs the real responder against a stub worker.
