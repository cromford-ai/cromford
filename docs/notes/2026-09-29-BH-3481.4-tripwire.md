# The mid-build spend tripwire: rules, pause row, launch guard (BH-3481.4)

Doc: COST, CALL-GUARD

## What changed

This is child 5 of 5 of BH-3481 (ticket BH-3501). It fills in the stub bodies
of `bin/lib/build-tripwire.sh`, the seam BH-3497 added, and adds a launch
guard to `rb_gate_prelude`. A build that runs away now pauses itself, pages
once, and cannot be relaunched until an operator releases it.

There is no dollar budget anywhere. Every threshold is a multiple of the
operator's own `usd_per_pr`, which `cost_budget_for` reads from the
`conf.cost-caps.*` settings rows or `catalog/cost-caps.conf`.

## The two rules

`tw_eval` makes one pass over the build's `$BUILD/cost.csv` (col 13
`cost_usd`, col 26 `guard_fp`) and adds the live session's usd its caller
passes in. It reads no knob, env or network.

- **Spend.** `expected = usd_per_pr x BUILD_TRIPWIRE_SHAPE_<shape>`. The shape
  is the last `SIZE:` line in the build's `plan.md`: S, M, L or XL. With no plan,
  or any other word, it is XL. The build trips when
  `spend > BUILD_TRIPWIRE_MULT x expected`. With the defaults ($100/PR, M,
  MULT 5) that is spend over 500. An expected of 0 (no per-PR figure, or a
  factor that is not positive) unarms this rule. It never turns into "any
  spend trips".
- **Repeat.** The build trips when `BUILD_TRIPWIRE_REPEAT_MAX` paid rows
  (`cost_usd > 0`) carry the same non-empty `guard_fp`. Unpaid rows (refused,
  zero cost, or unpriced), and rows with an empty `guard_fp`, never count. 0
  unarms it.

A `cost_usd` that is not a number, empty included, is counted as
`unpriced_rows` and not summed. When both rules fire, spend is reported.

## Knobs

`catalog/lanes.d/_lib.build-tripwire.json`, as `lib.build-tripwire.*`
settings rows. `lib_env_apply build-tripwire` resolves them on every check,
so a row written mid-build binds on the next call. The order is settings row
(clamped to the registry bounds), then env, then the registry default, which
the code fallbacks mirror.

| knob | default | bounds | meaning |
|---|---|---|---|
| `BUILD_TRIPWIRE` | 1 | 0..1 | master switch; 0 = off |
| `BUILD_TRIPWIRE_MULT` | 5 | 1.5..100 | spend rule multiple of expected |
| `BUILD_TRIPWIRE_SHAPE_S` / `_M` / `_L` / `_XL` | 0.5 / 1 / 2 / 3 | min 0.1 | factor on usd_per_pr per plan size |
| `BUILD_TRIPWIRE_REPEAT_MAX` | 4 | 2..50 | paid rows on one guard_fp; 0 = unarmed |

`BUILD_TRIPWIRE_REPEAT_MAX=0` only unarms through env, because a settings row
is clamped to 2..50. `BUILD_TRIPWIRE=0` stops new trips. It does not un-trip
a build whose dir already holds `TRIPWIRE`: `CC()` still refuses that build.

## What a trip does

`tw_check_build <project> <key> <build-dir> <live-usd>` runs the rules. On a
trip it calls `tw_trip`, which runs once per build dir. A noclobber
`.tripwire.claim` file makes sure only the first caller acts, even when the
live meter and `CC()` race.

1. It writes `$BUILD/TRIPWIRE`. Line 1 is the verdict, and the rest is a plain
   diagnosis: the rule, the spend arithmetic, the shape, per-stage spend, the top
   repeated guard_fp, unpriced rows, the live session and the release command.
2. It writes the ledger row `build-tripwire "<project> <KEY>" = paused` with
   `bin/jobs-client.sh ledger-put`. The result is recorded as `pause_row:
   written|FAILED`.
3. It sends one page: `bin/lane-alert.sh --severity critical --id
   tripwire:<p>:<KEY>:<build>`. If lane-alert is not there, the same line goes
   through `bin/alert-line.sh` (never a raw `logs/ALERTS.log` append).

After that, `CC()` ends the build with `BB tripwire_paused` and
`RESULT BUILD_REFUSED TRIPWIRE_PAUSED <line 1>` (BH-3497). A second check on
the same dir answers "tripped" and does not write or page again.

## The launch guard

`# >>> tripwire paused skip` sits in `bin/lib/rb/gates.sh`, right after the
abandoned-ticket skip and before the fly enqueue gate. It reads `tw_paused`:

- **rc 0 (paused).** The build answers `BUILD_REFUSED SKIP_TRIPWIRE <KEY>`
  and exits 3. Nothing is queued.
- **rc 1 (no row, or released).** The build runs as today.
- **rc 2 (ledger unreadable).** The build runs as today, with one
  `pipeline.log` line.

## Fail-open vs fail-closed

- The launch guard fails open: an outage never stops a lane.
- A tripped build stays paused locally even when the ledger write fails,
  because `TRIPWIRE` is on disk. The page then says `pause_row=FAILED`, and
  the next launch is NOT refused, since no row exists.
- If lane-gate cannot be sourced, the knobs fall back to env and then the code
  defaults. The build is never stopped for that.

## Release

```
bin/jobs-client.sh ledger-put build-tripwire "<project> <KEY>" released
```

The old build dir keeps its `TRIPWIRE`. A new build gets a new dir.
