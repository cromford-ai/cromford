# The otp inbox: email one-time codes for web-task lanes (BH-7732)

Doc: DB-COORDINATION-SPEC

## What changed

Web tasks that sign in to a vendor need the one-time code the vendor emails.
The harness had no inbox it could read. the operator's decision (2026-10-20): use
Cloudflare Email Routing on `otp.example.com`, an Email Worker and a D1
table. SMS codes stay on Twilio.

- **Email Worker `harness-otp-inbox`** (`worker/otp-inbox/`). Email Routing
  sends every message for `<anything>@otp.example.com` (catch-all) to it.
  `email()` reads the message, parses it (`src/mime.js`), finds the code
  (`src/code.js`) and writes ONE `otp_messages` row to the `harness-jobs` D1
  (binding `DB`). It is a separate worker from `harness-jobs`, so a parser
  crash never touches the coordination API. It has no HTTP surface
  (`fetch` answers 404).
- **Table `otp_messages`** (`worker/jobs/schema.d/202610211454-bh-7732-otp-messages.sql`):
  recipient, message_id, sender, subject, code, parse_status
  (`code` | `no_code` | `too_large`), received_at. No raw body is stored.
- **Route `GET /api/otp?to=<address>&since=<ts>`** (`worker/jobs/src/routes/otp.js`),
  bearer `HARNESS_SECRET`. It returns the newest code for the address received
  at or after `since` (ISO `YYYY-MM-DDTHH:MM:SSZ` or epoch seconds): 200
  `{code, sender, subject, received_at}`, 404 `{error:"no code"}`, 400 on a
  bad `to` or `since`, 401 without the bearer. The 200, 404 and 400 answers
  are `no-store`.
- **Helper `bin/otp-wait.sh <address> [--timeout 120] [--since <ts>] [--interval 5]`**.
  It polls the route and prints the code alone on stdout (exit 0). At the
  deadline it writes one stderr line and exits 1. Bad arguments exit 64.
  `--since` defaults to now minus 60 s; take the time before you ask the
  vendor to send the code and pass it.
- **Retention rule `otp_messages.age`** in `POST /api/retention/run` (the
  hourly `bin/d1-retention.sh` lane). It deletes rows received more than
  `retention.otp_messages.days` (seed 1) days ago. `retention.dry_run` applies,
  with one `retention_runs` row per run.

## The rules

- **One row per message per address.** The dedup is the unique index
  `uq_otp_messages_msg (recipient, message_id)` and `ON CONFLICT DO NOTHING`.
  A second delivery of the same message writes no row; its log line says
  `dup=1`. One message sent to two catch-all addresses gives each address its
  row. With no `Message-ID` header the id is `fp:` + sha256 of the envelope
  from, to, the subject and the `Date` header.
- **Addresses are trimmed and lowercased** at write (the worker) and at read
  (the route and the helper).
- **Too large.** A message over 1 MB (`MAX_RAW_BYTES`) is written as
  `too_large` with no code, from its envelope and headers. Its body is not read.
- **A failed insert is not "stored".** The worker logs
  `otp-inbox: store failed to=<address> err=<error name>` and rethrows, so the
  `email()` call fails instead of returning as a success. That Email Routing
  then refuses the message (and the sender retries) is assumed, not verified
  on Cloudflare.
- **The code is a secret.** No log line, alert or error holds one: the worker
  line is `otp-inbox: stored to=<address> from=<sender> status=<status> dup=<0|1>`,
  the route logs nothing, and the helper prints the code to stdout only (the
  jobs client never logs a 200 body).
- **Which token is the code** (`extractCode`): the candidate nearest a keyword
  (verification, verify, one-time, otp, passcode, security/login/sign-in/
  confirmation/authentication/access code, code, pin), subject first, then the
  body. A candidate is a 4-8 digit run (`123 456` and `123-456` join), the
  digits of `G-123456`, or a 4-8 char token of capital letters and digits.
  Never the code: a zip, postal, promo, discount, coupon, referral or area code
  and the token after it; a token after `#`, `$`, `€`, `£`, `+` or `/`; part of a
  phone, an amount or a 9+ digit number; a year next to a month name; a date or
  a time; anything inside a URL or an email address. With no keyword match, a
  body line that is only a 4-8 digit token is the code. The cases are the
  tests in `worker/otp-inbox/test/code.bh-7732.test.js`.

## Knobs

| Setting row | Default | What it does |
|---|---|---|
| `retention.otp_messages.days` | 1 | days a row is kept; 0 turns the rule off |
| `retention.dry_run` (existing) | prod value | 1 = the rule counts and deletes nothing |

## Operator steps (go-live)

The worker deploys through `bin/harness-sync.sh` with every other
`worker/<name>/wrangler.jsonc`, after the jobs schema (and `otp_messages`) is
applied. Email Routing itself is a Cloudflare dashboard step, once:

1. In the Cloudflare dashboard, open the `example.com` zone, then Email, then
   Email Routing. Add the subdomain `otp.example.com` and let Cloudflare add
   its MX and SPF records.
2. Set the catch-all rule for `otp.example.com` to "Send to a Worker", worker
   `harness-otp-inbox`.
3. Probe: send an email to `qa@otp.example.com` with the text
   `Your code is 123456`. Then run `bin/otp-wait.sh qa@otp.example.com --timeout 60`
   on the hub. It must print `123456`.
