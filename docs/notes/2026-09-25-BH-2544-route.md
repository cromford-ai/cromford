# Alert family scripts: the worker route (BH-2544.3, BH-2575)

Doc: ALERTS-STATE-MACHINE

## What changed

The jobs worker gains a bearer-gated route family over the `alert_family_scripts`
table that the contract slice (BH-2568, `2026-09-25-BH-2544-contract.md`) added.
An operator can now read and edit the family→script mapping without a deploy.

- **`GET /api/alert-family-scripts`** answers `{rows:[...], as_of}`: every row,
  enabled and disabled, `ORDER BY priority ASC, id ASC`. It is uncapped on
  purpose. This is an operator-edited registry of tens of rows, and a cap would
  hide rows from its reader.
- **`PUT /api/alert-family-scripts/<id>`** upserts one row (`ON CONFLICT(id) DO
  UPDATE`), stamps `updated_at` with the request's server clock and takes
  `actor` from the body. It answers `{row, as_of}` with the row read back from
  the table.

Both verbs sit in `ROUTES` in `worker/jobs/src/index.js`, behind the bearer like
every `/api/*` route. The code is `worker/jobs/src/routes/alert-family-scripts.js`.

## Validation: 400, never a clamp

Every field is checked before the DB is touched, so an invalid PUT writes
nothing. The first bad field is named in the 400.

| Field | Rule | Absent |
|---|---|---|
| id (path) | `^[a-z0-9-]{1,48}$` after `decodeURIComponent`; no lowercasing | n/a (no match is the worker's 404) |
| match_kind | `akey_prefix` or `line_regex` | 400 |
| match | string, non-empty after trim, at most 1024 chars; for `line_regex` it must compile with `new RegExp` (a syntax gate only; the runtime matcher is Python) | 400 |
| verify | null or `^[a-z0-9-]{1,48}$` (a basename under `bin/alert-verify/`, so no dot, slash or shell metacharacter) | NULL |
| on_clear | `settle` or `model` | `settle` |
| on_repro | `model` or `park` | `model` |
| enabled | integer 0 or 1 (`true`/`false` are 400) | 1 |
| priority | integer | 100 |
| note | null or a string of at most 500 chars | NULL |
| actor | `^[A-Za-z0-9._@-]{1,96}$` (the alert-actions class) | 400 |

The PUT is WHOLE-ROW, like `route-rules`: a field absent from the body takes the
schema default, on an update too. A body `id` is ignored; the path is the only
identity. An id of `%2e%2e` never reaches the route, because the URL parser
resolves it to `/api/` and the worker answers its 404.

A D1 failure is a 503 through `d1Guarded`, never a 200 with empty rows.

## Self-create

`CREATED_TABLES.alert_family_scripts` in `worker/jobs/src/lib/core.js` carries
schema.sql's DDL, so the first request creates the table if `harness-sync` has
not applied schema.sql yet. The node suite compares the two shapes.

## Deploy

`cd worker/jobs && npx wrangler deploy`. Until that runs, the route is not live.

## Tests

- `worker/jobs/test/alert-family-scripts.bh-2544.test.js`, through `worker.fetch`
  against node:sqlite. The ticket named `npx vitest run`, but this package runs
  `node --test` and has no dependencies, so the command is
  `cd worker/jobs && node --test test/alert-family-scripts.bh-2544.test.js`.
- `tests/alert-family-scripts-route.bh-2575-test.sh` checks the wiring (bearer
  table, not the open table) and runs the node suite.
