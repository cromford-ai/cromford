# A red end-to-end check on the head holds the Mergify enqueue (BH-9071)

Doc: MERGE-CONDUCTOR

## Why

Mergify gates only on the checks `.mergify.yml` requires (Unit, Type, Coverage,
Drift). `mc_cireq_apply` (BH-8012) turns the conductor's CI word green when
those checks are green. End-to-end shards are not required. So the conductor
added `merge-queue` to project-3 PR 940 with a red end-to-end shard, and PR 944 had
a red shard too. A queued PR with a red shard turns the end-to-end run on main
red. Decision (the operator, 2026-11-05): no new Mergify gate and no new test runs. The
conductor reads the check runs that already exist.

## What changed

- New fragment `bin/merge-conductor.d/bh-9071-e2e-red-hold.sh`. `pr_worker`
  calls `mc_e2e_red_hold` in the READY arm, right after the production-red
  hold. That is before the dependency gate, the pre-queue gate, the READY
  autoenqueue mark, the merge budget and every label write.
- The gate reads only a not-yet-queued PR on a Mergify repo (`QUEUE=1`,
  `PROVIDER=mergify`, previous state not `QUEUED`). It reads
  `GET repos/<slug>/commits/<head>/check-runs?filter=latest`, paged up to
  `MC_REST_PAGES_MAX`, with the `MC_CI_READ_TIMEOUT_S` timeout.
- A run is end-to-end class when its name matches the regex (case-insensitive).
  The latest run of each name by `started_at` counts.
  - `failure` on a latest run: HELD. One log line per (PR, head):
    `<key> READY and HELD: end-to-end check(s) <names> failed on <head8> — not
    queued; a new commit clears it`. One PR comment per (PR, head) that names
    each failed check and its URL. Ready-why kind `e2e-red`.
  - A latest run not completed: HELD with no comment. Ready-why kind
    `e2e-running`. The PR queues on the first tick after it finishes green.
  - The read failed, did not parse, or the pages did not hold `total_count`
    runs: HELD this tick with no comment. Ready-why kind `e2e-unread`.
  - No end-to-end run, or all finished and none `failure` (`cancelled`,
    `skipped`, `neutral` and `timed_out` are not red): the arm goes on as
    before.
- A PR labelled `fix-main-red` (`MC_MAIN_RED_LABEL`) is not read. It goes on,
  with one log line per (PR, head).
- Every mark carries the head sha, so a new commit clears the block. A red on
  the new commit posts one new comment.
- The comment is posted only when the tick takes actions (actions flag, merge
  flag, no kill switch). In observe mode the conductor writes one
  `E2E_RED_COMMENT WOULD <key> <head8>` line per (PR, head). The `e2eredcmt`
  mark is written only after the POST returns 0, so a failed POST is tried
  again next tick. A crash between the 2xx and the mark can post a second
  comment once.

## Knobs

- `lane.merge-conductor[.<project>].mc_e2e_red_hold` (`MC_E2E_RED_HOLD`):
  1 on (default), 0 off.
- `lane.merge-conductor[.<project>].mc_e2e_check_re` (`MC_E2E_CHECK_RE`): the
  check-name regex. Empty (default) = the fallback `E2E_CHECK_RE` in
  `bin/lib/e2e-paths.sh`:
  `e2e|playwright|production[ _-]?qa|prod[ _-]?qa|preview[ _-]?qa|browser`.
  A regex that does not compile reads as the fallback, with one log line per
  project-hour.

## Not gated

The other `mc_enqueue` callers (the console Merge button, batch-resolve
trains, rule-adopt, the dequeue requeue paths) and the GitHub-native queue are
not gated. The ticket names the conductor and the `merge-queue` label.

## State

Attempts ledger lines: `e2eredhold|e2eredcmt|e2eredpass|e2eredwould <key>
<head>`, `e2erebad <project> <YYYYMMDDHH>`. The existing ledger GC prunes
them with the PR.
