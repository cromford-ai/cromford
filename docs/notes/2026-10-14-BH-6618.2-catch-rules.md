# CI test value report: the catch, test defect and order rules (BH-6638, BH-6618.2)

Doc: CI-RUNNERS, FLAKY-TESTS

## What changed

The three placeholder rule files of `bin/lib/ci-test-value/rules.d/` now
decide rows. A row can now be `real-pr`, `real-main`, `test-defect` or
`order`. A row that no rule decides stays `unknown U1.undecided`. The shared
reads and predicates are in the new file `bin/lib/ci-test-value/followup.sh`.
The three rule files source it. Nothing else changed: no driver, library,
renderer or `bin/test-impact.sh` edit.

## Rule order

The first rule that decides a row wins. The order is the file order
(`LC_ALL=C`):

| File | Rules | Classes |
|---|---|---|
| `10-infra.sh` | I1, I2, I3 | `infra` |
| `20-flake.sh` | F1 | `flake` |
| `30-order.sh` | `O1.batch-member-added-suite` | `order` |
| `40-followup.sh` | `T1.followup-tests-only`, `R1.followup-reaches-suite`, `T2.main-fix-tests-only`, `R2.main-fix-pr` | `test-defect`, `real-pr`, `real-main` |
| `50-main-flake.sh` | F2 | `flake` |
| `60-batch-fix.sh` | `B1.batch-member-fix` | `real-pr`, `test-defect` |

So O1 runs before T1/R1/T2/R2, and T2/R2 run before F2.

## The predicates

- Test path: a path that starts with `tests/` or `catalog/fixtures/`. Every
  other path is a non-test path.
- Batch row: `CTV_IS_BATCH=1` (the driver sets it for `merge_group` and
  `gh-readonly-queue/*`), or a head branch that starts with
  `mergify/merge-queue/`. This repo batches through Mergify, so its batch runs
  are `pull_request` runs on that branch. T1 and R1 never decide a batch row.
- Batch members: the `#N` numbers in the row's title (`dqw_batch_members`).
  A title with no `#N` gives no members, and O1 and B1 make no read.

## The follow-up set

`ctv_followup_files <red_head> <red_base> <green_head> <green_base>`:

1. Read `compare/<red_head>...<green_head>`. Take every `filename` and
   `previous_filename`.
2. If `red_base` is not `green_base`, read `compare/<red_base>...<green_base>`
   and take its file names. If the two bases are the same, make no read.
3. Print the first set minus the second set.

An empty result is rc 0 with no output: the new head is a rebase only. It
decides nothing. A compare that is unread, 404 or at GitHub's caps (300 files
or more, more than 250 commits) is rc 1: do not decide. It is never an empty
set. A compare of two fixed shas goes to `<out>/cache/fu/compare-<a>-<b>.json`.

## Reach

`ctv_reaches <unit> <path...>` runs `bin/test-impact.sh select --changed
<paths> --map-only --map <map> --why`.

- rc 0: a `--why` row names the unit with a kind other than `always` or
  `full`. A pick by the always-run set alone is not reach evidence. A `full`
  row is the whole corpus, so it is not reach evidence too.
- rc 1: no such row.
- rc 2: cannot tell. The map is missing, the unit is not a suite in the map,
  the select failed, or the reason line says `full:` (a path has no known
  reach) and no row names the unit.

The map is built once per report run with `bin/test-impact.sh map` into
`<out>/cache/impact-map.tsv`. `<out>/cache/impact-map.stamp` holds the run id.
A failed build is kept as a memo for the rest of the run.
`CTV_IMPACT_MAP=<file>` replaces the map only when `HARNESS_TEST_SANDBOX=1`.

## The rules

- `O1.batch-member-added-suite` (`order`): a batch row with 2 or more
  members. One member A (sorted, at most 10) lists the unit in
  `pulls/A/files` as `added`, `modified` or `renamed`. A's last run of the same
  workflow before the batch run, on A's current head, completed with
  `success`. A batch of one, a red or absent own run, or a run of another
  workflow decides nothing.
- `T1.followup-tests-only` (`test-defect`): a `pull_request` row that is not a
  batch row. The rule finds the next green run of the same workflow for the
  same PR on another head (the smallest run id above the row's). Every path of
  the follow-up set is a test path.
- `R1.followup-reaches-suite` (`real-pr`): the same pick, and the non-test
  paths of the follow-up set reach the unit.
- `T2.main-fix-tests-only` (`test-defect`): a push row on `main`. The rule
  finds the next green push run on `main` (the F2 pick) and reads the compare
  from the red sha to that sha. The compare must be `ahead`, `behind_by` 0 and
  at most 250 commits. Each `Merge pull request #N` commit (at most 20) is a
  candidate. `pulls/N` must be merged. Its title or body must hold the unit's
  file name, or the red run id as a whole number. Every file of
  `pulls/N/files` is a test path.
- `R2.main-fix-pr` (`real-main`): the same candidate, and its non-test paths
  reach the unit.
- `B1.batch-member-fix` (`real-pr` or `test-defect`): a batch row. A member M
  merged later. M's head at batch time is its last run of the same workflow
  before the batch run. M's next green run after the batch is on a new head.
  The follow-up set between the two heads must reach the unit: a non-test path
  that reaches it is `real-pr`; only test paths, and they reach it, is
  `test-defect`.

## Reads

Every read goes through `_ctv_rr_get` (`20-flake.sh`), so it is in the rule
read ledger and `--max-reads` counts it. The reads are REST GETs only:

- `pulls/<n>` and `pulls/<n>/files` (pages 1 to 3; a third full page decides
  nothing). Memo for one run only, because an open PR can still change.
- `actions/workflows/<W>/runs?branch=<b>&event=pull_request` and
  `actions/runs?head_sha=<sha>&event=pull_request`. Memo for one run only.
- `compare/<a>...<b>`, cached under `fu/`.
- T2/R2 read the main green list and the main compare under F2's memo and
  cache key (`f2-green-…`, `f2/compare-…`), so F2 does not read them again.
