## What changed

This is child 1 of 5 of BH-3479 (ticket BH-3544). It registers the knobs the
other children read and writes down the strings they agree on. Runtime
behavior does not change. Nothing acts on the new knobs yet.

- `catalog/lanes.d/lead-review-land.json` gets `LEAD_REVIEW_AUTO_REPOS` and
  `LEAD_REVIEW_SPOTCHECK_PCT`.
- `catalog/lanes.d/lead-review.json` gets `LEAD_REVIEW_THREAD_MAX_BYTES`, right
  after `LEAD_REVIEW_DIFF_MAX_BYTES`.
- All three are `required: true`. With no settings row, `lane_env_apply`
  exports an env value if the box has one, else the registry default. A knob
  that is not required is left unset when there is no row, and the siblings
  need a value.
- `bin/lead-review-land.sh` and `bin/lead-review.sh` each get one inert read
  per knob, marked `BH-3479.0 contract seam`. They assign a variable nothing
  uses. They exist because `tests/lanes-registry-test.sh` section 6 refuses a
  wired lane's knob that its script never names. A sibling replaces the seam
  with the real reader. The reads are `${X:-}` with no literal, so the default
  lives only in the registry (`tests/config-literal-lint.sh`).
- `LEAD_REVIEW_AUTO_REPOS` is `settable: false`. Section 17a of the registry
  suite refuses a settable knob whose name ends in `REPOS`, because a settings
  row could re-aim a root lane at another repo. The console settings screen
  does not list it (`console-ui/src/lib/settings.js` drops `settable: false`
  knobs), PUT `/api/settings` refuses it, and `lane_env_apply` never reads a
  row for it. To change it, set
  it in `env/global.env`. Making it console-settable needs a `HAZ_OK` exception
  argued for in its own PR.
- `LEAD_REVIEW_SPOTCHECK_PCT` uses `zero_means: "off"`, the value section 8
  allows. 0 = off: no MERGE verdict is sampled. A row over 100 is clamped to
  100 with a `CLAMPED` line in `logs/lane-gate.log`.
- `catalog/lanes.json` is generated and git-ignored, so it is rendered by
  `bin/lanes-build.sh`, not committed.

## The `Lead-Lane:` trailer

A commit-message line starting `Lead-Lane:` (any value) on a non-merge commit
marks that commit as written by the lead lane. A PR whose `main...head` carries
one is never auto-requested for lead review, because the lead does not verdict
its own work. It goes to the operator as one warn digest line instead (parent
assumption A3).

Merge commits are ignored. So a clean main merge into a lead branch does not
hide a builder commit, and a builder PR that merged a lead commit is not
exempted.

## The findings-review marker

`<!-- lead-review:<request id> -->`

It goes in the body of the one PR review the hub posts for a lead BLOCK: event
`REQUEST_CHANGES`, `commit_id` = the reviewed head. `br_lead_pick` briefs the
fix round from that review. The marker is also the dedupe. The hub reads the
PR's reviews first and never posts a second review for the same id.

## The `## Rules pack` prompt section

The lead review prompt carries a `## Rules pack` section with exactly one of
these values:

- `clean`
- `could not run (rc N)`
- `not installed on this box`
- `not applicable to <repo>`

A rules-pack red is not a prompt value. It is a BLOCK report with no model
call, and its header carries `- reviewer model: rules-pack`.

## For the siblings

- Replace the seam line with the real reader.
- If your reader lives in a new script, move the knob's `read_in` to that
  script in the same PR.
- Don't re-register a knob.
- An empty value means the registry could not be read. Treat it as "not
  configured" and do nothing, never as "all repos".
