# gh_rest caches ETags and answers 304s from the cache

Doc: MERGE-CONDUCTOR, ACCOUNT-ROUTING

## Why

The example-org GitHub App installation (id 161623167, 6,600 requests/h, shared
by every hub lane and every pool machine) hit its rate limit twice on
2026-09-21. `logs/gh-rate.log` named the refused identity as
`app:example-org/cromford cmd=api -i` — reads through `bin/lib/gh-rest.sh`'s
`gh_rest`, the wrapper every decision path uses — and the burst logs were
`merge-conductor.log` (207 lines in one 6-minute window) and `gh-pr-list.log`
(the closed-PR listing, 3 pages x 9 repos, run every 10 minutes by three
lanes). The vast majority of those reads answered a body that had not changed
since the last read.

`gh api -i -H "If-None-Match: <etag>" repos/<slug>/pulls/<n>` answers `HTTP/2.0
304 Not Modified` on an unchanged resource, and a 304 does not count against
the primary rate limit (GitHub REST docs, "conditional requests"). Before this
change `gh_rest` mapped a 304 to rc 75 (UNVERIFIABLE) because nothing ever sent
a conditional request in the first place.

## What changed

**`bin/lib/gh-rest.sh`** (`gh_rest`, GET only): a cached ETag rides as
`If-None-Match`. A `304` replays the cached body, rc 0,
`GH_REST_STATUS=304`, `GH_REST_REASON=cached`. A `304` with no cached body
left (the file was lost mid-tick) is rc 75, `GH_REST_REASON=cache-miss` —
never an empty answer standing in for a state. A `2xx` with a body stores the
new `ETag` + body; a `2xx` with an empty body is unchanged (still rc 75,
`empty`, never cached). A non-GET never touches the cache. The kill switch
`GH_ETAG=0` restores today's behaviour byte for byte: no header sent, no file
read or written. The three exit codes, `GH_REST_STATUS`/`GH_REST_REASON`, the
"no `$( )` around a helper" rule and the no-GraphQL rule are unchanged — the
library gained internals, not a new contract.

The mechanics (key hashing, the on-disk format, the TTL/size sweep) live in a
**new file, `bin/lib/gh-rest-etag.sh`**, sourced by `gh-rest.sh`, for the
reason `bin/lib/gh-rest-list.sh`'s own header gives: `gh-rest.sh` is held under
a 110 code-line ceiling by `tests/gh-rest-lib-test.sh` on purpose, so the next
caller-conversion cannot quietly grow a contract file into a lane. `gh_rest`
itself grew from 96 to 109 lines — one under the ceiling.

**On-disk format.** One file per key under `$HARNESS/state/gh-etag/<sha1>`:
line 1 is the ETag, every line after is the response body. One file, not two,
so a cache hit is one read that answers both "is there an etag to send" and
"what do I replay on a 304" — two files could go out of sync (an etag with no
body, or the reverse) in a way one file cannot represent. The key is a sha1 of
method + path + every extra arg `gh_rest` was called with (accept headers,
`-f`/`-F` params) — deliberately **not** identity: no token, no `GH_TOKEN`
value, ever enters the hash, so the same resource read by two different
identities shares one cache entry, which is correct (an ETag is a property of
the resource, not of who asked). Verified in
`tests/gh-rest-etag-test.sh` section 6.

**A subtle portability bug caught during red-then-green.** The first
implementation extracted the `ETag:` header with
`awk 'BEGIN{IGNORECASE=1} /^etag:/{...}'`. `IGNORECASE` is a gawk-only special
variable; it is silently ignored by mawk (Debian's `/usr/bin/awk`) and by BSD
awk (macOS, where this suite's local runs happen), so a case-sensitive
`/^etag:/` never matched the `ETag:` header `gh` actually sends and nothing was
ever stored. Fixed to a bracket expression, `/^[Ee][Tt][Aa][Gg]:/`, which
matches on every awk. This is exactly the trap `_gh_rest_sniff`'s own comment
warns about one function away ("only the two statuses that can mean it") —
portability bugs in this codebase hide in the awk/sed dialect, not the logic.

**Measurability.** `gh_rest_etag_report <lane>` (in `gh-rest-etag.sh`) appends
one `logs/gh-rate.log` line — `gh-etag lane=<name> fetched=<n> cached=<n>` —
then clears its evidence and runs the TTL/size sweep (self-limits to once an
hour via a stamp file, so calling the report every tick costs nothing extra).
It is called at the end of a tick in `merge-conductor.sh`, `reconcile-prs.sh`,
`merge-sweep.sh` and `pr-url-reconcile.sh`.

The counter is a FILE (`_gh_etag_count`/`_gh_etag_count_file`), not a shell
variable — this took a review round to get right (see below). `mc_pr_view`'s
whole point is to return a value, so every real call site is `X=$(mc_pr_view
…)`, a `$( )` subshell, and `merge-conductor.sh` additionally backgrounds one
subshell per project. `$$` is identical across every `$( )`, `( )` and `&` in
bash (never reset for any of them), so a `$$`-keyed counter would sum every
project into one number; `$BASHPID` changes on EVERY `$( )`, including two in
a row inside the same subshell, so it cannot accumulate across more than one
read either. Neither shell state survives the way this needs, but a file does
— a write is visible to whatever next opens the same path, forked or not.
`GH_ETAG_COUNT_FILE`, when a caller exports it, names which file; otherwise it
defaults to `gh-etag-count.$$`, which is exactly right for every caller here
except one. `merge-conductor.sh` sets and exports a fresh, uniquely-named file
per project INSIDE that project's own backgrounded subshell, so parallel
projects never share a counter and each project's report line is its own.

## Hot readers converted

| Site | Before | After |
|---|---|---|
| `bin/reconcile-prs.sh` (the `state,closedAt,mergedAt` poll, every */10 pass, unmerged builds) | `gh pr view $URL --json state,closedAt,mergedAt -q '...'` (GraphQL) | `mc_pr_view "$URL" '"\(.STATE) \(.closed_at // "") \(.merged_at // "")"'` (REST, cacheable) |
| `bin/reconcile-prs.sh` (merge-commit sha, once a row turns MERGED) | `gh pr view $URL --json mergeCommit -q .mergeCommit.oid` | `mc_pr_view "$URL" '.merge_commit_sha // ""'` |
| `bin/review-prs.sh` `merge_retry()` (the approved-head re-check, every tick, per APPROVE record) | `gh pr view $NUM -R $SLUG --json state,mergeStateStatus -q '...'` | `mc_pr_view "https://github.com/$SLUG/pull/$NUM" '.STATE + " " + .MSTATE'` |

`bin/lib/gh-pr-list.sh` already called `gh_rest` before this ticket (BH-994) —
confirmed, no change. `bin/merge-conductor.sh`'s own PR state/body reads and
its diff read already went through `mc_pr_view`/`mc_pr_diff` -> `gh_rest`
before this ticket too (also BH-994); the ticket's line numbers (~1376, ~1909,
~2387) were written against an earlier revision of the file. `bin/merge-sweep.sh`
already reads state through `mc_pr_view` at every call site that matters
(`674`, `789`, `899`, `920`, `1127`, `1239`, `1283`, `1304` — confirmed by
grep, no direct `gh api`/`gh pr view` state reads left to convert); it only
gained the `gh_rest_etag_report` call.

**Per-tick call count.** Before: `reconcile-prs.sh` spent 1-2 GraphQL calls
per unmerged row per */10 pass (state always, merge-commit on a MERGED
transition); `review-prs.sh` spent 1 GraphQL call per APPROVE-recorded PR per
tick in `merge_retry`. After: the same call COUNT (the read still happens
every tick — GitHub decides whether it answers 200 or 304), but each read now
carries `If-None-Match`, and a PR whose state has not moved since the last
tick answers 304 — not counted against the rate limit — instead of a full 200.
The conductor's steady-state reads are the dominant traffic named in the
incident (`merge-conductor.log`, 207 lines in 6 minutes) and were already
routed through `gh_rest`/`mc_pr_view`, so they get the cache automatically
with no call-site change at all.

**Left alone, on purpose.** `bin/pr-url-reconcile.sh` reads through
`gh_pr_rest_read` (`bin/lib/gh-pr-create.sh`), a separate contract with its
own status/body split and its own per-call token override — not a thin
wrapper over `gh_rest`, so per the ticket's own caveat it is untouched. Its
`gh_rest_etag_report` call is a permanent no-op today (the lane never sources
`gh-rest.sh`) — left in place so the line already exists the day that read is
pointed at `gh_rest`.  `bin/review-prs.sh`'s other `gh pr view`/`gh pr
diff`/`gh api .../reviews` calls (state/mergeCommit right after `gh pr merge`,
the diff read, the comment/review-thread reads) run once per triggering event
— a merge attempt, a new head — not as a steady-state poll of an unchanged
resource every tick, so converting them buys little cache benefit for real
GraphQL-to-REST migration risk; left for a follow-up ticket if wanted.

## Review fix round (7131b264 -> this commit)

A review found three blocking issues and two "fix now" ones, all real:

- **B1.** `tests/closed-settle-guard-test.sh` (the ONLY suite exercising
  `mc_closed_settled`'s window through `reconcile-prs.sh`) still stubbed the
  OLD `gh pr view --json state` shape and went 14/0 -> 10/4. Fixed the same
  way as the two reconcile fixtures. Its "no merge-conductor-lib.sh" case
  exposed a real regression this round also fixes: before this ticket a
  missing lib only cost `mc_closed_settled` (fails open); after converting the
  state read to `mc_pr_view` too, a missing lib meant NO read at all. Fixed by
  giving `reconcile-prs.sh`'s no-lib fallback its own `mc_pr_view` that
  re-derives the same REST-shaped object over `gh pr view` (the exact call
  this lane made before BH-994) rather than failing every read.
- **B2.** `mc_rest_pr_json` ran `gh_rest` inside `$( )` — a REVIEW-CAUGHT
  instance of the exact bug class the library's own header warns about — so
  every `mc_pr_view` read (the dominant traffic named in the incident) was
  invisible to `gh_rest_etag_report`; it always printed `fetched=0 cached=0`.
  Fixed at two levels: `mc_rest_pr_json` now reads through a file (the
  `_gh_rest_field`/`gh-pr-list.sh` idiom), AND the counter itself moved to a
  file (see Measurability above), because the file-read fix alone is not
  sufficient — `mc_pr_view`'s own callers are `$( )` too.
- **B3.** A 304 replay could return rc 0 with an EMPTY body if the read after
  `[ -r "$f" ]` passed still failed (the TTL sweep never touched a hit's
  mtime, so a hot entry could be evicted between the two checks) — the exact
  #768 failure class this library exists to rule out. Fixed: the body read
  happens before anything is treated as a hit, a failure there is a miss, and
  a hit now also verifies line 1 still equals the etag `gh_rest` actually SENT
  (a stale writer between the read and the reply landing is now a `cache-miss`,
  never a reply built from two different writes) and touches the entry's
  mtime (so the sweep ages out cold keys, not ones still being asked about).
- **I1 (byte-for-byte).** The original store re-extracted the body from the
  raw response file with its own `awk` pass, which diverges from the fresh
  path's `$( )`-then-`printf` on a body ending in a blank line (14 vs 15
  bytes). Fixed by storing `gh_rest`'s own already-computed `$body` string
  directly — a replay is now byte-for-byte by construction, not by luck of
  input shape.
- **I2 (no-ETag response).** A 200 with no `ETag:` header left a stale
  entry in place, so the next 304 could replay a body GitHub had already
  superseded. Fixed: no ETag now removes the entry.

Both `_gh_etag_on_2xx`'s header scan and `_gh_etag_on_304`'s consistency check
are new load-bearing lines; `tests/gh-rest-etag-test.sh` grew four new
sections (1b/1c byte-for-byte + no-etag removal, 4b-4e stale-writer and
unreadable-entry races) and two more mutants (etag-consistency dropped, body
read after the etag check ignored) — the second mutant needed shadowing
`tail` on `PATH`, since the directory-replacement trick used for the first
fails at the earlier `sed` line and never reaches `tail` at all. All four
mutants are caught (28/0 with a working `sed -i`).

## Drain-train review round (ebe1e398 -> this commit)

Three Mac-only review rounds all missed two real regressions because BSD
`sed -i` breaks every mutant row on BOTH trees, so "identical to baseline"
was comparing two equally broken runs on the mutant suites specifically. A
drain-train review on the actual gate host (Linux, GNU sed, and CI itself)
caught both:

- **The library's own contract suite went red.** `gh-rest.sh`'s 404 arm
  became `404) rm -f "$tmp"; return 44 ;;` (needed once the 2xx arm had to
  keep `$tmp` alive for the ETag store), and `tests/gh-rest-lib-test.sh`'s
  existing mutant-1 `sed` still targeted the old text `404) return 44` —
  matched nothing, so the mutation guard silently became a no-op and the
  suite's own tripwire fired (145/1 on the host). Retargeted the `sed` at the
  new line; 146/0 on the host, mutant caught.
- **`review-prs.sh`'s merge retry stopped firing without the conductor lib.**
  `merge_retry()` reads `mc_pr_view` now; that lane has always treated
  `merge-conductor-lib.sh` as optional, and the no-lib stub this ticket added
  (`mc_pr_view() { return 75; }`) emptied `ST` on every lib-less box, so
  `case "OPEN CLEAN"` never matched and the retry silently never ran — the
  same regression class as `reconcile-prs.sh`'s B1 fix, not carried over.
  CI's `Pure-logic gate fixtures (shard 3/4)` was red on exactly the five
  `merge_retry` rows. Fixed with the same pattern reconcile-prs.sh got: the
  no-lib fallback re-derives `{STATE, MSTATE}` over `gh pr view` (GraphQL,
  the exact call this lane made before BH-994 — its `state`/`mergeStateStatus`
  enums are already the uppercase words REST's normalised fields use, so no
  value translation is needed, only field names). The suite's stub `gh` was
  updated to answer the shape a real `gh pr view -q '{STATE:…,MSTATE:…}'`
  produces (a JSON object) rather than the old single-stage plain-text
  `"OPEN CLEAN"`, since the fallback now runs the caller's own jq filter as
  a SECOND pass over that object, same as the real REST path always has.

Also taken from the same review, all non-blocking: the cache key is now
salted with `GH_LIMIT_IDENTITY` (a label, never a token) — the "identity-
independent" framing was wrong (an ETag is a property of the representation,
which CAN differ per viewer; it was safe anyway for three checkable reasons
the code comment now states, and the salt is free insurance); a per-entry
`GH_ETAG_MAX_BYTES` (default 1 MiB) bounds a single diff/patch read, since
`GH_ETAG_MAX` only bounds entry count; the same-process tmp-file name changed
from `.$key.$$` to `.$key.$BASHPID`, since `$$` is identical across every
`$( )`/`&` of one process and `$BASHPID` is not, closing a same-process
concurrent-writer interleave (cross-process was always safe — distinct `$$`,
atomic rename). Left for a follow-up: the counter file
(`$TMPDIR/gh-etag-count.<lane>.$$`) is removed only by `gh_rest_etag_report`,
so a lane killed before its own report leaves one file, bounded by pid
recycling — low severity, not fixed here.

**Correction to this note's own earlier claim**: "fixed at two levels" for
`mc_rest_pr_json`'s file-read change overstated it — with
`bin/lib/mc/classify.sh` reverted to main, `tests/gh-rest-etag-test.sh` is
unchanged, including the section that drives `mc_pr_view` end to end: the
file-backed counter alone is what makes counts survive the `$( )`. The
file-read change is still correct (it restores `GH_REST_STATUS` in
`mc_pr_view`'s own shell, which `mc_rest_status`'s log lines read), but it is
not load-bearing for any assertion in this PR.

## Both no-lib fallbacks moved from GraphQL to REST

The drain-train review's F1b fix (above) restored `review-prs.sh`'s no-lib
`mc_pr_view` with `gh pr view` (GraphQL) — matching `reconcile-prs.sh`'s own
B1 fix from an earlier round, which used the same call. Team lead's follow-up:
the fleet's standing rule is REST only, never GraphQL, in ANY decision path —
`gh_rest`/`bin/lib/gh-rest.sh` exists specifically because a GraphQL rate
limit kills a lane mid-session (#768), and a no-lib fallback is exactly the
path that fires when a box is already degraded, the worst possible place to
reach for the thing that caused the original incident. Both fallbacks now
call `gh api repos/$slug/pulls/$num -q '{...}'` directly (no `-i`, no
`gh_rest`, since gh_rest itself lives in a file this no-lib path cannot
assume is sourced either) — the slug/num are parsed from the PR URL with the
same sed/grep `bin/lib/mc/classify.sh`'s `mc_slug_of_url`/`mc_num_of_url` use,
and the STATE/MSTATE derivation matches `MC_REST_NORM`'s own logic exactly
(`merged_at` set -> MERGED, `state=="open"` -> OPEN, else CLOSED;
`mergeable_state` upcased -> MSTATE).

Three fixtures needed their stub `gh` updated to match: `tests/closed-settle-
guard-test.sh`'s "no merge-conductor-lib.sh" arm, `tests/external-review-ci-
read-test.sh`'s merge-retry stub (which also needed its `state` assertion
retargeted, since the old text `state,mergeStateStatus` no longer appears
anywhere in the call), and `tests/gh-default-identity-test.sh` — a suite
neither this nor the prior review round had checked, found only because its
fixture (main-red-detector + reconcile-prs.sh identity routing) never copied
`merge-conductor-lib.sh` either, so reconcile-prs.sh has ALWAYS run this
suite through the no-lib fallback; its assertion still expected the very
first `gh pr view` shape from before ANY of this ticket's rounds. Retargeted
to the REST call, verified 117/0 on the host (was failing 116/1 with the
stale assertion once the fallback itself changed under it).

`tests/gh-no-graphql-decision-guard-test.sh` carried no allowlist entry for
either fallback's old `gh pr view` line — nothing to remove — and is 35/0
after the conversion.

## The knobs

`GH_ETAG` (default 1, 0 disables), `GH_ETAG_TTL_H` (default 48),
`GH_ETAG_MAX` (default 20000) — documented in
`env-templates/lanes/360-gh-rest-etag-cache.env.example`, not in
`catalog/lanes.json`: they govern the shared `gh-rest.sh` library every lane
sources, not one lane's own script, so they follow the precedent of
`TRIAGE_FAIL_CONSUME_AFTER`/`BUILD_SLOTS` (fleet-wide knobs documented as
their own topic file) rather than being attached to `merge-conductor`'s or any
other single lane's registry entry. This branch was rebased onto BH-1247
(landed on `main` after this ticket started): `env-templates/global.env.example`
is now rendered on demand and git-ignored, same as `catalog/lanes.json` and
every `cron/<box>.cron` — only the `env-templates/lanes/` fragment this ticket
adds is committed.
