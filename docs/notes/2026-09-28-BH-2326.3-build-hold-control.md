# HOLD / UNHOLD on the Build screen (BH-3149, BH-2326.3)

Doc: DB-COORDINATION-SPEC

## What changed

- New `console-ui/src/ui/TicketHold.js`, built only from the BH-2326.0
  contract (`holdTarget`, `holdCommand`, `holdFromLedger`, `HOLD_REASON_MAX`,
  `api.ticketHold`) and `api.action`:
  - `useTicketHold(project, ticket)`: one hold read per screen. `hold` is null
    while loading, `{unknown:true}` when the read failed, else the ledger answer.
  - `TicketHoldControl`: HOLD when not held, UNHOLD when held, both plus
    "hold state unknown" when the read failed, nothing when `holdTarget` is null.
    A click asks in the in-app dialog with an optional reason (max 500) and, on
    confirm, queues one `hold_ticket` / `unhold_ticket` command. A positive
    integer `command_id` shows "HOLD queued as command #N" linking
    `/history/commands?id=N` and re-reads the hold once, 20 s later.
- `screens/Build.js` calls `useTicketHold` once and hands the answer to the
  header `HeldTag` (right after the verdict tag) and to the control (under the
  stats).

## Why

#3149: an operator on a build can hold or release its ticket without leaving
the page. The hub handler that turns the command into the GitHub label is
#3147; until it merges a queued command answers `unknown command type` on
/history/commands, which is what the console should say.

## What it does not do

No worker, proxy, `commands.js`, `JobActions` or `Modal` change. A failed POST
and a 200 with no command id never read as queued and arm no reload.
