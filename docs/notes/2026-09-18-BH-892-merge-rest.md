# Every merge write goes over REST

Doc: MERGE-CONDUCTOR, OPERATOR-SETUP

**What changed.** The four merge write sites in this harness — the console
`merge_pr` handler in `bin/poll-commands.sh`, `bin/merge-sweep.sh`, both landing
paths in `bin/merge-queue.sh` (the write `bin/tier2-merge-sweep.sh` delegates to)
and `mc_merge` in `bin/lib/merge-conductor-lib.sh` — now land a PR with
`PUT /repos/{slug}/pulls/{n}/merge`, `merge_method=squash`, carrying the REVIEWED
sha. The new `bin/lib/gh-pr-merge.sh` is the ladder: rung `rest` on the identity
the caller holds, then `rest:default-pat`, then `rest:admin-pat`. Each caller
keeps its existing `gh pr merge` line as the no-verdict fallback and its existing
post-merge state read for every answer except a REST 200.

**Why.** `gh pr merge` is a GraphQL mutation. On 2026-09-18 the PAT's GraphQL
bucket was empty — `API rate limit already exceeded for user ID 2220366` — and
console commands 15934 (example-org/project-4#1598) and 15937 (#1599) dead-lettered
while the same PRs merged instantly over REST. The cost of that is not one failed
click: the sweep parks "merge FAILED despite CLEAN", the conductor spends a
strike, two strikes park the ticket `merge-failed-twice`, and
`bin/blocked-resolver.sh` rebuilds a ticket that had already been approved. Same
fix shape as BH-848 (PR create over REST), same rung logic as BH-841/BH-847.

**What it touches.**

- **Rungs and verdicts.** Only exact HTTP status codes decide whether the ladder
  climbs: 403/429/404/5xx/no-status are "this identity could not answer" and move
  to the next rung; 200/405/409/422 are GitHub's answer about the merge and stop
  the ladder dead. A second identity never re-tries a merge GitHub already
  refused — that is the whole of "never merged blind". A rate-limit MESSAGE only
  words the log line.
- **The reviewed sha.** It rides on the PUT as the `sha` field, which is the REST
  equivalent of `--match-head-commit`: a head that moved after the approval comes
  back 409 instead of merging code no reviewer read. No reviewed sha in hand
  means an UNBOUND merge — today's behaviour at that call site — logged as
  unbound, never filled in with a guess. On the console lane the sha does not
  come from the request: Mission Control's merge button posts
  `{type, project, ticket, pr_url}` and nothing else, so the handler falls back
  to the ledger's verdict row (`job_verdict <pr-url>`, field 6 — the same lookup
  `bin/merge-queue.sh`'s `hb_sha` does) and only a row that makes no claim ("-")
  leaves that merge unbound.
- **The branch delete.** Best effort, only after a 200, and only against a head
  that lives in the base repo (`.head.repo.full_name` equals the slug). A PR from
  a fork keeps its branch, exactly as `gh pr merge --delete-branch` does — the
  DELETE goes to the base repo, where a branch of that name would be someone
  else's work.
- **The merge sha.** A REST 200 carries it, so `mc_settle_merged` and the sweep's
  `merge_sha` artifact read it from the answer and fall back to the GraphQL
  `mergeCommit` read only when it is absent. Under the cap that read is the one
  that fails, and a real merge read as a failure is how a landed ticket got
  rebuilt. `mc_merge` prints the sha on stdout — its production callers run it
  through `$(mc_merge_locked …)`, so a variable would die in that subshell — and
  `conductor_settle` threads the captured value into `mc_settle_merged`, which
  believes only a hex string and otherwise reads as before.
- **`HEADBOUND_ENFORCE=0` sends the PUT unbound.** The switch downgrades a
  head/reviewed-sha mismatch to a log line; binding the PUT to the stale sha
  anyway would turn that into a terminal 409. Off means no sha, said in the log.
- **A 405 in the conductor keeps the state read.** "Pull Request is not
  mergeable" is also what a PR the console or sweep already landed answers;
  `mc_merge` asks the state before it returns rc 1, as the gh line always did.
- **Native-queue repos are untouched.** Under GitHub's own merge queue
  `gh pr merge` IS the enqueue and REST has no equivalent, so `SWEEP_QUEUE=1`,
  `mc_enqueue_github` and a console merge on a repo whose provider probe says
  `github` all keep the GraphQL call.
- **The console ack.** A 409 now acks `refused: head moved since sha <8 chars> —
  <GitHub's message>` and a 405 `refused: GitHub would not merge — <message>`.
  `merge failed:` is kept for the case it was built for: the fallback call
  actually failing. What is PROVEN here is the box-side observable: `ok:false`
  with a `RESULT` that starts `refused:` and carries GitHub's own message, never
  the `merge failed:` string the dead letters carried. That `refused:` prefix is
  the convention every other handler in that file already uses, and the
  ASSUMPTION — not verified in this change — is that Mission Control's ack
  handler reads it as a finished refusal rather than re-leasing toward
  `dead_letter`. The ack endpoint lives in the jobs worker, not this repo, so
  nobody here read it. OWED: check `/api/commands/{id}/ack` console-side and,
  if it needs an explicit field, add one — a one-line change to the ack `jq`
  plus the console.
- **The kill flag.** `PR_MERGE_REST=0` in `env/global.env`, or
  `flags/pr-merge-rest-off`, makes the ladder answer rc 2 with zero REST calls,
  which puts every lane back on the `gh pr merge` line it ran before this — the
  same operator-flag shape as `PR_CREATE_REST_FALLBACK`.
- **Budget.** One PUT per merge (plus one GET and one DELETE when a branch delete
  is asked for) replaces one GraphQL mutation. Against roughly 20 merges a day
  fleet-wide that is nowhere near REST's 5000/h core limit.

**Not in this change.** `bin/run-build.sh`'s tier-1 gate merge and
`bin/review-prs.sh` also call `gh pr merge`; both are outside the four sites the
ticket enumerates and `run-build.sh` was live in a sibling PR. They die on the
same empty GraphQL bucket, so a follow-up ticket for those two is owed. PR
creation (BH-848) and the reconcile pass (BH-866) are out of scope by the ticket.
