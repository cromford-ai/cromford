# The hub handler for hold_ticket / unhold_ticket (BH-3147, BH-2326.1)

Doc: DB-COORDINATION-SPEC

## What changed

- New `bin/lib/ticket-hold-cmd.sh`, `thc_run <hold|unhold> <project> <payload>`.
  It prints one result line and returns rc 0 (OK), 1 (failed, retryable) or
  3 (refused, the line starts `refused:`).
- `bin/poll-commands.sh` sources it (guarded) and runs it from a new arm,
  `# >>> ticket hold handler`. Before this the hub answered
  `unknown command type hold_ticket`. A refusal acks with `outcome:"refused"`
  (BH-932) so the console does not re-lease it.

## What it does

1. Refuses anything but a GitHub-issues board in fleet.conf (column 4 `-`),
   and any ticket that is not `PREFIX-<n>` with `n` from 1 up. A fleet.conf it
   cannot read is rc 1, never a refusal (BH-2009).
2. Arms the App token for the repo (`gh_auth_for`), reads the issue over REST,
   refuses a PR or a closed issue. Any failed read, 403 and 429 included, is
   rc 1.
3. HOLD adds the `hold` label; UNHOLD deletes it (a 404 means it was already
   gone). A failed label write is rc 1 and nothing else happens.
4. When the label changed, posts one comment, but only as the App (`ghs_`
   token). On a box that cannot mint one the comment is skipped and the result
   says so: a PAT comment reads as a human comment to `hold_classify`, and
   "Hold lifted ..." would lift someone's earlier HOLD comment.
5. Re-reads through `hold_check` and writes the ledger row the cards read:
   `ledgers(kind=ticket_hold, key=<project>#<n>)`, status `held`, `clear` or
   `unknown` (UNHOLD whose re-read failed), detail
   `<verb> by <actor> at <iso>: <reason> | <why>`. A failed comment or ledger
   write keeps the command OK and is named in the result.

`bin/lib/hold.sh` is unchanged. No lock, cron line, lanes entry or settings
row. The command is not forwarded to the project's box.
