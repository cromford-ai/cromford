# Alert-triage settlement contract: hooks, table and knobs (BH-2544.0, BH-2568)

Doc: ALERTS-STATE-MACHINE

## What changed

This is the contract slice of BH-2544. It changes no behaviour. Every new
function is a stub, and a tick does what it did before, plus three `mktemp`
files it creates and removes in the same block.

- **`worker/jobs/schema.sql`** adds table `alert_family_scripts` (id, match_kind,
  match, verify, on_clear, on_repro, enabled, priority, note, actor, updated_at),
  and index `idx_alert_family_scripts_enabled_priority` on `(enabled, priority)`.
  No rows go into the table here, and nothing reads it yet. No settings row is
  seeded for `TRIAGE_RUNNERS` either (the operator, 2026-09-28): the runner-allowlist
  sibling that reads the knob sets its value.
- **`catalog/lanes.d/alert-triage.json`** registers four knobs:
  `TRIAGE_VERIFY_TIMEOUT_S` (20, 1-120), `TRIAGE_VERIFY_MAX` (20, 0-200, 0 = off),
  `TRIAGE_VERIFY_DEADLINE_S` (120, 10-600) and `TRIAGE_RUNNERS` (string, empty).
  None of them is read at runtime yet.
- **`bin/lib/triage-close.sh`** (new) holds `triage_close_ids <reason> <idsfile>`
  and `triage_settled_ids <settledfile> <idsout>`. Both return 0 and write
  nothing. The header is the contract the closing sibling implements.
- **`bin/triage-family-scripts.sh`** (new) takes `<filtered> <settled>
  <removed-fams-out>` and exits 0 without touching them. Any other arg count
  exits 64. Its header is THE PROTOCOL for registry rows and verify scripts.
- **`bin/alert-triage.sh`** gets four hook points:
  - (a) STEP 0 passes `TRIAGE_RETIRE_IDS_OUT=<tmp>` to
    `bin/triage-spool-retire.sh` (which ignores it for now), then calls
    `triage_close_ids step0` after the STEP 0 log lines.
  - (b) between FIX-PR ANSWERED and DETERMINISTIC SETTLEMENT it runs the registry
    pass. A non-zero rc writes one `family registry rc=N` line to the lane log
    and the tick goes on.
  - (d) right after (b), every family key the pass wrote to `<removed-fams-out>`
    goes back to its pre-tick stamp through `triage_restore_stamp`. That point
    comes before both later exits, so the empty-FILTERED exit is covered.
    `triage_restore_stamp` moved up, unchanged, to just after
    `PRESTAMP=$(mktemp)`, so it exists before this first caller.
  - (c) after the settlement log block, `triage_settled_ids` then
    `triage_close_ids settle`. The NOISE-STALE lines are always written first.
  - The lib is sourced fail-open, the same way as `cost-row.sh` and
    `lane-caps.sh`, with no-op fallbacks. The ticket asked for `|| exit 1`.
    That would have turned the seven existing suites that copy the lane into a
    scratch tree without the lib red, and the ticket also asks for those suites
    to stay green unchanged.

## Kill switches (settings row first, then the file; no deploy)

Both are registered in `catalog/switches.d/` and read through `lane_switch`
(BH-2320): the settings row `switch.<name>.<box>`, then `switch.<name>`, decides
when one exists; with no row, `flags/<name>` does. Without the lane-switch lib
the file alone decides.

- `triage-registry-off` skips the registry pass (b). Nothing is written
  to `<removed-fams-out>`, so (d) restores nothing.
- `triage-close-off` skips both close calls, step0 (a) and settle (c).

## Not in this slice

The registry client `alert_family_scripts` in `bin/lib/jobs/alerts.sh`, the ids
written by `bin/triage-spool-retire.sh`, any `bin/alert-verify/*.sh`, the real
close and extract functions, and the `TRIAGE_RUNNERS` read all belong to the
BH-2544 siblings.

## Test

`tests/alert-triage-hooks.bh-2544-test.sh` drives the real lane in a scratch
harness with recording fakes. It covers the hooks and flags, the restore on the
empty-FILTERED exit, the real stubs as no-ops (the tick with both hooks switched
off gives the same result), the schema, and the knobs.
