# Roadmap wave approve, file and issue sync (BH-7243.4, BH-7267)

Doc: CONSOLE, worker/jobs/README.md

Slice 5 of 5 of #7243. A person approves a drafted roadmap wave in the console. A hub
lane files each slice of the draft as an `ai-build` GitHub issue and links the issue to
the wave's ideas. A second hub lane keeps the state of each linked issue current, so the
board (BH-7243.2) can show filed ideas in Now and closed ones in Shipped. No table is
added: the tables and indexes are in the BH-7243.0 contract fragment.

## Status flow

`draft` → approve → `approved` → file-claim → `filing` → file-done filed → `filed`.
`draft` → reject → `rejected` (the reason is stored in `error` as `rejected: <reason>`).
A failed slice sends `filing` back to `approved` with the error in `error`. The claim
takes that wave again after `roadmap.file_retry_min` (30 min). A `filing` wave whose lane
died is also claimed again after that window. Every move is a CAS on `status`.

The filing lane never reads a wave in `requested`, `shaping`, `draft`, `empty`, `failed`,
`rejected` or `filed`.

## The approve gate

`POST /api/roadmap/waves/approve` and `/reject` answer 403 when the actor is blank,
`archie` (any case), a `staff_agents` name, or `console` while
`roadmap.approve_requires_identity` is 1. The default is 0, because the console session
stamps `console` today. The console can write approve and reject only. File-claim,
filed, file-done and links/state have no row in `coord-writes.d`, so a browser gets 405.

## Filing (bin/roadmap-file.sh, hub, every 5 min)

1. `POST file-claim {box}` takes one wave. At most `ROADMAP_FILE_MAX_PER_TICK` (3) per tick.
2. A project with a `board_api_prefix` (an in-app board) is not filed: the wave goes back
   to `approved` with `board not GitHub Issues`, and one warn alert
   `roadmap-file:<wave_id>` is sent.
3. For each slice k, one search for the body marker
   `<!-- harness-roadmap-slice: <wave_id>/<k> -->`. A hit is reused. Otherwise one
   `POST repos/<repo>/issues` with label `ai-build`, the slice text, the acceptance
   tests, spec refs, files, seam files, one `Blocked-by: #<n>` per earlier slice in
   `blocked_by`, `Part of roadmap wave <id>`, and the marker as the last line.
4. `POST filed` writes one `roadmap_links` row per idea of the wave. The primary key
   `(idea_id, repo, issue)` makes a replay write nothing.
5. `POST file-done filed` sets `filed` only when the wave's links name as many distinct
   issues as the draft has slices. A failed search or create sends the wave back to
   `approved` with `slice k: http <status>` and one warn alert. A rate limit also ends
   the tick. The lane writes no freeze flag.

`--dry-run` claims nothing, writes nothing and prints each issue it would create.

## Sync (bin/roadmap-issue-sync.sh, hub, every 15 min)

`GET /api/roadmap/links/stale` answers the links never read, then the oldest read, that
are older than `roadmap.issue_sync_stale_min` (30 min), at most `roadmap.issue_sync_batch`
(50). The lane makes one REST GET per issue and maps it: `open` → `open`, closed with
`state_reason=completed` → `closed_completed`, any other close → `closed_other`. Then
`PUT /api/roadmap/links/state`. A 410 (a deleted issue) is `closed_other`. A 404 or an
unknown state writes no `issue_state` and counts as failed. A rate limit or another
unverifiable answer stops the run. Every failed read except a rate limit sends
`{tried:true}`, which stamps `state_seen_at` and keeps `issue_state`. The link goes to
the back of the stale queue, so one dead issue never blocks the other links. The lane makes no model call. Both lanes
route `gh` through `bin/gh-rest-shim` when that file is executable.

## Knobs

| Knob | Default | Where |
|---|---|---|
| `roadmap.issue_sync_batch` | 50 (1..200) | settings row |
| `roadmap.issue_sync_stale_min` | 30 (1..10080) | settings row |
| `roadmap.approve_requires_identity` | 0 (0/1) | settings row |
| `roadmap.file_retry_min` | 30 (1..1440) | settings row |
| `ROADMAP_FILE_MAX_PER_TICK` | 3 (1..20) | catalog/lanes.d/roadmap-file.json |

## Off switches

`flags/lane-off-roadmap-file` or `bin/harness-ctl.sh off roadmap-file`;
`flags/lane-off-roadmap-issue-sync` or `bin/harness-ctl.sh off roadmap-issue-sync`.

## Indexes and retention

Each query and its index: approve, reject and file-done by the `roadmap_waves` primary
key; the claim read on `idx_roadmap_waves_status`; filed on the `roadmap_links` primary
key; waves/issues and the file-done count on `idx_roadmap_links_wave`; links/stale on
`idx_roadmap_links_state_seen`; links/state on `idx_roadmap_links_repo_issue`.
worker/jobs/test/routes/roadmap-wave-file.bh-7243.test.js (W11) runs EXPLAIN QUERY PLAN
on 5,000 links and 500 waves. No new table, so no new retention rule:
`roadmap_links` keeps forever by the contract's rule, and rejected waves fall under
`roadmap_waves.closed`.
