# A per-batch CI cost ledger: one row per merge-queue batch run (BH-4971, C3 of BH-4964)

Doc: MERGIFY, COST

## What changed

- `worker/jobs/schema.sql` gains the `ci_batches` table (natural key `run_id`)
  and `idx_ci_batches_repo_completed`. Both are additive `CREATE … IF NOT EXISTS`.
- `worker/jobs/src/routes/ci-batches.js` adds `PUT /api/ci-batches` (an upsert on
  `run_id`) and `GET /api/ci-batches?repo=&since=&limit=`. Both run inside
  `d1Guarded("ci_batches")`.
- `bin/ci-batch-ledger.sh` is a new hub lane, cron `11,41 * * * *`
  (`cron/lanes/726-ci-batch-ledger.cron`, `catalog/lanes.d/ci-batch-ledger.json`).

## What a row records

Each row covers one completed `harness-ci.yml` run whose `head_branch` starts
with `mergify/merge-queue/`:

| column | from |
|---|---|
| `run_id`, `head_ref`, `head_sha`, `conclusion`, `run_attempt` | the run, at the latest attempt the lane read |
| `started_at`, `completed_at`, `wall_s` | the run's `run_started_at` and `updated_at`, and the gap between them in seconds. GitHub moves `run_started_at` to each attempt's start, so on a re-run these are the latest attempt's |
| `mode`, `selected`, `total` | the plan job's `ci-plan` notice from bin/ci-plan.sh (BH-4968): `mode=`, `count=`, `total=` |
| `escalation` | the notice's `reason=` with its `full: ` prefix and any `; tiers: …` note stripped, when `mode=full`. NULL otherwise |
| `billed_min` | the sum of `ceil((completed_at - started_at) / 60)` over the run's jobs of EVERY attempt whose labels or runner name contain `CI_MINUTES_RUNNER_MATCH` (default `monkci`) |
| `as_of` | when the worker took the PUT |

**The billing rule** is bin/ci-minutes-watch.sh's per-job rounding without
its `CI_MINUTES_BILL_MULT`. The row stores rounded job-minutes, so to get
vendor minutes, multiply by the bill rate (MonkCI's 4-vCPU runner bills 2x).
Jobs are read with `filter=all`, so a re-run's earlier attempts, which were
billed too, are counted (GitHub's default `filter=latest` would drop them).
They are read 100 a page, up to `CI_BATCH_LEDGER_PAGES` pages. If the run has
more jobs than that, the run is `unread` rather than recorded with a partial sum.

**`full-legacy`** means the run has no `ci-plan` notice: either there is no
plan job, or none of its annotations is titled `ci-plan`. These are runs from
before BH-4968. Their `selected` and `total` are both NULL, because the run
never said how big the corpus was and the lane does not guess. A notice
under any other title is not parsed.

**A re-run attempt** of a recorded run_id is read again. The skip-set keeps
each row's `run_attempt`, and a run whose GitHub `run_attempt` is past it is
not skipped. The row is overwritten: `conclusion`, `run_attempt` and the
timing become the latest attempt's, and `billed_min` covers every attempt.
The ledger keeps one row per run_id. A re-run older than `CI_BATCH_LEDGER_DAYS`
is outside the window and is not re-read.

## When the lane records nothing

- If JOBS_URL or HARNESS_SECRET is unset, it logs `not configured` and makes no GitHub read.
- If the GitHub bucket is low (bin/lib/gh-budget.sh), it logs the skip and makes no read.
- If the ledger GET fails, for example `ci_batches schema not applied`, it logs
  `ledger unreadable (http=…)` and makes no GitHub read. That GET is the skip-set, and it runs before any GitHub read.
  A truncated skip-set (over 5000 rows in the window) also stops the tick.
- If a run's jobs or plan annotations read fails, that run is `unread`. It is
  not recorded, and the next tick retries it. A failed annotations read is never written as `full-legacy`.
- If a PUT fails, it logs `PUT failed run <id>`. No row is written, so the next tick's skip-set retries it.
- Past `CI_BATCH_LEDGER_MAX` runs, the rest are logged as `deferred <n> to next tick`. Runs drain oldest first.
- If every one of `CI_BATCH_LEDGER_PAGES` pages came back full, the log says `window not fully read`.
  An unrecorded run older than `CI_BATCH_LEDGER_DAYS` falls out of the window.

Each tick ends with one line:
`repo=<r> queue_runs=<n> already=<n> recorded=<n> put_failed=<n> unread=<n> deferred=<n>`.

## Schema apply

`ci_batches` and its index ride `worker/jobs/schema.sql`. bin/harness-sync.sh
applies that file statement by statement before `wrangler deploy`, and skips
the deploy if a statement fails. Until it has run, both routes answer 503
`ci_batches schema not applied`, and the lane records nothing.

## Reading the before/after median

```bash
curl -s -H "authorization: Bearer $HARNESS_SECRET" \
  "$JOBS_URL/api/ci-batches?repo=example-org/cromford&since=2026-09-30&limit=5000" \
  | jq '.truncated, (.rows | group_by(.mode == "full-legacy")
        | map({legacy: (.[0].mode == "full-legacy"), n: length,
               median_billed_min: (map(.billed_min) | sort | .[length / 2 | floor])}))'
```

`truncated: true` means the window held more rows than `limit`, so narrow
`since` before trusting the median.
