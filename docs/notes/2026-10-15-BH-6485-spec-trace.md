# Spec trace: plans and reviews check a slice against the spec it came from (BH-6485)

Doc: PLAN-CONTRACT, READINESS

## Why

project-6-os merged its launch cut line with green CI and approving reviews. A
PRD audit then found 29 missing and 3 contradicting requirements out of 98
(example-org/project-6 `docs/plan/PRD_TRACEABILITY_AUDIT_2026-10-13.html`). Every
stage judged a slice against its own ticket text. No stage read the spec the
ticket came from.

## What changed

A ticket body can now name its spec. Every check below is keyed on these lines,
and a body without them changes nothing: no prompt text, no gate, no row.

| Line | Meaning |
|---|---|
| `Spec: <path>#<section>` | A spec section the slice must deliver. With no `#section`, the whole file, keyed by its path. |
| `Reference: <path>` | A reference screenshot the UI must match. |
| `Cut: <section or requirement id>` | A part the slice does not deliver. |

The grammar is the one of `Spec-repo:` (bin/lib/spec-repos.sh): the key at the
start of a line, optionally after a `- ` bullet and one backtick; values split on
commas; fenced lines and comments never count; at most 20 values per key. A
`Spec:` value must be a path with a `/` or a `.` and no spaces, so a sentence
such as `Spec: the plan this build executed is in this PR at …` is not a spec.

1. **Plan.** The planner is told the rule through `UI_PLAN_NOTE`
   (`st_plan_note`). `bin/plan-gate.sh` with `PLAN_GATE_TICKET` (set by
   `PG_RUN`) refuses a plan with no `## Spec trace` line
   `S<section>: <requirement> → <task / file>` per named section, or with a
   Reference path missing from `## QA screens`: `UNTRACED: spec trace — …`,
   `PLAN_SPEC_TRACE: missing`, rc 2. The repair pass gets `st_repair_note`; a
   second refusal is PLAN_MALFORMED, and its reason names the spec trace.
2. **Review.** The general lens gets each named section verbatim in its gates
   note (`st_review_note`, capped per section and in total) and writes one row
   per requirement: `SPEC-TRACE: <section> | <requirement> | <status> |
   <file:line or ->`. `LENS_APPROVED review` runs `st_enforce` first. It acts
   only on an APPROVE, judges only the latest pass's rows, and appends
   `SPEC-TRACE-GATE: BLOCK — <reasons> (cut-exempt=<n>)` and `VERDICT: BLOCK`
   when a section has no row, cannot be read, or has a `missing`, `contradicts`
   or `cut` row that no `Cut:` token names (the token equals the section, or is
   a whole word in the requirement: `SET-4` never exempts `SET-40`). With
   exemptions only, it appends `SPEC-TRACE-GATE: ok (cut-exempt=<n>)` and
   restates `VERDICT: APPROVE`. The merged re-review prompt asks for the rows
   again (`st_rereview_note`).
3. **UI evidence.** With `Reference:` lines, the preview QA prompt asks for
   `qa-shots/ref/<slug>-<light|dark>-<1440|390>.png` (`st_qa_note`).
   `bin/reference-shots.sh publish` pushes a complete set as one orphan commit
   to `harness-shots/<key>-<yyyymmdd>` (the PR branch never moves), checks the
   ref with `git ls-remote`, and only then writes `$BUILD/reference-shots.md`
   with images. An incomplete set writes `Missing: …`, a failed push
   `Could not publish: …`, and neither has image markup. `bin/evidence-summary.sh`
   prints the file into the PR body. The self-check row `body-reference-shots`
   (trigger `spec-ref`: Reference lines and a UI diff file) refuses a body
   without a preview and a reference image under `## Reference screenshots`. At
   PR open (`PSC_PHASE=open`) it is a note, because the shots come after QA.
4. **Readiness.** `bin/readiness-report.sh` adds the report-only check
   `spec.trace` (category `spec`): `na` with no `design/` or `spec/` folder,
   `skipped` with `READINESS_GH=0`, `unknown` when gh cannot read the issues,
   `fail` with `WARN: <n> of <m> open ai-build issues carry no Spec: line: #…`.
   No level names it, so `.level` does not move.

## Formats: who writes, who reads

| Format | Writer | Reader |
|---|---|---|
| ticket `Spec:` / `Reference:` / `Cut:` lines | a person | `st_parse` only (plan gate, review, QA, self-check, readiness, replay) |
| plan `## Spec trace` | the planner | `st_plan_check` |
| `SPEC-TRACE:` rows | the general reviewer | `st_judge` (`st_enforce`, the replay) |
| `SPEC-TRACE-GATE:` line | `st_enforce` | `st_judge` (idempotency), the fix round |
| `$BUILD/reference-shots.md` | `bin/reference-shots.sh publish` | `bin/evidence-summary.sh`, then the self-check row |
| `harness-shots/<key>-<date>` refs | `publish` | the PR page images; `prune` |

## Knobs

`catalog/lanes.d/_lib.spec-trace.json` (id `spec-trace`), read by `st_conf`:

| Knob | Default | What it does |
|---|---|---|
| `SPEC_TRACE_ENFORCE` | 1 | 0: the plan refusal and the review BLOCK become log lines. |
| `SPEC_TRACE_SECTION_MAX_BYTES` | 12000 | Cap on one verbatim section; the cut says `[truncated at N bytes]`. |
| `SPEC_TRACE_TOTAL_MAX_BYTES` | 40000 | Cap on all sections in one note; the rest are named `NOT INCLUDED`. |
| `REFERENCE_SHOTS_KEEP_DAYS` | 30 | A `harness-shots/*` ref older than this is a prune candidate. |
| `REFERENCE_SHOTS_PRUNE` | dry | dry logs the candidates; on deletes them; off does nothing. |
| `REFERENCE_SHOTS_PRUNE_MAX` | 20 | Deletes per run when on. |

Retention: the shot refs are the only growing thing. `prune` runs at the start
of every `publish`, dry first, with one audit line per run in
`logs/reference-shots.log`. The `body-reference-shots` row's mode in
`catalog/pr-self-check.d/bh-6485-reference-shots.tsv` (`refuse` → `note`) is
its switch; `SPEC_TRACE_ENFORCE` does not cover it.

## The metric: replay over the project-6-os cut line

`bin/spec-lens-replay.sh <manifest> <project-6-clone> <out-dir> [--run] [--max N]`
replays the review lens over merged PRs, with the spec lines their tickets
should have carried. It checks its ledger (`<out>/ledger.tsv`, keyed on the
input fingerprint) before every paid call, and `summary <out-dir>` prints the
rows by status, the BLOCK count and the cut exemptions.

uses the env of its caller. A Claude execute session removes
