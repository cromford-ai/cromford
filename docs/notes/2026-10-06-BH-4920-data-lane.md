# The data lane proves its apply: probe, evidence file, evidence comment (BH-4925)

Doc: LANES, migration-ledger, MIGRATION_ENDPOINT_SPEC

The second slice of BH-4920. The first (BH-4923, see
`2026-10-06-BH-4923-data-lane-contract.md`) applies the one migration a BLOCK
review named, ahead of merge. This slice makes `bin/data-lane-apply.sh` prove
that apply with a read-only probe before anything can release the PR, and
leaves the two artifacts the resolver (BH-4926) reads: the ledger row and the
probe file. `docs/MIGRATION_ENDPOINT_SPEC.html` is the contract the app's
internal endpoints implement; the two body shapes below are what this lane
sends and accepts.

## What changed in `bin/data-lane-apply.sh`

- **Targets gate, before any POST.** After the classifier passes, the lane
  builds one SQL string per statement from the migration at the PR head (`--`
  comments stripped, matched case-insensitively):
  - `ALTER TABLE [IF EXISTS] <t> ADD [COLUMN] [IF NOT EXISTS] <c>` →
    `SELECT "<c>" FROM "<t>" LIMIT 0`
  - `CREATE TABLE [IF NOT EXISTS] <t>` → `SELECT 1 FROM "<t>" LIMIT 0`
  - `CREATE [UNIQUE] INDEX [CONCURRENTLY] [IF NOT EXISTS] <i> ON [ONLY] <t>` →
    `SELECT 1 FROM "<t>" LIMIT 0`

  An identifier is `[A-Za-z_][A-Za-z0-9_]*`, bare or in `"` or backticks, and is
  re-quoted with `"`. A schema prefix (`public."x"`), an unnamed index, `ADD
  CONSTRAINT`, or any ALTER TABLE / CREATE TABLE / CREATE INDEX / ADD the
  patterns do not match means the file has no complete probe target set:
  `not-candidate`, rc 3, before the configured gate, the ledger read and any
  POST. What cannot be proven is never applied ahead of merge. Targets are
  deduped in order.
- **Probe.** After the apply answers `applied` or `already-applied`, ONE POST to
  `<DATA_LANE_APP_BASE>/api/internal/migrations/probe` with the same 0600
  header file as the apply, `-m 60`. Success is curl rc 0, HTTP 2xx, `.ok ==
  true`, and every target sent present in `.results[]` with that exact
  `.target` and `.ok == true`. Anything else is a miss.
- **Miss.** Ledger `failed probe PR#<n> head=<sha12> fp=<FP>` FIRST, then one
  `lane-alert.sh --id data-lane:<project>:<file>:<FP>`, the job parked, no
  probe file, no comment, `failed` rc 1. No retry: the next run meets that row
  at the ledger gate and returns rc 3 with no POST.
- **Ledger order.** The success row (`applied`/`already-applied … fp=<FP>`) is
  now written after the probe passes, so a fresh run's calls go `apply probe
  ledger comment`.
- **Ledger short-circuit.** A ledger that already says applied at this FP no
  longer exits 0 at once: when `<build-dir>/data-lane-probe.md` has no exact
  `fp=<FP>` line, the lane probes (no apply POST, no ledger rewrite) and writes
  the file; then it goes to the comment step.
- **Evidence file** `<build-dir>/data-lane-probe.md` (`dl_probe_file`), written
  through a temp file and `mv`: the lines `project=`, `pr=`, `head=<40-hex>`,
  `fp=<FP>`, the statements in a fenced block, `## Apply response` (the first
  2000 bytes, or `ledger: <status>` on the short-circuit), and `## Probe rows`
  (`- ok  <target>` per target). No token and no env value.
- **Evidence comment.** The lane lists `issues/<pr>/comments` (100 a page, at
  most 10 pages). If any body contains `<!-- dl-fp:<FP> -->` it posts nothing.
  Otherwise it posts once:

  ```
  DATA-LANE-APPLIED: <file>
  We applied this migration to production ahead of the merge, at head <h12>.
  A read-only probe then found every column and table it adds, so the only blocking finding is answered.

  - ok  SELECT ...
  <!-- dl-fp:<FP> -->
  ```

  A listing that fails or is not a JSON array, 10 full pages, or a failed POST
  is logged only, with no alert and no ledger change, and the run answers the
  new outcome word `comment-pending` with rc 75 so the caller re-offers it. The
  next run takes the ledger short-circuit and the existing probe file straight
  back to the comment step.
- One `data-lane:` log line per successful run, now ending `probed, evidence
  comment posted` or `probed, evidence comment already posted`.

## The two bodies the app endpoint must implement

Pre-merge apply, `POST /api/internal/migrations/apply` (unchanged from BH-4923):

- request `{mode:"pre-merge", repo, pr, head_sha, file, statements, actor:"archie-data-lane"}`
- answer `{ok:true, status:"applied"|"already-applied"}`. Any other answer is a failure.

Probe, `POST /api/internal/migrations/probe`:

- request `{file, head_sha, targets:["SELECT … LIMIT 0", …]}`
- the server must refuse any target that is not a `SELECT … LIMIT 0` and run the
  rest read-only
- answer `{ok:bool, results:[{target, ok, error?}]}`, one result per target,
  keyed by the exact target string it was sent. A result for a target the lane
  did not send is ignored.
