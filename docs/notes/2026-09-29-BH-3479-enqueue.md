# Lead review auto-request: the hub trigger lane (BH-3479.1, BH-3545)

Doc: MERGE-CONDUCTOR

## What changed

A new hub lane, `bin/lead-review-enqueue.sh tick`, runs every 5 minutes from
`cron/lanes/713-lead-review-enqueue.cron` behind `bin/hub-lease.sh check`. For
every open, non-draft harness PR in `LEAD_REVIEW_AUTO_REPOS`, it asks for ONE
lead review (`POST /api/lead-reviews` with the lead token) when all of these hold:

- a builder APPROVE is bound to the PR's live head (`job_verdict` field 6
  equals the head read from `gh_rest GET pulls/<n>`, or
  `job_verdict_headbound` is `reapproved@<head>`);
- no lead or human verdict stands on that head (`vd_standing` rc 1);
- no non-merge commit in `<base>...<head>` has a line starting `Lead-Lane:`;
- the per-tick cap and the per-PR 24h tripwire allow it.

It makes no model call and no SSH call. The review itself stays in the box
lane `bin/lead-review.sh` (BH-1950), which claims `requested` rows, and
`bin/lead-review-land.sh` still promotes the answer.

Any read that fails (the PR list, the live head, the standing verdict, the
compare, or a compare that lists fewer commits than `total_commits`) is
counted `unreadable` and nothing is requested for that PR this tick.

## Decisions

- **D1. A head already asked for is POSTed again.** The ledger
  `state/lead-review-enqueue/requested.tsv` (`<epoch> <slug> <n> <head> <id>`,
  tab-separated, pruned to 7 days) records each 201. A recorded head is
  re-POSTed with the same notes; the worker answers `existing:true` and nothing
  is spent. Those re-confirms skip the cap, the tripwire and the compare. A
  201 on a recorded head means a second review was bought, and it pages
  critical once (`lead-repeat-<slug>-<n>-<sha12>`).
- **D2. `lr_post_lead`, not `bin/lead-verdict.sh request`.** The ticket names
  the CLI, but its output flattens a 201 and an `existing:true` answer into the
  same line, and the lane needs to tell them apart. The lane sends the same
  body to the same route with the same token file. The self-commit alert still
  names `bin/lead-verdict.sh request` as the command to ask by hand.
- **D3. Unset or garbage knobs stop the tick.** Both knobs are
  `required: true` with no literal in the script. Empty or not a positive
  integer = one log line and no request.
- **D4. `vd_standing` rc 1 also covers "the verdicts route is not deployed"**,
  which is the lib's own contract.
- **Alerts go through `bin/lane-alert.sh`**, never a raw ALERTS.log append
  (`tests/alert-writers-ratchet.bh-2314-test.sh`). Each is also deduped by a
  `state/lead-review-enqueue/alerted-<id>` marker written after the call
  returns. That includes the missing-token alert (`lead-enqueue-no-token-<UTC day>`).
- The trailer scan compares against the PR's own base, not main, so a
  stacked PR sees only its own commits.

## Knobs

| knob | lane | default / bounds |
|---|---|---|
| `LEAD_REVIEW_ENQUEUE_MAX_PER_TICK` | `lead-review-enqueue` | 5, 1-50 new requests a tick; the rest are deferred to the next tick |
| `LEAD_REVIEW_MAX_PER_PR_DAY` | `lead-review-enqueue` | 4, 1-50 requests per PR in 24h; over it = `tripped` and one warn per PR per UTC day (`lead-trip-<slug>-<n>-<day>`) |
| `LEAD_REVIEW_AUTO_REPOS` | `lead-review-land` (read here through its `lane_env_apply`, not re-registered) | env only; empty = nothing is requested |

## Switch it off

`bin/harness-ctl.sh off lead-review-enqueue` (flag
`flags/lane-off-lead-review-enqueue`). Or empty `LEAD_REVIEW_AUTO_REPOS` in
`env/global.env`; that knob is shared with the other BH-3479 readers.
