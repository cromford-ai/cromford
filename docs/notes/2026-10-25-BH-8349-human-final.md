# A human verdict on a head is final for that head (BH-8349)

Doc: MERGE-CONDUCTOR

A person posted a human MERGE on a head. A reset lead review of the same head
then landed a lead BLOCK over it (`re-landing: newer result job ... replaces
lead row #4040`). `GET /api/verdicts&head=` ordered the standing rows by id
only, so the newer lead BLOCK stood, and every `vd_standing` reader stopped the
merge.

## The rule

- `POST /api/verdicts` with `source=lead` on a head whose newest `source=human`
  row is final writes the row as advice. The note gets the token
  `human-final:#<id>`. The worker records no PR-gate lead-verdict fact for it.
  The answer carries `human_final: {id, verdict}` (`null` on every other post).
- A human row is final when it would stand today. A human BLOCK is always
  final. A human MERGE / MERGE-WITH-NOTES is final when it is proven, or when
  `human_verdict_sig_mode` is not `enforce`. An unreadable sig mode is not
  final. Under `human_verdict_mode=enforce` a row with `auth='lead-token'` is
  not final.
- `GET /api/verdicts&head=` answers the final human row as `standing` over any
  newer row. With no final human row the answer is the same as before.
- A new head has no human row, so a push resets the rule.
- If `human_verdict_mode` cannot be read and a `source=human` row is on the
  head, a lead post is 503 and nothing is written (the BH-3849 rule).

## The client and the land lane

- `bin/lead-verdict.sh post --source lead` exits 5 when the answer carries
  `human_final`. It prints `status withheld on <sha12>: human verdict #<id>
  (<word>) is final on this head; this lead row is advice` and publishes no
  status.
- `bin/lead-review-land.sh` logs `recorded as advice; human verdict #<id> is
  final on this head, status not changed` and stamps the request. It posts no
  findings review, dismisses nothing, asks no human and rings no conductor.
- A reset result (its earlier landing is lead row #S) is not re-landed when the
  head carries a newer row of any source that no landing of the request wrote.
  The lane logs `re-landing skipped: row #N on this head is newer than lead row
  #S; nothing posted` and stamps the request.

## The gate-record mode

`lr_gate_record_mode` (`bin/lib/lead-review/gate-record.sh`) reads
`lane_knob lead-review LEAD_REVIEW_GATE_RECORD` at the call. The settings
cache TTL is `LANE_GATE_CACHE_S`. A row set after the tick started applies to
the review that runs. The env value is the fallback when `lane_knob` is not
loaded.

## Rollout

The client reads `human_final` from the worker answer. An old worker answers
without it, and the client behaves as before. `bin/harness-sync.sh` deploys
the worker on merge. No schema change and no new knob.
