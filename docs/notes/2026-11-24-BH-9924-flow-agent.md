# BH-9924 (slice BH-9956): the flow agent tracer and its contract

Doc: PROJECT-LANES, DB-COORDINATION-SPEC

## Why

The fleet measures pool under-use (`bin/lib/pool-underuse.sh` writes the
"under-used for Nm" line) and nothing acts on it. The flow agent finds why
ready work waits. It gives each waiting ticket a cause code and runs one fixed
action per code. This slice is the thinnest end-to-end path. The siblings
#9957 (BH-9924.1) and #9958 (BH-9924.2) fill its seams.

The agent never merges, publishes, changes a ticket's scope or deletes a
dependency edge. In this slice its only writes are `flow_actions` and
`flow_waiting` rows.

## The contract

### Return codes

- A rule `flow_rule_<code> <record-file>`: 0 match, 1 no match, 2 an input it needs is unread.
- An arm `flow_arm_<code> <record-file>`: 0 done, 1 failed, 3 refused. Its stdout is the detail. It may set `FLOW_ARM_AFTER` to the state string after its action.
- A collector `flow_collect_<area> <records-file>`: it edits the file in place. A non-0 rc adds `<area>` to `unread` on every record.
- The `fa_*` client: 0 = 2xx, 9 = 409, 2 = 404, 1 = outage. A failed read prints nothing, never `0`.
  - `fa_claim` gives 0, 9 or 1.
  - `fa_record` gives 0, 9, 2 or 1.
  - `fa_count24h` prints the count only on rc 0.
  - `fa_mode` prints `act` or `log`. No row or a junk value prints `log`. An outage prints nothing and gives rc 1.
  - `fa_nudge` gives 0 (inserted), 9 (already nudged) or 1. Its dedupe is `flow:<key lowercased>:<sha256(episode) first 12>`.
- `flow_collect <p>`: rc 1 with no output when the board read or the D1 state
  read fails. `FA_COLLECT_WHY` names the read. `FA_TRUNCATED` counts the open
  tickets past `flow_agent.waiting_max`.
- `flow_cause < record` prints the first matching code of `FLOW_CODES`. With no match it prints:
  - `inputs_unreadable` when a rule gave rc 2.
  - `not_stalled` when the ticket is in normal flow.
  - `unknown` in all other cases.
- `flow_act <record-file> <code>` prints one outcome word: `done`, `failed`, `refused`, `would`, `already`, `could-not-claim`, `held` or `no-arm`.

`rules/ready_not_queued.sh` is the only real rule. It matches when every one of these is true:
- The verdict is current, and it is `ready` or `buildable`.
- There is no queue row and no live job.
- There is no open PR.
- The verdict is at least `flow_agent.stall_min` minutes old. The fallback is `FLOW_AGENT_STALL_MIN`, then 20.

### The record (one JSON line per open ticket)

`{project, key, id, repo, title, url, verdict, verdict_current, waiting_on,
triaged_at, queue:{status,enqueued_at,finished_at}|null, live_job:false,
parked, open_pr:{number,head}|null, pr_truncated:0|1, edges:[{parent,kind}],
unread:[...], episode, updated_at, now}`

A ticket with a live running job gets no record. A ticket that waits on the
client or the requester gets no record. `episode` is the `triaged_at` of a
current verdict, else the board's `updated_at`. A PR belongs to KEY when its
head is `ticket/<key lowercased>` or `ticket/<key lowercased>-r<digits>`.

### The decision key

`sha256(project|KEY|code|episode)` on the act path. In log mode it is
`sha256(project|KEY|code|episode|would)`. Because the would key is a different
key, a later switch to `act` can act on the same episode. A second log pass
gets a 409 and writes no second row.

### The log lines (`logs/flow-agent.log`)

- `<UTC> tick <p> mode=<m> trigger=<t> tickets=<n> codes=<code:n,...> actions=<n> refused=<n> truncated=<n>`
- `<UTC> act <p> <KEY> code=<c> action=<c> outcome=<o> before=<b> after=<a>[ gate=<g>][ note=record-lost:<key12>]`

- `<UTC> board-truncated <p> the open-issue list filled flow_agent.issue_list_pages`: the
  open ai-build issues filled every page the knob allows (seed 5 pages of 100),
  so tickets past that were not read in this pass.

`before` and `after` are `verdict:<v>,queue:<s>,job:<0|1>,pr:<n|none>`.
`actions=` counts the arms that ran after a 200 claim (done, failed and
refused). `refused=` counts the refused ones.

## The switch

1. To stop every project: `bin/harness-ctl.sh` or `PUT /api/settings` with
   `flow_agent.enabled=0`. A missing row also stops the lane.
2. To run one project in act mode: set `flow_agent.project.<p>.mode=act`. A
   project with no row runs `log`, which records only `would` rows. project-3 is
   seeded `act`. Every arm in this slice is a placeholder that records
   `refused not-built`, so act mode has no effect yet.
3. To hold one action: set `flow_agent.action.<code>` to `0`. That code then
   records `would`.
4. The lane gate also applies: `flags/all-off` and `flags/lane-off-flow-agent`.

## Retention

`worker/jobs/schema.d/202611242153-bh-9956-flow-retention-pending.sql`. #9958
