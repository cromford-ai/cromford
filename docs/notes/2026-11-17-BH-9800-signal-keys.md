# Signal keys: per-project Sentry and PostHog keys in an encrypted store (BH-9800, slice C0)

Doc: DB-COORDINATION-SPEC

## What changed

Until now a project's Sentry and PostHog keys lived only as lines in the
project env file on its box, written by hand over ssh. This slice adds the
store and the jobs-worker routes. It adds no screen and no reader. The console
"Signals" page (C1) and the readers and the one-time migration (C2) call
these routes.

- Tables (`worker/jobs/schema.d/202611172248-bh-9800-signal-keys.sql`):
  - `signal_key_kinds`: the kinds catalog, one row per kind. Seeds `sentry`
    (fields `org`, `project`, secret `token` with prefixes `sntryu_`,
    `sntrys_`) and `posthog` (fields `host`, `project_id`, secret `key` with
    prefix `phx_`). `fields_json` holds each field's `name`, `label`,
    `placeholder`, `re` and `secret` flag. `test_template`, `host_field` and
    `host_allow` drive the Test probe. `scope_note` is the line C1 shows.
  - `signal_keys`: one row per `(project, kind)` on `uq_signal_keys_entry`.
    `fields_json` holds the non-secret fields in clear. The secret is an
    AES-GCM `ciphertext` + `iv` with its `key_id`. No column holds a plain
    secret.
  - `signal_key_audit`: one row per set, clear, test, read and hub read, ok or
    refused. Never a value.
- Crypto: the web vault's (`worker/jobs/src/lib/web-vault-crypto.js`), the
  same Worker secrets `WEB_VAULT_KEY_<n>` and the same setting
  `web_vault.key_id`. The AAD is `signal_keys\n<project>\n<kind>`
  (`signalAad`), so a ciphertext copied to another row does not decrypt. A key
  rotation of `web_vault.key_id` now also covers signal keys. An old row keeps
  its own `key_id` until it is set again.
- Vendor seam: `worker/jobs/src/lib/signal-probe.js` is the only file that
  calls Sentry or PostHog. Tests replace `globalThis.fetch`.
- Token mask: `worker/jobs/src/lib/token-mask.js` (`maskTokens`). Every
  console line of the routes and the seam passes through it.
- Lane gate: `worker/jobs/src/lib/signal-lanes.js`. A lane listed in
  `signal_keys.read_lanes` gets the web-task rules: its claim answers
  `vault_token`, and its enqueue (`POST /api/lane-runs`, `/batch`) needs
  `x-web-vault-admin-token`. The seed is empty, so no lane changes until an
  operator lists one.

## Routes

Every route is behind the bearer. OPERATOR is `x-web-vault-admin-token`
(actor `operator`) OR the BH-9262 owner proof: `x-box-ops-token` +
`x-box-ops-identity` of an owner in `BOX_OPS_OWNERS` (actor = that email), or
`x-human-verdict-token` (actor `human-token`). There is no shadow mode:
`owner_proof_mode` is not read, and no proof is 403 with nothing written.

- `POST /api/signal-keys/set {project, kind, fields}` (operator). Each field
  is trimmed (spaces, tabs, line breaks). Each is checked against the kind
  row: `re`, the secret's prefixes, the host on `host_allow`, the secret size
  against `signal_keys.value_max_bytes`. 200
  `{stored, project, kind, fields, updated_at, updated_by, key_id}`. A set
  resets `last_test_*` to NULL.
- `POST /api/signal-keys/clear {project, kind}` (operator). 200 `{cleared}`.
- `GET /api/signal-keys[?project=P]` (bearer, metadata only).
  `{kinds:[{kind, label, fields, scope_note}], rows:[{project, kind, fields,
  secret_set, updated_at, updated_by, last_used_at, last_test_at,
  last_test_status, last_test_result, rotate_by, rotate_overdue}], more,
  rotate_days, as_of}`. No ciphertext, no iv, no secret.
- `POST /api/signal-keys/test {project, kind}` (operator). Decrypts, calls
  Sentry `GET https://sentry.io/api/0/organizations/<org>/projects/` or
  PostHog `GET <host>/api/projects/<id>/` with `Authorization: Bearer <key>`,
  `redirect: manual` and a `signal_keys.test_timeout_ms` timeout. Stores
  `last_test_at`, `last_test_status`, `last_test_result` and one audit row in
  one batch. 200 `{ok, result, status, reason, tested_at}`. `reason` is a
  fixed text per result, never vendor text.
- `POST /api/signal-keys/read {project, kind, run_id, machine}` +
  `x-web-vault-run-token` (a lane-run machine). 200 `{kind, fields, value}`
  only to the claimer of a live run of that project, of a listed lane.
- `POST /api/signal-keys/hub-read {project, kind}` +
  `x-envelope-hub-token` = `ENVELOPE_HUB_TOKEN` (the hub). 200
  `{kind, fields, value}`. The `sentry-triage` lane runs on the hub, so C2's
  readers call this route. The admin token alone does not read a value.

The read and hub-read answers carry `cache-control: no-store`. Both write the
audit row and `last_used_at` in one batch BEFORE the value leaves. A failed
batch is 503 with no value.

## Refusals

| Route | Answer | Why | Audit row |
|---|---|---|---|
| set, clear, test | 403 | no operator proof | none |
| set | 400 | a field fails its check (the answer names `field`) | none |
| set | 503 | `refused:key_missing` / `refused:encrypt_failed` | one |
| clear, test | 404 | `refused:no_entry` (test: also `refused:no_kind`) | one |
| read | 403 | `no_run`, `wrong_lane`, `not_claimed`, `not_claimer`, `bad_token`, `lease_expired`, `wrong_project` | one |
| read, hub-read | 404 | `no_entry` | one |
| read, hub-read | 503 | `key_missing`, `decrypt_failed` | one |
| hub-read | 503 | `hub_token_unset` | one |
| hub-read | 403 | `bad_hub_token` | one |
| any | 400 | a malformed project, kind, machine or run_id | none |

Test results: `ok` (200, 204), `http_<n>` (any other status, a redirect
included), `timeout`, `network`, `key_missing`, `decrypt_failed`, `bad_url`.

## Knobs (settings rows, each with a code fallback equal to its seed)

| Row | Seed | Bounds | Read by |
|---|---|---|---|
| `signal_keys.read_lanes` | `''` | comma list | the lane read, the claim, the enqueue gate |
| `signal_keys.test_timeout_ms` | 10000 | 1000..30000 | test |
| `signal_keys.rotate_days` | 90 | 1..3650 | list (`rotate_by`) |
| `signal_keys.list_limit` | 500 | 1..5000 | list |
| `signal_keys.value_max_bytes` | 4096 | 64..16384 | set |
| `retention.signal_key_audit.days` | 90 | 0 = off | retention rule `signal_key_audit.age` |

## Retention

`signal_key_audit` is history: rule `signal_key_audit.age`
(`worker/jobs/src/routes/retention.d/bh-9800-signal-keys.js`) copies a row
older than `retention.signal_key_audit.days` to the archive D1, then deletes
it, under `retention.dry_run`. `signal_keys` has no rule: at most projects x
kinds rows, and clear deletes a row. `signal_key_kinds` is a catalog.

## Operator steps

1. None for the deploy. `bin/harness-sync.sh` applies the schema fragment
   before `wrangler deploy`. No new Worker secret and no new env var: the
   routes use `WEB_VAULT_KEY_<n>`, `WEB_VAULT_ADMIN_TOKEN`, `BOX_OPS_TOKEN`,
   `BOX_OPS_OWNERS`, `HUMAN_VERDICT_TOKEN` and `ENVELOPE_HUB_TOKEN`, which
   exist.
2. To let a lane-run lane read a key, set `signal_keys.read_lanes` to its
   name. From then on that lane is enqueued with the operator token only.
3. To add a kind or a prefix, insert or edit a `signal_key_kinds` row.
