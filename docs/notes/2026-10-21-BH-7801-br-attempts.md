# The resolver record's attempts, rung fields and adjudications are D1 rows (BH-7801)

Doc: DB-COORDINATION-SPEC, MERGE-CONDUCTOR

Slice C1 of #4157. It is a dual write: the record file
`state/blocked-resolver/<p>/<rkey>.json` stays the authority while it exists.
The DB rows are what a wiped or rebuilt hub reads back.

## What changed

- Every attempt a record save appends is now one `ledgers` row: kind
  `br_attempt`, key `<project>/<rkey>#<stamp digits>#<n6>` (n is the attempt's
  index in the record), status = the action, detail = the attempt
  `{at, action, reason, detail, url?, head?}` plus `bump` (the counter
  `br_record` bumped). The writer is `bra_put_new` / `bra_put` in
  `bin/blocked-resolver.d/bh-7801-br-attempts.sh`, called from `br_save` in
  `bin/lib/br/record.sh`. So the head reset (`br_head_reset`) and the contested
  stamp, which append through `br_save` and not `br_record`, get rows too.
- An `adjudicate` attempt (`ACCEPT — <path>` or `REJECT — <path>`) adds
  `verdict` and `ruling`, the last 1500 bytes of the resolver's own
  `$ST/<p>/<rkey>.adjudication-run.txt`. No other path is read. The detail is
  kept at 3500 bytes or less (the worker cuts at 4000 characters): the ruling
  is cut to its last 400 characters with `cut:true`, then dropped.
- The `br_record` row detail (BH-2317) also carries `rung_head`, `rung_pr` and
  `ladder_reset` (BH-7660). `br_cap_rows` and the head gate read them, so after
  a wipe the fix-round baseline of a head reset is not lost.
- `br_load`, when the file is gone and the `br_record` row restored, also
  restores those three fields and the attempts (`restored:"ledger"` on each)
  through the new worker route `GET /api/br-attempts?project=&rkey=&limit=`
  (`worker/jobs/src/routes/br-attempts.js`, bearer-gated, one statement on the
  `ledgers` primary key, newest 100 by default, max 200, answered oldest
  first). A miss or an outage on the `br_record` row makes no attempts read.

## What did not change

- The file is still written first and read first. A failed row PUT changes
  nothing: no retry, no counter change. Slice C4 removes the file writers.
- There is no backfill. Rows start with the first attempt after the deploy.
- The other record fields (`ci_park_*`, `stale_*`, `preflight_*` and the rest)
  and the side files stay on disk only.

## Operate

- Kill switch: `BR_OPT_OFF=bh-7801-br-attempts` (BH-7450) skips the fragment.
  The resolver then behaves as before this change.
- Read one record's attempts:
  `curl -H "Authorization: Bearer $HARNESS_SECRET" "$JOBS_URL/api/br-attempts?project=<p>&rkey=<rkey>"`.
- Retention: `br_attempt` is a growing ledger kind, about one row per resolver
  attempt. `routes/retention.js` does not delete `ledgers` rows. To archive old
  rows, add `br_attempt` to the settings row `retention.ledgers.archive_kinds`
  (BH-6780). This change does not edit that row, because it holds an
  operator's list. An archived row is not returned by `GET /api/br-attempts`
  (it reads the hot table only), so a restore then brings back only the
  attempts still in the hot table.
