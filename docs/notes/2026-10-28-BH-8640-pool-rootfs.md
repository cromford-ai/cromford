# Pool machine rootfs size is a settings row (BH-8640, rest of BH-8499 Fix 3)

Doc: FLY-POOL, LANES

## What changed

- `spawn_one` in `bin/fly-pool.sh` launched every pool machine on the Fly
  default rootfs. The `fly machine run` line now carries
  `${PRFS_ARGS[@]}`: `--rootfs-size <GB>`, or nothing. The same line serves
  the push path and the pull path (BH-7430), so both read it.
- One new fly-pool lane knob, `ROOTFS_GB`
  (`catalog/lanes.d/fly-pool.knobs.d/ROOTFS_GB.json`), row
  `lane.fly-pool.<project>.rootfs_gb`, int, default 0, range 0..100 GB.
  0 = the Fly default rootfs, no flag. `lane_env_apply fly-pool <project>`
  exports the row as the env var. No new reader.
- `bin/lib/pool-rootfs.sh` (`pool_rootfs_resolve`) checks the value:
  - Blanks and newlines are trimmed. Leading zeros are stripped (no octal).
  - Empty or 0: no flag, rc 0.
  - Not a whole number, or above 100: no flag, rc 1, one log line.
  - A valid row runs `fly machine run --help` once per process. If flyctl
    does not list `--rootfs-size`, there is no flag, rc 1 and one log line.
    An older flyctl therefore launches on the default rootfs and does not
    refuse the launch.
  - The probe is cut after `POOL_ROOTFS_PROBE_TIMEOUT_S` seconds (knob
    `catalog/lanes.d/fly-pool.knobs.d/POOL_ROOTFS_PROBE_TIMEOUT_S.json`, row
    `lane.fly-pool.<project>.pool_rootfs_probe_timeout_s`, default 20,
    1..120). A cut probe reads as no flag.
- A row that is set but not used writes one line per spawn in
  `logs/fly-pool.log`:
  `<key>: rootfs row not used (<why>) — launching on the Fly default rootfs`.
  No alert. The spawn goes ahead.
- No row, or no lib in the tree: the argv is byte-identical to the one
  before, and there is no new fly call.
- Seed: `worker/jobs/schema.d/202611011704-bh-8640-pool-rootfs-seed.sql` sets
  `lane.fly-pool.project-6-os.rootfs_gb` = 20 (`INSERT OR IGNORE`, an
  operator value stays).

## Why

BH-8499: project-6-os pool machines have a 7.8 GB rootfs with 4.5 GB free
when idle. The seeded-volume suites of TK-1692 and TK-1836 filled it (ENOSPC
in the test Postgres). Every limit is a knob (BH-7945).

## Seed size

2x the measured peak was asked. No build box can measure the peak. The known
facts: base image about 3.3 GB, and the peak is at least 4.5 GB (it filled
the free space). 2 x 4.5 + 3.3 = 12.3 GB. The seed is 20 GB because 4.5 GB is
a lower bound. Owed: a measure on the live pool (see "Probe"), then a row
change. No code change is needed.

## Operator commands

```
bin/harness-ctl.sh status project-6-os | grep ROOTFS_GB
bin/harness-ctl.sh set fly-pool ROOTFS_GB 30 project-6-os
bin/harness-ctl.sh set fly-pool ROOTFS_GB 0 project-6-os     # back to the Fly default
```

## Probe

Not run from a build box. After one pool tick on project-6-os:

1. `fly machine status <id> -a pool-project-6-os` shows the rootfs size.
2. `df -h /` on the machine shows the larger rootfs.
3. `grep "rootfs row not used" logs/fly-pool.log` is empty.
4. The `HARNESS_PG:` and `df` lines in the `harness-suite*.txt` of a
   rebuilt TK-1692 or TK-1836 give the peak data dir size.

## Known gap

`bin/pool-budget.sh` prices CPU and memory only. It does not price rootfs GB.

Suite: `tests/fly-pool-rootfs.bh-8640-test.sh`.
