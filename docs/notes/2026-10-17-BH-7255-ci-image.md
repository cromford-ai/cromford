# harness-ci can run its four install-heavy jobs in a prebuilt image; the switch is off (BH-7255, slice C0)

Doc: CI-RUNNERS

## What changed

- `ci-images/cromford/Dockerfile` (new). `FROM debian:trixie-slim`. It
  bakes what the tests-shard install steps put on a runner: node 22.23.2 (the
  `bake.node.version` row on 2026-10-17, installed by
  `fly/testhost/node-install.sh`), codegraph 1.5.0, semgrep 1.176.1 (venv),
  gitleaks 8.30.1 and ShellCheck 0.11.0 (sha256-checked), PyYAML, age, zstd,
  rsync, gawk as `awk`. It also bakes the `worker/jobs` and `console-ui`
  `node_modules` from their lockfiles under `/opt/ci/node/<name>`, each with a
  `.lock-sha256` stamp. linux/amd64 only.
- `bin/ci-image.sh` (new). `tag` is 12 hex of sha256 over the Dockerfile, the
  two `package.json` + `package-lock.json` pairs and `node-install.sh`.
  `ensure` is the step of the new `ci-image` job.
- `bin/ci-node-modules.sh` (new). In image mode it links
  `<dir>/node_modules` to the baked tree when the stamp equals the checkout's
  lockfile hash. Any other state is rc 1 by name. It never runs `npm ci`.
- `.github/workflows/harness-ci.yml`. New job `ci-image` (no `if:`, so it runs
  on every event). `lint`, `console-ui`, `worker-jobs` and `tests-shard` need
  it and run in `container: image: ${{ needs.ci-image.outputs.ref }}`, pulled
  with the job token (`packages: read`). Each `actions/setup-node` and each
  `npm ci` step is host-only (`ref == ''`). Two new image-only steps link the
  baked `node_modules`. No step is removed or renamed. The guarded install
  steps (BH-1206) stay. In image mode each guard finds its pin and installs
  nothing.
- `catalog/ci-batch-escalate.tsv`: `bin/ci-node-modules.sh`,
  `bin/ci-image.sh` and `ci-images/` mark console-ui and worker-jobs affected
  on a merge-queue batch.
- `bin/test-impact.sh`: `ci-images` is a top-level source directory of the
  impact map, so a Dockerfile edit selects the suites that read it.
- Three shape suites change one premise each (the `TEST-CHANGE:` lines in
  the commits). `tests/harness-ci-cost-shape-test.sh` S5 accepts `ci-image`
  with no `if:`, as it accepts `lint` and `determinism`, and is red if it
  gets one. `tests/ci-shard-split-test.sh` D accepts
  `needs: [plan, ci-image]`. `tests/ci-merge-reuse-wiring.bh-5357-test.sh` W4
  pins lint's permissions with `packages: read` added.

## The switch

| `CI_IMAGE` repo variable | `ci-image` label on the PR | mode |
|---|---|---|
| unset | absent | host (the default, the path before this change) |
| unset | present | image, for that PR's runs |
| `on` | any | image |
| `off` | any | host (the kill switch) |
| any other value (`ON`, `true`, `1`, ` on`) | any | the `ci-image` job is red, rc 2 |

Host mode writes `ref=` and calls no docker. An empty `container.image` runs
the job on the runner. Image mode asks GHCR for
`ghcr.io/example-org/cromford-ci:<tag>`. If the tag is missing, the job
builds and pushes it. A failed login, build or push is
`::error::ci-image: <ref> is missing and could not be built (<step>)`. Then
the four jobs do not start. There is no fallback to the host.

To try it on one PR: add the `ci-image` label (and `full` for the corpus),
then push. To turn it on for all runs:
`gh variable set CI_IMAGE --body on`. Rollback: `gh variable delete CI_IMAGE`
(or set it to `off`), then re-run.

## Not verified here

This box has no docker and no CI token. So the image build, the GHCR push,
the container pull, the empty-image host behaviour and the symlinked
`node_modules` under vite and `node --test` are not run here. The PR's
unlabeled run proves host mode. One run with the `ci-image` label proves
image mode.
