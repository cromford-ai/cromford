# Dispatcher: the health lanes, a dead-feed watch and a post-deploy output check (BH-5566, wave 9 of #5556)

Doc: EVENTS, ALERTS-STATE-MACHINE

## What changed

1. Dispatcher owns the eleven health lanes. Schema fragment
   `worker/jobs/schema.d/202610150258-bh-5566-dispatcher-lanes.sql` adds one
   `staff_lanes` row per lane (`INSERT OR IGNORE`, no DDL). The roster route and
   the `/staff` screen show them. No lane changes: each one keeps its script,
   cron line, kill switch and alerts.
2. A new declaration directory, `catalog/staff-feeds.d/`. One file per declared
   feed or declared feature output, named `<id>.json`. Two feeds are seeded:
   `cost-rows-push` (window 2 h) and `vendor-spend-pull` (window 3 h). No
   output is seeded. `cost-rows-push` is a proxy. Its probe reads
   `cost_rows.ts`, the time of the model call in the newest row, not the time
   of the push. A fleet with no model call for 2 h also gives a dead-feed
   finding while the push lane is healthy.
3. A new collector, `bin/staff/dispatcher-collect.sh`. `bin/staff.sh tick
   dispatcher` runs it at step 6. Until now that step found no collector and
   collected 0 items. The collector makes no model call and no gh call. It
   prints two checks as staff findings:
   - `dead-feed`: L is the feed's last success, read from its probe. A finding
     when L is "never" (the probe answers null or "") or `now - L > max_age_h`
     hours. Exactly the window is not stale.
   - `post-deploy-output`: D is the newest `verified` deploy of the output's
     project in the D1 deploy ledger (`ledgers` kind `deploy`, written by
     `bin/deploy-train.sh`), inside `DSP_DEPLOY_LOOKBACK_H`. Its time is
     `detail.verified_at`, else `detail.departure`, else `created_at`. O is the
     output's newest record, read from its probe. A finding when `now - D >=
     window_h` hours and O is "never" or `O < D`. `O = D` is healthy. The check
     reads the output, never a lane rc: a lane that ran rc 0 and did no work
     is not output.
   The item holds the check, the id and one time (`last_success` or
   `deployed_at`), and no hour count. So one outage is one claim, and at most
   one ticket, however many ticks see it. The hours ride in the title.
4. The post-deploy finding also pages, once per (output, deploy):
   `bin/lane-alert.sh --id staff-dispatcher-postdeploy-<id>-<D epoch> --severity
   <DSP_PAGE_SEVERITY> staff "<title>"`, then the marker
   `state/staff/dispatcher/paged/<id>.<D epoch>`. A later tick that finds the
   marker does not page again. A newer deploy is a new D, a new item and one new
   page. The deploy is in the alert id. With one id per output, a second
   deploy's page inside `ALERT_AUTO_CLOSE_S` (6 h) is a `suppress` in
   `bin/lib/alert-state.sh`, and the marker then stops it for good. Markers
   older than `DSP_DEPLOY_LOOKBACK_H` are deleted. A marker is never older
   than its deploy, and a deploy past the lookback is not checked again. If the marker cannot be
   written, the page still goes, with one warn line; lane-alert's open-id
   dedupe stops a repeat while the alert is open. The dead-feed check never
   pages: it is a finding only.
5. Knobs are settings rows, `lib.staff-dispatcher.<env>`
   (`catalog/lanes.d/_lib.staff-dispatcher.json`), applied with
   `lib_env_apply staff-dispatcher`: `DSP_DEPLOY_LOOKBACK_H` (72),
   `DSP_DEPLOY_ROWS` (500), `DSP_PAGE_SEVERITY` (critical; warn, info or off).
   A value out of range is one warn line in `logs/staff.log` and the default.
6. The soul's REPORT list names both checks.

Failure: a probe that fails, or answers a value that is not a time, is
UNREADABLE. That declaration is skipped with one `dispatcher: probe <id>
unreadable` line in `logs/staff.log`. It is never read as "never succeeded".
When every probe is unreadable, or the deploy ledger is unreadable while an
output is declared, the collector exits 1 with no output and no page, and
staff.sh logs `collector rc=1; nothing claimed`.

Dispatcher stays at `automation` (observe mode). On the hub a dead feed is one
digest line in `logs/staff-digest.log` until a person raises the level; at
`augmentation` it is one GitHub issue labelled `staff:dispatcher`.

## The declaration format

```json
{"id": "cost-rows-push", "kind": "feed", "lane": "cost-rows-push", "max_age_h": 2,
 "probe": {"path": "/api/metrics/cost-rows?limit=1", "at": ".cost_rows[0].ts"},
 "note": "..."}
{"id": "<id>", "kind": "output", "project": "<fleet.conf slug>", "window_h": 6,
 "probe": {"path": "/api/...", "at": "<jq: the newest output record's time>"},
 "note": "..."}
```

The collector checks each file. A file that fails is one `declaration <file>
invalid (<why>)` log line and is skipped; the others still run.

- The file name is `<id>.json`, and `id` matches `^[a-z][a-z0-9-]{1,47}$`.
- `kind` is `feed` or `output`.
- `max_age_h` (feed) or `window_h` (output) is an integer from 1 to 2160.
- An output's `project` matches `^[a-z0-9][a-z0-9-]{0,47}$`. It is the
  `detail.project` the deploy train writes, the fleet.conf slug.
- `probe.path` starts with `/api/`, holds no `..` and no whitespace. It is a
  GET on the jobs worker. Use a route that returns newest-first rows, with
  `limit=1`.
- `probe.at` is a jq expression (at most 200 characters) that compiles. On
  the answer it must give one value: an ISO time (`YYYY-MM-DDTHH:MM:SS`, `T` or
  a space, optional fractions, `Z` or no zone = UTC) or an epoch in seconds or
  milliseconds. null or "" means never.

## How to declare a feature output

1. Find a jobs-worker GET route that returns the feature's newest output
   record first. The project must deploy through the deploy train with a
   `VERSION_URL`: a project with no verified deploy row is never judged.
2. Add `catalog/staff-feeds.d/<id>.json` with `kind: "output"`, the project
   slug, `window_h` (how long after a deploy the feature must have made
   output), and the probe.
3. Open a PR. The page goes to a person, so pick the window from the
   feature's real cadence, not a guess.

## Overlap with the two checks

None of the eleven lanes reads a declared feed's last success, and none reads
a feature's output after a deploy. `served-sha-watch` is the closest: it checks
that production serves main HEAD, which is the deploy, not what the feature
made after it. `healthcheck` checks the domain answers, not that work comes
out. `fleet-slo` and `pipeline-health` watch rates and queues, and
`heartbeat-reaper` watches process beats: a lane can beat, exit 0 and write
nothing, and all three stay green. The deploy ledger is read today only by the
DORA metrics (`worker/jobs/src/routes/dora.js`). The two new checks read the
output itself.

## Index and retention (BH-6730)

- `worker/jobs/schema.d/202610150259-bh-5566-ledgers-kind-updated-index.sql`
  adds `idx_ledgers_kind_updated ON ledgers(kind, updated_at, key)`. The
  post-deploy check reads `GET /api/ledger?kind=deploy` every tick (`WHERE
  kind=? ORDER BY updated_at DESC, key DESC`); before, it sorted every deploy
  row in a temp b-tree. `tests/staff-dispatcher.bh-5566-test.sh` D13 checks
  the plan on 20000 seeded rows.
- No new table. `staff_lanes` gains 11 rows (a fixed ownership list, its
  primary key serves both reads). The Dispatcher writes no database row, so it
  adds no growing table; `ledgers` keeps history by the BH-6750 rule.
- The lane seed was renamed to `202610150258-bh-5566-dispatcher-lanes.sql`
  (the build's `202610142053` sorted before fragments now on main).
