# A ticket can name a spec repo its pool build may read (BH-6576)

Doc: BOARD-API-CONTRACT, OPERATOR-SETUP

## What happened

TK-3487 cites a spec file in `example-org/project-6`. A project-5 pool machine's
GitHub token sees `example-org/project-5` only, so the plan stopped
`PLAN_BLOCKED cross-repo-read example-org/project-6`. The BH-5910 knob
`lane.fly-pool.project-5.extra_read_repos` fixes it, but it widens the read
access of EVERY project-5 build. The ticket asked for one ticket's access only.

## What changed

1. A ticket body line names the repos this ticket's build may read:

   ```
   Spec-repo: example-org/project-6
   Spec-repos: example-org/a, example-org/b
   ```

   - The key (`Spec-repo:` or `Spec-repos:`, any case) must start the line,
     after optional spaces, a `- ` or `* ` bullet and one backtick. The key
     inside a sentence does not count.
   - A line inside a ```` ``` ```` or `~~~` fence does not count.
   - Values are `owner/repo` words, split on commas and spaces, each optionally
     in backticks. Any other word is dropped. At most 10, deduped.
   - The BODY only. A comment cannot add a spec repo. Edit the body to add or
     remove one.
   - GitHub-Issues projects only (numeric ticket id). An in-app board ticket
     has no body for the pool to read, so the line has no effect there.
2. `bin/lib/spec-repos.sh` (new): `spec_repos_parse`, `spec_repos_load` (one
   `GET repos/<slug>/issues/<n>` per ticket per pool tick, cached in the pool
   process, the unreadable answer too), `spec_repos_extra` and
   `spec_repos_machine_has`.
3. `bin/fly-pool.sh` `spawn_one` reads the ticket body before the credential
   swap and says `<KEY> declares spec repos <list> (read-only)`. The swap block
   adds those repos (minus the project repo and the knob's repos) to the BH-5910
   `--extra-read` list. So the machine gets the same read-only token
   (`contents:read`, `metadata:read`), `GH_EXTRA_READ_REPOS` and
   `/run/harness-env/gh-token-read` as a knob repo gets. A ticket without the
   line gets exactly what it got before: no read token unless the knob is set.
   - A repo the App cannot read pages once per project per repo per UTC day
     (the BH-5910 flag), with the text `ticket <KEY> declares it as Spec-repo`.
     A knob repo keeps the BH-5910 text.
   - The machine json (`state/fly-pool/<project>/<MID>.json`) carries
     `spec_repos: "<comma list>"`. The key is absent for every other ticket.
4. `next_job_or_destroy` keeps the wider token on its own ticket:
   - A machine whose json has `spec_repos` is destroyed at reap, not reused.
     Log: `<MID> carries a read token for <KEY>'s spec repos — destroying
     instead of reusing`.
   - A queued ticket whose body declares spec repos is not handed to a reused
     machine (that machine has no token for them). Log: `<KEY> declares spec
     repos — left for a fresh spawn`. It spawns fresh on a later tick.
5. `xrepo_plan_note` (`bin/lib/rb/cross-repo-read.sh`) adds one sentence when
   `GH_EXTRA_READ_REPOS` is set: it names the readable repos and says to read
   them with `git clone`. `gh` and the API still use the project token.
6. The `PLAN_BLOCKED cross-repo-read` line in plan.md and its ALERTS line name
   both remedies: the knob, or a `Spec-repo:` line in the ticket body.

## Not in this change

- The read token is not rotated (BH-5910 limit). The plan stage reads spec
  files in its first minutes; the token lives 55 minutes or more at spawn.
- A body edited after the spawn does not change the running machine. The next
  spawn reads the body again.
- Box-local builds use the PAT, which already reads the org's repos.

## Operator steps

1. Install the builders GitHub App on the spec repo (same owner as the project
   repo). For TK-3487: `example-org/project-6`.
2. Add `Spec-repo: <owner>/<repo>` on its own line in the ticket body.
3. On the hub, check `logs/fly-pool.log` for `declares spec repos` and
   `gets a read-only token for the extra repos of` on the next spawn, and
   ALERTS for `EXTRA_READ_REPO_MISSING`.
