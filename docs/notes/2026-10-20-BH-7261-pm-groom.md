# PM weekly grooming brief (BH-7261, BH-7244.3)

Doc: CONSOLE, PROJECT-LANES

Slice 4 of 5 of #7244. Once a week, per product project, the PM agent grooms
the roadmap backlog of #7243. It flags stale ideas, re-scores the ideas,
proposes lane moves, Now proposals and the next wave, and sends a short brief
to Telegram with links to Mission Control. the operator approves or rejects each move
on Mission Control. An approve moves the idea's lane. It never files a ticket,
adds a label or starts a build.

## The lane

`bin/pm-groom.sh <project> [--force]`, Monday 11:0x UTC on the 8 run-product
boxes (`cron/lanes/737-pm-groom.cron`, the run-product minute offsets, two
hours after run-product). Registry `catalog/lanes.d/pm-groom.json`, off switch
`flags/lane-off-pm-groom`. `flags/lane-off-run-product` and
`flags/product-paused-<project>` stop it too. It takes
`locks/<project>-product.lock` with `flock -n`: a held lock is a skip.

| Step | What | On failure |
|---|---|---|
| model | `lane_model PM_MODEL product.pm` | rc 75, no read, no call |
| reads | `GET /api/settings/<key>` for the `pm.*` knobs (stale_days, backlog_limit, moves_max, now_max, next_wave_max, summary_max_chars, reason_max_chars, score_why_max_chars, note_max_chars, evidence_max, body_max_chars, scores_max, stale_max), `GET /api/roadmap/ideas` for `ideas` and `next` | one ALERTS line, rc 1, no claim |
| stale | `updated_at` age >= `pm.stale_days` (settings row, seed 30) | an unparsable time is not stale, one warn line |
| evidence | the `ok` rows of the newest `products/<p>/*/data-signals.json`, plus `stale.<idea_id>` per stale idea | no file: stale rows only |
| claim | `POST /api/pm/briefs/claim` before the call | not won: resend a ready unsent brief, else "already billed" |
| call | one `bin/agent-call.sh pm` (role `product.pm`, no tools) | brief `failed`, one ALERTS line, rc 0 |
| check | a move must name a backlog idea, start from its lane, go to another of ideas, next, discarded, and cite a listed evidence id | dropped, one log line each |
| fit | evidence cut to `pm.evidence_max`, scores (highest first) to `pm.scores_max`, stale to `pm.stale_max`; a body over `pm.body_max_chars` loses half its scores, then half its stale list, until it fits (`scores_partial`, `stale_partial`) | cannot fit: no write, one ALERTS line, rc 1, the row stays claimed, the answer kept in `state/pm-groom/<p>.failed-create.json` |
| write | `POST /api/pm/briefs` (status ready, sent_mc=1) | one ALERTS line, rc 1, the row stays claimed, the answer kept in `state/pm-groom/<p>.failed-create.json` |
| send | `bin/archie-tg-send.sh pm-brief:<p>:<week>`, then `POST /api/pm/briefs/sent` | sent_tg stays 0, one ALERTS line; the weekly cron does not resend it (the next run is a new week), a manual `bin/pm-groom.sh <p>` in the same ISO week resends it with no call |

The (project, week) row is the claim: a claimed or failed row is billed and
final for the week. Only `--force`, run by a person, re-claims it. A ready row
is final.

## Telegram has links, not buttons

The ticket asks for approve and reject buttons in Telegram.
`bin/archie-tg-send.sh` sends plain text, and no route handles a Telegram
callback. A callback route would be a new public write path into the idea
table. So the Telegram text carries one Mission Control link per move
(`/roadmap/<p>?view=brief&week=<w>&move=<id>`), and the buttons are on that
screen, behind the console sign-in. Inline Telegram buttons are a decision for
a person.

Superseded by BH-8650: `docs/notes/2026-10-27-BH-8650-pm-tg-buttons.md` adds a
second Telegram message with Approve and Reject buttons, behind the settings
row `pm.tg_buttons_enabled` (seed 0). The links in this section stay the
fallback.

## Tables and retention

`worker/jobs/schema.d/202610291810-bh-7261-pm-briefs.sql`: `pm_briefs`
(UNIQUE `(project, week)`) and `pm_moves` (index `(brief_id, status)`). Both
copy to the archive D1 and then leave the hot table after
`pm.brief_retention_days` (seed 365), through the hourly d1-retention lane
(rules `pm_briefs.age`, `pm_moves.age`). With the archive unbound they delete
nothing.

## The screen

`/roadmap/<project>?view=brief` (`console-ui/src/screens/roadmap/brief-view.js`),
opened from the WEEKLY BRIEF link above the idea list. One request
(`GET /api/coord/pm/briefs`, one D1 batch of 3 statements) and a Skeleton.
Approve and Reject go through `POST /api/coord/pm/moves/decide` and the in-app
confirm modal. An approve is a CAS on the idea's lane: when the idea left
`from_col` since the brief, the move is `stale` and the idea does not change.
