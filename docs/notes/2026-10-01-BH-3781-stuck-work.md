# stuck-work: the lane body, paging, the snapshot and the digest line (BH-3793)

Doc: OPERATOR-SETUP, ALERTS-STATE-MACHINE

## What changed

This is slice 5 of BH-3781. `bin/stuck-work.sh` stops being a stub: every 5
minutes on the hub it reads the open PRs and ai-build tickets, names the state
each one is in and who owes the next move (`bin/lib/stuck-work/classify.sh`),
and pages an item that has sat past its state's SLA.

One tick, under `flock -n locks/stuck-work.lock` (a held lock logs ` busy` and
exits; it never waits):

1. **Gather.** `swf_pr_facts <repo>`, then `swf_ticket_facts <repo> <file of
   the PR items>`. Any rc but 0 from either one makes the tick
   `incomplete=1`. Items a reader did not print are not looked at, so nothing
   pages for them. The ticket reader is still the rc 1 stub until BH-3792
   lands, so **every live tick reports `incomplete=1` until then**.
   `STUCK_WORK_MAX_ITEMS` caps the items looked at, and going over the cap is
   also `incomplete=1`.
2. **Per item.** State, SLA (`lane.stuck-work.stuck_work_sla_*` settings rows),
   age = now − the newer of entered_at and owner_action_at, the ledger row
   `stuck_work` / `<item>|<state>|<entered_at>`, then `sw_decide`.
3. **Page once, write first.** `job_ledger_put stuck_work <key> paged` (or
   `repaged` at `STUCK_WORK_REPAGE_FACTOR` × SLA, default 4). Only when the PUT
   answers rc 0 does `bin/alert-line.sh --severity warn --id stuck-work` write
   the page: `STUCK-WORK <item> <state> owner=<who> age=<m>m sla=<m>m — <url>`.
   A `repaged` row is quiet for good. `waiting-on-human` is counted and never
   paged. `excluded` (drafts, held or blocked tickets, tickets with a PR) is
   counted in `states=` only.
4. **Ledger down.** When an item would page but its row could not be read
   (GET failed) or written (PUT failed), it is `unpaged`. One line per UTC
   hour, `STUCK-WORK ledger unreachable — N items past SLA unpaged` (id
   `stuck-work-ledger`). When any of the N had its row unreadable it may
   already have been paged, so the line reads `up to N items past SLA unpaged
   (M could not be read, so may already be paged)`. The marker `state/stuck-work/outage-<YYYYMMDDHH>` is
   written after the send.
5. **Snapshot.** Ledger row `stuck_work_snapshot` / `latest`, detail
   `{"at":<epoch>,"complete":true|false,"by_state":{"<state>":n},"total":n}`,
   counting the items past SLA (waiting-on-human included, excluded never).
   A failed write adds ` snap=fail` to the log line and pages nothing, because
   the digest shows the snapshot as stale or unreadable.

No GitHub App token (and no `GH_TOKEN`/`GITHUB_TOKEN`): the log says
` no-token` and `bin/lane-alert.sh --id stuck-work-no-token --severity warn`
fires once a UTC day (`state/stuck-work/no-token-<YYYYMMDD>`).

## Reading `logs/stuck-work.log`

```
<ts> items=N states=<state>:<n>,... past_sla=N paged=N repaged=N incomplete=0|1 [unpaged=N] [snap=fail]
<ts> off | disabled | busy | no-token
```

## The digest line

The daily-digest route (`GET /api/metrics/daily-digest`) has a tenth section,
`past_sla`: `{ok, total, by_state, as_of, stale}` read from the snapshot row.
No row or a detail that does not parse is `{ok:false, error}`, never 0. A row
older than 30 minutes is `stale:true`, and `isEmptyDigest` is false for a stale
snapshot or a total over 0. `bin/lib/daily-digest-render.sh` prints one line
under Holds:

```
Open work past SLA: 4 (ready 3, blocked 1) <console>/alerts
Open work past SLA: 0 (as of 23:55Z, stale) <console>/alerts
Open work past SLA: unreadable (no stuck-work snapshot) <console>/alerts
```

It links to `/alerts`, where each page is a row that carries the item URL.
