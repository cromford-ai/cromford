# BH-6174: Mission Control shows each lane's spend today against its alert line and its ceiling (BH-5526 slice C4)

Doc: COST

**Why.** the operator's RESUME comment on #5526, item 2: "Show each lane's spend today
against its alert threshold and its ceiling." C2 computes the alert line on the
hub and C3 stores the ceiling as a settings row, but no screen showed either
next to the spend.

**What the section shows.** Nav COSTS → /costs → LANE SPEND · TODAY (UTC), after
the cost caps section. One sortable table, default sort TODAY descending:

| Column | Source |
|---|---|
| LANE | the lane id. A registered lane links to `/settings/<lane>`; a `stage-<s>` id has no detail screen and is plain text. |
| TODAY | `SUM(cost_usd)` of `cost_rows` with `lane_id=<lane>` and `ts` in `[day 00:00Z, day+1 00:00Z)`. This is the number the ceiling gate compares (`GET /api/metrics/llm-spend?lane=<lane>`, no stage). The C2 alert sums lane_id, else stage, from the hub's csv; the two are equal on a day with no un-stamped rows. |
| ALERT LINE | `alert=` of the lane's current `spend_p99` ledger row: `SPEND_ALERT_P99_MULT` x p99, the line `bin/spend-alerts.sh over` judges. |
| CEILING | the settings row `spend.ceiling.<lane>.day_usd`, read with the grammar of `_llm_ceiling`: `$X` armed, `off`, `0 (none)` for zero, `junk: <raw>`, `—` for no row. A `registry-seed` row counts as no row. |
| % OF CEILING | TODAY / CEILING, armed ceilings only. |
| P99 · DAYS | the p99 and the days of data behind it. |
| STATE | `OVER CEILING` (TODAY >= ceiling, the gate's own `>=`), `OVER ALERT` (TODAY >= alert line), `ok`, or `no line` when the lane has neither. |

A banner shows when the fleet settings row `switch.spend-ceiling-off` is on
(`1`, `on` or `true`). A box row (`switch.spend-ceiling-off.<box>`) or a
`flags/spend-ceiling-off` file on one box is not visible to the worker, so the
section cannot show it.

**The ledger rows.** `bin/pipeline-health.sh`'s `# >>> spend lane push` block
runs `bin/spend-lane-push.sh` once per UTC day on the hub, after the spend
alerts block wrote `state/spend-alerts/baseline-<YYYYMMDD>.tsv`. It pushes the
lines with axis `lane`, p99 > 0 and a registry lane id or a `stage-<s>` id (the
seeder's filter, without the 7-day floor) as one `PUT /api/ledger` each:
kind `spend_p99`, key `<lane>`, status `<YYYYMMDD>`, detail
`p99=<p> days=<d> mult=<m> alert=<a>`. It prints `pushed <lane>` only when the
answer's status and detail equal what it sent. The marker
`state/spend-alerts/lane-pushed-<day>` is written only on rc 0; a failed day
raises one `spendlanepush:fleet` alert (TTL 86400) and the next hourly tick
pushes every line again (an upsert).

One row per lane, not one row for the table: `PUT /api/ledger` cuts `detail`
at 4000 characters with no error, and a cut table would be a wrong table.

**The route.** `GET /api/metrics/lane-spend[?day=YYYY-MM-DD]`
(`worker/jobs/src/routes/lane-spend.js`) writes nothing. The current p99 rows
are those whose status is the newest day not after `day`; a lane on an older
table shows no alert line. A lane is listed when it has a current p99 row, a
ceiling row that is not `none`, or spend today as a registered lane. Spend is
read through the `(lane_id, ts)` index with `lane_id IN (…)` in chunks of 90 ids
(D1 binds at most 100 values).

**What it does not show.** Per-box kill switches; lanes with no line, no
ceiling and no spend; which calls made the spend (the SPEND BREAKDOWN section on
the same page answers that). It edits nothing: the settings path stays the one
writer of a ceiling.

through the real worker), `worker/jobs/test/lane-spend.bh-6174.test.js` (route),
`console-ui/tests/lane-spend.bh-6174.test.js` (section).
