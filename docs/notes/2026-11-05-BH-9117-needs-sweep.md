# NEEDS count: one row per ticket, and a sweep for parked build rows (BH-9117)

Doc: DASH-STALE-ROWS, OPERATING

## The gap

On 2026-11-05 NOW said "4823 need a person". 3613 of them were console
`builds` rows with merged=0 in a parked stage (`plan_blocked`, `plan_deferred`,
`plan_stale`, `plan_malformed`) or in `pr_created`. The oldest was from
2026-07-22. No lane closes these rows: `bin/sweep-stale-builds.sh` takes
non-parked stages only. `needCounts()` counted every row, so a ticket with six
old attempts counted six.

## What changed

- `needCounts()` and the `/needs` builds list in
  `console-ui/functions/api/cockpit/[[path]].js` keep one row per (project,
  ticket_key): the highest id. A ticket counts only when that newest row is
  itself parked or `pr_created`. A row with no ticket key is its own group.
  The subquery is not correlated (one LIST SUBQUERY scan of `builds`); the
  binds and the statement count (5 on `/now`, 6 on `/needs`) are unchanged.
- NOW shows the NEEDS A HUMAN number split by kind, each part a link to its
  list: open alerts (`/alerts`), parked builds (`/needs?kind=build`), stale
  builds (`/needs?kind=stale`), failed commands (`/needs?kind=command`), ideas
  at the gate (`/ideas?status=gate_pending`). `needsSplit()` in
  `console-ui/src/lib/cockpit.js`. When the jobs read fails, the stale part is
  a dash and the total is the server total, as before.
- New Pages Function `console-ui/functions/api/needs-sweep/[[path]].js`
  (Bearer `HARNESS_SECRET`, `CONSOLE_DB`): `GET candidates` pages the merged=0
  NEEDS rows by id with the newest id of the same project + ticket;
  `POST apply` moves up to 100 rows per call with a guarded UPDATE (still
  merged=0, still a NEEDS stage, `updated_at` unchanged since the read) and
  expires `dead_letter` commands older than `commands_before`. `apply:false`
  counts and writes nothing. Rows are never deleted.
- New hub lane `bin/needs-sweep.sh`, daily at 05:35Z. Per row, first match wins:
  unreadable `updated_at` keep; PR merged `pr_merged` (merged=1); PR closed
  unmerged and older than the settle window `MC_CLOSED_SETTLE` (bin/lib/mc/settle.sh)
  `pr_closed`, younger keep (`pr_unsettled`, a CI kick can reopen it); PR open or unread keep; newer row `superseded`; older
  than the window `stale`; github-issues ticket closed `stale`; else keep.
  GitHub reads are deduped and share one cap. One ledger row per run
  (`needs_sweep`, `run:<UTC stamp>`), counts from the endpoint's answer.

## Knobs (settings rows, seeded by `worker/jobs/schema.d/202611091634-bh-9117-needs-sweep-settings.sql`)

| row | seed | meaning |
|---|---|---|
| `console.needs.max_age_days` | 14 | window for `stale` and for expiring `dead_letter` commands |
| `console.needs.sweep_dry_run` | 1 | 1 = decide and log only |
| `console.needs.sweep_max_rows` | 5000 | rows changed per run |
| `console.needs.sweep_max_reads` | 300 | GitHub reads per run |
| `console.needs.sweep_page_size` | 500 | rows per candidates page |
| `console.needs.sweep_apply_chunk` | 100 | rows per apply call (keep at or under `NEEDS_SWEEP_APPLY_MAX`) |
| `console.needs.sweep_http_timeout_s` | 30 | seconds per console call |

The endpoint reads two optional Pages env vars: `NEEDS_SWEEP_PAGE_MAX` (fallback 500) and `NEEDS_SWEEP_APPLY_MAX` (fallback 100).

## Turning it on

1. Deploy console-ui (the endpoint) and let the lane run once dry.
2. Read `logs/needs-sweep.log`: the per-row lines and the `summary` line.
3. Set `console.needs.sweep_dry_run` to 0. The next daily run applies.

Off switch: `bin/harness-ctl.sh off needs-sweep`.

## New values

- `commands.status` = `expired`: a dead_letter command the sweep aged out.
  Nothing claims a non-`queued` command, so the boxes ignore it.
- Stages written: `superseded`, `stale`, `pr_merged`, `pr_closed`. All four are
  terminal on every screen already.
