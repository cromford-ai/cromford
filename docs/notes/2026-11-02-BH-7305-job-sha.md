# BH-7305: Fly machines and job start records carry the harness sha

Part of BH-7191 (child C4). The harness sha is a 7-40 hex git sha.

## What each record carries

| Record | Column | Writer | Reader |
|---|---|---|---|
| `lane_runs` (one claim attempt) | `harness_commit` | `POST /api/lane-runs/claim` from `bin/lane-run-worker.sh` | `GET /api/lane-runs`, `GET /api/lane-runs/<id>` |
| `build_queue` (the claim-machine stamp) | `harness_commit` | `PUT /api/pool-state/claim-machine` from `psr_claim_machine` (`bin/lib/pool-state-rows.sh`) | no route in this slice; a direct SELECT |
| `lane_machines` (a start record) | `harness_commit` | `POST /api/lane-fleet/machines` from `lf_record` (`bin/lane-fleet.sh`) | `GET /api/lane-fleet/machines` |
| Fly machine metadata | `harness_sha` | `spawn_one` (`config/fly-pool.d/3800-spawn-one.sh`), `bin/lane-fleet.sh` | `fly machine status <id> --display-config` |

The columns come from `worker/jobs/src/lib/core.d/0000-added-columns.js`
through `ensureColumns`. This change adds no column and no table.

The routes store a value only when it is 7-40 hex after a trim and a lower
case (`worker/jobs/src/lib/harness-sha.js`). Any other value, or no field,
stores NULL. The request then answers the same way it does with no field.
Each claim attempt and each live `lane_machines` POST writes its own sha or
NULL, so a re-claim never shows the sha of an earlier attempt. A stop or
destroy POST does not change the column.

## Where the sha comes from

- Pool push path: the `HARNESS_COMMIT` stamp that `harness_tarball` writes
  (it also sets `HARNESS_TARBALL_SHA`). With no git HEAD there is no stamp,
  and the launch gets no flag.
- Pool pull path: `POOL_PULL_SHA`, the sha the machine fetches.
- Lane-run new machine: the `harness.commit` image label of the newest listed
  machine of the same image (`lfi_image_commit`). With no label, or the label
  `unknown`, the launch gets no flag and the record gets no sha. After a push
  of `:latest`, the label can be the previous image's until a machine boots
  from the new image. The `lane_runs` claim record does not depend on it.
- Lane-run reuse (`machine start`, which takes no flags): the record names the
  reused machine's own label (`lfi_machine_commit`).
- Lane-run claim: `$H/HARNESS_COMMIT`, read right before the claim, after the
  code sync. So the record is the sha the run executes, not the boot sha.

## Why the push path gets no `-e HARNESS_SHA`

`fly/entrypoint.sh` reads a set `HARNESS_SHA` as "fetch this harness sha from
GitHub" (the pull path). A push-path machine has no `HARNESS_SLUG` and no
harness token, so the fetch would fail and the build would be deferred. The
push path gets `--metadata harness_sha` only. The pull path keeps the
`-e HARNESS_SHA` it already sent and adds `--metadata`. A lane-run machine
gets both flags, because no file in the lane-run image reads `HARNESS_SHA`.

## How to read it

- `GET /api/lane-runs?limit=5`: each run has `harness_commit` (string or null).
- `GET /api/lane-fleet/machines`: each machine has `harness_commit`.
- `fly machine status <id> -a <app> --display-config`: `metadata.harness_sha`.
