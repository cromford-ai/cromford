# Deploy queue HOLD / UNHOLD (BH-3154, BH-2510.4)

Doc: queue-panel, deploy-queue-rows

## What changed

- `POST /api/deploy-queue/action` takes `hold` (`queued` -> `held`) and
  `unhold` (`held` -> `queued`) next to `release`. All three share one audited
  CAS plus a `stage_events` row in one batch, with verdicts `RELEASED`, `HELD`
  and `UNHELD`. A reason and an actor are required, a row in the wrong state or
  already departed answers 409, and a lost CAS answers 409 with no event.
- `hold` is refused (409) unless the `deploy_queue_rows` settings row is exactly
  `1|on|true|yes`, the box's `_flag_on_row` truth table. A missing or empty row
  is refused too, because then each box decides from its own
  `DEPLOY_QUEUE_ROWS` env, which the worker cannot see. `unhold` is never gated.
- `POST /api/deploy-queue` answers a `held` row as `duplicate` and never
  re-opens it. The upsert also carries `WHERE deploy_queue.status <> 'held'`,
  so a hold that lands between its read and its write is not undone either.
- `bin/deploy-train.sh`: the train reads `deploy_queue_list <p> held` right
  after the `deploy queue rows (BH-1026.1)` block, on the file-dir fallback
  too. It reads it when the knob is on, when the settings read did not answer,
  or when `state/deploy-hold-armed/<p>` is there (left by any tick that saw the
  knob on). Any held row makes the tick depart nothing: no claim, no
  self-source, no file batch, and one `deploy hold: <sha8…> held` log line.
  When the held list does not answer on an armed box, nothing departs and the
  tick logs one `deploy hold: … (fail closed)` line. A box that answered the
  knob off and has no marker makes no held read.
- The console's DEPLOY QUEUE table also reads `status=held`. It offers HOLD on
  a queued row (knob on only), UNHOLD on a held row and RELEASE on a claimed
  one, each behind the in-app confirm with a required reason.

## Why the whole train pauses

A departure fires the hook and verifies that production serves `origin/main`
HEAD. Every queued sha rides along with any departure, so dropping only the
held sha from the batch would still ship its code. The HOLD copy promises
"The train will not depart and will not self-source while this is held."

## Known edges

- A box whose train has seen the knob on (by the settings row or by
  `DEPLOY_QUEUE_ROWS=1`) departs nothing while the worker is unreachable. The
  settings read failing resolves the knob off, but the marker keeps the held
  read on and an unanswered held list fails closed, as the ticket asks. The
  refute review found the first version of this build leaving that path open
  for boxes armed by the settings row.
- A box that has never seen the knob on and cannot read the held list during
  an outage reads the file dir, with one log line saying so. The worker only
  accepts a hold while the settings row is on, so such a box can hold
  something only if the knob was turned on and a hold taken between two of
  its train ticks, just before the outage.
- A hold taken with the knob on keeps pausing the train if the knob is later
  turned off, and one ALERTS line per held set says so. The marker goes only
  when the knob answers off and the held list answers empty.
- `bin/lib/qrf/deploy.sh` flip-preflight parity lists only `queued` and
  `claimed` rows, so a held sha's file reads as a parity mismatch there. Holds
  need the knob on and that preflight runs before the flip, so it is left as
  a follow-up.
