# web_vault: encrypted credential store (BH-7595, slice C0)

Doc: DB-COORDINATION-SPEC

## What changed

A web-task lane run must sign in to a site without the model seeing a secret.
This slice adds the store, the operator write path and the run-bound read.
It does not add the web-task agent, `type_secret`, the masked screenshot or
the sign-in step. Those need the files of #7594 (web-task S1) and are slice C1.

- Tables (`worker/jobs/schema.d/202610200735-bh-7595-web-vault.sql`):
  - `web_vault`: one AES-GCM ciphertext per `(project, site, field)`, with
    `iv`, `key_id`, `created_at`, `updated_at`, `last_used_at`. No column holds
    a plain value.
  - `web_vault_audit`: one row per set and per read, ok or refused
    (`outcome` = `ok` or `refused:<why>`). Never a value, never a token.
  - Indexes: `uq_web_vault_entry (project, site, field)` (the upsert, the read,
    the list; its prefix is the `(project, site)` index),
    `idx_web_vault_last_used`, `idx_web_vault_audit_at`,
    `idx_web_vault_audit_entry (project, site, at)`.
  - `web_vault_run_token`: one row per claimed web-task run, keyed by
    `run_id`: the claiming `machine` and the SHA-256 of the run token. Index
    `idx_web_vault_run_token_at (created_at)` for retention.
  - Settings rows: `web_vault.key_id` = 1, `web_vault.retain_days` = 180,
    `retention.web_vault_audit.days` = 90, `retention.web_vault_run_token.days` = 2.
- Crypto (`worker/jobs/src/lib/web-vault-crypto.js`): AES-GCM 256. The key is
  the Worker secret `WEB_VAULT_KEY_<n>` (base64 of 32 bytes). The iv is 12
  random bytes per write. The AAD is `web_vault\n<project>\n<site>\n<field>`,
  so a ciphertext copied into another row does not decrypt.
- Routes (`worker/jobs/src/routes/web-vault.js`, all bearer-gated):
  - `POST /api/web-vault/set {project, site, field, value}`: operator only.
  - `POST /api/web-vault/read {project, site, field, run_id, machine}` with
    header `x-web-vault-run-token`: a lane-run machine.
  - `GET /api/web-vault/entries?project=&site=&stale=1&limit=`: operator,
    metadata only.
  - `GET /api/web-vault/audit?project=&site=&limit=`: operator, newest first.
- Operator CLI `bin/web-vault.sh` (`set`, `list`, `stale`, `audit`).
- Read client `bin/lib/web-vault.sh` (`wv_read <project> <site> <field>`).
- Retention rule `web_vault_audit.age` (routes/retention.js) and archive table
  `web_vault_audit` (lib/archive.js).

## Who may write

Every lane-run machine holds `HARNESS_SECRET`, so the bearer alone does not
mean "operator". set, entries and audit also need the header
`x-web-vault-admin-token` to equal the Worker secret `WEB_VAULT_ADMIN_TOKEN`.
The compare is constant-time. The worker trims its own secret. Unset or blank
on the worker = 403 on all three routes.

`bin/web-vault.sh set` reads the value from stdin only. A 4th argument is a
usage error (exit 2), so a value typed as an argument is never sent. From a
terminal it reads with no echo. One trailing newline is stripped. Both tokens
go to curl in a `-K <(printf ...)` config, never on argv. The CLI prints only
`stored <project> <site> <field> key_id=<n>`.

## Who may read

`run_id` and `machine` are not secrets: `GET /api/lane-runs` lists them, and
every lane-run machine holds the bearer. So a read also needs the run token.

- `POST /api/lane-runs/claim` mints the token when the claimed row is a
  `web-task` run: 32 random bytes, base64url, in the claim answer as
  `vault_token` only. D1 keeps its SHA-256 in `web_vault_run_token`, with the
  claiming machine. A new claim of the same run (lease ran out) replaces the
  row, so the old token stops working. If the row write fails, the claim
  stands with no token, and the run's reads are refused `bad_token`.
- `bin/lane-run-worker.sh` gives the token to a web-task run as
  `WEB_VAULT_RUN_TOKEN`. It never logs it.
- `POST /api/lane-runs` and `POST /api/lane-runs/batch` with lane `web-task`
  need `x-web-vault-admin-token` (403 without it). Without this gate, a bearer
  holder could enqueue a web-task run of any project, claim it and get a
  token. The C1 enqueuer must send the operator token.

Residual risk: a bearer holder can still claim a web-task run that the
operator enqueued, because every lane-run machine may claim any lane. That
takes the run away from the real machine (the real run then does not start),
and the audit row names the claiming machine. A per-machine identity is the
fix for that, and it is out of scope for C0.

The read route reads the run row and the token row by `run_id` and refuses,
first failing check wins:

| why | status | when |
|---|---|---|
| `no_run` | 403 | no row for `run_id` |
| `wrong_lane` | 403 | `lane` is not `web-task` |
| `not_claimed` | 403 | `status` is not `claimed` |
| `not_claimer` | 403 | `claimed_by` is not the body's `machine` |
| `bad_token` | 403 | no `x-web-vault-run-token`, no token row, the token row is of another machine, or the SHA-256 of the token is not the row's hash (constant-time compare) |
| `lease_expired` | 403 | `lease_until` <= now |
| `wrong_project` | 403 | the run's project is not the body's project |
| `site_not_allowed` | 403 | the site is not exactly one entry (trimmed, lower-case) of settings row `lane.web-task.<project>.allowed_domains`; absent or empty refuses |
| `no_entry` | 404 | no vault row |
| `key_missing` | 503 | the row's `WEB_VAULT_KEY_<key_id>` is not set |
| `decrypt_failed` | 503 | the ciphertext does not decrypt |

Every outcome writes one audit row (actor = machine). An ok read writes the
audit row and `last_used_at` in one batch before the value is sent. A body
that fails validation is 400 and writes nothing.

`wv_read` sends `run_id=$LANE_RUN_ID` (set by `bin/lane-run-worker.sh`),
`machine=${WEB_VAULT_MACHINE:-$FLY_MACHINE_ID}` and the header
`x-web-vault-run-token: $WEB_VAULT_RUN_TOKEN` in a curl config, never on argv.
It prints the value with no newline (rc 0), `web-vault: refused <why>` (rc 1),
or sends nothing (rc 2) when an id or the token is missing.

## Rotation

Each row keeps its `key_id`. To rotate: add `WEB_VAULT_KEY_2`, set
`web_vault.key_id` = 2, then `set` each entry again. An old row reads with its
own key until it is set again. Then remove `WEB_VAULT_KEY_1`.

## Retention

- `web_vault`: no delete rule. `bin/web-vault.sh stale [project]` (route
  `entries?stale=1`) reports rows with `last_used_at` older than
  `web_vault.retain_days` (1..3650, else 180). Nothing deletes them.
- `web_vault_audit`: rule `web_vault_audit.age`, window
  `retention.web_vault_audit.days` (90; 0 = off), in the hourly
  `bin/d1-retention.sh` run, under `retention.dry_run` (seed 1 = count only).
  Rows are history: they are copied to the archive D1 before the delete. With
  the archive unbound, nothing is deleted.
- `web_vault_run_token`: rule `web_vault_run_token.age`, window
  `retention.web_vault_run_token.days` (2; 0 = off), same run and dry-run
  switch. A row is a short-lived credential hash, not history, so it is
  deleted, not archived.

## Operator steps (go-live)

1. `wrangler secret put WEB_VAULT_KEY_1 --name harness-jobs` with
   `openssl rand -base64 32`.
2. `wrangler secret put WEB_VAULT_ADMIN_TOKEN --name harness-jobs` with a new
   random token.
3. Put the same `WEB_VAULT_ADMIN_TOKEN=` line in the hub env `global.env`.
   Never put it on a box or a lane-run machine.

Until steps 1 and 2 are done, set answers 503 and every operator route 403.
