## Fix 1: what is behind index.js:26504

Sentry CROMFORD-HARNESS-24 named bundle line 26504. Method: rebuild the
worker at the event's sha (`git archive 45dc1de`, compose the catalogs,
`npm install` in `worker/jobs`, `npx wrangler deploy --dry-run --outdir`, wrangler
4.161.0, @sentry/cloudflare 11.6.0), then read the bundle's own source map.

- Line 26504 is `res = await handler();`. It maps to
  `node_modules/@sentry/cloudflare/src/wrapRequestHandlerWithInit.ts:168`.
- That is the Sentry request wrapper. Every unhandled error of every route
  passes through it, so the line names no query and no route. The event did

The hot query is `settingsRows()` in `worker/jobs/src/lib/settings-cache.js`.
It is the only sender of that SQL. About 49 call sites in 33 files use it, so
it is on almost every route. The per-tick route is `GET /api/settings/<key>`.

## Why it ran more often than its 30 s TTL

1. Wrong cache key on sampled requests. `withStmtStats` gives a sampled
   request `env.DB = stmtStatsDb(db)`, and index.js wraps that in
   `retryingDb`. The snapshot and the ensureTable/ensureColumns memos keyed on
   that proxy (`rawDb` unwrapped only the retry proxy). So a sampled request
   almost always found no snapshot and read all 1,008 rows again. That also
   made `/top` over-count the settings read: 4,042 is an upper bound.
2. No single-flight. N requests that arrive while the snapshot is cold or
   stale each started their own full read.

## What changed

- `src/lib/db-root.js` (new): `markWrapper(proxy, inner)` and `rootDb(db)`.
  The retry proxy and the stats proxy register themselves. `rawDb()` now
  returns `rootDb()`. Every per-isolate cache keys on the true binding.
- `settings-cache.js`: the snapshot keys on the root binding. Callers share one
  read in flight. A rejected read is not kept. `invalidateSettings` during a
  read drops that read's result from the cache (a generation count).
- `core.js` `ensureTable`: a table with 2 or more statements is one
  `db.batch()` (one D1 call, one transaction) when the root binding has
  `batch`. `ensureColumns` stays one statement at a time: its ALTERs need
  their own "duplicate column" catch.

## Fix 2: index

None needed. The statement reads every row by design (the snapshot is the
whole table). EXPLAIN on 1,008 rows: `SCAN settings USING INDEX
sqlite_autoindex_settings_1`, with no temp B-tree. The cut is in the call
count. Test AT3 pins the plan.

## Fix 3: batched writes

The hot single-row writes are already one batch per request (`gh_ledger`).
The repeated per-request sequence in the live counter was the ensureTable
DDL (`lane_ticks`: CREATE TABLE plus 2 CREATE INDEX, 3,889 / 3,888 / 3,884
sampled calls in 7 d). Most of that came from cause 1 (the memo missed on
every sampled request). The batch makes each cold create one call.

## Statement budget (AT4)

`SETTINGS_FULL_READS_PER_BURST = 1`: through the real `worker.fetch`, 20
concurrent `GET /api/settings/<key>` on a cold binding run the full settings
read once, and a sampled request inside the TTL runs it 0 times.

Before and after, from `worker/jobs/test/d1-load.bh-9657.test.js` on the
code before and after this change:

| Case | Before | After |
|---|---|---|
| B1: 20 concurrent `settingsRows` on a cold binding | 20 reads | 1 |
| AT4: 20 concurrent GET /api/settings/<key> | 20 reads | 1 |
| B2: a sampled request after a warm read | 1 read | 0 |
| T3a: `ensureTable(lane_ticks)` | 3 D1 calls | 1 (a batch of 3) |

## Test fixtures

ensureTable now sends a batch, so test fakes that count or gate "the batch"
must tell it from the route's own write batch. `test/lib/ensure-batch.bh-9657.js`
`isEnsureTableBatch` does that. The node:sqlite shim
(`test/lib/d1-sqlite.bh-1030.js`) now compiles SQL at first use, as D1 does,
and runs a batch as one transaction (a savepoint), as D1 does. Before, its
eager prepare made a batch that named a missing table fail before any
statement ran. That hid the missing transaction.
