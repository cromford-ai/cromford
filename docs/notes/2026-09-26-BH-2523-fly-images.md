# The Fly image pointer, bake and bake time as a fly_images row

Doc: DB-COORDINATION-SPEC, FLY-BUILDER-TRIAL

## What was wrong

The image a project's pool spawns from (`state/fly/<p>.image`), what that image
baked (`.bake`, `.cli`) and when (`.baked-at`) existed only as files on the hub
that baked it. A fresh hub had none of them. `bin/fleet-propagate.sh` read no
`.baked-at` as "never baked" and bought a remote Fly bake for every pool the
fleet had already baked minutes earlier.

## What changed

- New D1 table `fly_images` (`worker/jobs/schema.sql`, self-created through
  `CREATED_TABLES`): one row per (project, digest). `digest` is the pushed ref
  (`registry.fly.io/builder-<p>:deployment-XXXX`), the value `.image` holds.
  `active=1` marks the ref the pool dispatches from; the PUT flips it in one
  batch, so a project has at most one active row. Additive only.
- Routes (`worker/jobs/src/routes/fly-images.js`): `PUT /api/fly-images`
  (upsert; a resend without bake, cli or baked_at keeps the stored values;
  a digest that is not a `registry.fly.io/<app>:<tag>` ref under the row's own
  `app`, a future
  `baked_at` (more than 120 s ahead of the worker clock) or a bad
  project/app is a 400) and `GET /api/fly-images?project=` (the active row, or
  `row:null`).
- Seam `bin/lib/fly-image-row.sh`: `fir_put`, `fir_load`, `fir_active`,
  `fir_digest`, `fir_baked_at`, `fir_bake_to`. A put is never fatal to its
  caller; it answers rc 3 when the row was NOT recorded. Every read is 0
  answer / 1 none / 2 unknown, and every reader falls back to its file on
  anything but 0. A row naming another project, or a digest that is not a Fly
  ref under its own app, is unknown.
- The stale marker. A put that was not recorded leaves
  `state/fly/<p>.row-stale`, and every read for that project is unknown while it
  is there, so this hub runs on the files it just wrote. Without it one lost
  PUT during a rollback left the row, which every reader now prefers, on an
  image whose smoke had failed (BH-666). The next recorded activating put
  removes it.
- Writers: `bin/fly-image-build.sh` writes the active row only when it parsed a
  pushed ref, after the files. `bin/fly-pool-rollout.sh` activates the built
  ref when it publishes, and re-activates the previous ref when the smoke
  fails. The previous ref is the file's, or the row's on a fresh hub with no
  file. A restore the worker still has not recorded after a second try is one
  ALERTS line naming the project, the failed ref and the PUT that fixes the
  row, because every other hub's pool reads that row.
- DB-first readers: `fleet-propagate.sh` `stamp_of` (the rebake debounce; a
  row time that is not a number or is in the future falls back to
  `.baked-at`), `fly-pool.sh` (the image a spawn uses when the pool is empty
  or older), `fly-provision.sh` (`IMAGE`), and `fly-image-build.sh`'s
  "keep what this project last baked" input to `bake_dep_resolve`.
- Kill switch `FLY_IMAGES_DB` (`catalog/lanes.d/_lib.fly-image-row.json`,
  settings key `lib.fly-image-row.fly_images_db`, default on). 0 = no row is
  sent or read and everything runs on the files, as before.

The files stay. They are the fallback and what the unconverted readers
(`fly-image-refresh.sh`'s drift checks, the `state/fly/<p>.json` readers)
still use. The `fly_image.<p>` settings twins (BH-1035/1517/1528) are left as
they were.

## After deploy

`bin/harness-sync.sh` applies the schema and the routes self-create the table,
so there is no hand step. The first row appears on the next bake (a merge that
propagates, or the 05:40Z refresh). Check it with
`GET /api/fly-images?project=<p>`: the digest should equal the hub's
`state/fly/<p>.image`.

Test: `tests/fly-images.bh-2523-test.sh`, `worker/jobs/test/fly-images.bh-2523.test.js`.
