# BH-6975: the merge conductor acts on PR and check wakes within a minute

Doc: [docs/verification-map/BH-6975.md](../verification-map/BH-6975.md)

## What changed

A new hub lane, `bin/merge-conductor-wake.sh`, runs every minute
(`cron/lanes/413-merge-conductor-wake.cron`, registry
`catalog/lanes.d/merge-conductor-wake.json`). It reads the `pr` and `checks`
wakes above its own wake cursor (`wake_cursors` box `merge-conductor-wake`).
For each wake of an open harness PR it starts the conductor's keyed tick for
that PR only (`MC_ONLY_PR=<owner/repo>#<n>`) through `kw_conductor`
(`bin/lib/keyed-wake.sh`). The keyed tick takes the conductor's PR lock itself.

The 5-minute backstop (`411`) and the 30-minute full tick (`410`) do not change.
`bin/wake-loop.sh` does not change.

## Decisions

- **A cursor, not a claim.** `POST /api/wakes/claim` takes every row it hands
  back. A wake the budget did not reach would be gone. The lane uses its own
  cursor, as `bin/repair-on-push.sh` does. The cursor never passes a wake that
  is not complete.
- **`kw_conductor` is the launcher.** It already starts a detached keyed tick
  with every lock fd closed, and it dedupes per PR with a stamp that the
  conductor's other ringers share. The lane passes `MC_KEYED_WAKE_MIN_S=30` on
  its own call. The other ringers keep 120 s.
- **A deduped launch is carried.** `kw_conductor` rc 1 means a keyed tick for
  that PR started less than 30 s ago, and that tick can have read the PR before
  this event. The key goes to `state/merge-conductor-wake/carry.tsv` and the
  next tick pays it first.
- **Harness PR without a GitHub read.** A repo that no `fleet.conf` project owns
  is skipped. A `not-harness <key>` line in `state/merge-conductor/attempts.txt`
  (the conductor's own verdict) is skipped. A `not-harness-unread` line is not
  proof, so that PR still gets the keyed tick.
- **A checks wake names a head sha.** It maps through
  `state/merge-conductor/pr-state.tsv` (open rows only). A sha with no open row
  gets one `wck_sha_prs` read, at most `MC_WAKE_SHA_LOOKUPS` a tick.

## Log

`logs/merge-conductor-wake-cron.log`, one line per decision:

```
WAKE pr=<n|-> event=<ev> latency_s=<s|-> repo=<slug> wake=<id|carry> action=tick|skip|carry|hold reason=<r>
```

`latency_s` is now minus the wake row's `at` (the worker's receipt time of the
webhook). `action=tick` means the keyed tick started. It does not mean the PR
moved: `logs/merge-conductor.log` says that.

Skip reasons: `unowned-repo`, `not-harness`, `no-key`, `stale`, `no-open-pr`,
`sha-unplaced`, `done-this-tick`. Carry reasons: `deduped`, `budget`. Hold
reason: `budget`. Each tick ends with
`tick wakes=<n> pc=<pr+checks> ticks=<started> carried=<n> budget=<b> cursor=<c>`.

## Knobs

Settings rows `lane.merge-conductor-wake.<env>`:

| Knob | Default | Meaning |
|---|---|---|
| `MC_WAKE_BUDGET` | 10 | keyed ticks started per minute; 0 = none, wakes stay above the cursor |
| `MC_WAKE_WAKES` | 100 | wakes read per tick (every kind) |
| `MC_WAKE_MIN_S` | 30 | the `kw_conductor` dedupe window for this lane's launches |
| `MC_WAKE_MAX_AGE_S` | 900 | an older wake or carry line is skipped `stale` |
| `MC_WAKE_SHA_LOOKUPS` | 5 | `GET commits/<sha>/pulls` reads per tick |

No new env var.

## Off switches and rollback

Rollback: `bin/harness-ctl.sh off merge-conductor-wake "<reason>"`
(`flags/lane-off-merge-conductor-wake`). The lane also stops on `all-off`, a
factory stop (`switch.factory-stop`, it is a `merge` lane), `automerge-disabled`,
`lane-off-merge-conductor` and `lane.merge-conductor.mc_keyed_wake=0`. While it
is off its cursor does not move. After about 27 hours off (more than 10000 wakes
behind) `bin/doorbell-coverage-check.sh` names the box `merge-conductor-wake` as
a stale cursor once a day. That line is expected for a lane that is off.

## Overlap with the wake loop (follow-up)

`bin/wake-loop.sh` still starts its own keyed conductor launch for `pr` and
`checks` wakes (cooled `pr fleet`, 120 s). It does not use the `kw_conductor`
stamp, so the two launches meet only at the conductor's PR lock, and the second
run skips. Worst case is one extra keyed tick per 120 s fleet-wide. Retiring the
wake loop's arm is out of scope for this ticket (wave 3, #6976, or a ticket of
its own).
