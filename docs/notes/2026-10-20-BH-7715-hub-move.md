# Move the hub to a dedicated Fly machine (BH-7715)

Doc: HUB-THINNING-PLAN, RESTORE

## Problem

The hub is an Orgo VM with 4 vCPU. On 2026-10-20 its load was 40 to 81 all day
(14:16Z: 81 / 71 / 57), which is 10 to 20 runnable processes for each CPU. The
load is many short bash, jq, git and gh processes. Orgo does not support
16 vCPU (the operator, 2026-10-20), so the target is a dedicated Fly machine.

## What this change ships

- `bin/hub-move.sh`: one operator CLI. Verbs: `inventory`, `provision`, `seed`,
  `tick`, `dry-run`, `cutover`, `rollback`, `proof`, `drain`. Its header has
  the usage, the knobs and the exit codes.
- `bin/lib/hub-move-fly.sh`: the Fly seam. It is the only hub-move file that
  runs flyctl.
- `bin/lib/hub-move-nowrite.sh`: the no-write mode. A PATH shim directory that
  lets reads through and refuses each write that a guarded binary (gh, curl,
  git, flyctl, rsync, wrangler, ssh, scp, claude, codex, aws, npx) makes when a lane
  calls it by name. It is not a sandbox: a write through a language library
  walks past it. The one hub lane known to do that is `alerts-groom.sh`
  (`bin/alerts-supersede.py` POSTs with urllib), so the tick exports
  `HUB_MOVE_NOWRITE=1` and that script reads it as `--dry`. The tick also sets
  `FLY_BIN_DIR` to the shim directory, and it refuses to start when
  `/root/.fly/bin/flyctl` exists, because `fly-pool.sh`, `fly-dispatch.sh` and
  `fly-image-refresh.sh` put that directory before the shim on PATH.
- `fly/hub/Dockerfile`, `fly/hub/entrypoint.sh`, `fly/hub/fly.toml`: the hub
  image and its boot.
- `catalog/fly-idle-signals.json`: the app `harness-hub` is `exempt`.
  `bin/fly-idle-reaper.sh` runs on the hub and stops any idle machine of the
  org. With no entry, the hub app gets the `metrics` signal and the reaper can
  stop the hub.
- `tests/hub-move.bh-7715-test.sh`.

The move reuses what exists: `bin/state-backup.sh` and `bin/state-restore.sh`
copy the state, `bin/bootstrap-machine.sh --repos-only` clones the repos,
`bin/update-runners.sh` installs the crontab and the rules, and
`bin/hub-load-report.sh` measures the load.

### Tailnet name and IP (ticket item 2)

The new hub keeps the fleet name and the box id, so the jobs worker, the hub
lease, the watchdog ping and the standby line do not change. It gets a NEW
tailnet node and IP. Two nodes cannot share one tailnet hostname while the old
hub is a cold standby, and a copied `tailscaled.state` would clone a node
identity. No committed file dials the hub by tailnet name or IP: case C12 of
the suite greps `bin`, `cron`, `catalog`, `console-ui/functions` and
`worker/*/src` for `ts.net`, `root@<hub>` and the hub hostname, and finds
none. So no reference in git changes. Outside git, the operator gives the new
node the hub's ACL tag through the tagged auth key.

## The no-write mode

`tick` without `--real` puts a shim directory first on PATH. It logs every
call and refuses (exit 75) every write:

| Binary | Allowed | Refused |
|---|---|---|
| gh | `api` with no `-X`/`--method` other than GET or HEAD and no `-f`/`-F`/`--field`/`--raw-field`/`--input`; `pr view/list/diff/checks/status`; `issue view/list`; `run view/list`; `repo view`; `auth status` | every other verb |
| curl | no `-X` other than GET or HEAD, no `-d`/`--data*`/`-F`/`--form`/`--json`/`-T` (joined short flags are read one by one) | anything else |
| git | every verb except the refused ones | `push`, `send-email`, `remote set-url` |
| flyctl, fly | `status`, `version`, `machine list/status`, `apps list`, `volumes list` | everything else |
| rsync | local paths only | any `host:path` operand |
| crontab | `-l` (with an optional `-u <user>`) | every write: install from a file or stdin, `-r`, `-e` (BH-8038) |
| wrangler, ssh, scp, claude, codex | never | always |
| aws, npx | never | always (state-backup `aws s3api` writes the live bucket; `npx wrangler` skips the wrangler shim; lead BLOCK #3203) |

Limits: the shim sees only a binary called by name through PATH. A binary
called by its absolute path, or a script that resets PATH, is not guarded.
`bin/fleet-propagate.sh` resets PATH from `FLEET_PROPAGATE_PATH`, so `tick`
sets that variable to the shimmed PATH. Local file writes on the target are
allowed: they go to the target's copy of the state, not to the live hub.
`bin/lane-shims/_fence.sh` is not a no-write mode: it guards only the five
iron laws and fails open.

### Tick safety (BH-8038)

On 2026-10-22 a no-write tick on bh-hub-2 ran `bin/update-runners.sh`, which
installed the full hub crontab (173 active lines) on the target. From 14:35Z
to 14:43Z the target ran live hub lanes. Its `state/box-name` was the hub's,
so `hub-lease.sh check` passed on both boxes: a split brain. The tick now has
these guards:

1. The shim refuses every `crontab` write (table above).
2. A tick never runs the cron installers `update-runners`, `registry-sync` and
   `fleet-propagate`, in either mode. It prints
   `tick: skipped <lane> (it installs a crontab; ...)`. C6 runs
   `update-runners.sh` itself after the real tick.
3. `seed` sets a LOCAL `flags/all-off` on the target (the file, never a fleet
   row) and writes `state/hub-move/target-seeded`. Both stay until C6.
4. A no-write tick runs only on a box with `state/hub-move/target-seeded`
   (else exit 3). On the live hub, guard 5 would remove the live crontab.
5. On a seeded target, the tick reads `crontab -l` before and after the
   lanes. If it finds an active line (not blank, not a comment, not
   `NAME=value`), it saves the crontab to
   `state/hub-move/target-crontab-found-<ts>.txt`, runs `crontab -r`, sets the
   local `flags/all-off`, writes one ALERTS line (`hub-move-tick-crontab`),
   marks the tick table `# mode=<mode>-crontab-found` (C1 refuses it) and
   exits 4. When the crontab is found before the lanes, the tick writes a stub
   table with that mark and prints its `tick-file:`. `dry-run` fetches the
   table before it checks the tick rc, so C1 never reads an older clean table.
   A cron line that ends in `>/dev/null 2>&1 || true` loses only the redirect.
6. The no-write tick lifts the local `all-off` for its own lanes (else every
   gated lane exits 0 at its gate and the tick proves nothing) and sets it
   again when the tick ends, also on an error exit.
7. The tick keeps each lane's output. A cron line that ends in a redirect
   group to `/dev/null` (`>/dev/null 2>&1`) runs without that group, so its
   stdout and stderr land in `tick-<ts>.out/<row>.out`. A redirect to a log
   file (`>> logs/x.log 2>&1`) stays as it is.

## Runbook

Run every step on the OLD hub unless the step says otherwise.

### Operator prerequisites

1. Mint a Tailscale auth key with the hub's ACL tag. Put it in `fly.env` as
   `TS_AUTHKEY_HUB`.
2. Build and push the hub image from the repo root:
   `docker build -f fly/hub/Dockerfile --build-arg HUB_BASE_IMAGE=<builder image ref> --build-arg FLYCTL_VERSION=<x.y.z> --build-arg PNPM_VERSION=<x.y.z> -t registry.fly.io/harness-hub:hub-<date> .`
   The builder base has no flyctl, and the pool lanes on the hub need it. The
   hub layer installs the pinned flyctl in `/usr/local/bin`, sha256-checked
   against the release's `checksums.txt`. Use the flyctl version the old hub
   runs (`/root/.fly/bin/flyctl version`). Never install it with the flyctl
   installer on the target: that puts it in `/root/.fly/bin`, and a no-write
   tick then refuses. Every `tick` fails (exit 4) when it cannot find flyctl.
   then `docker push` it (or `fly deploy --build-only` with the same Dockerfile).
3. Set `HUB_MOVE_IMAGE` to that image ref.
4. Disarm `cfg:failover` for the cut-over window. The drain (C3) can take
   longer than the watchdog's failover ping window.

### A target that is not a Fly machine (BH-8038)

`provision` is Fly-only. To use an existing host (for example the Hetzner box
bh-hub-2), do not run `provision`. Write `state/hub-move/target.json` on the
old hub by hand:

```json
{"provider":"hetzner","ts_ip":"<tailnet IPv4>","ts_hostname":"bh-hub-2"}
```

With `provider` `hetzner`: `provision` refuses (exit 3); `dry-run` prints
`provision skipped` and runs seed and tick; `seed`, `tick`, C1 to C8 and
`rollback` use only `ts_ip` and need no Fly machine id. C8 prints the provider
and the host. No hub-move verb calls a Hetzner API. A provider other than
`fly` or `hetzner` refuses (exit 3). The host must have flyctl outside
`/root/.fly/bin` (the pool lanes need it; see the prerequisites).

### Dry-run

5. Run `bin/hub-move.sh dry-run --plan` and read the plan. It calls nothing.
6. Run `bin/hub-move.sh dry-run`. It provisions the target, seeds it from the
   latest snapshot, and runs `bin/harness-sync.sh deploy` plus one tick of each
   lane on the target in the no-write mode. The tick table goes to
   `state/hub-move/tick-<ts>.tsv`. The summary line is
   `tick: lanes=<n> ok=<n> fail=<n> timeout=<n> refused_writes=<n> mode=nowrite`.
7. Run `bin/hub-move.sh proof` and keep the output as the BEFORE numbers.

### Cut-over

Each step needs `--confirm`. Without it, the step prints what it would do and
changes nothing. A step refuses (exit 3) when the step before it is not `ok`
in `state/hub-move/steps.tsv`.

8. C1 preflight: `bin/hub-move.sh cutover --step C1 --confirm`. The newest
   tick file must be a no-write tick under 24 h old, with no lane that failed
   for a reason other than a refused write or a timeout. A lane that fails in
   the no-write mode by design (or fails on the live hub too) goes in the
   reviewed allow-list `HUB_MOVE_C1_ALLOW=<lane>,<lane>` (tick lane ids; `lib`
   also covers `lib~2`). Read each lane's `tick-<ts>.out/<row>.out` before you
   add it. C1 prints `HUB_MOVE_C1_ALLOW=<list>; allowed failures: <lanes>`, and
   its `steps.tsv` row records `allow=<list> allowed_failed=<lanes>`. A failed
   lane outside the list still refuses.
   C1 then compares each remaining failed lane with the old hub (this box).
   It maps the lane id to its command through `render-cron.sh <box-id>` (the
   same id rules as the tick), and it reads the cron journal
   (`journalctl -t CRON -o short-unix --since @<tick at - HUB_MOVE_C1_OLD_WINDOW_S>`,
   default window 86400 s; `HUB_MOVE_CRON_JOURNAL=<file>` reads a file in that
   form instead). The newest run of that command in the window gives the old
   hub rc: the `failed with exit status <rc>` line of the same `CRON[<pid>]`,
   else 0. If that rc is the same as the tick rc, the lane is
   `same-on-old-hub` and does not refuse. C1 prints
   `same-on-old-hub: <lanes>` and `steps.tsv` records
   `same_on_old_hub=<lanes>`. A lane with a different old-hub rc refuses with
   `old hub rc=<rc>`. A lane whose old-hub rc cannot be read (no journalctl,
   journalctl failed, the lane is not in the crontab, no run in the window)
   refuses with `old hub rc unreadable: <why>`. This needs cron to log failed
   jobs (the Debian `(CRON) error (grandchild ... failed with exit status N)`
   line). Without those lines every run reads rc 0, so a lane stays a failure;
   the allow-list is then the override.
9. C2 pause merge: `flag_set automerge-disabled` (a fleet harness_flags row)
   and `flag_set lane-off-merge-conductor` (a pause_flags row and its
   `flags/` mirror) on the old hub, through `bin/lib/flags.sh` (BH-4153).
   Each write is proved by a `flag_has` read.
10. C3 drain: saves the crontab to `state/hub-move/old-crontab`, runs
    `crontab -r`, and waits up to `HUB_MOVE_DRAIN_TIMEOUT_S` (1800 s) for no
    `bin/` process. At the timeout it lists them and exits 4. Rerun with
    `--force-drain` to go on. A rerun never overwrites a saved crontab with an
    empty one.
11. C4 copy: `BACKUP_FORCE=1 bin/state-backup.sh`, then `seed` from the exact
    snapshot that `state/backup-last.json` names (never `latest`), then
    sets `all-off` on the old hub with `flag_set --local-only` (the
    `flags/all-off` file and no row: a fleet all-off row would stop the
    target too).
12. C5 split-brain check: the old crontab is empty and `all-off` reads on
    (`flag_has`) on the old hub; on the target the crontab has no active line
    and (`bin/jobs-client.sh flag-has`) `all-off` (set by seed) and
    `automerge-disabled` read on.
13. C6 start: on the target, `flag-clear --local-only all-off` (proved off by
    `flag-has`), then `hub-lease.sh renew` until `hub-lease.sh check`
    is rc 0 (up to `HUB_MOVE_LEASE_WAIT_S`, 120 s), then
    `bin/hub-move.sh tick --real` (one real tick of each lane), then
    remove `state/hub-move/target-seeded`, then `bin/update-runners.sh`
    (crontab and rules). The marker goes first, so a C6 rerun after a failed
    `update-runners.sh` does not remove the crontab it installed. The lease
    comes first, so the
    lanes behind `hub-lease.sh check &&` really run in that tick.
14. C7 resume merge: `bin/jobs-client.sh flag-clear` of the two C2 flags on
    the target, then `flag-has` proves both read off. The old hub keeps
    `flags/all-off`.
15. C8 cold standby: writes `state/hub-move/cold-standby-until` (now + 7 days)
    on the target and prints the retire step.
16. Re-arm `cfg:failover`.

`--all --confirm` runs every step that is not `ok` yet, in order, and stops at
the first failure.

### Proof

17. 24 h after C8, run `bin/hub-move.sh proof --since <C8 time>` on the new
    hub. Compare `load5_per_vcpu` and the `conductor_ticks` line
    (secs_p50/p90/max) with the BEFORE numbers from step 7.
18. Decide about `hub_load.shed` (off since 2026-10-20) after the proof.

### Retire

19. After the date in `cold-standby-until`, retire the old Orgo VM in the Orgo
    console. `HUB_MOVE_OLD_VM_ID` makes C8 print its id.
20. On the new hub, remove the `tmp/hub-move-restore-*` directories that
    `seed` left.

## Rollback

Rollback restores the target's last snapshot into an empty tree and swaps it in (state, flags, logs; env through its compat link; the build summaries over their live copies; the orchestrator). The replaced dirs stay under `tmp/hub-move-prev-*`. It also writes a `reset` row for C1 to C8, so a later `cutover --all --confirm` starts again at C1 and runs the C5 split-brain check.

`bin/hub-move.sh rollback --confirm`, on the old hub, at any step after C3:

1. On the target: `crontab -r`, then `bin/hub-move.sh drain`, then
   `BACKUP_FORCE=1 bin/state-backup.sh`, then
   `bin/jobs-client.sh flag-set --local-only all-off on`.
2. On the old hub: `state-restore.sh hub <that ts> --apply`, remove
   `all-off` (`flag_clear --local-only`), and put back `state/hub-move/old-crontab` byte for byte
   with `crontab`.
3. Merge stays paused (`flag_set` of `automerge-disabled` and
   `lane-off-merge-conductor`). When the old hub is healthy, run
   `bin/jobs-client.sh flag-clear automerge-disabled` and
   `bin/jobs-client.sh flag-clear lane-off-merge-conductor` on it.

Without `--confirm` it prints the plan and changes nothing.

## State files

| File | Writer | Reader |
|---|---|---|
| `state/hub-move/target.json` (`app`, `region`, `size`, `ts_hostname`, `volume_id`, `machine_id`, `ts_ip`, `provisioned_at`) | `provision`, one field at a time, right after each resource is found or created; `ts_ip` only after tailscale shows the host | `seed`, `dry-run`, `cutover`, `rollback` |

| `state/hub-move/tick-<ts>.tsv` (`# mode=… at=…`, then `lane rc secs refused timed_out`) | `tick` | `cutover` C1, `dry-run` |
| `state/hub-move/tick-<ts>.out/<row>.out` (each lane's output; row 1 is the first lane of the table) | `tick` | the operator, when C1 names a failed lane |
| `tmp/hub-move-restore-<ts>-<pid>/` (the pulled snapshot) | `seed`, `rollback`, through `state-restore.sh --dest` | nobody; a new one each run, because `state-restore.sh` refuses a destination that exists |
| `state/hub-move/old-crontab` | `cutover` C3 | `rollback` |
| `state/hub-move/target-seeded` (on the target) | `seed` | `tick` (a no-write tick refuses without it); removed by C6 |
| `state/hub-move/target-crontab-found-<ts>.txt` (on the target) | `tick`, when it finds and removes a crontab | the operator |

The files are local to the old hub (the target keeps its own tick files and
`cold-standby-until`). They are move evidence and are not pruned.

## Not verified on the build box

The build box has no hub env, no age identity, no hub ssh key and no Fly org
token, and a real provision buys a performance-16x machine. The build ran
`bin/hub-move.sh dry-run --plan` (no call) and the fixture suite. The hub image
was not built (no docker on the build box). The real dry-run, the image build
and the cut-over are operator steps.
