# D1 hot statements: a sampled statement counter, 20 hot statements under EXPLAIN, retention for every table (BH-9076, slice 5 of BH-9067)

Doc: DB-COORDINATION-SPEC

## Why

On 2026-11-04 the jobs D1 read 2.86 billion rows in one day and the worker
answered 873 HTTP 500s ("D1 DB is overloaded"). The target from BH-9067 is under
300 rows read per query on average and 0 "overloaded" answers a day. Nothing
measured which statements read the rows. This slice adds the measurement, pins
the hot statements to an index, and gives every table a retention rule or a
written reason.

## 1. The statement counter

- `worker/jobs/src/lib/stmt-stats.js`, wrapped ONCE around the handler object
  in `worker/jobs/src/index.js` (`withHarnessSentry(withStmtStats({...}))`). The
  fetch body of index.js did not change.
- Sampling is per request. A request is sampled when
  `d1.stmt_stats_sample_pct > 0` and `random() * 100 < pct`. A sampled request
  counts every statement it runs on `env.DB`, OPEN_ROUTES (webhooks) included.
  An unsampled request gets the same `env` object: zero added work.
- The stats DB proxy is memoised per binding (as `retryingDb` is), so the
  ensureTable, archive-read and settings-cache caches keep a stable key. It
  sits OUTSIDE `retryingDb`: a retried attempt counts as one more call, because
  it is real D1 load.
- Key: `(hour, sql_hash)`. `hour` is the UTC `YYYY-MM-DDTHH` at the call.
  `sql_hash` is FNV-1a 64 (16 hex) of the normalized text: string and number
  literals become `?`, `?N` becomes `?`, `IN (?, ?, ...)` becomes `IN (?)`,
  comments go, whitespace collapses.
- `rows_read` comes from `meta.rows_read`. `all()`, `run()` and each statement
  of a `batch()` carry meta. `first()` and `raw()` do not, so they add a call
  with 0 rows_read. A statement that throws still counts as a call.
- Only where the runtime gives `ctx.waitUntil`. The knob read and the flush run
  in `ctx.waitUntil`, after the Response, so the counter adds no latency. A call
  without ctx (the node suites call `worker.fetch(req, env)`) is never sampled
  and reads nothing. The first request of an isolate is never sampled: it starts
  the knob read, so a settings row of 0 is never overridden by the code
  fallback of 1.
- The flush swaps the isolate accumulator out and writes it in ONE batch of
  upserts (`ON CONFLICT (hour, sql_hash) DO UPDATE SET calls = calls +
  excluded.calls, ...`). Two isolates flushing one hour add up. The flush and
  the knob read use the raw binding, so they never count themselves. A flush
  that fails logs one `stmt-stats: flush of N key(s) dropped` line and drops
  those counts: they are sampled stats, never user data.
- Over `d1.stmt_stats_max_keys` distinct keys, a new statement counts under the
  hash `overflow` (sql_text `(overflow)`), so the cap shows in `/top`.
- `GET /api/d1/stmt-stats/top?hours=24&n=20` (bearer) reads
  `idx_d1_stmt_stats_hour_calls` (range on hour, proven by EXPLAIN in
  stmt-stats.bh-9076 S9) and answers the statements by calls. `calls` and
  `rows_read` are sampled counts; `sample_pct` is in the answer.

| Settings row | Seed | Range | What |
|---|---|---|---|
| `d1.stmt_stats_sample_pct` | 1 | 0..100 | percent of requests counted (0 = off) |
| `d1.stmt_stats_refresh_s` | 300 | 10..3600 | seconds an isolate keeps the knobs |
| `d1.stmt_stats_sql_max_chars` | 500 | 50..4000 | normalized SQL kept per row |
| `d1.stmt_stats_max_keys` | 500 | 10..10000 | keys an isolate holds before `overflow` |
| `d1.stmt_stats_top_max` | 100 | 1..1000 | largest `n` for `/top` (more is 400) |
| `d1.stmt_stats_hours_max` | 336 | 1..8760 | largest `hours` for `/top` (more is 400) |
| `retention.d1_stmt_stats.days` | 14 | 0..3650 | rule `stmt_stats.age` |

D1 cost at the seed: about 1 percent of requests add one batch statement after
the response, plus one 4-row settings read per isolate per 5 minutes.

## 3. Retention coverage

Every `CREATE TABLE` in `worker/jobs/schema.d/` is now in the composed retention
RULES or has exactly one `-- no-retention: <table> <reason>` line
(`worker/jobs/test/d1-retention-coverage.bh-9076.test.js` C1). Of the 180
tables without a rule on main: 1 delete rule, 23 archive rules, 156
no-retention lines (154 in `schema.d/202611070341-bh-9076-no-retention.sql`, 2
in older fragments). `d1_stmt_stats` has the rule `stmt_stats.age`.

- Delete (`retention.d/bh-9076-ops-delete.js`): `ci_duration_runs` (30 days;
  its only read is by run_id when one CI run posts again).
- Archive (`retention.d/bh-9076-history-archive.js`, `quietUnbound`, specs in
  `src/lib/archive-tables.bh-9076.js`, spread into `ARCHIVE_TABLES` in
  `src/lib/archive.js` with one line): 180 days unless a reader needs more
  (route_shadow 400, block_findings 730). While the archive D1 is unbound
  (today: the binding is commented out in `wrangler.jsonc`) these rules delete
  nothing and only count.
- Every new window is a `retention.<table>.days` settings row, seeded in
  `schema.d/202611070340-bh-9076-retention-indexes.sql` with 17 `CREATE INDEX
  IF NOT EXISTS` on the time columns the id reads use
  (`retention-rules-explain.bh-9076.test.js` R1 proves each with EXPLAIN).
- The global `retention.dry_run`, `retention.max_rows` and `retention.batch`
  apply. The retention route module did not change. Each active rule adds one
  `retention_runs` row per hourly run (25 new rules: about 600 rows a day; the
  `retention_runs.age` rule keeps 90 days).
- A rule name must match `^[a-z_]+\.[a-z_]+$` (bin/d1-retention.sh skips any
  other name), so the stats rule is `stmt_stats.age` and the box_commands_v2
  rule is `box_command_history.archive`.
- Owed (the no-retention line says so): 11 rules need an index on a table with a
  hand-written schema copy pinned by created-tables.bh-4987 (alert_actions,
  config_changes, cost_cap_changes, model_route_changes, route_rule_changes,
  routing_changes, price_audit, steer_notes, risk_tiers, queue_risk_scores,
  context_packs). 43 more tables are claim or dedupe rows, tables a reader reads
  whole today (jobs and its children, verdicts, pr_state_events, decisions,
  findings, registry_audit, pr_costs), or records with no reader audit yet.
  Each needs a reader audit before a rule.

## 4. Summary tables owed

No summary table ships. The rule of this slice builds one only for a fixture
statement that is a GROUP BY over a hot table with no time window. Every
GROUP BY in the fixture (H10, H15, H16, H17, H18, H20) has a window. These
GROUP BY reads run over all history of a growing table and are owed:
- `worker/jobs/src/routes/utilization.js:121`, utilization_snapshots: latest
  hour per project (`MAX(hour) ... GROUP BY project`) over every snapshot.
- `worker/jobs/src/routes/alerts.js:472`, alerts: `group=family` with no
  `since_s` groups every alert row.
- `worker/jobs/src/routes/archie-actions.js:264`, archie_actions:
  `count_by=action` with no `day` groups every action.
- `worker/jobs/src/routes/roadmap-ideas.js:91`, roadmap_ideas: per project and
  lane counts over every idea.
- `worker/jobs/src/routes/lessons.js:99`, lessons: per category and status over
  every lesson.
