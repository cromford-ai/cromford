# Watchman: the security lanes, a history secret scan and a rotation register (BH-5565, wave 8 of #5556)

Doc: EVENTS, ALERTS-STATE-MACHINE

## What changed

1. Watchman owns the four security lanes. Schema fragment
   `worker/jobs/schema.d/202610170334-bh-5565-watchman-lanes.sql` adds one
   `staff_lanes` row per lane (`INSERT OR IGNORE`, no DDL). The roster route
   and the `/staff` screen show them. No lane changes: each one keeps its
   script, cron line, kill switch and alerts.
2. A new collector, `bin/staff/watchman-collect.sh`. `bin/staff.sh tick
   watchman` runs it at step 6. Until now that step found no collector and
   collected 0 items. The collector makes no model call. It prints two checks
   as staff findings, class `history-secret` and `rotation-due`.
3. A new register directory, `catalog/staff-rotations.d/`. One file per
   credential, named `<id>.json`. The build seeds no file: the real rotation
   dates are not in anything the build could read, and a guessed date files a
   false ticket.
4. Knobs are settings rows, `lib.staff-watchman.<env>`
   (`catalog/lanes.d/_lib.staff-watchman.json`), applied with
   `lib_env_apply staff-watchman`. A value out of range is one warn line in
   `logs/staff.log` and the default.
5. The soul's REPORT list names both checks.

## The lane read

Each lane was read (its header, its registry file, its switch) before the
ownership row was added. None of the four reads git history or a rotation
date, so the two new checks overlap with none of them.

| lane | what it watches | where it runs, how often | switch | what it writes or pages |
|---|---|---|---|---|
| `security-scan` | a weekly codex-security audit of a project repo, $20 cap per scan | project boxes project-4, project-1, project-2; Sundays | `lane-off-security-scan` | ALERTS and a beat for a new HIGH or CRITICAL finding; the export in `logs/security-scan.log` |
| `claude-auth-check` | the Claude credential of every box (`cred_probe claude`), plus one inference probe per account per UTC day | hub, hourly at :51 | `lane-off-claude-auth-check` | one alert per outage per box, one recovery line |
| `gh-pat-charge-alert` | GitHub calls charged to a personal access token bucket in the last complete UTC hour (`GET /api/metrics/gh-ledger`) | hub, hourly at :17 | `lane-off-gh-pat-charge-alert` | one ALERTS line per (box, bucket) per UTC day |
| `audit-tail` | the kernel audit trail of the harness roots; deletion, rename and truncate bursts | every box, every 5 min | `lane-off-audit-tail` | one line per burst in `logs/audit-tail.log`, one alert through `bin/lane-alert.sh` |

a cost signal for Quartermaster.

## history-secret

- The repos: `bin/fleet-conf.sh --projects`, each at `WM_REPOS_ROOT/<project>`
  (default `/root/repos`) on the box that runs the staff lane. The scan reads
  each clone as it is. It never fetches and never checks out. A project with
  no clone is logged once per interval (`<p> has no repo at <path>`), not
  scanned. A box must hold a clone of a repo for the scan to cover it.
- Due: the last attempt (`state/staff/watchman/scan/<p>.at`) is older than
  `WM_SCAN_INTERVAL_H` (default 24), or absent. Exactly the interval is not
  due. At most `WM_SCAN_REPOS_PER_TICK` (default 1) due repos per tick, oldest
  attempt first.
- Incremental, in chunks: the cursor `scan/<p>.tips` is a set of commits
  whose whole history is scanned. Done = the cursor is the ref tips; equal =
  no gitleaks run. Otherwise the unscanned commits are `git rev-list
  --reverse --topo-order --all --not <saved tips that still exist>`, oldest
  first. If they fit in the chunk (`WM_SCAN_CHUNK_COMMITS`, default 400), the
  pinned gitleaks 8.30.1 (`bin/lib/gitleaks-pin.sh`) runs `git <repo>
  --log-opts "--all --not <cursor>" --redact=100 --gitleaks-ignore-path
  <repo>`. If not, it reads the first chunk only: `--log-opts "<heads of the
  chunk> --not <cursor>"`. Reverse topo order puts each parent before its
  children, so the chunk holds every unscanned parent of its commits and that
  range is exactly the chunk. After a good chunk the cursor becomes `git
  merge-base --independent <cursor> <heads>`. A saved tip that no longer
  exists (force push, gc) is dropped from `--not`, so the range only grows.
- The tick budget: `bin/staff.sh` kills the collector at
  `STAFF_COLLECT_TIMEOUT_S` (default 120, now passed to the collector). Scans
  get that minus 20 s. One gitleaks run gets `WM_SCAN_TIMEOUT_S` (default 90)
  or what is left of the budget, whichever is less. A `WM_SCAN_TIMEOUT_S`
  over the budget is one warn line and the budget. Chunks of one repo run
  while the budget lasts. A run cut short by the budget is not a failure: the
  tick stops and the next tick resumes. A repo whose scan is not done is due
  again at once (`.at` = now - interval - 1 s), behind the repos that waited
  longer.
- A chunk of more than one commit that times out with the full limit halves
  the chunk size of that repo (`scan/<p>.chunk`). A run that takes under a
  quarter of the limit doubles it back, up to `WM_SCAN_CHUNK_COMMITS`. One
  commit that times out is a failed scan.
- The repo's own `.gitleaksignore` applies (`--gitleaks-ignore-path <repo>`;
  the gitleaks default is the working directory, not the repo), and so does a
  `.gitleaks.toml` at the repo root. They are how a repo allowlists its test
  fixtures.
- Measured by the refute review (2026-10-15, the real `cromford` clone, 3602
  commits): one `--all` run took 169 s and found 2859 locations (2312
  generic-api-key, 49 private-key, most in test files). That is the case the
  chunks and the baseline are for. See "First scan of cromford" below.
- Only `RuleID`, `File`, `StartLine` and `Commit` are read from the report.
  `Secret`, `Match` and `Message` are never read. A row that fails validation
  (commit 40 hex, rule `[A-Za-z0-9_.-]{1,64}`, line a positive integer, file
  1..200 chars after control characters are stripped) is skipped with one log
  line.
- Item: `{"check":"history-secret","project","commit","file","line","rule"}`.
  Title: `Critical: secret in git history: <rule> in <p> <file>:<line> (commit
  <sha12>)`. Source url: `https://github.com/<slug>/commit/<sha>`.
- The first scan of a repo (no `scan/<p>.based`) is held: each chunk's
  locations go to `first/<p>.jsonl`, with no line and no beat. When its last
  chunk is done:
  - at most `WM_FIRST_SCAN_MAX` (default 100) locations: each one is NEW, as
    below. The project-3 case (one key in history) is this path.
  - more: a baseline. The locations go to `base/<p>.jsonl` and are never
    printed one by one. ONE finding, class `history-baseline`, item
    `{"check":"history-baseline","project","locations","at"}`, title
    `Critical: <N> secret-shaped locations in the git history of <p> at its
    first scan (<F> files; <top 3 rules with counts>). Too many to file one
    by one: review state/staff/watchman/base/<p>.jsonl on <host>, and
    allowlist test fixtures in the repo .gitleaksignore`. One beat with that
    title (`--id staff-watchman-baseline-<p>-<epoch>`). A person reads the
    file once; a real key among the fixtures is in it.
  - then `scan/<p>.based` is written.
- A location not in the leak cache (`leaks/<p>.jsonl`), the baseline or the
  held first scan is NEW. The cache is written first. Then, if NEW > 0 and
  `WM_PAGE_SEVERITY` is not `off`, ONE beat per scan run: `bin/lane-alert.sh
  --id staff-watchman-leak-<p>-<scan epoch> --severity <WM_PAGE_SEVERITY>
  staff "<first title> (+N more)"`. Then the cursor is saved. A location
  found again is not NEW and does not beat.
- A failed scan (gitleaks rc not 0, one commit that times out, a report that
  is not a list, a cache that cannot be written) is one `scan <p> failed
  (<why>)` line. Nothing is saved, so the next due scan repeats the range.
  `scan/<p>.fail` counts failed attempts in a row; the `WM_SCAN_FAIL_ALERT`-th
  (default 3) is ONE warn beat (`--id staff-watchman-scanfail-<p>-<epoch>`):
  the repo is not covered. A good scan resets the count. A pinned install
  that fails is one warn line and no scan this tick; the project is not
  stamped, so the next tick tries again, and the same count (`_gitleaks`)
  pages at the same threshold.
- Every tick prints every cached location and every baseline finding. A
  cached location is a finding until a person suppresses it (BH-5560); the
  claim makes the repeat free.

## rotation-due and the register

A register file, `catalog/staff-rotations.d/<id>.json`:

```json
{"id":"anthropic-api","where":"env file global.env, variable ANTHROPIC_API_KEY","owner":"operator@example.com","rotated_at":"2026-09-01","every_days":90}
```

or, for a credential with a fixed expiry, `"due":"YYYY-MM-DD"` in place of
`rotated_at` and `every_days`. Rules, each checked per file (a bad file is one
`register <id>.json invalid (<why>)` line and is skipped):

- the file name is `<id>.json`; id `^[a-z][a-z0-9-]{1,47}$`;
- `where` names the file and the variable, 1..200 chars, and holds no run of
  24 or more `[A-Za-z0-9+/=_-]` characters, so a value cannot be pasted in;
- `owner` 1..100 chars;
- exactly one of `due`, or `rotated_at` + `every_days` (an integer 1..3650);
- dates are real `YYYY-MM-DD` dates.

To add a credential, open a PR that adds its file. To record a rotation, open a
PR that moves `rotated_at` (or `due`). So every rotation is in git history.

The check fires when now >= due + 1 day (00:00Z after the due date; the due
date itself is not late). Item: `{"check":"rotation-due","credential","due"}`,
one claim per due date, so one ticket at `augmentation`. A fire writes the latch
`state/staff/watchman/due/<id>` = the due date.

A ROTATED credential: the register's due is later than the latch, and now <
the new due + 1 day. The collector then reads `GET
/api/staff/findings?agent=watchman` once. A `filed` row with the old item's
agent-core fingerprint gets `gh_rest PATCH repos/<o>/<r>/issues/<n>`
`{"state":"closed","state_reason":"completed"}`, then `POST
/api/staff/outcomes` with outcome `merged`, then the latch is deleted and one
`closed <id> as merged` line is logged. A failed read, PATCH or POST keeps the
latch and the next tick tries again; the hourly resolver
(`bin/staff-outcomes.sh`) also maps the closed issue to merged. A finding that
was never filed (Watchman is at `automation`, so it was a digest line) is one
log line, the latch is deleted and nothing is posted. A new due that is already
past does not close: it fires as a new item. A register file deleted: the latch
is deleted, nothing is closed.

## Print order

Rotation lines come first, by id, then the baseline findings. History lines follow, ordered by when each
was last inside the first `STAFF_MAX_ITEMS` lines
(`state/staff/watchman/printed.tsv`), then by location. `bin/staff.sh` claims
only the first `STAFF_MAX_ITEMS` lines, so a backlog moves through the claim
window and every location is claimed within ceil(total / STAFF_MAX_ITEMS) ticks.

## Blast radius

The first hub pass over the 13 fleet repos sends at most one beat per repo:
a leak beat (at most `WM_FIRST_SCAN_MAX` findings) or a baseline beat (one
finding). A repo that fails `WM_SCAN_FAIL_ALERT` times in a row adds one warn
beat. After that a beat needs a new commit with a secret. rotation-due sends
no alert. The kill flags (`staff-off-all`, `staff-off-watchman`) stop the tick
in `bin/staff.sh` before the collector runs, so a set flag stops every scan,
beat and issue close.

## First scan of cromford

Run on 2026-10-15 on this box: the collector with the pinned gitleaks 8.30.1,
default knobs, against the real `/root/repos/cromford` clone (3602
commits), each tick under `timeout 120` as `bin/staff.sh` runs it.

- Tick 0 (101 s): the first 400 commits timed out at 90 s, so the chunk went to
  200. The rest of the budget (10 s) was too short for a chunk; the tick stopped.
- Ticks 1 and 2 (100 s each): 200, 200, 200, then 400-commit chunks (the chunk
  doubled back after fast runs).
- Tick 3 (6 s): the last 6 chunks of 400. The first scan was done: 2783
  locations (keyed by commit, file, line and rule) in 73 files. That is more
  than 100, so the result was 1 `history-baseline` finding and 1 critical beat.
  There were 0 `history-secret` lines.
- Tick 4 (0.2 s): `scanned cromford unchanged`, 1 line (the baseline).

No tick went past 101 s. Before this change, every due scan of this repo
timed out at 90 s and saved nothing.
