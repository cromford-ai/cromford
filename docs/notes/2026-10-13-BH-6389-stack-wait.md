# A child slice builds on an open parent only with a disjoint Stack section (BH-6389)

Doc: MERGE-CONDUCTOR

## Why

In the 7 days to 2026-10-13, 96 cromford PRs were stacked on an open
parent. 53% of them had a merge conflict (plain PRs: 18%). Their median time to
merge was 52.0h (plain: 12.4h). They were 27% of merged PRs and used 49% of all
PR-hours.

## What changed

1. **New default `STACK_WAIT_PARENT_MERGE=plan`.** The values `off`, `rollouts`
   and `all` keep their BH-5234 behaviour. `plan` is `rollouts` plus the stack
   plan gate below. An invalid value now reads as `plan`.
   `bin/unblocked-children.sh` treats `plan` as `rollouts`, so the STACKABLE
   lines are still emitted.
2. **Pre-plan decision.** In the `stacked child builds` block of
   `bin/lib/rb/gates.sh`, `sw_pre` (`bin/lib/stack-wait.sh`) answers:
   - `exempt`: the child is a hotfix (`HOTFIX=1`). It stacks as before.
   - `wait`: a `waiting` row exists and is under the cap. The build answers
     `BUILD_DEFERRED stack-wait: … Blocked-by #<parent> …` and exits 3. No plan
     is bought.
   - `capped`: the `waiting` row is at or over `STACK_WAIT_CAP_H`, or the row is
     already `capped`. The row goes `capped`, the log names the cap, and the
     child builds from the real base without the parent.
   - `pending`: anything else. The child is planned on the parent branch, and
     `$BUILD/stack-wait-pending` (parent branch, then the parent's files) tells
     the planner the `## Stack` rule through `UI_PLAN_NOTE`.
3. **Post-plan decision.** The `stack plan check (BH-6389)` block is the first
   block of `rb_gate_overlap`. `sw_post` approves the stack only when plan.md
   has a `## Stack` section (level 2, outside code fences) that lists files, and
   no listed file is in, under, or over a path of the parent's diff
   (`origin/<base>...origin/<parent>`) or the parent's committed
   `.harness/specs/*/plan.md` (minus its `## Sibling claims` and `## Verify`
   sections and `VALIDATE:` lines). Approved: row `stacked`, the build goes on
   stacked. Else: row `waiting` (the first deferral's time is kept), one issue
   comment with a `Blocked-by #<parent>` line, then `BUILD_DEFERRED stack-wait:`
   and exit 3.
4. **Parent merged.** No change: its branch is deleted, the fetch in the
   stacked block fails, and the child builds on main.

## State

- Ledger kind `stack-wait`, key `<project> <KEY> <parent-branch>`, status
  `waiting | stacked | capped`, detail `since=<epoch> why=<text>`. File twin:
  `state/stack-wait/<project>/<KEY>.<parent, / as _>`.
- Comment marker: ledger kind `commented`, key
  `stack-wait <project> <KEY>:<parent>`, file
  `state/comment-marks/stack-wait/<project>/<KEY>.<parent, / as _>`. Board
  projects get no comment. A skipped or failed post is one line in
  `logs/stack-wait.log`.

## Knobs

- `STACK_WAIT_PARENT_MERGE` (lib `stale-parent`): default `plan`. Set
  `rollouts` to restore the pre-BH-6389 stacking.
- `STACK_WAIT_CAP_H` (lib `stale-parent`): hours, 1..336, default 24.
