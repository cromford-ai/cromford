# The rollout dispatch hook: a `## Rollout` master files its waves, it never plans

Doc: BUILD-CONCURRENCY

**What changed.** BH-816 is split in slices; this is the run-build half, the
dispatch hook and the two terminals it can write.

- **A new `# >>> rollout hook` block in `bin/run-build.sh`**, between the
  `# <<< ticket meta` marker and `# >>> preplan adopt`. It reads the ticket body
  out of the build's `ticket-meta.json`, skips any ticket whose title is already
  a child (the size gate's own `<KEY>.<n>` regex, byte for byte), asks
  `bin/run-rollout.sh --is-rollout` whether the body carries a rollout section,
  and on yes runs the lane, records its result line and exits 0. It parses
  nothing itself. Detection is delegated, because the fence rules live in one
  place (`fc_strip_fences` and `fc_has_rollout` in `bin/lib/file-children.sh`)
  and a second copy of them is how the two drift.
- **`TICKET_META()` now also selects the ticket body**: `--json title,labels,body`
  on the issues lane, `.description // .body` inside the existing envelope on the
  board lane. Same single call either way, so the hook costs no extra API spend.
  `bin/kind-gate.sh` reads the type, label and title fields only, and the size
  gate reads the title only, so the extra key is inert to both.
- **`_job_finish` maps `ROLLOUT_FILED*` to `done`**, in the same case arm as
  `DECOMPOSED*`. `ROLLOUT_FAILED` is not named there and falls to `failed`,
  exactly as `DECOMPOSE_FAILED` does. A `done` row is therefore only ever
  produced by a `ROLLOUT_FILED` line the lane itself wrote, with rc 0 behind it;
  a FILED line from a run that exited non-zero is demoted to FAILED before the
  RESULT is written.
- **The result-sweep rule is in the prompts.** `ROLLOUT_FILED <n>` means the
  children are ordinary new tickets from here and the master has been parked on
  purpose: unlabelled on the issues lane, `in_progress` on an in-app board.
  Never re-label it, never close it by hand, add nothing on it. `ROLLOUT_FAILED`
  means a rollout body filed no waves, so it is one ALERTS.log line naming the
  ticket and `<dir>/rollout-run.txt`, and no comment.

**Why the hook sits where it does.** A rollout master is not work, it is a list
of work. Planning one buys a model call to summarise text its author already
wrote, and the plan it produces is thrown away the moment the waves are filed.
So the hook sits ahead of the pre-plan adoption and ahead of the PLAN launch:
the master never adopts a pre-plan, never reaches `agent-call.sh`, and the size
gate never sees it. The only ticket that gets planned is a wave, when its turn
comes.

**Fail-open, on every absence.** No `ticket-meta.json`, no `body` field in it
(a build resumed from a dir written before this change), an empty body, or no
executable `bin/run-rollout.sh` on the box, and the block does nothing at all:
the ordinary PLAN path runs as it does today. A detector that answers no, or
crashes, falls through the same way. Nothing is filed on an answer we did not
get. That is deliberate and it is what lets this slice merge on its own:
**`bin/run-rollout.sh` does not exist yet** (it is its own ticket, #984), so on
every box today this hook is inert and a `## Rollout` body is planned and built
like any other ticket. When that script lands the hook starts dispatching with
no further change here.

**For BUILD-CONCURRENCY.** Rollout children are chains ON PURPOSE. Each wave
carries `Blocked-by: #<n> (hard)` on the one before it, because a rollout author
sequences waves for the reason that wave 2's code builds on wave 1's. That is a
declared hard dependency, not an ordering preference, so the dependency
verifier leaves it alone and the queue rules simply release each wave when the
one before it has merged. A chain of waves is not a queue the concurrency rules
should break up: running two waves at once is the failure mode the rollout kind
exists to prevent. The other half of this is the decomposition cap. The
two-level cap and the depth-1 guard key off `.n.m` titles, and a wave's title is
`.n`, so a wave that plans out XL is still decomposed normally into `.n.m`
children and those children are the ones that are never split again. Waves are
cheap to add; depth is what we cap.
