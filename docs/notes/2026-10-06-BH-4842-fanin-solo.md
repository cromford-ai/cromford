# A conductor worker killed before fan-in says why, and a PR missing twice is worked alone

Doc: MERGE-CONDUCTOR

## What changed

BH-4842. On the hub, `logs/merge-conductor.log` had 134 `ALERT FANIN
merge-conductor … (run died before fan-in)` lines naming the same PRs fire
after fire, and clean, green, approved PRs (#4680, #4620) never reached READY.

**What kills the run, read from the code.** `bin/merge-conductor-backstop.sh`
runs every keyed fire as `timeout 240 bin/merge-conductor.sh`. GNU `timeout`
signals its whole process group, which holds every `tick_project` subshell and
every per-PR worker. Nothing there trapped TERM, so the run died before
`fanin_end`, and everything after the fan-out never ran either, including the
tier-2 `ae_project` enqueue for the clean siblings in the same batch. The
backstop picks the oldest `since` first, so the PRs that keep the run slow are
picked again on every fire. Which call each starved PR was in when it was
killed is not proven by the code. The stamps below exist to show it.

What ships, all in `bin/lib/fanin.sh` unless named:

- **Two new ledger lines.** `X <id> signal=<SIG> after=<N>s` is written by a
  worker wrapper (`fanin_run_sub`) that gets TERM/INT/HUP before its body
  returns. The body runs as a background child the wrapper waits on, so the
  stamp lands at once and the signal is forwarded to the body. No `A` line is
  written, so the id stays missing. `T signal=<SIG> after=<N>s` is written by
  the run's own shell when the caller opted in with `fanin_trap_run`, which the
  conductor's `tick_project` does right after `fanin_begin`. SIGKILL cannot be
  trapped and leaves neither line.
- **A body killed outright while its wrapper lives** is still accounted, now as
  `… rc=137 signal=KILL`.
- **The stage.** `fanin_run_sub` sets `FANIN_STAGE_FILE` (a plain shell var,
  not exported) to `state/fanin/<lane>/.stage/<ledger name>/<id>`, and `mc_log`
  (`bin/lib/mc/log.sh`) overwrites that file with every line the worker logs.
  `mc_log`'s return code is still the log write's. `fanin_end` and the orphan
  reap delete the run's `.stage/<ledger name>/` dir.
- **The alert text.** Today's text is kept as a prefix, byte for byte. The
  orphan path appends ` run: signal=TERM after=241s` when the dead run left a
  `T` line. Either path then appends
  ` why: <id> signal=TERM after=240s stage: "<last mc_log line>"; <id> …` for
  each missing id that has a stamp or a stage. The stage is flattened to one
  line and cut to 160 characters (`FANIN_STAGE_MAX`). An id with neither adds
  nothing. A worker that had logged nothing yet when it was killed has no
  stage. In the suite's fixture a worker killed at its CI read is exactly that.
- **The streak.** `state/fanin/<lane>/.streak` (TSV `id`, `count`, `epoch`) is
  rewritten under a flock on `.streak.lock` by every report, on the run-end path
  and the orphan path. A missing id gets +1. An id whose worker finished is
  removed. `deferred:solo`, `deferred:window`, `killed:deadline` (the BH-4918
  worker deadline), a ` signal=` death and a lock-skip keep the count, so a
  solo run killed at its deadline does not send the PR back to batches. A
  lock-skip is a worker that found the PR's lock held by an earlier worker (a
  solo run still on it). `pr_worker` leaves `<FANIN_STAGE_FILE>.locked`, and
  `mc_fanin_outcome` says `skipped:locked`, or `READY held:worker-locked` for a
  READY row. The row's own state would have cleared the streak. Other ids are untouched, and
  rows older than 7 days are dropped. `fanin_streak <id>` reads it. A run killed
  between its alert and its ledger delete is reported twice by design, so it
  counts twice. That only isolates the PR one run sooner.
- **Worked alone.** In `bin/merge-conductor.sh` `tick_project`, a row whose
  streak is at least `MC_FANIN_SOLO_AFTER` (default 2, 0 = off) goes to
  `mc_fanin_solo`. That calls `kw_conductor` (`bin/lib/keyed-wake.sh`):
  detached, every lock fd closed, deduped per PR by `MC_KEYED_WAKE_MIN_S`. On a
  launch the row is accounted `deferred:solo`, dropped from this run's workers
  and from `ae_project`, and its hotfix marker (if any) is dropped. A refused
  launch keeps the row in the batch. The launched run carries
  `MC_FANIN_SOLO_RUN=1` (`kw_conductor` sets it from `KW_FANIN_SOLO`) and never
  solos. A one-key run without the marker (a backstop fire whose only
  candidate is the starving PR, still under `timeout`) does solo it. The solo
  run's own finished outcome clears the streak, so a PR that
  completes alone goes back to batches. Log lines: `<key> FANIN_SOLO: missing
  from fan-in on N runs in a row — launched alone (keyed run)` or `… — solo
  launch refused (…); kept in this run`.
- **A backstop fire fits its window.** A 14-key fire died at `timeout 290` on
  2026-10-08 with "enumerated 7 accounted 0", and enqueued nothing. Two bounds
  now hold. `MC_BACKSTOP_MAX_KEYS` defaults to 6 (it was 20). And the fire
  passes `MC_WORKERS_DONE_BY` (the run start plus its worker cap, the timeout
  minus 45 s) and `MC_WINDOW_DEFER_FILE` to the keyed run. `tick_project`
  starts a worker only while `mc_window_cap` finds 15 s or more left until
  then, and caps that worker at what is left. A row it does not start is
  accounted `deferred:window`, logged `<key> WINDOW_DEFERRED: …`, and written
  to the defer file. The backstop puts those keys at the head of the carry.
  `kw_conductor` clears both vars, because a detached run has no timeout.
- **The order is fair.** The backstop takes the keys the last capped fire
  deferred first (`state/merge-conductor/backstop-carry`), then the harness's
  own repo (`HARNESS_REPO`), then the oldest `since`. With the harness first,
  a repo with as many candidates as the cap took every slot on every fire.
- **A `&` wrapper gets none of its parent's traps.** In a subshell, bash shows
  the parent's traps to `trap -p` until the subshell's first `trap` call.
  `fanin_run_sub` saved that view and put it back, which installed the run's
  `_fanin_run_signal` in each worker wrapper. A no-op `trap - RETURN` now
  clears the view before the save.
- **The backstop's timeout is a knob.** `MC_BACKSTOP_TIMEOUT_S` (default 240,
  60-290; a non-number falls back to 240), settings row
  `lane.merge-conductor-backstop.mc_backstop_timeout_s`. The solo threshold is
  `lane.merge-conductor.mc_fanin_solo_after`. Both reach the lane through the
  existing `lane_env_apply`.

Tests: `tests/fanin-solo.bh-4842-test.sh` (lib cases S1-S9, the real conductor
TERMed mid-worker, the solo run, the lock-skip and the window K1-K10, the
backstop's knob, order, carry and default cap K5, K8, K8b, K11).

## Still owed after deploy (operator probe, not claimed here)

- `grep 'ALERT FANIN merge-conductor' logs/merge-conductor.log | tail` shows
  `run:`/`why:` segments naming the signal, and a stage where the worker had
  logged one.
- `grep FANIN_SOLO logs/merge-conductor.log` shows the starved PRs launched
  alone.
- Over 24 h, no PR appears in `run died before fan-in` on two consecutive runs
  without a `FANIN_SOLO` line after it.
- `grep 'hit timeout' logs/merge-conductor-backstop.log` stays empty, and
  `grep WINDOW_DEFERRED logs/merge-conductor.log` names any key a fire had no
  time for.
