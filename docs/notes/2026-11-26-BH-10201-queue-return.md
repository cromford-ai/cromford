BH-10201: a PR that leaves the merge queue is on record, and one person is told when it does not come back

Doc: MERGE-CONDUCTOR, MERGIFY

Refs #10201. Hotfix. Owner's word, 2026-11-26: "we need to fix the factory agents to deal with PRs that get out of the queue so they come back."

## The incident

- #10134 was queued by a person at 21:28Z on 2026-11-25.
- Build 50666 rebased the branch and pushed it at 23:10Z. Mergify dequeued the PR because the head moved.
- The conductor's settle arm removed the `merge-queue` label at 23:12Z.
- The lane approved the new head at 23:24Z. The READY arm held it at the lead fence (BH-1606).
- A hold comment is one per PR and kind, not per head. So the new head got no comment and no alert for 9.5 hours.

## What changed

1. **Push guard.** `hold_push` (`bin/lib/hold-push.sh`) calls `hold_push_queue_guard` before the push.
   - It reads `pulls?head=<owner>:<branch>&state=open` one time.
   - If the open PR carries Mergify's `queued` or `checking` label, the push is refused: rc 6, one line that names the PR.
   - A `new` lease reads nothing. A remote that is not a GitHub repo reads nothing.
   - A read that fails does not refuse the push. One line per process says that the guard did not run.
   - Knob `HOLD_PUSH_QUEUE_GUARD` (default 1, 0 = off).
2. **The record.** New fragment `bin/merge-conductor.d/bh-10201-queue-return.sh`.
   - `mc_qr_owe` runs where the settle arm removes the label, in merge mode.
   - It writes one jobs-ledger row: kind `queue_return`, key `<slug>#<num>`.
   - Detail: `left_head`, `cause` (the word of `bin/lib/mc-eject-cause.sh`), `left_at`, `queued_by`, `told[]`.
   - Status `owed` for a moved head, a base conflict or an unknown cause.
   - Status `ladder` for a red batch (`checks`, `batch-red`, `timeout`). The existing ejection ladder owns it.
   - Status `released` when a person removed the label, or the cause is a standing changes-requested review.
3. **The pass.** `mc_qr_pass` runs one time per project tick, after the settle pass.
   - One ledger list read per project (`status=owed`). One cached PR read per owed row.
   - It reads the conductor's own row and its ready-why note. It sends no requeue.
   - A row whose leave this tick made is not read until the next tick.
   - `mc_qr_decide` (pure) answers one word per row. The table is below.
4. **Knobs.** `MC_QUEUE_RETURN` (default 1, 0 = no row and no pass). `MC_QUEUE_RETURN_ALERT_MIN` (default 30 minutes, 0 = no stale alert).

## The decision table

The first rule that holds answers.

| # | Condition | Word | Action |
|---|---|---|---|
| 1 | The PR is MERGED or CLOSED | `done` | status `done` |
| 2 | The PR could not be read | `wait` | none |
| 3 | The PR carries `merge-queue`, `queued` or `checking`, or the conductor row is QUEUED | `done` | status `done` |
| 4 | A `hold` label, a ticket or PR hold, or a culprit mark on the head that left | `released` | status `released`, no alert |
| 5 | A person was told about this head | `told` | none; the row stays `owed` |
| 6 | Main is red | `wait` | none |
| 7 | The ready-why note for the live head says `lead-held` | `lead-alert` | ONE warn alert, ONE PR comment |
| 8 | Out of the queue for `MC_QUEUE_RETURN_ALERT_MIN` minutes or more, and no stale alert was sent for this leave | `stale-alert` | ONE warn alert, ONE PR comment with the conductor state and reason |
| 9 | None of the above | `wait` | none |

The told head is written to the row before the alert. A crash costs the alert, never a second one. If the ledger does not take the write, nothing is sent in that tick. The row stays `owed` after an alert, so a later head that the lead fence holds gets its own alert. Each alert and PR comment names the hold, the head, the one action that clears it and who can do it (`mc_qr_clears`).

## Why the pass does not requeue

The conductor has one door into the queue for each case, and each door holds gates.

- Same head: the re-entry arm. It holds the pre-queue gate (BH-6161), the changes-requested hold and the culprit marks.
- New head: the READY arm. It holds the lead fence (BH-1606), the block gate (BH-762), the client approval gate (BH-9887) and the migration, prod-red and e2e-red holds.
- `mc_enqueue_mergify` publishes the verdict status that Mergify's queue rules require. A direct requeue of a lead PR's new head would land it with no lead MERGE.

A requeue from the pass is thus redundant or it goes round a gate. The gap of the incident was the push and the silence, and those are what this change closes.

## How to see it on a live hub

- `grep -E 'QUEUE_RETURN_(OWED|CLOSED|TOLD)' logs/merge-conductor.log`
- `bin/jobs-client.sh ledger-list queue_return`
- A refused push: `grep 'QUEUED — NOT pushing' logs/*.log builds/*/pipeline.log`

## Off switches

- Settings row `lane.merge-conductor.mc_queue_return = 0`: no row and no pass.
- Settings row `lib.stale-parent.hold_push_queue_guard = 0`: the push guard is off.

## Not in this change

- The 9-per-24-hours requeue ceiling and `MC_QUEUE_RETURN_MAX` of the issue text: there is no requeue to count.
- A fix-round hand-off for a PR that stays `dirty`: the stale alert names the conductor state.
- The custody table (#9554), `dequeue-watch` act mode (#9610), the lead fence rule (BH-1606).

No user-facing entry point.
