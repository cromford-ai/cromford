The one-line diagnosis. Every reviewer in the harness is binary. The lane that reviews project-6 and project-5 (bin/review-prs.sh:1555) asks the model for "severity-tagged findings" and then for VERDICT: APPROVE or REQUEST_CHANGES with no rule connecting severity to verdict. The in-build lenses (bin/lib/rb/review.sh:772) have no NOTE grammar at all. So a 2 px padding finding and a cross-company data leak become the same object: a review-changes-requested park, the same two fix rounds, the same terminal (close the PR or rebuild from scratch, plan stage included). Nothing in the ladder knows what the finding was about.
And the system only ratchets tighter. bin/lesson-propose.sh drafts a new gate for any BLOCK category with ≥3 hits in 14 days ("pick the EARLIEST stage that would have stopped it"). review-tighten.sh only tightens. lead-review-precision.sh measures bad MERGEs, never bad BLOCKs. There is no false-BLOCK metric anywhere, so nothing ever pushes back. BH-7072 and BH-7074 (open) are the ratchet's latest output.

2. Where the blocks come from (three reviewers, one vocabulary problem)

A. review-prs lane — project-6 + project-5

Posts a GitHub PR review as cromford-board[bot]: [HIGH]/[MEDIUM]/[LOW] findings + VERDICT: APPROVE|REQUEST_CHANGES. REQUEST_CHANGES = BLOCK; the fix round consumes it. 125 + 21 RC reviews in the window. This is where your pain is. The prompt enumerates every iron law and all nine BH-6946 perf items "each one a BLOCK"; severity tags are decorative.

B. In-build lenses — every project

bin/lib/rb/review.sh: 1–3 lenses before a PR exists. "Last line must be exactly VERDICT: APPROVE or VERDICT: BLOCK." No NOTE form. A BLOCK → one fix round → REVIEW_BLOCKED, exit 6, no PR is opened (TK-734's "branch with no PR"). Review tier T2 is uncapped. "A task with no VALIDATE evidence is a blocking finding" → NOT RUN (needs Clerk) → needs-human/classify.sh regex NH_RE_CRED turns it into a NEEDS-HUMAN hold.

C. Lead review — cromford (+project-4/cromford)

bin/lead-review.sh + prompts/lead-review.md. The only lane with [NOTE] and MERGE-WITH-NOTES, but "one real BLOCK finding makes the verdict BLOCK", checklist v8 has 15 items each with BLOCK clauses, and lead-outcome-cap.sh forces BLOCK on any INCONCLUSIVE perf claim. [BLOCK needs-human] fails the lead-verdict commit status, so Mergify will not queue — the hold gates the merge.

What a BLOCK costs today

finding (any kind)→REQUEST_CHANGES / BLOCK→park review-changes-requested→fix round 1: agent + merge main + push + full CI + re-review→fix round 2 (same)→ABANDON (close PR) or REBUILD FRESH (plan → execute → 80-suite gate → lenses → PR → CI → review)

Caps: BR_REVIEW_FIX_ROUNDS=2 per ticket (env knob; the per-project row exists but blocked-resolver.sh:307 never reads it), BR_MAX_REBUILDS=3, LEAD_REVIEW_MAX_PER_PR_DAY=4. Live right now: project-6-os queue 11 deep, oldest 382 min; of the last 40 merged project-6 PRs, 10 carry an -r2/-r3/-r4 rebuild suffix.

6. Root causes, in order of leverage

  1. No severity → verdict rule in any reviewer. review-prs.sh:1555 ("severity-tagged … VERDICT: APPROVE or REQUEST_CHANGES"), rb/review.sh:772 (binary, no NOTE form), lead-review.md:33 ("one real BLOCK finding makes the verdict BLOCK"). The model is asked to find everything and given one lever.
  2. Nits are written as BLOCK in the prompts, verbatim, in 12 places. "PERFORMANCE BY DEFAULT (BH-6946), each one a BLOCK" · "a speed claim without before and after numbers" · build-discipline D22 "the touched-file iron laws are BLOCK-level, not style: sortable headers, no dead identity rows, native dialogs, 375px" · "new behavior with no new test is a blocking finding" · "a task with no VALIDATE evidence is a blocking finding" · checklist v8 items 4, 7, 8, 11, 13, 14, 15 · intent.md:7-10.
  3. Verifications the box cannot run become human holds. execute.sh:51 records NOT RUN → review.sh:772 blocks on it → needs-human/classify.sh:4 regex NH_RE_CRED ("key/env var … build box lacks") → hold:waiting-on-human. Repo CLAUDE.md demands (design evidence PNGs, docs/notes) feed the same chute.
  4. The ladder has no severity. Same park, same 2 rounds, same ABANDON/REBUILD for every finding. The per-project fix-round row is never read (blocked-resolver.sh:307 calls lane_env_apply without a project).
  5. Follow-up tickets have no floor and no chain guard. Six prompts say how to group follow-ups, none says whether. gh issue create goes through a shim with no marker, depth check or cap. Checklist item 8 makes an undeclared deferral a BLOCK, so builders declare every nit as a ticket.
  6. Mechanical false positives tagged HIGH. "No CI result: cancelled" (13 verdict-leading findings) — a superseded push, not a defect. Migration file-number clashes. Stacked-PR "scope-stacking".
  7. The ratchet. lesson-propose.sh (min_blocks 3 / 14 days) proposes a new gate per BLOCK category; nothing measures false BLOCKs; nothing loosens.

7. The fix: strictness scales to user impact, fully autonomous

One shared severity model, rendered into every reviewer from settings rows, plus one mechanical demoter so a model that still writes BLOCK on a nit is corrected without a human. Then delete the sentences that say "each one a BLOCK".

ALWAYS BLOCK at any level

  • data loss; destructive or non-additive migration; new table with no RLS
  • cross-company (tenant) read or write
  • auth or permission bypass; secret in a commit; open redirect
  • wrong money or billing; metered call with no dedup before the spend
  • red main; build or typecheck that does not pass (real, not "cancelled")
  • a core user flow a user cannot finish
  • clearly wrong data, or a screen/button the ticket asked for that is missing or dead
  • hardcoded claude-* model id

CORE-FLOW level

The diff touches a flow in review.core_flows.<project> (project-6-os: company setup, departments, dashboards, agents, workflows). Check: the flow works end to end, and the screen looks like the reference to a person's eye. A few px, copy, a cache window, an eviction policy, a missing loading.tsx, a sequential await, a missing sort indicator, a missing test for a branch no user reaches → [NOTE]. One follow-up ticket per screen at most, only for a defect a user would notice.

SMOKE level — everything else

It works and breaks nothing else. Every other observation is a [NOTE]. File no follow-up ticket. Speed: BLOCK only a measured regression on a key screen over review.perf_block_ms (300) or review.perf_block_stmt_pct (20); never ask for a perf proof unless the ticket is a perf ticket. "A speed claim without numbers" is a NOTE.

8. Cowboy mode: one dial per project, time-boxed, audited

strict

Today's behavior. Kept so the before/after can be measured and so a project can opt back in.

levels — the new default

Always-block list blocks; core-flow and smoke levels as in §7; 2 non-BLOCK rounds then merge-with-notes; human steps never gate.

cowboy

levels with fix_rounds_max=0, every non-always finding a NOTE, no follow-up tickets, no human holds. The always-block floor stays on — tenant leaks, data loss, money, red main still stop. Everything else lands with notes on first review.

off

No review at all: the lead-verdict status is auto-stamped, green CI merges. Exists for completeness; recommended never to leave on. The floor in cowboy costs nothing and catches the only things you cannot iterate your way out of.

  • Time-boxed by default. bin/gates.sh cowboy project-6-os --for 6h writes review.mode.project-6-os=cowboy + review.mode_until; a cron flips back to levels at expiry and posts to the operator channel. --for forever if you mean it.
  • One row overrides every scattered kill switch that exists today: needs-human-hold-off, tier_gate_mode, group_findings, console-QA gate, size gate, BR_REVIEW_FIX_ROUNDS, LEAD_REVIEW_INCONCLUSIVE_BLOCK. Per-stage surgery via gates.<project>.<stage>=off when you want to keep the lead review but kill plan-contract strictness, say.
  • Audited and visible. Every flip is a config_changes row; Mission Control shows mode + expiry countdown per project; every verdict and PR body carries judged at: <mode> so a cowboy sprint can be audited afterwards.
  • The ratchet ignores it. lesson-propose and review-tighten skip anything merged under cowboy/off, so a sprint never teaches the system to tighten.
  • Mechanically it is a few extra rows on the same code path as levels — not a second system.
