The price per minute is not the problem. The number of minutes is. MonkCI charges $0.008 per four-vCPU minute. GitHub charges $0.012 for the same size. Every per-minute vendor is in the $0.008 to $0.014 band. GitHub would have cost $11K to $14K for the same work. The invoice is high because the two busiest repos test each tree several times and run large test sets for small changes.

Five changes cut the burn from about 37K to about 13K minutes per day. That is about $3,100 per month at MonkCI prices. A fixed pool of dedicated servers takes the same load for about $700 to $1,000 per month, with queueing at peaks.

cromford: the merge queue does the spending

What one merged PR costs

One green batch is about 265 minutes, $2.1. The all-in cost of a merged PR is higher: today's 17,000 minutes a day over about 50 merges a day is 340 minutes, $2.7, because red batches, the pre-queue gate, the PR checks, and the 1.7 PRs closed unmerged for every PR merged all land on the same bill.

  • The PR run itself is cheap: lint 4.3 min, determinism lint 2.2 min, no test corpus. This part of the 2026-09-24 design works.
  • The merge conductor dispatches a pre-queue gate: 15 minutes, the impact suites on the head merged onto main.
  • Mergify opens a batch draft. .mergify.yml has batch_size: 1 and batch_max_wait_time: 0 s on every queue, so one PR is one batch. The plan job selects the batch's impact set. For the six batches read, that was 409, 737, 869, 918, 954 and 1,038 suites of a 2,680-suite corpus, sized to 7 to 15 shards by a 1,200-second shard budget. A shard spends 19.5 of its 20 minutes in the suites. Setup is under 1 minute. Each batch costs 140 to 490 minutes, median about 265.
  • 27 of the 54 batches in the last 24 hours went red. In every red batch the fan-in job reported a suite failure in a shard. A red batch is a lost 265 minutes, and the PR goes through the queue again.
  • The suite-reuse ledger (BH-5366) works in some batches (690 of 1,427 reused, 6,154 seconds saved) and does nothing in others (0 of 1,038, 0 of 409, 3 of 872).

Why the impact set is so large

An impact set of 400 to 1,000 suites for a one-ticket PR is 15 to 40 percent of the corpus. The selector adds the always set and every suite that reaches a touched library file. tests/lib/scratch.sh is sourced by 2,109 of 2,147 suites, and many bin/lib files are reached by hundreds. The 2,680-suite corpus grew by about one suite per merged PR. The test-to-code ratio is now the main cost driver of the repo: the corpus takes about 24 shards of 25 minutes, 10 runner-hours, to run once.

The 50 percent red rate

Half the batches fail after the pre-queue gate passed the same head on main's tip. The gate runs the impact set with a cap and budget; the batch runs a larger set with no cap. So the batch finds what the gate skipped, or a suite is flaky under the traced runner. Either way, 5,900 minutes a day, about $1,400 a month, pay for runs that merge nothing.

project-6: each tree is tested three times

ci.yml and e2e.yml both trigger on pull_request (opened, synchronize, reopened), on merge_group, on push to main, on a daily schedule, and on workflow_dispatch. Every PR push runs the full unit suite (4 shards, 35 min) plus the full E2E suite (8 shards, 75 min) plus design-guard (4 shards, 12 min) plus checks and build: about 130 runner minutes per push.

The harness pushes a PR branch many times. In the last 24 hours 42 branches had 1 run, 27 had 2, 28 had 3 to 4, 19 had 6, 8 had 9, 2 had 12, and one had 18. Each push starts a new e2e run and cancels the previous one (cancel-in-progress), but the minutes before the cancel are billed: 41 cancelled e2e runs a day.

The merge group then runs ci and e2e again on the batch (batch_size 8, 26 queue runs a day). This is the run that proves the tree. Then the push to main runs ci and e2e a third time on the same tree: 42 ci and 41 e2e runs a day, about 2,500 minutes, for a tree the merge group already passed.

Two more lines need an answer. The operator token dispatches 42 ci runs a day by workflow_dispatch, 42 minutes each; this is the harness, and the audit did not find which lane. And deploy-worker and deploy-agent-worker fail on every push to main (49 and 48 failures a day, 5 minutes each on ubuntu-latest). Those are GitHub minutes, not MonkCI, but the deploy step fails every time, so either the deploy is broken or the workflow is dead weight.

project-6's 186 merges on 2026-10-17 and 157 on 10-18 are the launch days. Those two days alone were about 160K and 130K raw minutes, $1,300 and $1,000.

Design waste, ranked by minutes

  1. project-6 runs the full E2E suite on every PR push (7,200 min/day). The merge group runs it again on the tree that lands. The PR push needs the unit suite and the impact E2E set, not all 8 shards.
  2. cromford merge-queue drafts are restarted by red batches (13,800 min/day on batches). Correction 2026-10-22 22:00Z: the default queue already batched 4 PRs with a 3-minute wait, and the last 24 hours of drafts held 1 to 8 members. The 54 runs a day come from the 50 percent red rate, where a red batch ejects one PR and re-queues the rest, and from max_parallel_checks 3, where every red batch restarts the two speculative drafts above it. The gate fix is the lever; batch_size 6 helps only after.
  3. cromford red batches (5,900 min/day). Half the batches fail. The pre-queue gate is capped, so it does not predict the batch. Either raise the gate's cap to the batch's set or stop running the gate and let the batch be the test.
  4. project-6 tests the merged tree a third time on push to main (2,500 min/day). cromford already solved this: its push-to-main plan job asks whether the queue tested this tree and runs nothing when it did.
  5. project-6 cancelled runs (about 900 min/day in e2e). The harness pushes commits in bursts. A short debounce on the harness side, or one push per build attempt, removes most of them.
  6. project-6 workflow_dispatch runs (1,200 min/day). 42 a day from the harness token. Find the lane and check that it does not repeat a run the PR event already made.
  7. cromford pre-queue gate plus batch (1,100 min/day). While batch_size is 1, the gate and the batch test the same head on the same main tip. One of them is redundant until batches hold several PRs.
  8. cromford impact sets of 400 to 1,000 suites. The corpus is 2,680 bash suites, and the selector reaches a third of it for a typical change. This is the structural cost and the slowest to fix: tier the always set down, and stop letting a shared lib file pull in every suite that sources it.
  9. The watch never paged. The 2x multiplier doubled the estimate, so the line was set at 150K. At 1x the line must be about 12K raw minutes a day ($100). Set CI_MINUTES_BILL_MULT to 1 and CI_MINUTES_DAY_MAX to 12000.
  10. project-6 deploy workflows fail on every push. Not a MonkCI cost, but 97 failed deploy runs a day is a broken lane nobody sees.

MonkCI is at the cheap end of the per-minute market. Moving vendors changes the bill by at most 30 percent in either direction. Cutting the minutes changes it by 3x. A dedicated pool changes it by 10x, but it needs the runner-pool operations the fleet retired when it stopped the Fly pool, and a peak day like 2026-10-18 would queue for hours.
