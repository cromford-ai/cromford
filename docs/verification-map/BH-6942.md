# Lane-run machines check fleet repos at start and refuse unreadable repos at claim (BH-6942)

**What it is:** a lane-run machine reads each fleet repo once when its worker
starts. It refuses, at claim time, the merge-conductor-pr rows of a repo it
cannot read, so those rows stay queued for the hub. The head-read error of an
UNVERIFIABLE conductor row names its status and reason. Details:
[the note](../notes/2026-10-15-BH-6942-lane-run-repo-check.md).

- Boot check (`bin/lib/lane-run-repos.sh`, on with `LANE_RUN_CODE_SYNC=1` or
  `LANE_RUN_REPO_CHECK=1`). See it: `flyctl logs -a lane-run` shows
  `repo check: <r> of <n> repos readable, <u> unreadable, <k> unknown` once
  per worker start, plus one line per unreadable or unknown repo, for example
  `repo check: example-org/x unreadable 404-no-token; ...`. An unreadable repo
  raises one warn alert `lane-run-repo-unreadable-<project>`.
- Refusal: `GET /api/lane-runs/by-prefix?lane=merge-conductor-pr&project_prefix=<project>.`
  shows a refused row as `status:"queued"`, `attempts:0`, `claimed_by:null`.
  After `MC_FLY_QUEUE_STALE_S` the hub runs it (`logs/merge-conductor.log`:
  `fallback=no-capacity`).
- Prof line: an rc 75 row's `prof_line` is
  `PROF mc-pr state=UNVERIFIABLE reason=head-read-rc75-<status>-<reason>-via-<rung> deferred=-`.

**Preconditions:** a lane-run machine started with the current harness code
(code sync swaps it in, no rebake).
