# web-task human step resume, slice C0 (BH-8314)

**What it is:** the page half of `request_human(kind, prompt)` and the resume
run. `createHumanStep` in `bin/lib/web-human-step.mjs` holds the run's page
open while `wh_request_human` waits, types the person's code, and on no answer
saves a resume record. A later run calls `wh_resume_human` (in
`bin/lib/web-human.sh`) through `resume(page, record)` and takes over the
step. Details: [the note](../notes/2026-10-25-BH-8314-web-task-human-resume.md).

- Route (harness-jobs, bearer-gated): `POST /api/web-task/human/resume`. It
  also needs the run token `x-web-vault-run-token` of the NEW run's claim.
- Resume record: `<stateDir>/<step>.json` and `<stateDir>/<step>.storage.json`,
  mode 0600, in a 0700 dir. stateDir: `WEB_TASK_HUMAN_STATE_DIR`, else
  `$HARNESS_STATE/web-task-human`, else `$HARNESS/state/web-task-human`.
- Lib knobs: `lib.web-human-step.web_task_human_step_timeout_s`,
  `lib.web-human-step.web_task_human_resume_keep_s`.
- No production caller yet: slice C1 wires the module into the web-task
  agent loop after #7650 merges.

## Preconditions

- The preconditions of [BH-7598](BH-7598.md): `WEB_VAULT_KEY_1`, a claimed
  `web-task` run with its run token, the site in
  `lane.web-task.<project>.allowed_domains`.
- The old run of the step is `done` or `died` (or it is the same run row,
  claimed again).

## Check after deploy

```bash
printf '%s' '{"run_id":"x"}' \
  | curl -sS -w '\n%{http_code}\n' -K <(printf 'header = "authorization: Bearer %s"\n' "$HARNESS_SECRET") \
      -H 'content-type: application/json' --data-binary @- "$JOBS_URL/api/web-task/human/resume"
```

Expected: `{"error":"run_id, machine, project, site and step_id are required"}`
and HTTP 400. The route is live. A 404 means the route fragment is not in the
deployed table.
