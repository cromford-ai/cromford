# blocked-resolver placed on Fly (BH-6260)

**What it is:** schema fragment
`worker/jobs/schema.d/202610170602-bh-6260-blocked-resolver-flip.sql` seeds
`lane_placement.blocked-resolver=fly`, so the hub publishes each project's
snapshot and the Fly lane machines run the lane (the path is
[BH-6128.md](BH-6128.md)). Details: [the note](../notes/2026-10-14-BH-6260-blocked-resolver-flip.md).

- Placement: `lp_decide blocked-resolver` answers
  `fly|lane_placement.blocked-resolver=fly`. The publisher line ends
  `blocked-resolver placed fly (lane_placement.blocked-resolver=fly)`.
- Kill knob: set the row `lane_placement.blocked-resolver` to `hub`. The
  publisher publishes nothing and the dispatch enqueues no fly row. No deploy.
- Knobs: `lane_snapshot.file_max` (262144, 1..1000000) is the per-file cap of
  the snapshot and the write-back (`_lri_file_max`). A file still on the
  machine but over the cap at checkpoint time is not a hub deletion
  (`_lri_checkpoint_locked`); the hub copy stays.
  `lane_snapshot.prune_after_s` (604800, 3600..7776000) is the write-back
  ack's prune window (`pruneAfterS`). Out of range or unset is the default.
- Skips: `logs/lane-snapshot-publish.log` has one
  `lane-snapshot-publish: skip <p> <relpath> (<why>)` line per file over the
  cap and per record dir older than `lane_snapshot.builds_days`, when the skip
  starts. The open skips are in
  `state/lane-run-inputs/blocked-resolver/<p>/skipped.tsv`.
- Agent CLIs on the lane machines (the operator, 2026-10-17): `fly/lane-run.Dockerfile`
  bakes node, `claude` and `codex` with the pool image's pinned blocks, and
  `fly/lane-run-entrypoint.sh` writes the Fly secrets
  `CLAUDE_CODE_OAUTH_TOKEN` (into `global.env`), `CODEX_AUTH_JSON` and
  `CODEX_CONFIG_TOML` (into `$HOME/.codex/`), mode 600.
