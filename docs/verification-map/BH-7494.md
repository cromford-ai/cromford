# Pool tick CPU: the settings-cache loader does bounded shell work (BH-7494)

**What it is:** `_lg_sc_load` in `bin/lib/lane-gate.sh` fills the settings memo
with ONE jq and ONE eval. The old loader read three NUL fields per key, called
`_lg_sc_name` per key, ran `printf -v` per key and appended to one growing
`names` string twice per key. On the hub it took 8.1 s per load at load5 70 and
was 62% of one `lane_env_apply`. Now it takes 0.95 s.

- jq prints one assignment-only command: `fa=… tot=… names=… _LG_SK_x=1
  _LG_SV_x='…' …`. The key encoding (`_` to `__`, `.` to `_d`, `-` to `_m`) and
  the key filter (`[A-Za-z0-9_.-]+`) are in the jq program, as in `_lg_sc_name`.
- The memo is the same: `_LG_SK_*`, `_LG_SV_*`, `_LG_SC_NAMES`, `_LG_SK_N`,
  `_LG_SFETCHED`. A key the memo cannot hold is counted and not memoised.
- A value reaches the eval only through jq `@sh`. A key reaches it only when it
  matches the filter. No value is ever executed.

**How to drive it:**

| what | how |
|---|---|
| the acceptance cases | `bash tests/settings-load-cost.bh-7494-test.sh` |
| shell commands per load | `bash -c '. bin/lib/lane-gate.sh; trap "_C=\$((_C+1))" DEBUG; set -T; _C=0; _lg_sc_load; echo $_C'` with `HARNESS` set to a dir that holds `state/settings-cache.json` |
| time on the hub | time `lane_env_apply fly-pool <project>` in a bash that sources the lib, `HARNESS` set to a scratch copy |

**Kill knobs:** none.

**What must never regress:**

- One load of a 3,000-key cache runs at most 200 shell commands (L1).
- A load is one jq. Reads after it add none (L2, L3).
- The memo is byte-identical for odd bytes, false and null rows, JSON values
  and non-memoisable keys (L4). A value is never executed (L4).
- `tests/conf-rows.bh-2478-test.sh` M4/M5 and `tests/lane-knob-memo.bh-7251-test.sh`
  still count one settings read per load.
