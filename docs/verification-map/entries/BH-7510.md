GET reads come from a per-isolate cache for `GH_BUDGET_CACHE_TTL_S` seconds (env, integer 0..30, default 5, 0 = off) (no screen; preconditions: harness-jobs worker, bearer `HARNESS_SECRET`) | [shared-facts-db.md](shared-facts-db.md) | API: `GET /api/gh-budget?fingerprint=<fp>` with Authorization `Bearer <secret>`. Normal answer: 200 `{row,as_of}`, `row: null` for no reading yet. `stale` appears only on the overload fallback. A POST never serves a stale row: its read-back skips the cache and refreshes it. During an overload: one worker log line `d1-overload: gh_budget GET served a stale row …` or `d1-overload: gh_budget GET answered 503 after 5 attempt(s)`. Box side: `bin/lib/jobs/req.sh` retries a 503 whose body holds "overloaded" once, then `gh_budget_row_get` returns rc 1 and the box reads its own rate limit. What usually lies: a 200 can be up to 5 s old (the cache) or up to 120 s old with `stale: true`; the client still checks `row.fetched_at` against its own max age. A non-overload error still throws and reaches Sentry. Live check after deploy: Sentry CROMFORD-HARNESS-11 has 0 new events in 24 h.
