| Remote-results consumer cursor as jobs-DB ledger rows: each staged ledger result (`rr-handled`), each consumed relay json (`rr-consumed`) and the ledger-feed watermark (`rr-since`) (BH-7803, C3 of #4157) | [../notes/2026-10-21-BH-7803-remote-results-cursor-rows.md](../notes/2026-10-21-BH-7803-remote-results-cursor-rows.md) | No screen. Code: `bin/lib/rr-cursor.sh` (`rrc_job_handled`, `rrc_job_mark`, `rrc_since_get`, `rrc_since_put`, `rrc_json_consume`), called by `rt_stage` in `bin/lib/rt/staging.sh` and by section 3b of `bin/triage-gate.sh`. Rows: kind `rr-handled` key `<project>/<job_id>` status `staged`; kind `rr-since` key `<project>` status `at`, detail = the watermark; kind `rr-consumed` key `<project>/<KEY>@<build-id>` status `staged`, `duplicate`, `empty` or `badjson`. The files under `state/remote-results/<project>/` (`.handled/*.job`, `.handled/*.json*`, `.since`) are still written and are read first; a row answers only when the file is absent, and heals the file. Probe on an owner box after one remote build is staged: `bin/jobs-client.sh ledger-get rr-handled <project>/<job_id>` prints `staged`. What usually lies: a box whose files are intact never reads a row, so a missing row shows only after a wipe; a failed PUT is the `rr-cursor: <kind> row NOT written` line in `logs/<project>.log`. Tests: `tests/rr-cursor-rows.bh-7803-test.sh` |
