| Remote-results relay json as a jobs-DB ledger row: `rr-relay`, parked by the hub's ingest and settled by the owning box's consumer; the hub's pending count asks `rr-consumed` (BH-7860, C0 of #7860) | [../notes/2026-10-21-BH-7860-relay-json-rows.md](../notes/2026-10-21-BH-7860-relay-json-rows.md) | No screen. Code: `bin/lib/rr-relay.sh` (`rrr_rowkey`, `rrr_park`, `rrr_consumed`), called by the relay branch of `bin/fly-results-ingest.sh` and by the `remote_results_pending` count in `bin/fleet-status-push.sh`; `rrc_json_consume` in `bin/lib/rr-cursor.sh` sets the outcome. Row: kind `rr-relay` key `<project>/<KEY>@<build-id>` (the `rr-consumed` key) status `parked`, then `staged`, `duplicate`, `empty` or `badjson`; detail = the relay payload. The json file is still written and is still the input. Probe on the hub after one fly result is relayed: `bin/jobs-client.sh ledger-get rr-relay <project>/<KEY>@<build-id>` prints `parked`, and after the owning box's next triage tick `staged` (or `duplicate`). What usually lies: a box that consumed the file before the parked PUT landed leaves the row at `parked` while its `rr-consumed` row exists; a failed PUT is the `rr-relay: rr-relay row NOT written` line in `logs/fly-dispatch.log`. Tests: `tests/rr-relay-rows.bh-7860-test.sh` |
