# The break-it verifier (BH-6970)

**What it is:** after the lead verdict on a medium- or high-tier head, one model
call writes at most 5 test cases that try to break the patch. They run at the
head. The result goes on the verdict row. Details:
[the note](../notes/2026-10-17-BH-6970-break-it.md).

## Where to look

- The code: `bin/lib/break-it.sh` (`bi_review`, `bi_run`), called from the
  `# >>> break-it (BH-6970)` block of `review_one` in `bin/lead-review.sh`.
- The box log: `grep 'break-it' /root/harness/logs/lead-review.log` on a board
  box. Each reviewed head has one line `lr-<pr>-<sha12>: break-it: <result> (mode <m>)`.
- The report: `state/lead-reviews/lr-<pr>-<sha12>.md` has the header line
  `- break-it (BH-6970): <result> (mode <m>)` above `- pr body:` when a run happened.
- The replay files: `state/break-it/<owner>_<repo>-<pr>-<sha>.result` (the word,
  the test path, the case count and the failing names) and `.file` (a failing file).
- The verdict row: the `break_it` field of each row that
  `GET /api/verdicts?repo=<owner/repo>&pr=<n>&head=<sha>` answers. It is `clean`,
  `failed:<k>`, `could-not-run` or null. `bin/lead-verdict.sh show` does not print it.

## The switch

- `bin/jobs-client.sh setting-get break_it.mode` prints `off`, `shadow` or
  `enforce`. The seed is `shadow`. No row is `off`.
- `enforce` + `failed:<k>`: the review gets `- [BLOCK wrong-data] break-it: ...`,
  the verdict is BLOCK and the test file is committed to the PR branch.
