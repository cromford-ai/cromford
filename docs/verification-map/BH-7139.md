# Hub overload: keyed-tick queue, one fly-pool run per project, full-tick clock (BH-7139)

**What it is:** three changes that stop the hub from piling up its own
processes. On 2026-10-16 the hub (8 CPUs) ran load 171-238 with up to 112
`merge-conductor.sh`, 111 `fly-pool.sh` and 38 `project-lane-run.sh`
processes alive at once.

- Keyed ticks (`bin/lib/keyed-wake.sh` `kw_conductor`, `bin/mc-keyed-pool.sh`):
  a keyed tick is queued, one entry per PR, in
  `state/merge-conductor/keyed-queue/`. A second wake for a PR that is still
  queued folds into that entry. A drain runs the queue through
  `MC_KEYED_MAX_PARALLEL` slots (`locks/mc-keyed-slot-<i>.lock`, default 4),
  oldest first. A wake that finds every slot busy waits. It is never dropped.
  `bin/merge-conductor-wake.sh` starts one drain every minute as the backstop.
- fly-pool (`bin/fly-pool.sh`): the per-project lock is taken first, before any
  other work. A second start exits rc 0 at once with one `already running` line
  in `logs/fly-pool.log`. `fly agent start` runs with fd 8 closed.
- stuck-work: no change. `stuck-work.sh <p>` already took its per-project lock
  (BH-5943) and logs `busy`; the suite pins it.
- Full-tick clock (`bin/lib/mc-tick-clock.sh`): the cron full tick writes
  `state/merge-conductor/full-tick/<pid>.start` and logs `FULL_TICK wall_s=<n>`
  at its end. The wake lane writes ONE alert (`--id mc-full-tick-slow`) for a
  live full tick older than 2 x `MC_FULL_TICK_PERIOD_S` (default 1800).

**How to drive it:**

| what | how |
|---|---|
| the acceptance cases (Q1-Q4, F1, S1, C1, C2) | `bash tests/hub-overload-queue.bh-7139-test.sh` |
| the queue on the hub | `bin/mc-keyed-pool.sh status` and `logs/merge-conductor-keyed-pool.log` |
| fly-pool overlaps | `grep -c 'already running' logs/fly-pool.log` |
| full-tick wall time | `grep FULL_TICK logs/merge-conductor-cron.log logs/merge-conductor-wake-cron.log` |

**Kill knobs (settings rows):** `lane.merge-conductor.mc_keyed_max_parallel=0`
turns the pool off (every queued tick starts at once, as before).
`lane.merge-conductor.mc_full_tick_period_s` moves the alert age.

**What must never regress:**

- At most N keyed ticks run at once, and every wake still runs (Q1).
- Two wakes for one queued PR are one tick (Q2).
- A second fly-pool start for a project exits at once with one line (F1).
- A slow full tick writes one alert, not one a minute (C1).

**Metric to watch:** hub `uptime` load average every 5 minutes for 1 hour at
normal traffic (target: under 3 x nproc = 24), and the counts of
`merge-conductor.sh` and `fly-pool.sh` processes (`pgrep -fc`).
