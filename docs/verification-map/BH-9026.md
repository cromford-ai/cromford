# The hub asks the lead to review a head a machine deferred (BH-9026)

**What it is:** a lane-run machine that runs one PR's conductor tick
(`bin/merge-conductor-pr.sh`) leaves the re-review of a moved head to the hub
and reports `PROF mc-pr ... deferred=rereview`. The hub's next tick reads
that row (`mc_fly_deferred_for`, rc 5 of `mc_fly_enqueue`) and, for a repo in
`LEAD_REVIEW_AUTO_REPOS`, files the lead review request for that head in the
same tick (`mc_fly_rereview_request` in `bin/lib/mc/fly-workers.sh`). The
hub's own fallback for the PR still runs after a request.

- The call: `bin/lead-verdict.sh request <slug> <pr> <head40> --notes "pool
  deferred rereview of <head12> (BH-9026)"`, plus `--priority
  MC_REREVIEW_REQUEST_HOTFIX_PRIORITY` (500) when the PR has the hotfix label
  (whole-name match). A value outside 1..1000 is 500 with one log line.
- Once per (PR, head): the attempt line `rrleadreq <slug>#<pr> <head40>` is
  written after the worker answered created or 409. A later tick makes no
  call. A new head is a new request.
- A failed request (API down, no lead token, missing script): no marker, the
  line `rereview request FAILED for <head12> (pool deferred): <why>`, the PR
  `BLOCKED_HUMAN` with reason `rereview-request-failed`, one alert per (PR,
  head) (`rrleadreqfail`), no local worker that tick. The next tick asks again.
- A repo not in `LEAD_REVIEW_AUTO_REPOS`, or a run on a machine
  (`MC_ON_MACHINE=1`): no request, the fallback as before. An unreadable
  `LEAD_REVIEW_AUTO_REPOS`: one `not decided` line, the fallback as before.

See it live, on the hub:

1. `grep 'rereview requested\|rereview request' logs/merge-conductor.log`
2. `bin/lead-verdict.sh list example-org/cromford` lists the request row
   for that head.
3. `grep rrleadreq state/merge-conductor/attempts.txt`

Suite: `tests/conductor-rereview-request.bh-9026-test.sh`.
