# The hub lands a READY PR a machine left unlanded (BH-9202)

**What it is:** a lane-run machine that runs one PR's conductor tick
(`bin/merge-conductor-pr.sh`, `MC_ON_MACHINE=1`) never lands a PR. Before
BH-9202 only one exit of the READY arm wrote `deferred=land`; the other exits
(a hold, a gate, a moved state) wrote none, so the row said
`state=READY ... deferred=-`. The hub read that as "handled" and enqueued a
new row every tick. Nothing landed.

- Machine: when the PR's row is `READY` after the run and the run wrote no
  deferred word, the PROF line carries `deferred=hold` (an exit of the READY
  arm before the land step held it). The land step still writes
  `deferred=land`; a set word such as `prequeuegroup` is printed as is.
- Hub: `mc_fly_deferred_for` reads a newest `done` row of the key with
  `state=READY` and `deferred=-` (or no deferred field) as `hold`. This also
  covers rows stored before the fix and machines on an older checkout.
  `mc_fly_enqueue` answers rc 5 and the hub runs the PR's own worker
  (`fallback=machine-deferred (hold)`), with every normal gate. No new
  lane_runs row for that head.
- Tripwire: `_mc_fly_ready_loop` counts the `done` rows of this head's key
  whose PROF line says `state=READY`. At `MC_FLY_READY_LOOP_ALERT_N` (3) or
  more, one alert per (PR, head); attempt marker
  `flyreadyloop <slug>#<pr> <head40>`. A value that is not an integer >= 2
  is 3 with one log line.

See it live, on the hub:

1. `grep 'fallback=machine-deferred (hold)' logs/merge-conductor.log`
2. `/api/lane-runs/by-prefix?lane=merge-conductor-pr&project_prefix=cromford.<pr>.`
   shows no new row for a READY head after the next hub tick.
3. `grep flyreadyloop state/merge-conductor/attempts.txt`

Suite: `tests/conductor-ready-land.bh-9202-test.sh`.
