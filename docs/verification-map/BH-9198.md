# A hotfix PR and a READY-undeferred PR run on the hub (BH-9198)

**What it is:** with `conductor_workers_on_fly` on, the hub's conductor tick
does not send two kinds of PR to the lane-run pool (`bin/lib/mc/fly-workers.sh`,
`mc_fly_arm`). It runs them on the hub this tick, after one `fallback=<why>`
line in `logs/merge-conductor.log`.

- A hotfix PR: not a draft, and `hotfix_pr_is` accepts it (the `hotfix` label
  on the PR, case-insensitive whole name, or the label in its build record's
  `ticket-meta.json`). The hotfix lane switch (`HOTFIX_LANE`, the
  `switch.hotfix-lane-off` row) turns this off. A machine does not land, so a
  pool row only delays the emergency. The PR's rows are still read first, so a
  machine's `deferred=rereview` still asks the lead (BH-9026), and a failed or
  deferred row keeps its own `fallback=` word. See it: `<slug>#<n> fallback=hotfix —
  this PR runs on the hub this tick`, and no `merge-conductor-pr` row for that
  PR's key.
- A READY PR the machine did not land: the newest row of the key is `done`,
  rc 0, with `PROF mc-pr state=READY ... deferred=-`
  (`mc_fly_ready_undeferred_for`). The machine stopped at one of `pr_worker`'s
  READY gates (block gate, prequeue, lead-unpinned, MERGE_HELD) and wrote its
  reason only on the machine. See it: `<slug>#<n> fallback=machine-ready-undeferred
  (<key> READY on the machine with no land deferred; the hub lands it or logs
  why)`. Since BH-9202 (#9207) the same row answers `deferred=hold` first,
  so the live line is `<slug>#<n> fallback=machine-deferred (hold)`. The next
  hub line for that PR is a land or a named READY reason.

Read the rows: `GET /api/lane-runs/by-prefix?lane=merge-conductor-pr&project_prefix=<project>.<n>.`

Verified by `tests/conductor-fly-hotfix-hub.bh-9198-test.sh` (real tick, real
jobs worker).
