# Resolver modules (`bin/lib/br/`)

**What it is:** the split of `bin/blocked-resolver.sh` — 3,778 lines that 19 of
the last 200 merges touched — into one file per concern under `bin/lib/br/`.
It is the resolver's half of the conflict-reduction plan that already produced
`bin/lib/mc/` (BH-477) and `bin/lib/rb/` (BH-478): on the day the plan was
written, those five files and their two suites accounted for 40 of 53 conflicted
files. Two builds that touch two unrelated concerns should not conflict in a
file neither ticket is about.

**Four modules. All four are cut: the build-record discovery sources, the keys, the ladder and the record layer.**

| module | what it owns |
|---|---|
| `bin/lib/br/discovery.sh` | the build-record discovery sources (BH-6517): the parked queue rows `br_from_queue`, the build-record walk `br_from_builds`, the held-rebuild reads `br_rebuild_outcome`, `br_rebuild_artifact` and `br_from_rebuilds`, and `br_candidates`, which calls every source in order. `br_candidates` still calls `br_from_conductor` and `br_from_reviews` in the driver, at run time |
| `bin/lib/br/keys.sh` | the ticket key (BH-6461): `br_key_shape`, `br_key_from_branch`, `br_key_from_title`, `br_key_from_dir`, `br_ticket_key`, `br_key_source_phrase`, `br_derive_ticket_key`, the give-up alert `br_nokey_alert` and the `--only` scope check `br_key_in_only`. The globals they set (`BR_TICKET_KEY`, `BR_KEY_SOURCE`, `_BR_ONLY_REPO`) stay declared in the driver |
| `bin/lib/br/ladder.sh` | the classifier: `br_ladder_class`, `br_skips_mechanical`, `br_ladder_rung`, `br_regen_offered`, `br_regen_ladder`, `br_action`, `br_reason_of`; and the regenerate rung `br_regen_rung` (BH-5241) |
| `bin/lib/br/record.sh` | the per-`(project, key)` json under `$ST`: `br_rkey`, `br_cap_key`, `br_file`, `br_load`, `br_num`, `br_record`, `br_event`, `br_set_outcome`, `br_set_num`, `br_set_field`, `br_seen_rebuild`, `br_json_edit`, `br_save`; and, since the BH-5241 record cut, `br_rows_count`, `br_cap_rows`, `br_row_closed`, `br_set_flag`, `br_push_field`, `br_has_field_value`, `br_shape`, `br_fix_cap`, `br_rebuild_cap` |

**The first slice landed DARK; BH-5241 cut the ladder and the record layer, BH-6461 cut the keys, BH-6517 cut the build-record discovery sources.** The `# >>> resolver
modules` loop sources the modules where the inline copies used to follow them.
BH-5241 deleted the inline copies: first the ladder, then the record layer.
BH-6461 deleted the inline key family. BH-6517 deleted the inline build-record
discovery sources. So `discovery.sh` is the only definition of its 6 functions,
`keys.sh` of its 9, `ladder.sh` of its functions, `record.sh` of its 22, and all
four are load-bearing. `tests/br/expected-map.tsv` marks each function `lib` (dark: the
module's copy must be byte-identical to the inline one, and the inline one must
still exist) or `mod` (cut: the module defines it and the driver must not), and
`tests/br-split-layout-test.sh` case 4 holds both.

**The driver has a ceiling.** `tests/br/driver-ceiling.tsv` caps the lines of
`bin/blocked-resolver.sh` (`lines`) and its column-0 `br_*` definitions
(`br_fns`). Each slice that moves a concern out lowers both rows in the same PR.
After the discovery cut they are 9055 lines (8905 plus 150 lines of headroom)
and 144 definitions.
The end state is `br_fns 0`. `bin/lib/br/MODULES` is generated by
`bin/module-map-build.sh --write bin/lib/br` from each module's `# module:`
header.

**A missing module is a REFUSAL, not a shrug.** Boxes take `bin/` through
`rsync -a` per FILE (`bin/harness-sync.sh`), so a tick that fires mid-sync can
see the lane new and a module missing or half written. Either case ends the tick
with rc 1 and one line:

```
<stamp> RESOLVER MODULE MISSING: bin/lib/br/<module>.sh is missing or unusable on <box> — the box's bin/ is half-synced; no park was drained this tick
```

in `logs/ALERTS.log`. Failing open would drain parks with half a classifier —
every park answered `none`, nothing fixed, and a log line that reads exactly
like a quiet tick.

**How an operator reaches it:** there is no new lane and no new cron line. It is
`bin/blocked-resolver.sh`, the hub's `*/10` drain (`cron/hub.cron`), loading the
modules in `BR_MODULES` on startup.

```sh
grep -n '^BR_MODULES=' /root/harness/bin/blocked-resolver.sh
ls /root/harness/bin/lib/br/
```

**Fixtures:** a suite that copies `bin/blocked-resolver.sh` into a scratch
harness must install the modules beside it, or the copy refuses its own tick.
That is one call, from one lib, in every such suite:

```sh
. "$DIR/tests/lib/br-modules.sh" || exit 1
br_modules_install "$DIR" "$H" || exit 1
```

Since BH-1196 the seven `tests/br-*-test.sh` suites take the WHOLE fixture —
the scratch tree, the sibling libs, the stubbed `PATH`, and the `RUN` / `ROW` /
`ROWST` / `STATEJSON` / `SPENT` helpers — from one lib, which sources
`br-modules.sh` itself, so a fixture change is one edit rather than seven:

```sh
. "$DIR/tests/lib/fixture-harness.sh" || exit 1
fx_br_harness "$DIR" "$T" || exit 1        # the base harness
fx_br_ladder_git "$DIR" "$T" || exit 1     # + the real local git the ladder runs on
```

A suite that EXTRACTS a `br_*` function by name (awk/sed `^name() {` … `^}`)
reads the resolver corpus, not the driver alone, because a function that moved
is no longer in the driver. The corpus is the driver first, then each module in
`bin/lib/br/MODULES` order:

```sh
. "$DIR/tests/lib/br-corpus.sh" || exit 1
br_corpus "$DIR" "$T/br-corpus.sh" || exit 1
```

The `cp` of the scripts a suite DRIVES stays in that suite's own text, on
purpose: `bin/test-impact.sh` reads rooted `$DIR/...` tokens to decide which
suites a change selects, and a `cp` that moved into the lib would stop selecting
the family when the lane changes.
