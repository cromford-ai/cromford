# web-task resume-run enqueue, slice C0 (BH-8360)

**What it is:** a side effect of `POST /api/web-task/answer`. With the settings
row `web_task.resume_enqueue` = 1, an answer to a step whose web-task run
is `done` or `died` enqueues one new `queued` web-task lane run with the old
run's args and `enqueued_by = web-task-resume:<step_id>`. The seed is 0 (off).
Details: [the note](../notes/2026-10-25-BH-8360-web-task-resume-enqueue.md).

- Route (harness-jobs, bearer-gated): `POST /api/web-task/answer`, in
  `worker/jobs/src/routes/web-task-human.js`.
- Answer fields with the switch on: `resume` (`enqueued` or `skipped`),
  `resume_run_id`, `resume_why` (`run_live`, `already_live`, `not_web_task`,
  `not_enqueued`).
- No consumer yet: slice C1 makes the web-task lane read `enqueued_by`.

## Preconditions

- The preconditions of [BH-7598](BH-7598.md) to make a step.
- The switch row is 1, and the run that asked has stopped.

## Check after deploy

```sql
SELECT value FROM settings WHERE key='web_task.resume_enqueue';
```

Expected: `0`. The seed row is applied and the enqueue is off.
